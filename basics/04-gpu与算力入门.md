> 读完你会获得：FLOPS / 带宽 / roofline / 显存三笔账 / NVLink / MFU

## 一、为什么 AI 必须用 GPU：几万个学生 vs 几个教授

CPU 是几个**顶级教授**：单核极强、逻辑极复杂、什么事都能干，
但一次只能聊几个话题——适合做操作系统调度、分支复杂的通用逻辑。

GPU 是**几万个学生**：每个学生只会算加减乘除，但**同时坐进一个教室
算同一道题的不同小块**——一个指令广播给所有人，大家一起动手
（这套打法叫 **SIMT**，单指令多线程）。

上一篇说过：神经网络里 95% 的计算是矩阵乘——**几百万个互相独立的
乘法加法**，天然适合广播给几万个学生一起算。所以 GPU 不是「更快的
CPU」，而是**专为「同一件事重复一亿次」设计的并行机器**。CPU 能跑
LLM 推理吗？能，就像教授自己手算一万份卷子——跑得动，但没法看。

## 二、GPU 的两个物理上限：算力与带宽

衡量一块 GPU，面试层面只要盯两组数：

| 指标 | 单位 | 是什么 |
| --- | --- | --- |
| **算力（FLOPS）** | TFLOPS（每秒万亿次浮点运算） | 每秒能算多少乘法加法 |
| **显存带宽** | GB/s（或 TB/s） | 每秒能往显存里搬进搬出多少字节 |
| **显存容量** | GB（80GB / 141GB / 192GB……） | 能同时装下多少参数 / 中间结果 |

补一句：**HBM（高带宽显存）**就是把显存芯片用超宽通道直接堆在 GPU
旁边、牺牲容量换带宽——今天的 H100 / B200 论「贵」，很大一部分贵
在 HBM 而不是算力本身。带宽才是稀缺品。

直觉：**GPU 不是「算不快」，而是「搬不动」**——矩阵乘一次要 read
一大堆权重、写一大堆中间结果，算 1 次乘法往往要搬好几个字节。
搬运比计算慢得多时，算力再强的卡也只能干等搬货。

## 三、roofline：每个搬进来的字节，配得够乘法吗

roofline 模型的全部精华一句话：

> **每搬进来 1 字节数据，你能不能配够至少 X 次乘法？** 配得够，
> 算力吃得满；配不够，瓶颈在带宽，算力空转。

「X」= 卡的算力 ÷ 卡的带宽（A100 大约是 100+），工程上叫
**计算强度（arithmetic intensity）**。

三种典型场景的直觉对照：

- **训练大 batch**：一条数据在显存里被反复用几千次，字节一次进、
  乘法万次跑 → **算力瓶颈**，GPU 吃得很饱，这是 GPU 最爱的活。
- **推理 prefill**（读用户输入）：整段 prompt 一次性并行算完，
  强度也不低 → 偏算力瓶颈。
- **推理 decode**（逐 token 生成）：每吐一个 token，要把**所有权重
  完整搬一遍**却只算 1 次前向——**1 字节权重配 1 次乘法都不到**
  → **严重带宽瓶颈**。这就是为什么 LLM 推理的吞吐瓶颈往往不是算力，
  以及为什么量化（把权重压成 INT8/INT4）能立竿见影——字节数直接减半。

## 四、显存三笔账：7B 全量微调为什么单卡放不下

训练时显存不是只有参数，拿 7B 模型粗算三笔账（以 Adam 优化器、
混合精度为例）：

| 项目 | 每个参数 | 7B 一共 |
| --- | --- | --- |
| 模型参数（BF16） | 2 字节 | ~14 GB |
| 梯度（BF16） | 2 字节 | ~14 GB |
| Adam 优化器状态（FP32：一阶 + 二阶动量 + FP32 主权重） | 12 字节 | ~84 GB |
| **小计** | 16 字节 | **~112 GB** |

还没算**激活值**（前向传播的中间结果，反向时要用），那跟 batch 大小、
序列长度正相关，动辄再加几十 GB 到上百 GB。

所以 80GB 的 A100 跑 7B 全量微调：装不下。**不是模型装不下，是
优化的家伙什装不下**。业界解法三件套：ZeRO（把优化器状态/梯度/参数
切到多卡上）、梯度检查点（省激活，重算换显存）、混合精度——这就进入
分布式训练的领域了。

> 进阶指针：ZeRO-1/2/3 各切什么、显存精确拆账，见
> [distributed-training/zero与显存优化.md](../interview-questions/distributed-training/zero与显存优化.md)。

## 五、通信：多卡为什么变难

两张卡各自算完自己的那份，最后**必须交换梯度**同步一下，才能成为
「一个模型」。交换走什么路，量级差极多：

| 通道 | 带宽量级 | 直觉 |
| --- | --- | --- |
| **NVLink**（机内 GPU 直连） | 几百 GB/s（H100 一代 ~900 GB/s） | 同一台服务器里的专用高速公路 |
| **PCIe**（机内走主板） | 几十 GB/s（32~64） | 市内主干道，能走但不快 |
| **InfiniBand / 万兆网络**（跨机） | 几十 GB（100G/200G/400G 网卡 ≈ 12.5~50 GB/s） | 跨机房长途，最慢一环 |

多卡训练的全部麻烦来自这张表：**算力早就过剩，通信才是稀缺品**。
所以并行策略的核心设计思想是「**把最频繁的通信留在最快的通道上**」——
张量并行对联频繁，走机内 NVLink；数据并行通信少，走跨机网络。
这就是三维并行为什么长成那个样子。

## 六、MFU：标称算力 vs 实际吃到多少

**MFU（Model FLOPs Utilization）= 实测有效算力 ÷ 标称算力**。
标称 312 TFLOPS 的 A100，真正训模型时，因为通信、内存搬运、
算子调度、重启 checkpoint 等损耗，能把 50% 以上吃满就是世界第一梯队
（35%~45% 是工业界常见区间，50%+ 值得写进技术博客）。

**口算例题**：A100（312 TFLOPS，取 MFU 50%）训 7B 模型，一天能过
多少 token？

```text
经验公式：训练一个 token 约需要 6 × N 次浮点运算
  N = 7B = 7×10^9 → 每 token 约 4.2×10^10 FLOPs

有效算力 = 312 × 50% = 1.56×10^14 FLOPs/秒

每秒 token 数 = 1.56×10^14 ÷ 4.2×10^10 ≈ 3700 token/秒

一天 = 86400 秒 → 3700 × 86400 ≈ 3.2 亿 tokens
```

假设标注（面试时主动说出假设 = 加分）：不含数据加载和通信损耗、
假设算子已足够融合、7B 是 dense 模型。所以「几千亿 token 的预训练」
靠单卡是天文数字——这就是为什么预训练要几百上千张卡联训几个月。

## 七、▶ 面试挂钩

**问题 1：为什么推理 decode 阶段是 memory-bound？60 秒答**
「decode 一次只生成 1 个 token。做一次前向，需要把全部权重从显存
读一遍，但这次前向只为 1 个 token 服务——搬了 N 字节权重只做了约
N 次乘法，计算强度远低于 GPU 的算力带宽比，所以瓶颈卡在带宽。
优化思路两条：把权重压小（量化）、把一次前向喂给更多 token（大 batch /
continuous batching / 投机采样）。」

**问题 2：给你 8 张 A100，怎么测出真实算力？**
「三行思路：
1. 先跑纯矩阵乘基准（cuBLAS / matmul microbenchmark）确认卡本身达
   到标称 FLOPS——排除硬件降频、PCIe 问题；
2. 再跑 NCCL allreduce 基准测卡间通信带宽——8 卡是否真走 NVLink；
3. 最后跑真实模型的一步训练，用 6N × tokens / 耗时 反推 MFU，
   和纸上算的对比。三层对不上，瓶颈在哪一层一目了然。」

**问题 3：PCIe 机器和 NVLink 机器并行策略怎么选？**
「NVLink 机内敢放张量并行（通信密集），跨机只放数据并行 / 流水线
并行（通信稀疏）；PCIe 机器要尽量压缩 TP 规模甚至全走 DP + ZeRO。」
