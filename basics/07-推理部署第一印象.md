## 一、训练和推理：烧菜 vs 上菜

训练像**研发菜谱**——反复试味调整（反向传播改参数），一次几个月，
错一步大不了重做。推理像**高峰期出餐**——菜谱冻结（参数只读），
每来一位客人（请求）就要按菜谱快速出菜，客人多、要求快、灶台就那么多。

这个比喻直接推出推理的三个硬约束：

- **延迟**：客人盯着手机等字一个个蹦出来，首字慢了人就走了。
- **吞吐**：晚高峰几千人同时点单，灶台必须连轴转。
- **成本**：每一道菜烧的都是 GPU 秒，老板天天问你「一份回复几毛钱」。

**面试黄金三角：延迟 × 吞吐 × 成本，不可能同时最优，所有推理优化
都是在这三角里换位置。** 记住这一句，后面所有技术都能挂上去。

## 二、两个永远先问的名词：TTFT 和 TPOT

衡量一次聊天体验，业界用两个指标，几乎所有推理面试题都从它们出发：

- **TTFT（Time To First Token，首字延迟）**：你按下回车，到第一个字
  蹦出来的时间。主要由**读入你输入**的那次计算决定——输入越长越慢。
- **TPOT（Time Per Output Token，字间延迟）**：之后相邻两个字之间的
  间隔，决定「打字机」流不流畅。人眼阅读的舒适线是每秒 10 个字以上，
  即 TPOT < 100ms。

背后是推理的两个阶段（04 篇已有伏笔，这里点名）：

```text
Prefill（预填充）：把你的全部输入一次性算完 → 决定 TTFT
                  特点：成千 token 并行，算力吃饱（compute-bound）

Decode（解码）：   一个字一个字往外蹦        → 决定 TPOT
                  特点：一次只产 1 token，权重反复白搬（memory-bound）
```

**一次请求 = 一次 prefill + 几百次 decode。**
优化 prefill 靠算力，优化 decode 靠带宽——分工完全不同，
这正是「PD 分离」这类架构存在的原因（延伸阅读里有专文）。

## 三、一次请求在推理引擎里的旅程

你发一条消息到 ChatGPT 类服务，消息会走这样一条路：

1. **API 网关**接住请求，做鉴权、限流、排队；
2. **推理引擎**（vLLM / SGLang 等）把你的文本切成 token，
   排进调度队列；
3. **调度器**把你和别人的请求**拼成一个批次**送上 GPU；
4. GPU 做完 prefill，蹦出第一个字 → 流式推回给你；
5. 之后每 decode 一个字推一个字，直到说完。

## 四、四大优化直觉（入门版）

推理优化技术多如牛毛，但入门阶段只要记住**四根支柱各占一个直觉**：

### 支柱 1：连续批处理（Continuous Batching）——拼车

传统做法：凑够一车人，大巴开到终点再回来接下一批。
问题：有人坐两站就下车，座位空着也不许上人——GPU 全程有空座。

连续批处理：**每蹦一个字就重新排一次座位**，下车的立刻腾位、
新来的见缝插针。GPU 座位利用率直接翻倍起跳。
这是现代推理引擎的第一灵魂特性，vLLM/SGLang 都围绕它构建。

### 支柱 2：KV Cache 分页（PagedAttention）——停车场网格化

每个请求的对话历史都要存在显存里（KV Cache），像停车场。
传统做法：每辆车按「预计最大长度」预留一整排车位——浪费一半。

PagedAttention：把停车场划成**统一大小的格子**，车停哪格记哪格
（页表），用多少占多少。显存浪费从 ~60% 降到 ~5%，
省下的显存全部喂给支柱 1 的拼车规模。

### 支柱 3：投机采样（Speculative Decoding）——草稿+审阅

小模型先飞快地打个草稿（连猜 5 个字），大模型**一次前向**审阅
这 5 个字、对的照收、错的从错处重来。
大模型「审 5 个」和「写 1 个」耗时几乎一样（decode 是 memory-bound，
多算几个 token 不增加权重搬运），白捡 2~3 倍速度、输出一字不差。

### 支柱 4：量化（Quantization）——行李托运减重

权重大、显存小，像行李超重：
把参数从「16 位浮点」（大行李箱）换成「8 位/4 位整数」（压缩袋），
显存占用砍半甚至 quarter，带宽搬运同比例变轻——
decode 是 memory-bound，所以**直接提速**。
代价是精度轻微损失，面试爱考「怎么选量化位宽」的权衡。

## 五、和训练的三点关键区别（高频对比题）

| 维度 | 训练 | 推理 |
|---|---|---|
| 参数 | 每步都在改（反向传播） | 冻结只读 |
| 目标 | loss 下降 | 延迟低、吞吐高、成本省 |
| 瓶颈 | 算力 + 卡间通信 | decode 阶段卡在显存带宽 |

回答「训练和推理的区别」时如果只说出第一行，是及格；
三行都说到并补一句「所以训练堆 FLOPS、推理堆 HBM 带宽，
同一张卡在两边的用法完全不同」，是优秀。

## 六、▶ 面试挂钩

**问题 1：大模型推理为什么这么慢？60 秒答**
「一次请求分 prefill 和 decode 两个阶段。prefill 是并行计算，
充分利用算力，不慢；慢在 decode——每生成一个 token 都要把全部
权重从显存搬一遍，只为一个 token 服务，计算强度极低、卡在显存
带宽。所以优化主线是：提高每批 token 数摊薄搬运（continuous
batching）、把权重压小（量化）、让一次前向多审几个字（投机采样）。」

**问题 2：vLLM 为什么比朴素部署快那么多？**
「两手抓：PagedAttention 把 KV Cache 分页管理，显存浪费从六成
降到五个点，省下的显存全部开给更大的 batch；Continuous Batching
做 token 级动态凑批，GPU 不再为一个请求的空转买单。
两个合起来，吞吐在同硬件上翻了一个数量级——这也是为什么
vLLM 迅速成了开源部署事实标准。」

**问题 3：TTFT 和 TPOT 哪个更应该优先优化？**
「看场景：代码补全这种『短输入长等待』场景用户盯着首字，
TTFT 优先，手段是 prefix caching 和 prefill 扩容；
长文写作和 Agent 场景输出几百上千字，TPOT 决定体感，
手段是投机采样和量化。面试里先说『看场景』再分头展开，
比直接站队强得多。」
