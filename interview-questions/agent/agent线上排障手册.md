## 一、本质差别：Agent 排障的单位是轨迹，不是请求

普通 LLM 服务挂了，排查单位是一次请求：这次调用 5xx 了吗、延迟多少、token 多少。Agent 线上出问题，单看任何一次请求往往都是健康的——模型每次都正常返回，工具每次都正常应答，但整条轨迹已经跑偏了。

原因是**单请求故障会被轨迹结构放大**。一次工具超时，模型重试一次；重试的回包进了上下文，上下文变长；上下文变长推高每一步的 `prompt_tokens` 与延迟；步数变多、单步变贵，成本与延迟双升；上下文被截断后模型忘了自己刚试过什么，再试一次——循环跑偏。初始故障是一次 500ms 的超时，最终现象是一条 40 步、烧了几十倍 token 的轨迹。

所以 Agent 排障三板斧，全部围绕轨迹展开：

1. **步级 trace 下钻**：拿到问题轨迹的 `trace_id`，逐步展开，每一步看模型输入输出、工具入参回包、该步延迟与 token。字段契约与设计见 [观测与trace工程](./观测与trace工程.md)，本篇只消费它。
2. **失败模式聚类**：单条轨迹是故事，一百条同形态轨迹才是故障模式。把同时间段的问题轨迹按「出错步骤类型 + 错误签名」聚类，先打最大的那一簇，别被长尾噪声带偏。聚类产线的建设归评测闭环专题管，本篇只讲如何用它定位。
3. **最小复现轨迹**：把无关步骤剥掉，构造一条三到五步就能稳定复现问题的最短轨迹。复现不了的上不了修复，修复完了它也转成回归用例。

记住一句话：**请求级指标用来发现，轨迹级下钻用来定位，聚类用来排优先级**。

## 二、八大症状排查树

以下八个症状覆盖 Agent 线上事故的大多数。每个症状固定五段格式：**线上信号** → **在 trace 里看什么** → **根因树** → **处置** → **预防**。

### 2.1 死循环与打转

**线上信号**：单轨迹步数突然暴涨（平时 8 步的任务跑出 40 步）、轨迹级成本出现长尾尖刺、`max_steps` 熔断触发率抬升。

**在 trace 里看什么**：是否存在「同工具、同参数」连续调用——这是面经里反复出现的陈年老坑，也是最便宜的检测：给每条轨迹算一个同工具同参数连续计数，大于等于 3 基本就是打转。

**根因树**：

1. 工具持续返回相同错误，模型拿同样参数重试；
2. 上下文被截断，模型忘了自己已经试过，原样再来；
3. 目标本身不可达，但没有写退出条件，模型只能硬磨。

**处置**：循环检测三层——同工具加同参数连续 N 次强制打断；打断时向模型注入一条系统提示（「你已重复该调用 N 次，换参数或换路径」）；仍不收敛则降级重规划或直接失败退出，把错误数据化喂回而不是让它继续烧 token。

**预防**：`max_steps` 与单轨迹 token 预算硬上限；去重式记忆让模型能查到「我试过这个、失败了」；工具回包文案写成可行动的，降低模型原样重试的冲动。

### 2.2 工具失败率升高

**线上信号**：工具 span 的 `status_code` 错误比例抬升、某个工具的 P99 延迟恶化、大量轨迹卡在同一步。

**在 trace 里看什么**：按工具名 × 错误类型做分布——超时、限流、解析失败、参数非法各占多少，失败集中在单个工具还是全面开花。

**根因树**：

1. 第三方超时或限流（对方服务问题）；
2. 上游 schema 漂移，接口改了字段没通知你；
3. 模型侧参数生成错误（刚换过模型或输入变长）；
4. 认证过期或配额耗尽。

**处置**三件套：超时预算与指数退避重试，且重试只对幂等调用开放；写操作带幂等键，重试前先查状态；工具降级链——主工具失败后切备工具，备工具也没有就明确告知用户「这一步做不到」，绝不假造结果。工具契约与简化协议见 [mcp与工具调用深度对比](./mcp与工具调用深度对比.md)。

**预防**：工具健康度看板（成功率、延迟、错误类型按工具分解）；给关键工具写契约测试，上游 schema 漂移在发布前被 CI 拦下。

### 2.3 成本与 token 暴涨

**线上信号**：账单环比明显抬升、`prompt_tokens` 均值或 P99 走高，但请求量没怎么涨。

**在 trace 里看什么**：按 step 画 `prompt_tokens` 曲线。健康轨迹是缓坡，问题轨迹是台阶式跳涨——跳涨那一格塞进来的东西就是病灶。

**根因树**：

1. 工具回包没截断，整页 HTML 或整段日志进了上下文；
2. 前缀缓存失效，重复的 system prompt 每次都全价重算；
3. 检索一次塞太多 chunk，召回精度没换来预算先爆了；
4. 死循环导致步数膨胀（与 2.1 互为因果）。

**处置**：工具回包统一截断，大工件摘要后进上下文、原文外置成文件引用；system prompt 前缀稳定化，动态信息绝不插进前缀中间（缓存命中率掉一个点都是真金白银）；检索加硬性 token 预算。完整拆账方法见 [agent成本与token预算专题](./agent成本与token预算专题.md)。

**预防**：缓存命中率与步均 token 进监控大盘；给工具回包设字节上限，超限自动走摘要路径。

### 2.4 JSON 与函数调用格式错乱

**线上信号**：工具调用解析失败率抬升、`finish_reason=length` 增多、自愈重试轮数变长。

**在 trace 里看什么**：解析失败样本的原文。先回答两个指纹问题：是不是模型升级后才出现的？是不是集中在某一类长输入上？这两个答案直接把根因砍半。面经信号：Function Call 返回的 JSON 不标准时必须备兜底方案，这在面试与生产里都是高频题。

**根因树**：

1. 模型升级后输出习惯微漂移（参数塞进字符串、多余前后缀）；
2. 特定长输入触发截断，JSON 不完整；
3. 参数类型错误（数字进引号、嵌套结构拍平）；
4. 宿主侧拼接 bug，发了模型没见过的工具描述。

**处置**三件套：带错误信息重试一轮，多数能自愈；正则提取与常见错误修复兜底；schema 硬校验，校验不过不执行、错误原文喂回。病型分型（截断、schema 偏移、语义幻觉）详见 [harness工程实战](./harness工程实战.md) 的 9.2 节，本篇不重复。大面积漂移且重试救不回时，上约束解码（xgrammar/GBNF 类）让非法 JSON 在生成端就不可能出现；训练侧加固见 [function-calling训练专题](./function-calling训练专题.md)。

**预防**：模型升级必须灰度，灰度集里包含格式回归用例；解析失败率作为升级门禁指标，不是事后才看的仪表盘。

### 2.5 上下文溢出与压缩失效

**线上信号**：长会话后半段答非所问、用户反馈「明明是你说过的约束，它又违反了」。面经信号：第二十轮丢信息的排查链是经典追问——通常答案就藏在压缩点里。

**在 trace 里看什么**：找到最近一次压缩或截断发生的步骤，对比压缩前后模型可见内容：早期系统指令、用户硬性约束是否还在。把「丢的那条信息」和「它在压缩前的位置」对起来，就定位完了。

**根因树**：

1. 压缩摘要丢了关键约束（摘要模型没认为这是重点）；
2. 早期指令在压缩点之外，被整体截掉；
3. 关键工件一直内联在上下文里，挤占了指令的生存空间。

**处置**：工件外置——文件、变量引用、工具按需重读，别让整个中间结果常年占据上下文；关键约束 pin 住不参与压缩，每轮复述。完整机制见 [记忆与上下文工程](./记忆与上下文工程.md)。

**预防**：压缩策略上线前跑「压缩后关键信息保留率」评测；上下文水位告警，接近窗口上限前主动触发整理而不是等溢出。

### 2.6 模型升级质量回归

**线上信号**：灰度组的任务成功率或用户负反馈率差于对照组，且差距稳定不收敛。

**在 trace 里看什么**：横向对比同任务在新旧模型下的轨迹，按维度拆掉分的位置：是指令遵循掉了、输出格式变了，还是事实与推理能力回了。盲评与 judge 校准归 [agent评测与观测闭环专题](./agent评测与观测闭环专题.md)，本篇只讲定位动作。

**根因树**：

1. 指令遵循维度掉（系统约束被忽略）；
2. 输出格式维度掉（与 2.4 联动，工具链首当其冲）；
3. 事实与推理维度掉（答错但格式漂亮，最难发现）。

**处置**：先回滚保住线上，再按掉分维度做专项修复——遵循掉就调 system prompt 组织方式，格式掉就加约束解码与校验兜底，能力掉就评估是否值得为该能力接受新版本。灰度 5% 流量、离线回归集加 rubric 双评过了才放量。

**预防**：回归集随每次事故沉淀（最小复现轨迹直接转用例）；升级公告里的「行为变化说明」当合同读，逐条对到自己的回归集上。

### 2.7 记忆污染与串话

**线上信号**：Agent 说出它不该知道的信息（别的租户的偏好）、坚持一条已经被用户推翻的旧结论。

**在 trace 里看什么**：该步检索召回的记忆条目原文与来源命名空间。串话的指纹很明确：召回条目里出现了不属于当前租户或当前会话的内容。

**根因树**：

1. 多租户命名空间隔离有洞，检索跨了边界；
2. 旧记忆与新指令冲突，召回时旧记忆排前面；
3. 写入端没校验，模型的幻觉被当成事实写进了记忆库。

**处置**：先止血——涉事命名空间的记忆整体失效或回滚；再修检索过滤条件；写入端加校验（事实性与用户确认过的内容才入库）。安全边界与隔离设计见 [agent安全与防护](./agent安全与防护.md)。

**预防**：记忆加过期与遗忘策略；写入路径加来源标记，召回时支持按来源追溯；命名空间隔离进发布 checklist。

### 2.8 长任务目标漂移

**线上信号**：几十步的任务做完，交付物和原始需求对不上；用户说「我要的不是这个」。

**在 trace 里看什么**：步骤与目标的一致性抽检——隔几步抽一条，问「这一步在服务于原始目标吗」。漂移通常不是突变，是每步偏一点、复利出来的。

**根因树**：

1. 原始目标被中间结果挤出模型注意力；
2. 中间步骤的反馈悄悄改写了隐式目标（模型迁就工具能做的事）；
3. 全程无 checkpoint，没有任何一步被要求对照目标。

**处置**：目标卡机制——每 N 步让模型 echo 一次当前目标与已完成进度，偏了当场可见；关键节点设 checkpoint，需要人或高层策略审批后才继续。

**预防**：阶段验收协议写进任务模板；长任务拆成有验收标准的阶段，而不是一口气跑完再验收。

## 三、两个完整排障故事（示例构造）

以下两则均为示例构造的时间线，用于演示 runbook 如何串起来，数字不代表任何真实公司。

### 3.1 故事一：客服 Agent 成本一夜翻倍

- 09:10 财务告警：昨日 token 账单环比翻倍，请求量只涨了一成。
- 09:25 看大盘：请求量平缓，但轨迹级 `prompt_tokens` 的 P99 涨了约两倍——涨价轨迹是少数长尾，不是普涨。
- 09:40 抽一条最贵的轨迹按 step 画 token 曲线：第 3 步出现台阶式跳涨，那一格塞进来的是订单查询工具的原始回包——上游昨夜上线，给回包加了一个带完整请求日志的调试字段，单条回包从几百字节变成几十 KB。
- 10:05 继续下钻：同一条轨迹还发现缓存命中率暴跌。排查发现有人把「当前时间」插进了 system prompt 中间，前缀每轮都在变，缓存基本不命中。两个病灶叠加，成本翻倍。
- 10:30 止血：工具回包统一截断，调试字段进黑名单不进上下文；时间字段移到前缀之外的动态区。当天账单回落。
- 次日收编：回包字节上限进发布 checklist，前缀稳定化写进 prompt 模板规范，缓存命中率进监控告警。最小复现轨迹转成回归用例。

### 3.2 故事二：升级模型后工具调用成功率从九成七掉到八成八

- 14:00 模型版本灰度 5%，两小时后工具调用成功率从九成七掉到八成八，解析失败告警触发。
- 14:20 拉解析失败样本原文做指纹分析：集中在长输入任务；形态是新模型把数字参数包进了字符串、工具调用前后偶尔多一句解释性散文——典型的新模型格式微漂移。
- 14:35 确认范围：未灰度的流量无异常，纯版本问题，排除第三方与宿主改动。
- 14:50 止血三件事：解析层加类型纠错（字符串数字自动还原）；schema 校验不过不执行、错误原文喂回让模型自愈；重试上限两轮。成功率回到九成四。
- 16:00 救不回的长尾上约束解码，非法 JSON 在生成端被禁掉，成功率回到九成七。
- 次日收编：该批失败样本转成格式回归集，作为后续所有模型升级的门禁；灰度观察期从两小时拉长到覆盖一个业务高峰。

## 四、面试怎么讲：一次线上事故的组织法

面试官问「讲讲你处理过的一次 Agent 线上事故」，用五段式组织答案：

1. **现象**：先说量化信号——哪个指标、变了多少、什么时候发现的。「轨迹级成本 P99 翻倍、缓存命中率掉到地板」比「出了点问题」有力十倍。
2. **定位**：讲下钻路径——如何用最便宜的分析把根因砍半（按 step 画 token 曲线、按工具 × 错误类型看分布、压缩点前后对比）。
3. **止血**：先恢复服务再谈优雅——截断、回滚、降级链、约束解码，哪个快用哪个。
4. **根因**：一句话说清真正的病根，而不是事故现场的症状。
5. **预防**：回归用例、门禁指标、checklist——证明这次事故不会第二次发生。

全程把 Agent 排障的特征词挂在嘴边：**轨迹**、**步级 trace 特征**、**失败模式聚类**、**最小复现轨迹**。这四个词一出口，面试官就知道你排的是 Agent 不是普通接口。

## ▶ 面试题

**问题 1：Agent 线上排障和普通 LLM 服务排障有什么不同？**
「排查单位不同。普通服务排请求，Agent 排轨迹——单请求故障会被轨迹结构放大：一次工具失败引发重试，回包撑大上下文，成本延迟双升，模型在截断后忘了试过什么再重试。所以三板斧都是轨迹级的：步级 trace 下钻定位，失败模式聚类排优先级，最小复现轨迹验证修复。请求级指标只负责发现异常。」

**问题 2：线上发现 Agent 死循环，怎么排查和处置？**
「信号是单轨迹步数暴涨和成本长尾。trace 里先查同工具同参数连续调用，这是最便宜的检测。根因三类：工具持续返回相同错误模型原样重试、上下文截断后忘了已试过、目标不可达但没写退出条件。处置是循环检测三层：同工具同参数 N 次强制打断、注入系统提示让它换路径、不收敛就降级重规划或失败退出。预防靠 `max_steps` 硬预算和去重式记忆。」

**问题 3：成本突然暴涨，你的排查顺序是什么？**
「先分清是量涨还是价涨——请求量平缓但 `prompt_tokens` 的 P99 走高，就是价涨。抽最贵轨迹按 step 画 token 曲线，台阶式跳涨的那一格就是病灶。常见四因：工具回包没截断、前缀缓存失效、检索塞太多 chunk、死循环步数膨胀。处置按因下药：回包截断与摘要外置、前缀稳定化、检索预算、循环检测。缓存命中率必须进监控，掉一个点都是钱。」

**问题 4：模型升级后 Function Call 的 JSON 经常不合法，怎么办？**
「先看指纹：是否升级后才出现、是否集中在某类输入。处置三件套：带错误信息重试一轮、正则与类型纠错兜底、schema 硬校验不过不执行并喂回自愈。大面积漂移就上约束解码，让非法 JSON 生成不出来。根治在流程：模型升级必须灰度，格式回归集做门禁，解析失败率是升级指标而不是事后仪表盘。」

**问题 5：长会话后半段 Agent 开始违反早期约束，怎么定位？**
「信号是『第二十轮丢信息』。定位动作固定：找到最近一次压缩或截断的步骤，对比前后模型可见内容，看丢的是不是早期指令和硬性约束。根因通常是摘要丢了约束、截断切掉了前缀、或内联工件挤占了指令空间。处置是工件外置成文件引用、关键约束 pin 住不压、每轮复述。预防是压缩上线前跑关键信息保留率评测，加水位告警。」

**问题 6：多租户 Agent 的记忆串话了，如何处置和预防？**
「trace 里看该步召回的记忆条目原文与命名空间，串话的指纹是召回内容不属于当前租户。根因三类：隔离有洞、旧记忆压过新指令、写入端没校验把幻觉存成了事实。处置先整体失效涉事命名空间的记忆止血，再修检索过滤与写入校验。预防靠过期遗忘策略、来源标记可追溯、隔离进发布 checklist。」
