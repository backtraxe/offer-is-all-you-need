## 一、Agent 的 SLO 为什么不能照抄推理服务的

### 1.1 请求级之上多了任务级

[推理服务slo与运营](../inference/推理服务slo与运营.md) 的 SLO 三件套
——`TTFT p99`、`TPOT p99`、请求成功率——量的是「一次调用健不健康」。
Agent 的一次用户任务却是十几到几十个调用加工具调用、检索、记忆
读写：单看请求级每步都健康，用户感受到的却是任务做了五分钟、
烧了几十倍 token、还给了错答案。承诺对象必须从请求换到任务：
**请求级指标管底层供方，任务级指标才是对用户的承诺**。

### 1.2 多步成功率：必背的算术

最小模型：每步成功率同为 p、步间独立，N 步轨迹全对走完的概率是
p 的 N 次方。三个数字锚，面试脱口而出：

- 单步 99%、20 步：0.99 的 20 次方 ≈ 0.818，**单步九十九分、
  二十步任务只剩八成二（算术本身，示例口径）**；
- 单步 99%、50 步：≈ 0.605；单步 95%、20 步：≈ 0.358，不可用。

小概率近似版更好背：**单步失败率每多 1 个点，N 步任务的成功率
近似损失 N 个点**。两个推论比公式值钱：长轨迹稳定性瓶颈在「最弱
一步的兜底能力」；提单步 0.5 个点在长任务上等于一轮大优化。
独立性假设线上不成立（同工具故障整串放大、重试恢复缩小），
算术只建直觉，真实成功率必须按轨迹实测。

### 1.3 任务级指标清单

口径为示例，阈值需按自有分布标定：

| 指标 | 定义 | 在哪看 | 告警阈值建议（示例口径） |
|---|---|---|---|
| 任务成功率 | 按 outcome 判定 pass 的轨迹占比（终态断言，非模型自评） | trace 平台按标签聚合、按任务类型分桶 | 小时环比跌幅超 3 点，或跌破基线 2 点先 P2 |
| 轨迹时长 p95 | 任务从发起到终态的端到端耗时 | 轨迹级 `end_time - start_time` 分布 | 超基线 1.5 倍且持续 15 分钟 |
| 任务均耗 token | 每条成功轨迹的输入加输出 token 均值（失败轨迹单列） | `gen_ai.usage` 按轨迹求和 | 环比涨 30% 但成功率没涨 → 烧钱不产出 |
| 工具调用成功率 | 工具 span 非错误 `status_code` 占比，按工具名分解 | 工具 span 聚合看板 | 单工具跌破基线 5 点；全工具普跌即 P1 候选 |
| 人审接管率 | 被人审接管或人工改写的轨迹占比 | 审批系统埋点回写 trace | 突增告警（求助或护栏在拦），趋势应缓降 |
| 兜底率 | 走过降级链任一级的轨迹占比（重试不算，降级起算） | 兜底动作埋点 | 超 5% 说明兜底从保险变常态 |
| 死循环检出率 | 触发同工具同参数打断的轨迹占比 | 循环检测埋点 | 从千分之几翻倍即预警 |

三条看榜纪律：任务成功率必须分桶看（三桶平均会掩盖单桶塌方）；
失败轨迹成本单列；**所有任务级指标都要带「版本分桶」维度**。

## 二、三类变更的发布工程

Agent 线上事故按触发源归因，大头就三类：模型切换、system prompt
与模板变更、工具 schema 变更——三者是三种不同的「分布变了」，
不能用同一套发布姿势。

| 变更类型 | 风险指纹（改的是什么分布） | 发布姿势（示例口径） | 回滚条件与动作 |
|---|---|---|---|
| 模型切换 | 能力、格式习惯、延迟、价格四个分布同时换 | 全量回归集门禁 → 灰度 5% → 覆盖一个业务高峰的观察窗 → 阶梯放量 | 任务成功率或工具成功率破线，立即切回旧版本路由 |
| prompt 与模板变更 | 指令分布变，作用域默认全量用户，是权重最大的文本 | 回归集加黄金集门禁 → 按租户或流量 5% 灰度 → 观察窗至少半个高峰 | 分桶成功率任一桶破线即回滚该 prompt 版本 |
| 工具 schema 变更 | 模型与环境的接口分布变，模型按旧习惯生成参数 | 契约测试进 CI → schema 版本共存期 → 新 schema 灰度挂在工具层 | 解析失败率或参数非法率抬升即冻结新版本路由 |

**模型切换**不是换一个 endpoint：指令遵循、JSON 格式习惯、首
token 延迟、每 token 价格同时变。三件套缺一不可：回归集必含格式
回归用例；灰度期按版本分桶看成功率、解析失败率、时长 p95 三线；
观察窗覆盖业务高峰，夜间看到的只是空载健康。版本路由做成可秒级
切回的配置而非新部署——**回滚动作必须快于诊断动作，先切回再
慢慢归因**。

**模板变更的军规**：**「prompt 变更视同代码变更」是军规，反例是
「页面上改一句话直接生效」**。具体五条：进 git 有版本号与 diff
审计；改动挂评审、强度不低于代码评审；每次变更绑定回归集 run
报告；线上可独立回滚、不跟代码发版走；trace 打 `prompt_version`
标签否则分桶对账无从谈起。风险指纹：模板是上下文里权重最大的
一段文本，blast radius 默认全量用户——改一个 JSON 引号转义字符
就崩过解析（示例构造，形态真实），错别字也要走灰度。

**工具 schema 变更**最阴：模型按旧 schema 习惯生成参数，改字段
名、改类型、把嵌套拍平，模型继续用旧习惯传参，错误形态是「参数
非法率抬升」而不是「工具报错」——没有红色报错，格外难发现。
姿势三条：契约测试进 CI（上游没通知你改了字段，测试替你发现）；
schema 版本共存期，模型侧用 feature flag 控制暴露哪一版；先在影子
流量上比新旧 schema 的参数合法率与终态一致率，一致才灰度。

**运行期版本锁定（run 级 pin）**：三类变更各自灰度之外，还有一条
正交军规——**同一次会话或 run 必须 pin 住 prompt 版本、Graph 版本、
工具 schema 快照三件套**。理由：run 中途换掉其中任何一件，这条轨迹
就是两个分布拼出来的四不像，事后排障无法归因，judge 回放也没法复现。
实现口径：每个 run 打 config snapshot id（三件套版本的组合哈希），
trace 全程携带；版本切换只影响新 run，旧 run 按老快照继续跑到终态。
长 run 跨越发版只有两条路：默认任它跑旧版本到终态（安全）；或者
checkpoint 迁移——在明确定义的恢复点上把 state 显式迁到新版本并记
录迁移事件，迁移本身视同一次变更，照样走灰度。与模板军规的关系：
「prompt 视同代码」管的是发布流程，run 级锁定管的是运行期的版本
一致性——一个管发，一个管跑，缺一条都会出现「线上跑着一个谁也没
发布过的组合」。

## 三、兜底设计矩阵

### 3.1 故障模式 × 检测信号 × 兜底动作

| 故障模式 | 检测信号 | 兜底动作 |
|---|---|---|
| 工具超时 | 工具 span 超预算未返回；按工具名聚合超时率 | 带退避重试（仅幂等）→ 备工具降级 → 告知用户该步做不到 |
| JSON 与 FC 错乱 | 解析失败率、自愈重试轮数、`finish_reason=length` | 错误信息喂回重试 → 类型纠错与正则兜底 → schema 硬校验 → 约束解码 |
| 模型输出退化 | judge 低位回流分、轨迹级负反馈率、与基线 diff | 切备选模型路由 → 缩任务范围改受限回答 → 人审接管 |
| 上下文溢出前兆 | 上下文水位近窗口上限、压缩触发频次 | 主动整理与工件外置 → 关键约束 pin 住 → 超长任务强制分段验收 |
| 死循环 | 同工具同参数连续计数 ≥3 | 强制打断注入提示 → 降级重规划 → 失败退出并错误数据化喂回 |
| 第三方限流 | 429 占比、限流错误签名聚类 | 指数退避加抖动 → 备用供方 → 排队并告知延迟 |
| 记忆污染 | 召回条目跨命名空间、旧记忆压新指令告警 | 按命名空间下架涉事记忆 → 写入端校验回滚 → 会话级禁用记忆 |

矩阵两条注：根因树与症状五段式排障归
[agent线上排障手册](./agent线上排障手册.md) 管，这里只定义
「兜底线在哪」；每行兜底动作从左到右是「花钱更少到兜底更硬」
的顺序——**兜底矩阵的读法是从左往右逐级认输，不允许跳级硬扛**。

### 3.2 兜底分级链：四级，不是「重试三次」

1. **自动重试**：指数退避加抖动，只对幂等调用开放；写操作带
   幂等键、重试前先查状态——重试写操作不查幂等是重复扣款类
   事故的经典来源（示例构造，形态真实）。
2. **降级**：降级工具（主工具失败切备工具）、降级模型（旗舰
   切轻量，质量换可用）、降级检索。
3. **受限回答**：明确告知用户「这一步做不到」并给出已完成部分，
   绝不假造结果——假造是兜底链里唯一不可接受的一档。
4. **人审接管**：进审批队列（见 3.4），这是兜底手段不是兜底失败。

设计意图：**「失败重试」只覆盖第一级，兜底链回答的是重试也
救不回来之后系统长什么样**——这道区分本身是面试题。

### 3.3 断路器三态套在 Agent 工具上

```text
closed ──滑动窗错误率/过载信号超阈值──▶ open
open   ──冷却计时到────────────────────▶ half_open
half_open ──探测流量连续成功───────────▶ closed
half_open ──探测失败，重新计时─────────▶ open
```

三态的 Agent 化：closed 态统计对象是**每个工具**（不是整个服务），
窗口内错误率与 p99 双条件开门；open 态的关键是「熔断期间模型
得到什么」——返回结构化的「该工具暂不可用，请换路径」伪回包，
而不是让请求挂在超时上；half-open 用打标的探测流量关门，避免
污染任务成功率分桶。断路器状态本身进观测大盘。

### 3.4 人审接管的工程形态

人审不是「发消息给运营群」三个字，三件工程部件：

- **审批队列**：按风险级别与到期时间排序，自身是独立 service
  （队列挂了大面积任务卡死，它也要有兜底）；
- **超时默认动作**：每个审批项必须带默认值——危险动作（写、删、
  对外发送）超时默认拒绝，只读与低风险动作可配默认放行，
  「超时无人处理」不可能成为系统行为；
- **审批界面最小要素**：任务目标与进度摘要、待执行动作及参数
  原文、风险标注（为什么被拦、命中哪条规则）、一键批准/拒绝/
  改写后放行三键——缺「改写后放行」等于逼人审在「批准错动作」
  与「整条任务作废」之间二选一。

## 四、告警与值班

### 4.1 告警分级：三级够用，别搞五级

| 级别 | 触发判据（机器可读，示例口径） | 动作 |
|---|---|---|
| P1 | 任务成功率全桶骤降；工具成功率全线普跌；安全事件（越权工具调用、记忆串话） | 电话级触达值班，立即执行预案（回滚或降级保底态） |
| P2 | 单桶成功率破线；任一任务级指标持续 15 分钟边际超阈 | 即时消息触达，工作时间 30 分钟内介入 |
| P3 | 趋势预警——环比缓降、兜底率爬升、成本缓涨未破线 | 进趋势看板，工作日例行巡检处理 |

两个纪律：判据必须机器可读且带持续时间窗口（毛刺不报警）；
**每个级别挂一个被演练过的预案，没有预案的级别是装饰品**。

### 4.2 告警疲劳治理

告警疲劳是唯一「再多传感器也治不好」的病，三招有效：先分级再
聚合——同一根因（一个工具挂了引发二十条轨迹失败）只报一次；
加抑制窗口——处理中的同签名告警静默；定期做手术——没人点开的
规则降级或删除。**治理的本质是保护 P1 的信噪比**——真事故被
噪声淹没的那天，所有监控白做。

### 4.3 一页纸 runbook 原则

值班同学凌晨三点拿到的不能是一份「请展开排查」的文档。runbook
是症状索引不是知识普及：每条症状一行，直接链到
[agent线上排障手册](./agent线上排障手册.md) 的对应症状树章节，
再挂止血动作的开关位置。三条原则：按「值班看到的信号」写条目；
每条症状处置第一步必须是止血动作（切流、回滚、降级）而不是
调查；每季度拿真实告警回测，跳过率最高的条目重写或删除。

## 五、两个设计题演练

两题按「SLO 指标 → 变更管理 → 兜底矩阵 → 告警」四件套各填一遍，
可直接当系统设计题答题骨架。数字均为示例口径。

### 5.1 客服 Agent（多租户、7×24）

- SLO 指标：任务成功率按「意图 × 租户」两维分桶，核心意图如
  退款单列桶（防长尾租户塌方被均值掩盖）；人审接管率是北极星，
  目标缓降但拒绝归零——该人工的必须敢人工；另按「session 内
  无重复无升级」定义桶级解决率；轨迹时长 p95 按意图分。
- 变更管理：模型与 prompt 双版本路由、按租户灰度（先大客户
  验证、后长尾放量）；租户级回滚必备——客服场景租户自定义
  模板多，复数模板是常态不是异常；system prompt 前缀的共享段
  严格稳定化保前缀缓存。
- 兜底矩阵：读类工具（订单查询）标准三级链；写类工具（退款、
  改单）直连人审接管、不进自动重试；回复对外发送前过
  guardrail 复核合规与承诺边界；记忆按租户命名空间硬隔离。
- 告警：P1 加「写类工具错误执行」专项（错了比不做更坏）；
  P2 按租户分桶，避免大租户健康掩盖小租户事故；夜间节假日
  设白名单租户值班制度，非白名单租户故障降级为 P2。

### 5.2 数据分析 Agent（代码执行、沙箱第三方依赖）

- SLO 指标：任务成功率的 outcome 判分难（报告对错难自动评），
  起步用「执行成功且无人工打回」；沙箱执行成功率独立成一级
  指标；任务均耗 token 含失败重试轨迹单列（分析任务重试多）；
  报告确定性校验通过率单列（数字能对上明细）。
- 变更管理：沙箱镜像与依赖版本视同模型版本管理——升级走
  灰度与回归；第三方库版本 pin 死、升级走独立变更窗口；
  工具 schema 变更重点防 import 路径与 API 签名漂移。
- 兜底矩阵：执行失败喂回错误自愈两轮 → 依赖缺失降级到内置
  白名单环境 → 第三方数据源超时降级缓存数据并标注时效；
  死循环检测加「同代码块执行次数」维度；出报告前过确定性
  校验，不过则退回模型修订。
- 告警：P1 增加沙箱逃逸与越权文件访问（安全事件）；P2 含
  第三方数据源限流率爬升（数据过期风险先于失败暴露）；
  成本告警按任务均耗环比不设静态线——分析任务大小差异大，
  静态线必误报；沙箱队列积压设独立告警。

## ▶ 面试题

**问题 1：Agent 的 SLO 怎么定，和推理服务的 SLO 有什么不同？**
「推理服务承诺请求级：TTFT p99、TPOT p99、可用率。Agent 承诺
任务级：任务成功率、轨迹时长 p95、任务均耗 token、工具调用
成功率、人审接管率、兜底率。定法：先拍流量画像，按任务类型
分桶定基线，全部挂在版本分桶上对账灰度。请求级指标不当对外
承诺，只用来归因底层供方问题。」

**问题 2：多步任务的成功率怎么算，单步 99% 为什么不够？**
「最小模型是联合概率：N 步全对等于单步成功率的 N 次方。单步
99% 走 20 步只剩约八成二、50 步只剩六成。小概率近似更好背：
单步失败率每多 1 点，N 步任务成功率近似损失 N 个点。推论：
长轨迹稳定性取决于最弱一步的兜底能力而非平均智力。线上独立性
不成立，算术建直觉、实测定 SLO。」

**问题 3：prompt 变更要不要走灰度？不就是改几个字吗？**
「要，且视同代码变更。改的是所有请求上下文里权重最大的一段
文本，作用域默认全量用户；历史上改一个引号转义字符就崩过
JSON 解析（示例构造）。工程姿势：进 git 有版本号与 diff
评审、变更绑定回归集 run 报告、线上可独立回滚、trace 打
`prompt_version` 标签支撑分桶对账。」

**问题 4：兜底设计和「失败了重试几次」差在哪？**
「重试只是兜底链第一级。完整链四级：带退避且只对幂等开放的
自动重试；降级（备工具、降级模型）；受限回答（告知做不到、
绝不假造）；人审接管。差在两点：重试假设故障是瞬态的，兜底
链假设故障可能持续、需要改变解题路径；重试没有终态承诺，兜底
链每一级都定义了给用户的交代。断路器三态是它的触发器。」

**问题 5：人审接管会不会把体验拖死？**
「会，如果全量过审。保体验四条：审批按风险分级，只拦危险动作
（写、删、对外发送），只读默认放行；每个审批项带超时默认动作
——危险动作超时拒绝、低风险可配放行；审批界面含风险标注与
改写后放行；人审接管率本身是北极星——突增告警、趋势缓降，
用指标倒逼高频审批模式沉淀回自动链。人审是兜底手段不是兜底
失败。」

**问题 6：告警太多值班麻木了怎么办？**
「把告警疲劳当系统病治：先分级——只对 P1 电话触达，P3 趋势
类只进看板；再聚合——同根因的多条症状告警折叠成一条；加
抑制窗口——处理中的同签名告警静默；定期手术——降权或删除
无人看的规则。配套 runbook 是一页纸症状索引，每条症状链到
排障手册对应症状树，第一步永远是止血动作。」

## 口径与未核实说明

1. 全部阈值（成功率跌幅点数、灰度比例、观察窗时长、兜底率水位、超时默认动作等）均为示例口径，需按业务分布自行标定。
2. 多步成功率算术（p 的 N 次方）是独立同分布假设下的最小模型，算术只建直觉、实测定 SLO。
3. 引号转义崩 JSON 解析、重试写操作重复执行两则均为示例构造，形态取自常见事故模式，不指向具体公司或事件。
4. 断路器三态为通用模式的 Agent 化套用，实现参数（窗口大小、开门阈值、探测流量比）以所用框架官方文档为准。
5. 观测字段名沿用仓内观测契约约定，平台实现以官方文档为准。
