## 一、主线一句话：记忆从「框架功能」分化成独立产品层

一句话直觉：**从 2024 到 2026 年，记忆从框架里的一张向量表，分化成一个有基准、
有产品形态、有合规边界的独立产品层**。

四条证据线可以串起这个判断：

1. **开源侧五条路线各自成军**：mem0 走抽取式事实库、Zep/Graphiti 走时序知识图谱、
   Letta 走自编辑记忆块、LangMem 走工具化 SDK、Memobase 走 SQL 化用户画像——五家
   抽象不同，且在 LOCOMO / LongMemEval 上以量化方式互相验证。
2. **产品侧已经默认开启**：ChatGPT Memory **全量于 2024-09-05（OpenAI 官方口径，
   2024）**，Claude memory **上线于 2025-09-11（Anthropic 官方口径，2025）**——
   记忆从产品卖点变成了默认功能。
3. **基准侧给出硬理由**：商用助手和长上下文模型在 LongMemEval 持续交互中
   **准确率掉下来三成（LongMemEval 论文 arXiv:2410.10813，ICLR 2025，第三方口径）。**
   「长上下文 ≠ 有记忆」是记忆层存在的硬证据。
4. **工程侧收敛成四笔账**：写入成本 × 读取占用预算 × 前缀缓存冲击 × 删除权合规，
   本篇后半基本就是这四笔账的展开。

## 二、五条开源路线：本质是三种抽象之争

### 2.1 社区实测水位（全部 gh api 当场实测，2026-10-11）

| 仓库 | star（实测） | 路线 | 一句话定位 |
|---|---|---|---|
| mem0ai/mem0 | **mem0 拿到 66,977（实测，2026）** | 抽取式事实库（+可选图谱 Mem0g） | 简单即王道，社区第一名 |
| getzep/graphiti | **graphiti 拿到 31,640（实测，2026）** | 时序知识图谱引擎 | Zep 事实上的开源载体 |
| letta-ai/letta | **letta 拿到 25,102（实测，2026）** | 自编辑记忆块 | MemGPT 正统续作 |
| getzep/zep | **zep 主仓只有 4,955（实测，2026）** | Zep 主仓（服务化） | 事实已让位 graphiti |
| memodb-io/memobase | **memobase 拿到 2,928（实测，2026）** | SQL 化用户画像 | 成本敏感场景样板 |
| langchain-ai/langmem | **langmem 拿到 1,700（实测，2026）** | 工具化 SDK | 「记忆 = Agent 的两个普通工具」 |

三个读法：

- **社区赢家是 mem0：**体量约为第二名 graphiti 的 2.1 倍、letta 的 2.7 倍。
  抽取式管线（对话 → LLM 抽事实 → embedding 入库 → 向量召回）以最简单的心智
  模型拿走了最大份额。
- **Zep 生态的锚点已经迁移**——「Zep 主仓 star 高于图谱引擎仓」的直觉作废，
  写「记忆框架选型」时 graphiti ≥ zep，社区聪明钱在图谱引擎上而非服务 shell 上。
- **表格之外的两个名字不要引：**`MemoryOS-ai/MemoryOS` 与 `memagent-lab/memagent`
  两个仓名在 GitHub API 实测 404（2026-10-11），属幻觉引用，正文一律不引
  （详见文末勘误）。

### 2.2 抽取式事实库：mem0

管线一句话：**对话进来、LLM 抽事实、embedding 入库、向量召回。**没有图谱、
没有复杂数据模型，所以拿得到 66,977 star——面试被问「为什么简单方案赢了」，
答案就是记忆层的 80 分场景只需要「事实的增删改查」。

mem0 论文（arXiv:2504.19413，2025-04，厂商自测口径）给了三笔可背的账：

1. LOCOMO 上 LLM-as-judge 相对 OpenAI 记忆系统**高出 +26%（mem0 论文，厂商自测）。**
2. 图版本 Mem0g 在全量分上只再**多出约 +2%（mem0 论文，厂商自测）。**——
   这 +2% 是「图谱在通用聊天记忆上收益有限、成本却不低」的直接证据。
3. 相对 full-context 方案，p95 延迟低 91%、token 成本**省掉九成以上
   （mem0 论文，厂商自测）。**——「记忆层 = 用十分之一的成本逼近长上下文上限」
   是最有力的产品化论据。

### 2.3 时序知识图谱：Zep / Graphiti

图谱路线的核心卖点一句话：**事实会过期、会被取代，向量库回答不了时效问题。**

机制：实体 + 关系建图，**每条边带时间戳**，新事实到来时旧边「失效但保留历史」
（temporal invalidation，invalidate-not-delete）。于是「用户现在住哪」这类时效
问题天然优于向量检索，且「后来为什么变」可回溯。

Zep 论文（arXiv:2501.13956，2025-01，厂商自测口径）的两笔账：

1. 在 MemGPT 团队自己的 DMR 基准上**以 94.8% 对 93.4% 反超 MemGPT（Zep 论文，
   厂商自测）。**——在对方主场赢下，话术很好看。
2. 在更符合企业场景的 LongMemEval 上准确率最高**提升 +18.5%、**同时延迟
   **降 90%（Zep 论文，厂商自测）。**

代价同样要写进答案：构图是写入侧的多轮 LLM 调用，**写入成本平摊到所有请求，
而收益集中在时序/关系题**。所以工程结论是「按问题类型路由」，而不是全局上图谱
（见 §5.2 与 §九 Q1）。

### 2.4 自编辑记忆块：Letta / MemGPT

把记忆建模成**操作系统分页**：LLM 用函数调用主动改写若干 memory block，
main context（在窗口内）与 archival memory（落库）之间换入换出。Agent 自己
决定「什么值得记住」，是五家里最激进的抽象。

注意两个于己不利的锚点：DMR 基准就是 MemGPT 团队自己提出的，却被 Zep 以
94.8% vs 93.4% 反超；letta 仓 25,102 star 也不敌 mem0。自编辑路线的叙事价值
仍在（agent 主权记忆），但基准与社区两面都没有赢下。

### 2.5 工具化 SDK：LangMem

极简观一句话：**记忆 = Agent 的两个普通工具。**`create_manage_memory_tool` /
`create_search_memory_tool` 塞进热路径让 Agent 自管，外加 background manager
异步抽取整合，原生接 LangGraph Store。不当服务、当库——数据主导权留在调用方。

它还埋了另一条线：prompt refinement（后台优化系统 prompt）是**程序性记忆的
最小实现**，后面 §八 接「skill 固化」时会用到。

### 2.6 SQL 化用户画像：Memobase

立场先行——只做用户画像（memory for user, not agent），**归户主所有**。

工程参数精选（Memobase README changelog，2025，厂商自述口径）：

- **写入批处理化：**离线 buffer 攒到约 1024 token 或空闲约 1 小时才触发 flush；
  v0.0.40 把单次写入管线的 LLM 调用从 3–10 次**固定压到 3 次**，token 成本
  降 40–50%。
- **读取分层：**profile 在线读取只做 SQL，**延迟小于一百毫秒**；context 搜索
  API 含 embedding，500–1000ms。
- **全栈自托管：**FastAPI + Postgres + Redis，是成本敏感场景（陪伴/教育 App）
  的样板。

「批处理 buffer 天然滞后 = 廉价遗忘 + 去重窗口」这个赠品，面试里值得主动点出。

### 2.7 选型话术：别问哪个最好

**选型 = 数据主导权（库 vs 服务）× 时效需求（向量 vs 图谱）× 成本档位
（同步抽取 vs 批处理）。**别问「哪个最好」，问「我的事实多久过期一次、
我的用户事实多久需要可用一次」。

## 三、基准三段论：LOCOMO / LongMemEval / MemBench

### 3.1 LOCOMO：记忆层厂商的主场

规模数字锚：**单条对话平均 300 轮、约 9K token、至多 35 个会话（LOCOMO 论文
arXiv:2402.17753，2024）。**它测的是「超长对话回忆」，mem0、Zep、Memobase
都拿它打榜——正因如此，引用任何一家的 LOCOMO 分数都必须带「厂商自测」限定，
**LOCOMO 上没有公认中立榜单**。

### 3.2 LongMemEval：第三方给记忆层产品背书

- 规模与覆盖面：**共 500 题、五种能力**（信息抽取、多会话推理、时序推理、
  知识更新、拒知）（LongMemEval 论文 arXiv:2410.10813，ICLR 2025）。
- 硬结论：商用助手 + 长上下文模型在持续交互记忆上**准确率退化约 30%
  （同上，第三方口径，可无保留引用）。**——「长上下文 ≠ 有记忆」就从这里来。
- 论文同时给出读取管线的参考答案：**三步走——indexing（session 分解为 value
  粒度）→ retrieval（fact-augmented key expansion）→ reading（time-aware query
  expansion）**，可以直接当「读取管线怎么搭」的模板背
  （各段优化的具体提升幅度见文末口径说明，正文不报绝对分）。

### 3.3 MemBench：设计自家评测时抄框架

MemBench（arXiv:2506.21605，ACL 2025 Findings）补维度：**以 factual /
reflective 两级记忆 × participation / observation 两种场景 × 效果 / 效率 /
容量三类指标为框架**，目前评估面最全。答辩「你们的记忆系统怎么评估」时，三个
基准的组合话术是：**先用 LOCOMO 打榜、LongMemEval 测真实退化、MemBench 补
维度，不可只跑一个。**

## 四、产品形态对照：ChatGPT / Claude / 编程工具

### 4.1 ChatGPT：三级演进 + 开关式控制面

时间线（OpenAI 官方页口径，2024–2025）：

- 2024-02 开始测试、**正式全量（2024-09-05 GA）**（显式 saved memories）；
- **综合升级（2025-04-10）**：saved memories + 从全部历史会话自动归纳
  insights 的双通道；
- **下放免费版（2025-06-03）**：轻量 continuity。

控制面是「开关 + 查看/删除 + Temporary Chat」。注意勘误：「ChatGPT Memory 是
2025 年新功能」的说法作废——GA 在 2024-09，2025 年的两个日期是升级与下放。

### 4.2 Claude：project 级隔离当 guardrail 卖

**上线于 2025-09-11（Anthropic 官方口径，2025）**，Team/Enterprise 先行，
定位「for work」：

- **每个 project 独立记忆**——边界划在 project 级隔离，商务机密不串项目，
  当成安全 guardrail 来卖；
- memory summary **可查看可编辑**，支持记忆导出/迁移；
- **Incognito chat** 不进历史、不进记忆——卖点本质是「不落盘的写入路径」。

对照读：Claude 把边界划在 project 级隔离，ChatGPT 把边界划在「开关 + 临时会话」。

### 4.3 Cursor / Cline：反方向的「文件即记忆」

开发型产品走了显式路线：

- **Cursor 靠 rules 文件**（`.cursor/rules`、`AGENTS.md`）人工/半自动维护项目级
  记忆；
- **Cline 的 Memory Bank** 是社区总结的一组 markdown 文件族模式（属社区模式
  而非官方内置功能，定性口径见文末）。

产物可读、可 git、可 review，但**没有召回机制，也没有冲突消解**。

启示一句话：**聊天型产品做隐式记忆 + 用户可控面板；开发型产品做显式文件记忆。**
边界划在内容敏感性与可审计性需求上。

## 五、工程管线三段：写入 → 冲突消解 → 读取

### 5.1 写入：成本 vs 新鲜度的档杆

三档写入策略，对应三家的选择：

| 档位 | 代表 | 机制 | 代价 / 收益 |
|---|---|---|---|
| 同步抽取 | mem0 | 每次对话同步调 LLM 抽事实 | 最新鲜；每轮都有 LLM 开销 |
| 批处理 buffer | Memobase | 攒约 1024 token 或空闲约 1 小时 flush；单次管线固定 3 次调用 | 廉价、token 成本降 40–50%（厂商自述）；滞后但附赠去重窗口与天然遗忘 |
| 模型自触发 | Letta | Agent 自己决定改写记忆块 | 灵活；依赖模型的自我管理可靠性 |

追问点话术：「你的用户事实多久需要可用一次」**决定档位**——陪伴类分钟级无感，
就走批处理；客服首句就要画像，就得同步或会话开头预取。

### 5.2 合并与冲突消解：两种正统

- **向量去重**：相似度阈值合并。简单，但会误并——「喜欢咖啡」和「喜欢手冲咖啡」
  可能被并成一条丢信息。
- **时序失效（invalidate-not-delete）**：Graphiti 式，新事实让旧边失效但保留
  历史。**企业场景这是硬需求**——「后来为什么变」可回溯，审计与回滚都有抓手。

配套结论：图谱不是伪需求，但要**按问题类型路由**——LOCOMO 上 Mem0g 只多 +2%
（厂商自测），LongMemEval 时序题却是 Zep 的主场 +18.5%（厂商自测）。
收益集中在时序/关系题，成本平摊到所有请求，全局上图谱不划算。

### 5.3 读取：三段式 + 注入预算

读取管线直接套 LongMemEval 论文给的三段式：

1. **indexing**：session 分解为 value 粒度建索引；
2. **retrieval**：fact-augmented key expansion 扩展检索 key；
3. **reading**：time-aware query expansion，时序感知地读。

索引粒度、检索扩展、阅读时的时序感知，一层一层都要回答「注入多少 token、
放在 prompt 哪里」——这就引出了下一节的缓存账。

## 六、记忆注入 × 前缀缓存：隐蔽冲击与四条规避

仓内 [记忆与上下文工程](./记忆与上下文工程.md) §3.6 讲的是「压缩重写历史 →
前缀作废」。**记忆层带来的是另一个、更隐蔽的破坏点**：每轮注入的记忆片段若放在
system prompt 之后、且逐轮内容变化（召回集不同），则整个对话前缀对同一用户
也不再稳定，多轮之间前缀缓存命中率塌陷。

四条规避套路：

1. **会话开头一次性加载**（session-start prefetch，Memobase / Claude 风）：
   之后不逐轮重取，前缀在会话内天然稳定。
2. **稳定槽位**：记忆块固定槽位 + 固定最大 token 预算，少变。
3. **稳定排序**：记忆按创建时间等稳定键注入，而非按相关性逐轮重排。
4. **近似/分块缓存**：允许 block 级缓存，变化只作废变化的 block。

一对可考的矛盾记好：**记忆放得越靠后越省缓存，越靠前模型越重视**——注入位置
本身就是产品决策。

## 七、删除权工程与合规分叉

### 7.1 删除权（GDPR/CCPA）的五步落地清单

「支持用户彻底删除记忆」不是删一行 SQL 完事，要穿透四层加一条旁路：

1. **命名空间隔离**：记忆按用户/项目命名空间隔离（LangMem namespace、
   Memobase 单用户 profile、Claude project 隔离），删除有明确的边界单元。
2. **向量库物理删除**：tombstone 标记 + 索引段物理清理，软删除不等于删除。
3. **图谱边级联**：图谱路线下删用户要级联处理其相关边。
4. **呈现层缓存穿透**：**已合成进 system prompt 的记忆也要失效**——呈现层缓存
   是漏删的高发区。
5. **旁路设计**：Temporary Chat / Incognito 类「不落盘的写入路径」，从源头
   不产生记忆，是删除权的最廉价实现。

对话历史与记忆是**双库**，两边都要删——只删一边是最常见的合规事故。

### 7.2 user memory vs agent self-memory：合规分叉

- **user memory**（Memobase 立场）：profile 归户主，是用户数据，受删除权约束。
- **agent self-memory**（Letta 记忆块）：agent 人设/自省的长期沉淀，是产品资产。

两者合规边界不同，**混在一个库里是面试扣分点**。

## 八、程序性记忆 → skill 固化的边界

LangMem 的 prompt refinement（后台优化系统 prompt）是程序性记忆的最小实现；
再往上就是 Agent Skills 的索引卡模式（详见
[agent-skills详解](./agent-skills详解.md)）。

分工一句话：**记忆层负责「发现什么该沉淀成 skill」，skill 文件负责「以可审计
形式固化」。**前者是隐式、易漂移的；后者可读、可 git、可 review。

## 九、▶ 面试题

**Q1（高频）：mem0 和 Zep 架构差在哪，什么时候选图谱？**
深度提示：抽取式 vs 时序图谱的机制差异先讲清（向量相似召回 vs 带时间戳的边、
invalidate-not-delete）；各给一个自测数字锚做对照——LOCOMO 上 Mem0g 只多 +2%
（mem0 论文，厂商自测），LongMemEval 时序题 Zep 最多 +18.5%（Zep 论文，厂商
自测）；结论落在「图谱收益集中在时序/关系题、构图成本平摊到所有请求，按问题
类型路由而非全局上图谱」。

**Q2（高频）：记忆写进 prompt 会怎么影响推理成本？**
深度提示：前缀缓存逐 token 匹配 → 逐轮变化的记忆片段让同一用户的前缀也不稳定；
至少给两条规避（会话开头一次性加载、稳定槽位 + 稳定排序，最好再补 block 级缓存）；
主动区分「压缩重置前缀」（§3.6 已讲）与「记忆注入破坏前缀」两个不同破坏点，
并能说出「越靠后越省缓存 × 越靠前越受重视」的矛盾。

**Q3（高频）：产品要求支持用户彻底删除记忆，你怎么实现？**
深度提示：命名空间隔离 → 向量库 tombstone + 索引段物理清理 → 图谱边级联 →
呈现层缓存穿透（已注入 system prompt 的记忆）→ 对话历史与记忆双库同删 →
Incognito 类旁路设计兜底。漏掉呈现层缓存是常见失分点。

**Q4（高频）：为什么长上下文模型不能直接取代记忆层？**
深度提示：三个论据按序给——LongMemEval 上商用助手与长上下文模型持续交互
**准确率退化约三成（第三方口径，ICLR 2025）**；mem0 相对 full-context
p95 延迟低 91%、token 成本省九成以上（厂商自测）；机制上注意力稀释、
lost-in-the-middle。

**Q5（中频）：记忆和上下文压缩是替代关系吗？**
深度提示：不是——压缩管本会话窗口内的轨迹下降，记忆管跨会话持久；
协同点是**压缩产物（会话摘要）正是记忆层的优质写入源**。

**Q6（中频）：写入成本和新鲜度怎么权衡？**
深度提示：三档（mem0 同步抽取 / Memobase 批处理 buffer：约 1024 token 或
约 1 小时 flush、单次管线固定 3 次 LLM 调用、token 成本降 40–50%（厂商自述）/
Letta 模型自触发）；判据是「用户事实多久需要可用一次」，并点出批处理附赠
去重窗口与天然滞后遗忘。

**Q7（中频）：记忆系统怎么做评测？**
深度提示：三基准组合——LOCOMO 打榜（平均 300 轮 / 约 9K token，注意无中立
榜单、引用必带厂商自测）、LongMemEval 测真实退化（500 题五种能力、第三方
30% 退化可无保留引用）、MemBench 补维度（两级记忆 × 两场景 × 三指标）；
不可只跑一个。

**Q8（低频）：user memory 和 agent self-memory 为什么要分开？**
深度提示：前者是用户数据、归户主、受删除权约束（Memobase 立场）；后者是
产品资产、agent 人设与自省沉淀（Letta 立场）；合规边界不同，混库即扣分。
