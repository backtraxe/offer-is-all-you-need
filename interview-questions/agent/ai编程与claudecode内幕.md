## 一、引言：AI 编程面试的两种形态

先分清面试管在考你哪一面——两种形态，两套准备：

| 形态 | 考什么 | 答法锚点 |
|---|---|---|
| **「用 AI 写代码」的手撕场** | 工程纪律：你怎么指挥 Agent、怎么验证产出、怎么兜底 | 本文第五节（Vibe Coding 的正确姿势） |
| **编码 Agent 内幕问答** | 你懂不懂工具为什么这么设计：检索、续命、纠偏、成本 | 本文第二、三、四、六节 |

面试官的潜台词是同一句：**你是「用过 Claude Code」还是「读懂了 Claude Code」。**
前者聊体验，后者聊设计动机。本文所有考点都围绕后者展开——每个机制都要能回
答「它这样设计，是在防什么、省什么」。

## 二、检索哲学：为什么 Claude Code 不用 RAG 检索代码

> ▶ 面试题：Claude Code 找代码为什么用 Grep/Glob 而不是向量索引？
> ——**最高频**（本板块第一题）

### 2.1 两种路线的本质差别

| | Agentic Search（Claude Code 路线） | 向量索引代码库 |
|---|---|---|
| 检索原语 | `ls` / `grep` / `glob` + 按目录结构导航 | 代码切块 → embedding → 近邻召回 |
| 找的东西 | **位置线索**（"定义大概在哪个文件"） | "答案片段"（直接拿回一段代码） |
| 后续动作 | 模型自己 open 文件、读上下文、再决定去哪 | 拿着片段直接生成 |

### 2.2 为什么 agentic search 赢了（四连击）

1. **代码是精确符号系统，不是自然语言**。函数名、类型名、调用关系是离散的精确
   匹配问题——`grep "def retry"` 永远命中，向量近邻只能保证"语义像"，而"语义像"
   在代码里常常是错的开始（同名不同义的函数、重载、宏展开）。检索错了，后面
   的修改全错。
2. **检索目标是「位置线索」，不是「答案」**。编码 Agent 的任务是找到"该改哪里"，
   一个文件路径 + 行号就够；拿回了线索，模型自己会去读完整文件。向量检索把
   这一步压缩成"直接还你片段"，看似省了一步，实则把"读上下文"这个最关键的
   理解环节砍掉了。
3. **LLM 自主导航的意外收益**。模型按目录结构往下钻的过程，会**沿途读到测试、
   配置、注释、README**——这些是向量切块永远召不回的隐性知识（"这个目录的测试
   约定是 XXX"、"这个配置说明该模块已 deprecated"）。agentic search 的副产品
   是理解，向量检索的副产品是上下文碎片。
4. **索引漂移与增量成本**。代码是高频变更资产：每次提交都要增量重建索引，索引
   慢了就是"查到昨天的代码"——比查不到更糟，因为错误答案一脸正确。文件系统
   的 `grep` 永远新鲜，零维护成本。

### 2.3 什么时候 RAG 代码检索反而合适

别把话说死，工程判断才有分。三种例外：

- **超大规模 monorepo 的冷启动定位**：百万文件级仓库，`grep` 全扫一次几十秒，
   语义索引做"先粗筛到候选模块、再 agentic 精读"**两级检索**的一级是合理的。
- **未知领域探索**：不知道关键词怎么拼（新接手的 codebase、术语不熟），精确
   匹配无从下手，语义召回可以给入口。
- **跨仓库/跨团队的语义问题**："哪里处理过类似的鉴权逻辑"——这是概念检索，
   不是符号检索，向量路线天然适配。

**参考答法一句话**：精确符号用精确工具，语义探索用语义工具——Claude Code 的
默认场景是"在已知仓库里改已知模块"，所以选了前者并为它设计了整套导航原语；
RAG 代码检索是冷启动和未知领域的补充，不是替代。

## 三、长任务续命三件套

> ▶ 面试题：上下文就这么大，Claude Code 凭什么能跑几小时的任务？
> ——**高频**（与「Auto-Compact 压缩了什么」追问绑定出现）

任务跑几小时，轨迹 token 迟早超过窗口。续命靠三件套的组合，不是单招：

### 3.1 Auto-Compact：水位触发的上下文压缩

- **触发机制**：上下文占用到水位线（接近窗口上限前）自动触发，不是固定步数——
  按"还剩多少空间"而非"走了多少步"决策。
- **摘要结构**：压缩产物不是流水账，是结构化摘要，核心三栏——
  **已完成（done）/ 进行中（in-flight）/ 关键决策（decisions & why）**。
  进行中那栏最容易被丢，丢了它模型会返工重做已走到一半的工作。
- **保什么丢什么**（追问采分点）：
  - **保**：任务目标、设计决策及其理由、文件路径与行号线索、工具调用的
    最终结论、错误教训（"这条路试过了，不通"）。
  - **丢**：中间探索过程、被推翻的方案细节、冗余的工具原始输出。
  - **判据一句话**：丢的是「过程」，保的是「结论 + 决策 + 教训」——
    过程可以重推，决策和教训不能重交学费。
- **与手撕题的对应**：这就是[手写最小 Agent](../../coding/工程手撕/手写最小agent.md)
  里滑动窗口摘要的生产级版本——压缩前把关键结论落盘（scratchpad/文件），
  摘要只当"目录"，关键 ref 可回查原文，防止单一摘要文本失真。

### 3.2 Subagent 隔离：独立上下文 + 摘要回传

- **机制**：主 agent 把探索型子任务派给 subagent——subagent 有**独立的上下文
  窗口**，跑完只回传**压缩后的结论**，几十步搜索轨迹不进主上下文。一次
  "搜遍全仓找用法"可能烧掉几万 token 轨迹，回传的只是三行结论。
- **经典场景**：TDD 探索（subagent 先去理清现有测试约定）、大规模代码搜索、
  文档调研——共同点是**读得多、结论少**。
- **与主 agent 共享什么**（高频追问）：共享**文件系统**（改动的代码两边可见）、
  任务目标与最终结论；**不共享**对话上下文、工具调用轨迹、中间推理。
  一句话：共享世界，不共享记忆。

### 3.3 Checkpoint 与恢复：失败回滚

- 长任务里一次失败的工具调用（改错文件、跑挂测试）不该让整段工作报废：
  在关键动作前落 checkpoint（文件状态快照 + 会话状态），失败可**回滚到
  断点重来**，而不是从头再烧一遍。
- 这是通用 HITL/checkpoint 设计（见[多 Agent 与评测 §四](./多agent与评测.md)）
  在编码场景的具体化：编码任务的状态大头是**工作区文件**，所以
  "回滚 ≈ git 粒度的工作区快照 + 会话轨迹断点"。

**参考答法结构**：三件套分工一句点透——**Auto-Compact 管单上下文内的寿命，
subagent 管把"读多结论少"的开销移出主上下文，checkpoint 管失败不回零**；
然后追问来了能逐件展开保/丢清单。

## 四、Steering 机制：长任务怎么中途纠偏

> ▶ 面试题：Agent 在自己跑，你发现它方向偏了，怎么不打断地纠回来？
> ——**中高**

不能每偏一次就 Ctrl-C 重来——轨迹和已完成的文件改动都是沉没成本。Steering
（纠偏）的设计目标是**在不打断主循环的前提下注入人类/系统的意志**：

1. **Hook 注入**：预设生命周期钩子（工具调用前/后、会话开始前），在特定事件点
   自动注入约束或上下文——比如"每次写文件后自动跑 lint 并把结果喂回去"，
   把纠偏规则**代码化**而不是靠人盯。Hook 是确定性的，模型不听话它也在。
2. **系统提示实时干预**：运行中向循环里插入新的指令消息（用户中途补一句
   "先别动 db 目录"），模型在下一个决策步就能看到并纳入规划——关键点是
   干预**进入轨迹**成为后续推理的输入，而不是事后补丁。
3. **Plan mode 先设计后动手**：把"规划"和"执行"分成两个模式——先只读探索 +
   产出实施计划，人确认后再进入可写执行。这是对纠偏需求的**前置化**：
   最贵的纠偏是在错路上跑了半小时，最便宜的是在动手前改掉一行计划。
   （与 [Agent 基础与规划](./agent基础与规划.md) 里 Plan-and-Execute 的取舍
   同源：步骤可预知的长任务，先定计划显著降低返工。）

**一句话收口**：steering 的本质是把纠偏从「打断 - 重来」降级为「注入 - 继续」，
三招分别对应**自动化规则（hook）、即时意志（消息注入）、事前对齐（plan mode）**。

## 五、工程纪律：Vibe Coding 的正确姿势

> ▶ 面试题：用 AI 写代码，你怎么保证质量？/ 你怎么带一个「重度 Vibe Coding」
> 的团队？——**「用 AI 写代码」手撕场必考**

### 5.1 Spec-Driven Development（SDD）：spec 质量决定产出质量

- **核心主张**：先写清需求/设计文档再让 agent 动手。Agent 产出质量 ∝ spec
  质量——模糊的输入换来"看起来对"的输出，精确的 spec 换来精确的实现。
- **spec 里必须有的东西**：输入/输出契约、边界条件与错误处理预期、
  验收标准（什么算完成）、**不做什么**（防 scope 蔓延）。
- **面试话术**：「我把写 prompt 的时间前移成写 spec 的时间——返工一次的成本
  远高于写清需求一次。」

### 5.2 小步快跑 + 可回滚

- **任务切分到一次能验证的粒度**：一次让 agent 做的事，应该小到你能在一个
  diff 里审完、一条测试命令里验完。大任务拆小，每步交付可编译/可运行的
  中间态，不接受"憋三个小时来一次大爆炸式提交"。
- **测试先行**：让 agent 先写/先跑失败测试再实现（编码场景的 TDD），测试充当
  自动 verifier——没有 verifier 的 vibe coding 产出是不可信的。
- **可回滚**：每步一个原子 commit（或 checkpoint），任何一步验证失败能丢弃
  这一步而不伤前面所有步——呼应第三节 checkpoint 机制在纪律层的对应物。

### 5.3 审查重心转移与成本意识

- **从「逐行读」到「验证点设计」**：AI 生成的代码行你逐行读不过来，也不该读——
  审查重心转移到三处：**spec 对不对、测试覆盖的验收点对不对、diff 的
  blast radius**（动了哪些不该动的文件/接口）。人做方向与边界的守卫，
  细节交给测试和自动化闸门。
- **额度与成本意识（token 经济学一句话）**：每个指令动作都在烧钱——让 agent
  "顺便把整个仓重构了"的请求，账单和 diff 一起失控。给任务的 scope 越窄，
  token 效率和结果质量同时越高；**成本约束本身就是最好的纪律**。

## 六、Token 成本治理

> ▶ 面试题：编码 Agent 的 token 大头在哪？怎么省？——**中高**（常与第二、三节
> 联动追问）

### 6.1 账单结构：钱烧在哪

编码场景的 token 账单大头不是"聊天内容"，是三块结构性开销：

1. **系统提示**：工具 schema、行为规则、环境信息，**每一轮都重复计费**——
   长会话里它是最大的固定成本。
2. **工具结果回灌**：一次 `grep` 返回几百行、一次测试失败返回整段 log，
   全部进上下文并随轨迹滚动累加。
3. **文件注入**：读文件的原文注入——"为了改 10 行，读进 2000 行"是常态浪费。

### 6.2 吝啬原则：三招降本

- **按需读片段**：默认读文件片段（按行区间/symbol 定位），而不是整文件吞——
  与第二节 agentic search 配合：先 grep 到行号，再只读相关区间。
- **压缩工具输出**：工具返回在进上下文前裁剪（截断长 log 只保 head/tail、
  grep 结果限量 + 摘要），超长输出卸载到文件、上下文里只留指针——
  原则与[记忆与上下文工程](./记忆与上下文工程.md)的工具结果压缩同源。
- **缓存命中**：系统提示与仓库静态背景放在 prompt 前缀、走 prefix caching——
  结构稳定的前缀让每轮重复部分命中缓存，直接打折固定成本的大头。

**一句话收口**：编码 agent 的成本治理 = **固定成本靠缓存（前缀稳定），
可变成本靠吝啬（按需取、进前裁）**。

## 七、▶ 面试追问五条（附答法骨架）

1. **「为什么 Claude Code 不用 RAG 检索代码？」**
   代码是精确符号系统，向量只保"语义像"不保"语义对"；agentic search 检索的是
   位置线索而非答案，沿途还白捡测试/配置/注释的隐性理解；加一句索引漂移的
   维护成本。收尾补例外：monorepo 冷启动与未知领域探索里，语义召回做一级
   粗筛是合理的——说不死才是工程判断。
2. **「Auto-Compact 压缩了什么？丢了什么？」**
   保：任务目标、设计决策及理由、路径/行号线索、工具最终结论、错误教训；
   丢：中间探索过程、被推翻方案、冗余原始输出。判据：丢过程、保"结论 + 决策 +
   教训"。再补一句防失真：压缩前关键结论落盘，摘要当目录可回查原文。
3. **「subagent 和主 agent 共享什么？」**
   共享文件系统（改动互见）、任务目标与压缩结论；不共享对话上下文与工具轨迹。
   一句话：共享世界，不共享记忆——这也是它省 token 的原因，几万 token 的搜索
   轨迹只回传三行结论。
4. **「Vibe Coding 怎么保证代码质量？」**
   三段式：SDD 保输入质量（spec 有契约/边界/验收/不做什么）→ 小步 + 测试先行
   保每步可验证可回滚 → 审查重心转向 spec/验收点/blast radius 而非逐行。
   收尾甩成本意识：scope 越窄 token 效率与质量同升。
5. **「SDD 和 TDD 什么关系？」**
   互补不互替：SDD 管「做对的事」（需求与设计的精确化，输入质量），TDD 管
   「把事做对并持续对」（可执行验收，过程质量）。AI 编程场景里两者是天然
   搭档——spec 让 agent 知道做什么，测试让 agent（和你）能验证做对了没有；
   测试同时充当 agent 的自动 verifier。
