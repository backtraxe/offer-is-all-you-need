## 一、先分清：记忆 ≠ 上下文

面试常混淆的两个概念，一次说清：

- **上下文（Context）**：这一次调用 LLM 实际"看到"的全部 token——窗口有限、
  按次计费、过窗即失。是**运行时工作内存**。
- **记忆（Memory）**：跨步骤、跨会话需要保留的信息——可能存在上下文里，
  也可能长期落库。**记忆是「存什么」，上下文是「现在给模型看什么」**。

上下文工程管的是：**在有限的窗口里，每一轮该放哪些信息、以什么形态放、
放不进去的怎么压。** 记忆设计管的是：**什么信息值得跨轮/跨会话留存、存哪、
怎么召回、怎么防污染。**

## 二、短期记忆 vs 长期记忆

> ▶ 面试题：Agent 长短期记忆怎么设计？存什么库、粒度、召回、防记忆污染？
> ——**高**（京东/携程/美团/字节，Top 20 第 15 题）

### 2.1 分工

| 维度 | 短期记忆（工作记忆） | 长期记忆 |
|---|---|---|
| 内容 | 本会话轨迹：消息历史、TAO 循环中间态、工具返回摘要 | 跨会话知识：用户偏好、历史结论、领域事实、沉淀经验 |
| 存储 | LLM 上下文窗口（本质是 prompt 拼接） | 向量库（语义召回）+ SQL/KV（结构化、精确字段） + 知识图谱（关系） |
| 生命周期 | 会话结束即消亡（或由总结转存长期） | 显式写入/淘汰，长期存在 |
| 召回方式 | 全量呈递（或裁剪后呈递） | 按需检索：向量相似 / SQL 查询 / 混合 |
| 失效模式 | 窗口爆掉、早期信息稀释 | 记忆污染、过期、召回不准 |

### 2.2 长期记忆粒度怎么定（追问高频）

三种粒度，按场景选：

- **事实级**：`用户偏好: 用中文回复`、`上次结论: 客户A的 SLA 是4h`——KV 存储，
  精确写入。
- **摘要级**：会话结束时生成"本次会话摘要"存库，下次会话召回拼进 system——
  成本低、召回面广，是最常用的起步方案。
- **轨迹级（经验）**：成功/失败的完整任务轨迹存起来，下次遇到同类任务做
  few-shot 召回（Voyager / Reflexion 式经验记忆）——复杂但天花板高。

### 2.3 召回策略

- 召回时机：**查询触发**（每轮跑一次相关性召回）或**前置加载**（会话开头拉
  用户画像 + 最近摘要，之后不再动）。
- 召回方式：向量相似（语义）+ 过滤字段（user_id、时间、tag），生产上必加
  **时间衰减**（越久权重越低）。
- 防爆：召回条数 × 每条长度要有预算（见第四节 Token 分配）。

### 2.4 防记忆污染（面试官爱挖的细节）

"记忆污染"= 错误/过期/被注入的信息进了长期库，以后一直被错误地召回。防护：

1. **写入门槛**：不是所有会话都沉淀——由模型自检"这是稳定事实还是一次性
   中间态"，只有通过门槛的事实才入库。
2. **冲突解决**：新事实与旧记忆冲突时显式 reconcile（更新/改写/记版本），
   不是无脑追加。
3. **过期机制**：带 TTL 或时效字段（"用户当前公司"这类易变事实）。
4. **注入隔离**：来自工具返回/外部文档的内容**不直接写长期记忆**——先过
   污染源过滤，防间接注入落库（呼应上一篇的 Prompt Injection）。
5. **可追溯**：每条记忆带 provenance（来自哪次会话、什么时间），出事能查账。

> **参考答法一句话**：短期记忆管"这一回合模型看得见的轨迹"，长期记忆管
> "跨会话沉淀的事实与经验"；存库分向量/SQL/KV，召回加时间衰减，写入设门槛防
> 污染，高危内容入库前先过污染源隔离。

## 三、上下文工程全景（2026 重灾区）

> ▶ 面试题：上下文压缩策略有哪些？压缩放在链路哪一步？工具结果怎么压？
> ——**高，2026 新热点**（字节系追问主线）

### 3.1 先定义：上下文工程是什么

Prompt Engineering 是"写好那段提示词"；Context Engineering 是**管理每轮
放进窗口的整个信息组合**：系统指令、记忆召回、工具 Schema、历史轨迹、工具
返回、当前输入。随着 Agent 长任务化（几十步、上百轮），上下文成了最稀缺
资源之一——放错位置的信息 = 浪费钱 + 稀释注意力 + 拉长首 token 延迟。

### 3.2 压缩四大策略

| 策略 | 怎么压 | 保住什么、丢掉什么 | 适用场景 |
|---|---|---|---|
| **截断 / 滑动窗口** | 直接丢弃最老 N 轮或超出 T token 的部分 | 保"最近态"，丢早期历史 | 短链路对话、早期信息与当前任务弱相关时 |
| **摘要（Summarize）** | 用小模型/主模型把历史压成摘要 | 保"语义主线"，丢细节 | 长对话、多轮客服；代价是有损（关键数字可能丢） |
| **向量化 / RAG 化** | 历史全部入库，按需召回 Top-K | 保"按相关性取回"，不在窗口里的"不可见" | 超长轨迹、需回查细节的场景（Agent 回溯某一步） |
| **工具结果压缩** | 只压工具返回：大 JSON 裁字段、网页/文档正文抽取、日志过滤 | 保"决策所需信息"，去冗余格式与噪声 | **重灾区**：工具返回往往是上下文膨胀元凶 |

工程真相：**四种不是互斥，是组合拳**。生产系统常见配置：轨迹 RAG 化（全量
入库）+ 最近 K 轮原样 + 更早部分摘要 + 每个工具返回先过压缩器。

### 3.3 压缩放在链路哪一步（核心追问）

压缩位置决定了信息损失的传播路径，四种位置：

| 位置 | 含义 | 优点 | 风险 |
|---|---|---|---|
| **工具返回时（源头压）** | 工具执行完、进上下文前先压 | 粒度最细、最省 token | 压掉的信息模型永远不知道存在过（需谨慎设阈值：返回 >N token 才压） |
| **历史轨迹追加前（滚动压）** | 每轮结束，老轮次逐步摘要/清理 | 平滑、窗口利用稳定 | 摘要模型自身的误差会累积多轮 |
| **触发式压**（超长才压） | 上下文接近上限才启动压缩 | 未超限零成本零损失 | 压缩本身要消耗一大段上下文，可能"临门一脚"撑爆 |
| **离线沉淀（分层）** | 原轨迹全量入库，窗口只放索引 | 信息零丢失，可回查 | 需要召回机制准，否则"我有但找不到" |

**建议话术**：源头压 + 滚动压组合——工具返回超过阈值就地裁（大 JSON 留关键
字段、网页留正文），同时全局轨迹分层（最近原样 / 中期摘要 / 全量入库）。
既防膨胀，又保留"必要时回查原文"的逃生门。

### 3.4 工具结果压缩的实操要点（单独追问高频）

1. **结构化裁剪优于自然语言摘要**：JSON 删字段 > 让模型写摘要（后者
   morph 数字概率高）。
2. **按工具类型定压缩器**：网页 → 正文提取（读ability/trafilatura）；
   SQL 结果 → 限制行数 + 列裁剪；日志 → 正则过滤 + 错误段上下文窗口。
3. **压缩后保留指针**：`（完整结果存于 memory://trace/12，可回查）` ——
   让 Agent 自己决定要不要回查原文。这是高阶设计也是加分项。
4. **压不了的别压**：代码 diff、报错堆栈等"每一个字都有意义"的内容，宁可
   走"截断窗口把别的挤掉"也别乱压。

## 四、Token 预算分配（量化追问的弹药）

> ▶ 面试题：上下文怎么分配？——**高**（字节纵深）

预留预算的参考配置（以 200K 窗口为例，面试中按需缩放）：

| 区块 | 占比建议 | 内容 |
|---|---|---|
| 系统指令 + 角色 + 安全规则 | 5–10% | 固定 |
| 工具 Schema（裁剪后） | 10% | 几百个工具要走检索注入（见上一篇） |
| 长期记忆召回 | 10–15% | 用户画像 + 会话摘要 + 事实 |
| 轨迹（TAO + 消息） | 40–50% | 工作记忆主体；摘要层也计入这里 |
| 工具返回（最新压缩后） | 10–15% | 每步工具结果总和 |
| 预留输出空间 + 冗余 | 10–20% | 输出 token + 压缩缓冲 |

关键工程指标（面试能报数即合格）：**上下文使用率（实际/窗口）、压缩比、
压缩后任务成功率变化、TTFT 影响**。压缩的评估不是"省了多少 token"，而是
"成功率掉没掉"——省 token 不牺牲成功率才是好的压缩。

## 五、常见模式参考（工程实践汇总）

真实系统里常见的上下文管理模式：

1. **Scratchpad 模式**：给模型一个显式"记事本"区（如结构化 JSON），让它把
   关键中间结论写回去；轨迹可以被摘要，但 scratchpad 永久在窗口。Claude Code
   的 todo list、Deep Research 类的 research log 都是这个思路。
2. **子任务隔离**：复杂子任务派给子 Agent，只把**结论**回填主上下文——子
   Agent 的内部十几步轨迹不污染主 Agent 窗口（详见下一篇多 Agent）。
3. **分层记忆区**：system 区 / 长期记忆区 / 滚动摘要区 / 原始轨迹区
   / 工具返回区，各自有生命周期与预算，由"上下文管理器"统一调度。
4. **可回查指针**：被压缩掉的内容留引用（trace id / memory id），让模型
   可以发起"回查"请求——上下文从"一次性快照"变成"可寻址内存"。
5. **KV Cache 友好摆放**：稳定内容（system、工具 Schema）放最前，频繁变化
   的内容放最后，**最大化前缀缓存命中**——这是很多团队忽略的免费优化，
   面试提及极加分。
