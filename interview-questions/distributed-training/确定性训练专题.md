# 确定性训练专题：万卡比特级可复现的完整方法论（Megatron Core 案例）

> 面向已经读过 [训练框架与稳定性](./训练框架与稳定性.md) 与
> [Megatron 源码深度拆解](./megatron源码深度拆解.md) 的训练栈读者。
> 本篇拆解 NVIDIA Megatron Core 的比特确定性工程（2026-10 官方技术
> 报告）：万亿参数混合架构（Mamba SSM + Attention）在 2,432 GPU 上
> **800 步保持逐位相同**，确定性税从 17%~60% 压到约 2%。读完获得：
> ① 比特确定性的严格定义与四个业务价值；② 「打印 loss 不够敏感」
> 之后的指纹验证法；③ 排查非确定性的**五层分层追踪 SOP**（输入匹配
> 输出不同即源头）；④ 确定性税的压降路径与 grouped-GEMM 经典案例；
> ⑤ 防退化三层体系与六条症状速查。
>
> **口径声明**：全部百分比与规模数字为 NVIDIA 官方技术报告口径，未

## 一、严格定义：两条轨迹，两个保证

在数据顺序、架构、配方、并行策略、软件、运行时设置和硬件全部固定的
前提下，比特确定性要求：

1. **独立可复现**：同一初始状态启动的两次运行，每一步逐位相同；
2. **比特级 checkpoint 恢复**：保存并恢复一次或多次 checkpoint 的
   运行，与不间断运行逐位相同。

最容易踩的认知坑：**打印出来的 loss 相同，不等于逐位相同**。两次运行
可以打印出相同的舍入后 loss，而梯度或参数的低位比特早已不同——
验证必须对数值本身做指纹，不能看打印值。

## 二、为什么愿意为它付钱：四个价值 + 一笔规模账

| 价值 | 一句话 |
|---|---|
| 复现故障 | 在同一个 step 重现 loss 尖峰，一次只改一个组件隔离原因 |
| checkpoint 连续性 | 中断恢复不改变数值轨迹，断点续训敢说「等价」 |
| 发现意外差异 | 本该相同的两次运行不匹配 → checkpoint 损坏或软硬件问题的探针 |
| 区分变更与噪声 | 有意改动的数值效应 vs 运行间自然波动，终于分开 |

规模账（官方口径）：万卡跑 100 天的非确定性基线下，把确定性税从
15% 压到 5%，省 10 天 = **100,000 GPU 天**。万亿参数规模上「慢
一点点」都是数千 GPU 天，所以确定性必须做到生产可用的低税。

## 三、验证法：逐步指纹 + 恢复五件套

更强的验证流程是每一步对选定指标做指纹，逐步配对对比：

- **指纹指标集**：训练 loss、语言建模 loss、负载均衡 loss（MoE）、
  MTP loss、梯度范数；第一个不匹配的 step 缩小排查范围。
- **checkpoint 恢复验证五件套**：参数、优化器状态、RNG 状态、数据
  位置、后续输出，逐项与不间断参考运行逐位对比。
- **全精度真值路径**：万亿模型的 checkpoint 路径保留全精度真值，
  运行时低精度表示通过与训练时**相同的转换路径**重建——低精度权重
  的缩放元数据重建方式不同，是「加载后参数立刻不同」的标准病因。

**不要只追 loss 明显分离的那个迭代**——第一个不同的比特往往出现得
更早，宽追踪先定位最早分叉的迭代和 rank，再在该范围开细粒度。

## 四、核心武器：五层分层追踪 SOP

同一个因果测试贯穿每一层：**进入某范围时输入逐位相同、离开时输出
不同，分叉就源于这个范围**。

| 层 | 覆盖 | 产出 |
|---|---|---|
| 端到端 | 训练迭代级指标 | 定位第一个序列化指标不同的迭代 |
| 宽语义 | 集合通信、流水线通信、重计算、优化器操作、梯度归约 | 定位分叉的训练阶段 |
| 模块/层 | Transformer 层、MoE 块、优化器阶段 | 定位到具体组件 |
| 操作级 | ATen 操作与扩展调用指纹 | 第一个输入相同输出不同的 op |
| 内核级 | 内核、算法配置、非确定性机制 | 归因完成，出修复方案 |

配套的解读表（按 rank 各自算「首次不匹配」，序列号不跨 rank 排序）：

| 首次不匹配形态 | 解读 | 下一步 |
|---|---|---|
| 输入匹配，输出不同 | 候选源头 | 排查该操作或其隐藏生产者 |
| 输入、输出都不同 | 下游接收者 | 继续向上游追踪 |
| 被追踪 rank 上无源头 | 源头在捕获范围外 | 扩大迭代窗口或 rank 集合 |

两条工程军规：

- **按 rank 本地捕获、离线对齐**（按 op 名、出现次数、模块范围对齐
  事件），不引入集合通信或跨 rank 排序——观察本身不能成为新的
  竞态源；
- **聚合形态有信息量**：很多 rank 指向同一个源头操作 → 该操作本身
  大概率非确定（atomics、未固定顺序的归约）；只有部分 rank 指向 →
  排查拓扑、rank 布局、输入分布、归约顺序。

## 五、指纹工程细节（决定这套方法灵不灵）

- 指纹用 GPU 上的 `torch.hash_tensor`，附带形状、dtype、元素数；
  MXFP8/NVFP4 张量要**同时给编码值和 scale 缓冲做指纹**；
- 整张量 XOR 指纹**检测不到置换**——路由图、MoE 分发输出这类顺序
  敏感数据必须按行/分块做指纹；
- 指纹匹配只是高效筛查，**确认逐位相同要字节级对比**；
- 误报三排除，排除完再断言生产者非确定：
  1. `TorchDispatchMode` 只能观测走 PyTorch 调度器的 ATen 操作——
     自定义 kernel 会逃出追踪；首次不匹配落在 view/slice/add 这种
     简单操作上时，去探测**产生其输入的自定义 kernel**；
  2. 未初始化张量、未完成的异步集合通信、非阻塞拷贝可能在内容
     有效前被读到；
  3. 修完用配对运行验证：原配对应复现分叉、打补丁配对应逐位相同；
     并回答「补丁是修正了非确定实现，还是绕开了它」+ 测量新增税。

边界说明：比特确定性只在**相同软硬件环境内**成立；跨 GPU 代际、
网络配置、库版本的对照超出范围，结果不同不能当 bug。

## 六、确定性税怎么压：三条战线 + 一个经典案例

受控基线先行：同模型、同硬件、同 batch、同并行策略、同精度、同软件
栈、同测量窗口，对比确定性执行与最快非确定性配方的吞吐/step 时间、
峰值显存、GPU 利用率、暴露通信时间、主要内核组耗时——数据只在训练
性能稳定后采集。

Nemotron 3 Ultra（混合 Mamba SSM + Attention，万亿参数）的三线战绩
（官方口径）：

| 战线 | 确定性税 | 关键动作 |
|---|---|---|
| 主线 | 17% → 2% → **降至 1.5%（3,072 GPU 实测）** | 避免使用前被覆写的填充缓冲 |
| 混合 Triton 代理 | 60% → 37% → **降至 2%** | 恢复 MoE-MLP 融合 |
| CuTeDSL 权重梯度路径 | ≈3.6%（@256 GPU） | 专用确定性路径 |
| **稳态结论** | **约 2%（2,432 GPU、800 步逐位相同）** | 三件套合流 |

注意纪律：**几块 GPU 上的低税不能保证生产规模同样低**——通信、
同步、流水线气泡、专家路由、负载均衡都会改变相对开销，税必须在
目标规模上实测。

**经典案例：grouped-GEMM 的同步搬家。**epilogue 里多个 N-tile 原来
累加到同一个 `dprob[token]` 地址，结果取决于到达顺序。暴力串行化
写入者能恢复确定性，但并行度被毁。优化：**每个 N-tile 一个私有输出
槽，内核内保持并行，全部写入者完成后按固定顺序合并**——输出契约
不变，性能代价只取决于顺序在何处强制执行。这个模式（竞争同址 →
私有槽 + 定序归并）是确定性修复的第一直觉模式，面试可直接背。

## 七、防退化三层 + 症状速查六条

防退化体系（新内核、融合、精度格式、并行配置都可能引入非确定性）：

1. **配方验证**：`--deterministic-mode` 应用规范环境设置、启用
   PyTorch 确定性算法、拒绝没有确定性路径的特性；
2. **内核测试**：相同输入和 RNG 状态重复操作，逐字节对比输出与梯度；
3. **模块验证**：跨并行配置（含 FP8/FP4）用恢复的 RNG 重复模型与
   Transformer 块，端到端独立运行再验证全精度指标逐位相同。

| 症状 | 可能原因 | 处置 |
|---|---|---|
| 两次运行第一步就分叉但不稳定 | 运行时自动调优选了不同 kernel 配置 | 对比所选配置，固定或缓存验证过的配置 |
| MoE 只在开启融合辅助损失时分叉 | 归约顺序未固定 | 逐个关融合追踪损失计算；用确定性归约或关掉该融合 |
| 恢复运行逐渐偏离连续运行 | RNG 状态恢复不完整 | 恢复前后对比 RNG 状态，逐位保存恢复每个流 |
| 软件/容器更新后出现分叉 | 底层库 kernel 变化 | 二分软件栈、最小 kernel 复现；修复前选确定性内核路径 |
| 加载 checkpoint 后参数立刻不同 | 低精度权重或缩放元数据重建不同 | 保留全精度真值与精确重建路径 |
| 小规模通过、大规模失败 | 规模相关的通信或 EP 路径 | 逐级扩大规模追踪选定 rank，隔离第一个规模相关操作 |

## 八、和 RL「训推一致性」的关系与边界

训练比特确定性（同输入同轨迹）与 RL 关心的**训推数值一致性**
（rollout 引擎与训练引擎的 logprob 对齐）是两件事但共享底层武器：
批不变 kernel（batch-invariant kernel）、确定性归约、指纹对账方法。
推理侧的同族工程见 [推理引擎 2026 新进展](../inference/推理引擎2026新进展.md)
Q6（batch-invariant 配套方向）与
[RL 训练工程实战](../训练与对齐/rl训练工程实战.md)（训推不一致的
工程后果）。面试被问「可复现」要分清问的是哪一层：**训练轨迹可复现
（本篇）/ 训推一致（RL 篇）/ 推理输出确定（推理引擎侧）**。

## 九、▶ 面试题与追问

**Q1【高】大规模训练里怎么排查 loss 尖峰？**
先要有比特确定性才有「同一个 step 重现尖峰」的前提；重现后按五层
追踪收窄：端到端指纹定位最早分叉迭代 → 宽语义定位阶段 → 模块层 →
操作级第一个输入同输出不同的 op → 内核级归因。每一步的判据都是
「输入匹配、输出不同」。

**Q2【高】为什么打印 loss 相同不能证明训练可复现？**
打印是舍入后的低精度视图，梯度和参数的低位比特不同不会改变打印值。
验证要对选定指标做每步指纹（loss 族 + 梯度范数），恢复场景再加
参数/优化器/RNG/数据位置逐项逐位对比，最终用字节级对比确认。

**Q3【中高】确定性训练的税从哪来？怎么压？**
来源：禁快选慢（确定性 kernel 通常不是最快实现）、融合被拆、归约
顺序固定化损失并行性、autotuner 被钉死。压法三件套：受控基线找出
税负最大的内核组 → 用「私有槽 + 定序归并」「恢复值得恢复的融合」
「确定性专用实现（CuTeDSL 类）」逐组压 → 在目标规模实测，不以
小规模低税外推。

**Q4【中高】MoE 模型的确定性坑比一般模型多哪些？**
三组：路由图/分发输出是顺序敏感数据（整张量指纹测不出置换，要按
行/分块）；负载均衡损失与辅助损失的归约顺序；EP 路径的规模相关
行为（小规模过、大规模挂）。验证指标集要把负载均衡 loss 纳入指纹。

**Q5【中高】首次不匹配落在 view/slice/add 上，说明什么？**
大概率是追踪盲区：这些简单 op 很少自己非确定，真正的生产者是逃出
`TorchDispatchMode` 视野的自定义 kernel——沿数据流向上找隐藏生产者，
别在受害者身上归因。

**Q6【中】恢复运行逐渐偏离连续运行，第一嫌疑是什么？**
RNG 状态恢复不完整——独立验证方法：恢复前后逐位对比每个 RNG 流
的保存/恢复值。第二嫌疑是数据位置（sampler 状态/数据偏移）。这正
是「恢复五件套」存在的意义。

**Q7【中】确定性只在什么边界内成立？跨硬件对比怎么理解？**
只在相同软硬件环境成立。跨 GPU 代际、网络拓扑、库版本的差异会
改变归约与内核选择，结果不同不算 bug；所以论文/报告里报「逐位一致」
必须带环境清单，迁移环境后要重新验证。
