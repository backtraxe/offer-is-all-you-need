# 训练光速手算实战专题：DeepSeek-V3 一步训练的全量拆账（FSDP vs PP 判决书）

> 面向已经读过 [三维并行](./三维并行.md) 与 [zero与显存优化](./zero与显存优化.md)
> 的训练栈读者。本篇是「训练侧 roofline」的完整实战：不用搭两套系统、
> 不在全尺寸集群上实测，用**电子表格 + speed of light** 给 DeepSeek-V3
> （671B MoE、36.6G 激活、EP64、DualPipe）在 2,048 张 H800 上的一步训练
> 算出墙上时间，并先验地判定「FSDP/ZeRO-3 是坏主意、PP 才是答案」——
> EP 通信单独吃掉算力时间的 **84.8%**、ZeRO-3 在 8 microbatch 下 **69%
> 暴露通信**、PP 只引入 **248 ms bubble（3.89%）**、光速步时间 6.64 s。
> 最后用 DeepSeek 官方 64 卡 trace 逐 kernel 对账，解释光速与实测的
> **3 倍**差距。读完你应该能手推：6ND 从哪来、为什么 attention FLOP
> 不能省、EP 通信量怎么算、ZeRO-3 为什么是钳形困境、PP 的 bubble 公式、
> 以及「光速为什么永远预测不准但永远值得算」。
>
> **口径声明**：方法与数字来自 Edward Yang 的 DeepSeek-V3 注释版研究
> （第 3 章 roofline，2026-10 转述），DeepSeek 官方 trace 为公开 profiling
> 数据；所有推导在文内给出，可复核。

## 一、roofline 在训练侧的两条改写

kernel 级 roofline 判「算力受限 vs 带宽受限」。一整步训练也能做同样
的判定，但有两处改写：

1. **瓶颈从 HBM 换成跨节点带宽**（IB；NVL72 域内把 NVL 域当「节点」看）；
2. **FLOP 总量与并行策略无关**（披萨总量固定，怎么切都吃完它），而
   **通信量完全由并行策略决定**——所以「选 FSDP 还是 PP」在架构固定时
   就是一个「哪种切法通信时间 < 算力时间」的问题。

经验法则就是想待在算力受限区：通信能被 overlap 掉（假装免费，其实不
免费）；算力盖不住通信，就改架构或改并行。注意一个反直觉：**算力效率
优化（如 FP8 GEMM）会让通信受限更严重**——GEMM 变快、通信量没降。

## 二、6ND 从哪来：每个参数每个 token 两次 FLOP

非 attention 的矩阵乘占 FLOP 大头。一个权重对每个 token 做一次乘加：
**2 FLOP/参数/token**。一个权重矩阵有三个 matmul：前向、反向算输入
梯度、反向算权重梯度——所以乘 3：

**每步 FLOP = 6 × N × D**（N 激活参数、D 每步 token 数）

为什么这个近似在「规模论证」里严格成立：加宽时非 matmul 算力线性涨，
而可学习投影的 FLOP 随宽度平方涨，极限下后者压倒一切；LM head 随词表
涨但只占线性项，小模型显眼、极限下趋零。DeepSeek-V3 的数字：
N=36.6G 激活 × D=62.9M token/步（B=15,360 序列 × S=4,096）=
**13.8 EFLOP/步**；÷（2,048 卡 × FP8 光速）= **4.63 s（裸版）**。

**修正三处，全部可复核：**

1. **attention 的 FLOP 不能省**——QKᵀ 与 PV 两个无参数 matmul，随
   序列长度涨：每层每序列 `4S²d`（causal 减半）。DSv3：QKᵀ 412 GFLOP
   每层每序列、PV 275 GFLOP；QKᵀ 形状跑 4 次（前向+dQ+dK+recompute）、
   PV 形状 3 次 → **2.32 EFLOP/步 → 1.49 s（BF16 光速）**。预训练
   序列不长时 attention 占比小；长序列 midtraining 它成瓶颈。
2. **recompute 很便宜**——DSv3 只重算 MLA up-projection 输出：
   3.33G 参数 → 419 PFLOP/步 → **140 ms**，加到墙钟里几乎看不见。
   （反例警戒：全 recompute 换 activation 显存，多整整一个前向的
   算力且 EP 通信重跑一遍，通常是很烂的交易。）
3. **BF16 和 FP8 分开除光速**——attention/router/LM head 是 BF16：
   1.03G 参数 → 390 PFLOP；从 6ND 里拆出后 FP8 剩 13.4 EFLOP→4.50 s、
   BF16→251 ms，净修正只多 121 ms（FP8 主导时这条影响小，主导精度
   不明显的模型上它会很大）。

**算力总账：T+c = 4.50 + 0.251 + 1.49 + 0.140 = 6.39 s。**

## 三、EP 通信：光它就吃掉算力时间的 84.8%

假设：均匀路由 + 同节点去重（IB 按节点广播一次、NVLink 本地分发）+
路由至多 4 节点 + FP8 按 1×128 tile 带 scale（d/128=56 个、224 B）。

手算链（全部入表）：

- 每 token 送 `M_IB = 4 × (1 − 8/64) ≈ 3.5` 个远端节点（去重+期望，
  实际仿真均值 3.46）；
- dispatch 每 token 每层：`3.5 × 7,168 × 1 B ≈ 25.1 KB`（FP8），
  combine：`3.5 × 7,168 × 2 B ≈ 50.2 KB`（BF16）；
- 58 个 MoE 层 × 前后向：`V_tok ≈ 8.73 MB/token`（带 FP8 scale 后
  8.82 MB）；
- 每 GPU 30.7K token/步 → `V_EP ≈ 268-271 GB` → **T+EP ≈ 5.42 s**。

对照算力 6.39 s：**f_EP = 5.42 / 6.39 = 84.8%**——光是 EP 通信就
逼近算力时间，任何再叠加的通信都会越过算力线。这个数字就是
DeepSeek 「infra-model codesign 余量很薄」的直接证据（均衡路由是
假设，真实偏斜更糟）。

## 四、ZeRO-1 的分层 all-gather 账（ZeRO-3 判死刑前的台阶）

分层 all-gather：先 IB 跨 256 个同 local-rank 卡各拿 1/8，再节点
内 NVLink 分 1/8——IB 通信降为全量的 1/8。**但 routed expert 参数
蹭不到 NVLink**（EP 下不同节点本就不同 expert，NVLink 被 EP all-to-all
占着），它们全额走 IB：

- 非 expert：17.1G → 经 IB 2.14G/卡（`×(1−1/256)`）；
- expert：654G → EP 分片后 10.2G/卡，EDP 32 副本全额 IB（`×(1−1/32)`）；
- 反直觉亮点：**expert 分片后参数更少，IB 通信反而更多**——因为一片
  NVLink 都蹭不到。

合并后 ZeRO-1 的步内同步：BF16 all-gather 24.1 GB（481 ms）+ FP32
reduce-scatter 48.1 GB（962 ms）= **1.44 s**，已经贴着通信受限线。

## 五、ZeRO-3 的钳形困境（本篇主角判决）

FSDP 每个 microbatch 都要「前向 all-gather + 反向 all-gather + 梯度
reduce-scatter」：`V_mb = 96.2 GB、T_mb = 1.92 s`。困境两端夹击：

1. **FSDP 不省 activation 显存**——要装下就得加 microbatch 数（减小
   每个的大小）；DSv3+H800 上只有 m=8 才把峰值压进 80 GiB；
2. **microbatch 越小，FSDP 通信露得越多**——每个 microbatch 独立付
   1.92 s，能拿来 overlap 的算力同步变少：m=2 时 3.85 s、m=4 时 7.70 s、
   **m=8 时 15.4 s ≫ 算力 6.39 s，暴露通信占 69%**。

判决书写法：**EP+ZeRO-3 在原始配置下无解**——不是实现不够好，是
流量结构上「一个 microbatch 的 EP+FSDP 流量就已经通信受限」。这正是
「想在不全尺寸集群上决定 FSDP 还是 PP」这类问题的标准答案形态。

## 六、PP（DualPipeV）：bubble 公式与 248 ms

PP 只搬跨 stage 的 residual stream，随 hidden size 线性涨，便宜：
PP=8、每 rank 2 chunk、每 replica 246K token/步 → V_PP=14.1 GB →
**TPP = 282 ms**。ZeRO-1 在 PP 下只对自己 stage 的参数做 collective，
通信量除以 PP：V_PPsync=7.30 GB → 146 ms。

真正的代价是 bubble。1F1B：bubble 占算力 `(PP−1)/m`，m=60 时
11.7%（745 ms）。DualPipeV 压到：

`(PP−1) × (tF&B + tB − 3·tW) / (sGPU · m · (1+tB))`，F≈W、tB≈2
→ **3.89% → 248 ms**。

bubble 只与 stage 数、microbatch 数有关，**与模型大小无关**；
microbatch 越多 bubble 越小（代价是 GEMM 利用率）——和 FSDP 的
「microbatch 越多暴露越多」恰好镜像：同一个旋钮，FSDP 往坏走、PP
往好走，这就是架构判决的全部理由。

**光速汇总**：`T_IB = T+EP 5.42 + TPP 0.282 + TPPsync 0.146 = 5.85 s
< 算力 6.39 s` → **算力受限、通信被 overlap 完毕**；
`T_step = 6.39 + 0.248 = 6.64 s`。深一层：通信离算力不到 10%——
这是人为按 profile 调到「刀锋上均衡」的痕迹，后面 trace 给了实锤。

## 七、光速 6.64 s 对实测：3 倍差在哪

DeepSeek 官方：14.8T token 用了 2.664M H800 GPU·小时 →
**ρ_DS = 1.54K token/s/GPU**，光速 ρ_sol = 30,720/6.64 =
**4.63K token/s/GPU**，fsol = **3.00×**。用 DeepSeek 官方 64 卡
trace（EP64、4 层 MoE 稳态 chunk）逐 kernel 对账：

| 差距来源 | 量级（官方 trace 口径） |
|---|---|
| GEMM 普遍比光速慢 | **1.4–2.8 倍**（真实尺寸跑不出 microbench 最优；维度小的 up/down projection 最差 2.6–3.0 倍） |
| overlap 不免费 | DeepSeek 的 DeepEP kernel 分 20 个 SM 做通信（132 剩 112），光速时间应再涨 ≈18% |
| 非 matmul 算力 | 前向 9.3 ms 里 2.7 ms、反向 14.9 ms 里 5.3 ms——光速模型里它们是 0 |
| 通信也慢 2 倍出头 | dispatch 前向 2.05×/反向 1.61×；combine 1.46×/1.55×；**notify 握手 0 → 4,932 µs**（方差大、等远端 rank） |
| 剩余 gap | 路由不均衡、pipeline bubble 实测、MTP、batch ramp、straggler、checkpointing |

**最重要的观察**：4 层稳态 chunk 里算力与通信几乎各占一半（每层约
31 ms vs 29 ms）——DeepSeek 的系统就是调在「勉强算力受限」的刀锋
上。光速分析最后给的不是预测，是**理解**：GEMM 慢一倍多是因为
microbench 理想化，通信慢两倍是因为握手与 jitter，overlap 有真实
成本（20 个 SM）——这三个修正项是任何团队做同类分析都该默认带上的。

## 八、方法论收束（面试可以直接复述）

1. **FLOP 与并行无关、通信由并行决定**——所以并行选型可以纸面判决；
2. 算力账四步：6ND → +attention（4S²d）→ +recompute → 按精度拆分；
3. 通信账三问：每 token 每 link 多少字节（含 dtype 与 scale 尾巴）、
   IB/NVLink 分开算、有没有蹭到分层 collective；
4. **microbatch 数在 FSDP 和 PP 下是方向相反的旋钮**；
5. **光速永远预测不准，但逼你把系统讲清楚**：报告里每一项「慢了
   几倍」都必须有机制解释，解释不了的就是你的知识盲区。

## 九、▶ 面试题与追问

**Q1【高】不用实测，怎么判断一个模型该用 FSDP 还是 PP？**
算力账（6ND+attention+recompute，6.39 s）对通信账（EP 5.42 s 已占
84.8%）。FSDP 每 microbatch 加 96.2 GB/1.92 s，activation 装下要的
m=8 时暴露 69%；PP 只多 residual 流量 282 ms+bubble 3.89%。结论：
EP 大模型在 IB 跨节点下先验判 PP。**先算力通信两条光速线，再看并行
的边际通信，谁的线破谁出局**。

**Q2【高】6ND 什么时候失效？**
三种：序列很长（attention 的 S² 项成主导，长序列 midtraining）；结构
大量非 matmul 化（Mamba/SSM 类、稀疏查找类）；主导精度不单一
（必须按精度拆分光速）。本例三条修正全部演示过。

**Q3【中高】EP 的通信量怎么估？路由不均衡怎么进模型？**
每 token：远端节点期望数 × hidden × dtype；dispatch/combine 两向、
前后向两遍、乘 MoE 层数。均衡假设给 MIB=3.5（含去重），真实偏斜
上界是「全部挤到热点 expert 的节点」——所以光速报告只能给下界，
实测 notify 握手 4,932 µs 的方差就是偏斜的直接体现。

**Q4【中高】ZeRO-3 为什么「microbatch 越多越糟」而 PP「越多越好」？**
FSDP 的通信按 microbatch 计次（每块 2 次 AG+1 次 RS），m 涨则通信
线性涨、可用于 overlap 的算力段线性缩；PP 的 bubble 是 `(PP−1)/m`，
m 涨则 bubble 占比反比降。**同一个 m，在两种并行里是方向相反的
旋钮**——这句话本身就是面试答案。

**Q5【中高】光速和实测差 3 倍，说明光速没用吗？**
恰好相反，它的产出是修正清单：GEMM 1.4–2.8×（microbench 理想化）、
overlap 20 SM（不是免费）、非 matmul 2.7/5.3 ms（光速记 0）、握手
与 jitter（notify 4,932 µs 方差）。**光速负责拆出「该解释的一切」，
trace 负责逐项解释**，两者合并才是性能工程闭环。

**Q6【中】为什么 expert 参数 shard 后更少，IB 通信却更多？**
分层 all-gather 的前提是能蹭节点内 NVLink；EP 下不同 NVLink 域的
节点本来就是不同 expert，NVLink 被 all-to-all 占满，参数同步只能
全额走 IB。这是「通信看拓扑不看体积」的标准案例。
