## 一、主线直觉：主战场从「3D 并行与显存」迁移到「RL 后训练全栈」

2024 年训练框架面试的顶流问题是「ZeRO-3 怎么拆显存」「TP/CP/PP 怎么组合」；
2025–2026 年换成了三件事：**后训练怎么做 RL 全栈、训练好的权重怎么快速同步
到推理侧、训推两个 kernel 栈怎么保证数值一致**。转变的直接证据链：

1. **RL 框架 star 反超预训练框架**：verl 23,825★ 超过 Megatron-LM 18,115★
   （gh api 实测，2026-10-12），是「RL 时代框架王座易主」最直观的一图数字；
   verl 2026 年全年路线就是一条「rollout 服务化 → 全异步 → 服务器化硬件抽象」
   的三级跳。
2. **预训练栈双寡头重新分工**：Megatron 转向 HybridModel 模型类换代 +
   MXFP8/NVFP4 低精度 + 全程 CUDA Graph，把自己改写成「训练+推理混合并行
   操作系统」；TorchTitan 以「原生 PyTorch 可组合性 + declarative SPMD +
   GraphTrainer」站稳 Meta 参考栈位置。DeepSpeed star 全场第一（43,217★）但
   前沿叙事已被分走——**生态心智的三家分账**。
3. **权重同步（weight update）成为新的系统级竞争点**：verl v0.9 的
   delta_sharded 引擎把「每 step 全量 NCCL 广播」改成「按 shard byte-diff
   稀疏传输」，官方自测加速 1.9–3.1×；Moonshot 的 checkpoint-engine 宣称
   1T 参数跨数千 GPU 约 20s 完成更新。这类机制 2024 年还是附属功能，
   2026 年已经是独立开源项目。

## 三、主线一：Megatron-LM 0.17–0.19——HybridModel 换代 + 低精度 + 全程 Graph

时间轴：0.17.0（2026-04）→ 0.18（2026 年中）→ 0.19.0（2026-08-19 release），
同步出现日历版本（2025-10 的 25.09 为首个，2026-10-06 的 26.09 rc 为最新）。

### 3.1 HybridModel 是下一代模型类

- 0.19.0 正式公告 **GPTModel deprecation**，发布 GPTModel→HybridModel 迁移
  指南，并支持直接加载 GPTModel checkpoint（issue #5792），迁移成本被刻意
  压低；DeepSeek v4 已迁移至 HybridModel。
- 前置基建是 0.17.0 的 **MIMO heterogeneous parallelism**：多模块（视觉/
  音频/语言）各自独立 nD 并行切分、colocated 与 non-colocated 两种布局、
  multimodule 1F1B 调度——HybridModel 表达的「多模块混合架构」靠它落地。
- 配套换代信号：FSA 化（ModuleSpec→Protocols refactor，spec 层协议化）；
  MFSDP v2 开发中（有 design doc）；Muon/Lion 被收进 DistributedOptimizer
  （0.19，Muon 配置里 scalar 参数走 Lion）。

> 勘误提醒：网上流传的「Megatron hybrid parallelism manager」组件**查无对应物**
> （勘误框 4）。2026 年 Megatron 混合并行管理的真实载体是上述
> 三件套——0.17 的 MIMO heterogeneous parallelism + 开发中的 MFSDP v2 +
> HybridModel。面试听到类似说法应落到这三件套作答。

### 3.2 MoE 支持面大扩容（0.19.0）

- Quantile Balancing router：aux-loss-free 的删偏置式均衡，不用再为负载
  均衡损失和主损失的权重打架。
- fused shared-expert MLP；**支持 packed-sequence（THD）下的 DeepEP/HybridEP
  dispatcher**；NCCL EP token dispatcher 后端；per-sequence AlltoAll 融合。
- 系统性坑写在 release note 里：NCCL 2.30.5/SPCX 栈在高 EP 下 grouped
  all-to-all 可能**静默损坏 payload**——不报错、不出错码、数据悄悄坏。
  绕行方案是设 NCCL_NET_PLUGIN=none NCCL_NET=IB 或换 HybridEP。这是「EP
  规模上去瓶颈在哪」追问从 router 理论一路讲到 IB 插件的最佳素材
  （通信原理见 [通信与网络专题](./通信与网络专题.md)）。

### 3.3 低精度从训练扩展到加载

- 训练侧：MXFP8 训练路径（附 Nemotron 3 Super GB200 参考配置）；NVFP4
  param gather（0.18）。
- 加载侧：**支持 streaming quantized checkpoint loading**（0.19）——FP8/MXFP8/
  blockwise-FP8/NVFP4 逐块反量化加载，不再为全模型分配 BF16 scratch buffer。
  这是 checkpoint schema 混战（第八节议题六）里 Megatron 的答案。

### 3.4 CUDA Graph 走向训练全程

- 0.17 起 Adam optimizer step 入图；EP-overlap 动态计算流上跑 full-iteration
  CUDA Graph（issue #3820）。
- 0.18 full-model CUDA Graph + paged stashing。
- 0.19 CUDA-graph 兼容的细粒度 activation offloading、partial CUDA Graph
  显存优化——动态形状（变长序列、packed THD）与 graph capture 的冲突靠
  「部分入图」化解，推导见第八节议题三。

### 3.5 工程含义与已知代价

Megatron 正把「预训练框架」改写成「训练+推理混合并行 OS」：单点能力（FP8、
graph、dropless MoE）继续领先，但入坑成本上升、团队规模膨胀、GB200 优先
——H100 上已出现 T5 性能回归 10% 的案例（0.18 release note 自述，
26.04 base image 引入）。2026 年 YTD commit 2,305 为全场第一，迭代速度
同样第一。版本制从 core_vX.Y 切到日历版本制，回答「你在用哪个版本」时
要习惯说 26.04 / 26.09 这类编号。

## 四、主线二：verl v0.5→v0.9.1——rollout 服务化 → 全异步 → 硬件插件化

verl 这一年半的 release notes 可以串成一条清晰的三级跳：先把 rollout 从
trainer 进程里拆出去（服务化），再把训练与 rollout 彻底异步化（V1 统一
trainer + staleness 语义），最后把硬件与平台抽象成插件（服务器化）。逐版本
数字如下（全部取自官方 release notes 原文）。

### 4.1 v0.5.0（2025-07）：AgentLoop 起步

- AgentLoop 抽象 beta：工具调用与多轮 rollout 的统一入口。
- one-step-off-policy recipe：trainer/rollout 分离、staleness=1，小规模
  实验吞吐 +20–40%（官方口径，限定小规模）。
- 远端生成式 RM 原型——奖励模型也开始服务化。

### 4.2 v0.6.0（2025-10）：rollout 全量 server 化

- model engine 即 service 的原型（FSDP+Ulysses / Megatron core）。
- **rollout 全量切 native server mode**：SGLang 进程与 trainer 解耦、vLLM
  server 化；rollout 支持 DP+EP。
- 算法加入 GSPO、token-level / sequence-level TIS（重要性采样校正，专治
  rollout 与 training 两个 kernel 栈的分布不一致——训推一致性问题的
  第一代答案）。

### 4.3 v0.7.0（2026-01）：引擎族扩容 + 奖励服务化

- Megatron-Bridge 集成 + LoRA（官方示例口径：万亿参数 reasoning RL 用
  10% 的 GPU）；Megatron 后端实验性 FP8。
- 奖励服务化：generative / discriminative / rule 三类 reward 混合调用。
- 算法加 CISPO、SAPO；VeOmni 引擎 alpha。

### 4.4 v0.8.0（2026-06）：数据流解耦

- Megatron-FSDP 模式；动态 CP（micro-batch 按需缩 CP 组）。
- 端到端 on-policy distillation（FSDP/Megatron/VeOmni 三后端，含 fused
  top-K KL kernel）。
- sync trainer + **TransferQueue**（控制流/数据流解耦，官方引用的博客口径
  为 128 卡多模态端到端最高 2x，未外部复核，详见文末未核实说明）。
- NVFP4 W4A16 QAT；SGLang PD 分离 rollout。

### 4.5 v0.9.0（2026-08）：增量最大的一次

1. **统一 V1 trainer 默认开启**：sync / colocate_async / separate_async
   三种部署形态收敛到一套实现；staleness 控制策略成形（drop/wait +
   max_off_policy_threshold）。
2. vLLM PD-disaggregated rollout over NIXL/Mooncake——rollout 侧直接
   对接推理引擎 2026 主线的 PD 分离（镜像篇见
   [推理引擎2026新进展](../inference/推理引擎2026新进展.md)）。
3. **rollout 与 RM 推理全确定性**：两次同配置运行 reward 曲线逐位对齐
   ——可复现性工程从口号变成 release feature（训推一致性的第三代答案）。
4. **delta_sharded checkpoint engine**：actor 每 rank 对 pinned CPU 快照
   做 byte-diff → 稀疏传输 changed (position, value) → rollout 侧原地
   patch，全程无 rank 持有整模型快照。**实测加速 2.4x/1.9x/3.1x（7B/32B/72B，
   verl v0.9.0 官方自测，H100 + SGLang，2026-08）**——模型越大差分收益
   越大，权重同步正式从「功能」升级为「系统设计题」。
5. **平台抽象层 + 插件引擎注册表**（verl.plugin.platform）：插件覆盖
   Cambricon/MetaX/Iluvatar/Intel XPU/Enflame，AMD ROCm 与 Ascend NPU
   进入一线支持——「框架」收敛为「RL 操作系统」。
6. agent 栈 uni-agent：官方宣称支持 1,000+ 并发 stateful session，可接
   任意 OpenAI/Anthropic 兼容 harness（宣称口径，见文末未核实说明）。

### 4.6 v0.9.1（2026-09）：收尾打磨

- separate_async 下 trainer 空闲 GPU 可借给 rollout（enable_switch）。
- Liger fused PPO head：**实测 actor 提速 13.5%、峰值显存降 5.6%（verl v0.9.1
  release note，2026-09，4 seed 口径）**。
- deprecated fully_async_policy / one_step_off_policy——历史方案被 V1
  统一 trainer 吸收，这说明异步语义已经收敛完成。
- recipe 整体迁往 verl-project/verl-recipe 子模块（2026-01 起），算法
  （verl-recipe）与引擎（FSDP2/Megatron/VeOmni）与硬件（plugin registry）
  三层解耦至此成形。

> 勘误提醒：「DAPO/BAPO/GiGPO 都被收进 verl 官方 recipe」的说法**只有 DAPO 成立**
> （勘误框 2）。实测 verl-recipe 目录清单有 dapo/（2025-03 自认领，README
> 明示官方），无 bapo/、无 gigpo/——GiGPO 是第三方社区仓库
> langfengQ/verl-agent（2,368★，2025-03 创建，verl README 仅作生态链接
> 提及）；BAPO 截至 2026-10-12 未见官方 recipe。引用时必须拆开表述。
> 新算法目录还有 fapo/flowrl/gvpo/sppo/spin/partial_rollout 等长尾，可
> 一句话带过。

### 4.7 工程含义

verl 的竞争力从「框架」升级为「RL 操作系统」的三层解耦：算法（verl-recipe）、
引擎（FSDP2/Megatron/VeOmni）、硬件（plugin registry）。面试里「weight
sync 为什么成为瓶颈、delta 化怎么做、训推 kernel 数值不一致（logprob
mismatch）如何治」都是 v0.6–v0.9 明说在解的题——答法在第八、九节展开。

## 五、主线三：DeepSpeed 实测不降活，但生态继承权已旁落

「DeepSpeed 凉了吗」是 2026 高频陷阱题，正确答案是分层而不是站队。

- **实测不降活**（gh api，2026-10-12）：commit 615（2024）→ 385（2025）→
  **同比回升至 523（2026YTD，至 10 月，gh api 实测）**；release 保持月级
  （v0.18.6 到 v0.19.7，2026-02→2026-09-16）；star 43,217 全场第一。近期
  主线：ZeRO-3 维护（fp32 buffer、P2P transfer 计划）、**把 AutoEP + AutoTP
  折叠进 ZeRO-3**（2026-10-10 合入）、CPUAdagrad/OPSD 等。
- **但生态心智已被三家分走**：预训练主线归 Megatron-Core + TorchTitan，
  RL 后训练归 verl + prime-rl + slime。
- **真正休眠的是 torchtune**（勘误框 1 的另一半）：同一 Meta 屋檐下，
  2026 全年代码只有 11 个 commit（gh api 实测），最后 release 停在
  v0.6.1（2025-04-07）。「DeepSpeed 后继者」这条线答 FSDP2 / TorchTitan /
  Megatron，不要答 torchtune。

面试最佳表述：**拆显存的 ZeRO 思想已是行业基线**——它被 PyTorch 原生
FSDP2/DTensor 吸收，DeepSpeed 本体退居 Megatron 之外的 ZeRO/offload 维护
线；说「DeepSpeed 死了」属于不实信息，会被实测数字当场打脸。

## 六、主线四：TorchTitan v0.1→v0.3——原生 PyTorch 可组合性 + GraphTrainer

TorchTitan（5,797★，2026 年 commit 1,427，活跃度全场第二）在
v0.3.0（2026-09-03，compat：PyTorch 2.14）从「参考实现」升级为可生产形态：

1. **Declarative SPMD 默认后端**（spmd_types）：状态/激活的声明式分片，
   覆盖 Llama 3 / Qwen3 / DSv3 / GPT-OSS / Flux / Qwen3.5 / Kimi K2.7 /
   Muse Glimmer；有官方 devlog（2026-08-26）。
2. **GraphTrainer / GraphPP**：把 forward+loss+backward 整步 capture 成一
   张图，rank-agnostic 预编译，graph pass 管激活显存与 FSDP/EP 通信
   overlap；GraphPP 切 stage 支持 **DualPipeV**。
3. **MoE 统一 token-dispatcher**：routing / token 搬运 / 专家计算三层
   分离，后端含 Standard / MinimalAsyncEP / DeepEP v2 / HybridEP，可与
   TP/CP/PP/AC/compile 自由组合——与 Megatron 的 dispatcher 子系统殊途
   同归（第八节议题五）。
4. **低精度**：MXFP8、NVFP4、BF16 optimizer states，README 明确可与
   CP/TP/PP all-gather 组合。
5. **TitanRL（实验性）**：async + 多轮 rollout、continuous batching、多
   generator 路由、overlapped weight sync、checkpoint/resume，附 Search-R1
   与 DAPO recipe——Meta 系正式进入 RL 后训练赛道的信号。

README 平行的既成能力（不止 v0.3 新增）：async TP、zero-bubble PP、1M 序列
CP、DCP（含 async checkpointing）、HF↔DCP checkpoint 互转脚本、checkpoint
可被 torchtune 直接加载做微调（这也是答今年题时被切分的主线）。

> 勘误：「TorchTitan AsyncDP」的说法**查无此特性名**（勘误框 3）。已实测
> torchtitan README、docs/fsdp.md 与 docs/composability.md 全文及仓库代码
> 搜索，无名为 AsyncDP/Async-DP 的功能条目。「Async」在 torchtitan 语境里
> 的真实出现位置是 async TP、async DCP checkpointing、TitanRL 的 async
> rollout 三处，正文禁止引用「AsyncDP」。

## 七、主线五：新星谱系——RL 栈百花齐放

- **prime-rl**（Prime Intellect，2,152★，2025-02 创建，2026 commit 1,248）：
  完全异步 RL；FSDP2 训练 + vLLM 推理（FP8、P/D 分离、EP/CP）；与自家
  verifiers 环境库（4,696★，2025-01）生态闭环；README 给出 GLM-5 FP8 +
  llm-d router + Mooncake KV offload 的 SLURM 一键部署样例。官方宣称目标
  在 1,000+ GPU 训 1T+ MoE（宣称口径）。
- **slime**（THUDM，8,632★，2025-06，与 GLM-4.5 同日诞生）：Megatron
  训练 + SGLang rollout 的最小硬连接，自述为 **GLM-4.5→GLM-5.3 全系背后
  RL 框架**（官方 README 口径）；有 PD 分离、Delta Weight Sync（共享存储
  传 changed weight bytes）、外部 rollout 引擎接入文档。知乎系的
  **miles**（radixark，3,089★，2025-10）是从 slime fork 的「企业向」
  复刻，与 slime 协同进化。
- **ART**（OpenPipe，10,792★，2025-03）：GRPO 训多步 agent，绑 Thinking
  Machines 的 Tinker SDK；v0.5.19（2026-08-14）迭代 Lifetime trajectory
  capture 与 topology-portable checkpoint；并包装成 W&B Serverless RL，
  宣称 -40% 成本、+28% 训练速度、2000+ 并发（营销口径）。这是「RL 训练
  即服务」路线。
- **AREAL**（inclusionAI/蚂蚁，5,828★，2025-02）：自我定位「RL Bridge
  for LLM-based Agent」，agent 应用向桥接层，是 verl 之外的另一选项。
- **checkpoint-engine**（Moonshot，1,007★，2025-09；2026 年 commit 仅
  24——稳定件而非热度件）：ParameterServer 与推理引擎同机部署；
  Broadcast（默认，快）/ P2P（经 mooncake-transfer-engine，供新实例动态
  加入）双路径；H2D→广播→reload 三段流水线，ZeroMQ 控制面；被 Kimi-K2
  生产使用（技术报告 arXiv:2507.20534）。官方 README 口径：1T 参数跨
  数千 GPU 约 20s 完成更新；broadcast 实测 GLM-4.5-Air 3.47s /
  Qwen3-235B 6.22s（8×H800 TP8）。

一句话记忆：**各家的生态位一句话锁定——verl 是通用单控 + 引擎插件，slime/miles 是 Megatron+SGLang
硬连接的 GLM 生产验证线，prime-rl 是 async-first + verifiers 环境生态，
ART 绑 Tinker 走 RL 即服务，AREAL 做 agent 桥接，checkpoint-engine 专攻
权重传输这一件事。**

## 八、工程议题六条（面试可深挖）

### 8.1 Weight sync 从「功能」变成「系统设计题」

演进链：全量 NCCL 广播 → bucket/pipeline（verl v0.7 时代的 checkpoint
engine）→ 按 shard byte-diff 稀疏传输（verl v0.9 delta_sharded）→ 推理侧
原地 patch（custom weight loader）。trade-off 三选二：CPU pinned 内存占用、
差分计算开销、传输量；还有与 FP8/MXFP4 权重量化路径的兼容性——verl 特意
按量化 scheme 拆分同步路径。数字锚：**差分实测加速 1.9–3.1×（verl
v0.9.0 官方自测，2026-08）**；checkpoint-engine 宣称 1T 参数约 20s。

### 8.2 rollout 服务化后的训推一致性

痛点：rollout 与 training 两个 kernel 栈的 logprob 逐位差（kernel 顺序、
量化、折 batch 差异）。verl 的三代答案：v0.6 的 TIS（importance sampling
校正，算法侧包容不一致）→ v0.8 的基础设施打磨 → v0.9 的 full determinism
rollout（系统侧消灭不一致，reward 曲线逐位对齐）。深问方向：determinism
要牺牲多少吞吐；flex-attention / PD 分离下为何更难做到逐位一致。

### 8.3 CUDA Graph 在训练侧的边界

Megatron 把 graph 推进到 optimizer step + full iteration（含 EP-overlap
动态流），代价是动态形状与 graph capture 冲突——变长序列、packed THD、
动态 CP 组都会迫使重捕获。0.19 的应对是「graph 兼容的细粒度 activation
offloading」与 partial CUDA Graph：只把形状稳定的部分入图。深问：什么样
的形状变化迫使 graph 重捕获；torch.compile 的 guard 重编译与 CUDA Graph
重捕获的成本结构差异（编译侧见
[ai编译器与torch-compile专题](../ai编译器与torch-compile专题.md)）。

### 8.4 分布式并行组合的方案竞争（表格式问题）

MFSDP（Megatron，v2 开发中）vs FSDP2/DTensor（PyTorch 原生）vs
declarative SPMD（TorchTitan v0.3 默认）：三者都在追求「TP/CP/PP/EP/FSDP
用同一套 DTensor 或 DTensor-like 抽象任意折叠」，差异在覆盖度与侵入性。
记忆法：Megatron 求最大能力面，TorchTitan 求原生可组合与可教学，FSDP2
是行业公共分母——DeepSpeed 让出来的心智正是被这三家接走的。

### 8.5 MoE dispatcher 成独立子系统

Megatron（DeepEP / HybridEP / NCCL EP / per-sequence A2A）与 TorchTitan
（Standard / MinimalAsyncEP / DeepEP v2 / HybridEP）殊途同归：routing、
token 搬运、专家计算三层分离。配套 aux-loss-free 均衡（Megatron Quantile
Balancing）与 SPCX 静默 payload 损坏这类 transport 级 bug，「EP 规模上去
的瓶颈是什么」可以一路从 router 熵讲到 IB 插件——MoE 原理见
[moe架构](../llm基础/moe架构.md)，NCCL 与拓扑见
[通信与网络专题](./通信与网络专题.md)。

### 8.6 Checkpoint schema 兼容混战

四个战场同时开打：Megatron streaming 反量化加载（不再分配全模型 BF16
scratch）；verl checkpoint manager 重写、optimizer state 与 grad bucket 按
精度对齐；torchtitan HF↔DCP 互转 + torchtune 互载；ART topology-portable
checkpoint。问题本质：**训练布局 ≠ 推理布局 ≠ 存储格式**，谁在做
on-the-fly resharding 谁就掌握了切换自由。

## 十、▶ 面试题（标注频率与期望深度）

1. 「verl v0.6→v0.9 这一年最大的架构变化是什么？」【高频】期望三层：
   rollout 服务化（server mode + DP/EP）；统一异步 trainer（staleness 语义
   drop/wait + max_off_policy_threshold）；权重同步 delta 化（能报
   2.4x/1.9x/3.1x 加分）。深度提示：只答「支持了更多模型」不及格；再问
   「为什么异步需要 staleness 语义」要能接 PPO 重要性比值失真。
2. 「Megatron 0.19 为什么敢 deprecate GPTModel？」【高频】期望答到
   HybridModel 定位（多模块混合架构统一表达，前置是 0.17 MIMO
   heterogeneous parallelism）、checkpoint 直载降低迁移成本、
   ModuleSpec→Protocols 的 spec 化重构。深度提示：追问「混合并行怎么
   管」时落到 MIMO + MFSDP v2 + HybridModel 三件套，别编组件名。
3. 「weight sync 为什么成为瓶颈？delta 化怎么做？」【高频】期望从「每
   step 全量 NCCL 广播 O(模型大小)」讲到 byte-diff 稀疏传输 + 原地
   patch，能画出 pinned CPU 快照与 (position, value) 流的图。深度提示：
   FP8 量化路径要按 scheme 拆分是进阶层；checkpoint-engine 的
   Broadcast/P2P 双路径可对照。
4. 「训推数值不一致（logprob mismatch）怎么治？」【高频】期望从 kernel
   顺序/量化/折 batch 三个来源讲起，给出 TIS（算法校正）与 full
   determinism（系统消差）两条路线的 trade-off。深度提示：determinism
   的吞吐代价与 flex-attention/PD 分离的难点是区分度所在。
5. 「DeepSpeed 现在还值得学吗？」【中频】期望分层：ZeRO 思想是通用八股
   必学；本体仍在维护（能报 615→385→523 与月级 release 即加分）；新项目
   起点一般选 FSDP2/Megatron/verl。深度提示：顺手纠正「torchtune 是
   DeepSpeed 后继」的流行误答——torchtune 才是休眠者。
6. 「CUDA Graph 在训练侧能推进到哪？边界是什么？」【中频】期望答
   optimizer step 入图 → full-model → partial graph 的演进，以及动态形状
   （变长、packed THD、动态 CP）迫使重捕获的边界。深度提示：与
   torch.compile guard 重编译对比是进阶层。
7. 「MFSDP / FSDP2 / declarative SPMD 怎么选？」【中频】期望表格化作答：
   三家都在用 DTensor-like 抽象折叠 TP/CP/PP/EP/FSDP，差异在能力面
   （Megatron）与侵入性/可组合性（TorchTitan、FSDP2）。深度提示：给出
   「能力面最大 vs 公共分母」的二元记忆即可通过。
8. 「prime-rl / slime / verl / AREAL 差在哪？」【中频】期望点出：verl =
   通用单控 + 引擎插件；slime/miles = Megatron+SGLang 硬连接、GLM 生产
   验证；prime-rl = async-first + verifiers 环境生态；AREAL = agent 桥接
   层。深度提示：ART 绑 Tinker 的「RL 即服务」可作为第五选项顺带。
9. 「FP8 这条线 2026 有什么新东西？」【中频】期望三段各举一例：训练
   （Megatron MXFP8、verl 后端实验性 FP8）、checkpoint（streaming 反量
   化加载）、rollout（NVFP4 W4A16 QAT）。深度提示：TransformerEngine
   2.18 修 te fused cross-entropy 收敛问题这类工程坑是氛围加分项。
10. 「EP 规模上去瓶颈是什么？」【低频但区分度高】期望从 router 负载
    均衡（aux-loss-free、Quantile Balancing）→ token 搬运（dispatcher
    三层分离）→ transport（NCCL/SPCX 静默 payload 损坏案例）一路讲下
    来。深度提示：能把 SPCX bug 的绕行参数背出来基本封顶。

## 十一、口径与未核实说明

本章正文已按要求标明「官方自测」「官方 README 口径」「宣称」等限定词；
以下各项素材未能完全核实，**只在本节列出，正文未当作事实引用**：

1. prime-rl「1,000+ GPU 训 1T+ MoE」：README 宣称的目标能力（designed
   to），无第三方实测背书。
2. ART / W&B Serverless RL「-40% 成本、+28% 速度、2000+ 并发」：官方营销
   口径，非基准复现。
3. uni-agent「1,000+ 并发 stateful session」：verl v0.9.0 release note
   宣称，未见压测细节。
4. DCP（torch.distributed.checkpoint）与 HF safetensors/TensorStore 的
   后向兼容版本矩阵：未逐项核实；确定的是 torchtitan 提供 HF↔DCP 双向转
   换脚本、checkpoint 可被 torchtune 直载（README 原文）。
5. Megatron 26.09 正式版特性集：截至 2026-10-12 只有 alpha/beta rc
   （body 为空）；0.19.x 特性线只到 core_v0.19.2（TE 2.18 + FP4 in 1F1B
   A2A overlap）。
6. verl「TransferQueue 2x」：v0.8.0 note 引用的博客未外部复核，且限定
   「multimodal 128 卡」场景。
7. slime「GLM-4.5→5.3 背后 RL 框架」：仅 slime README 自述，GLM 官方
   博客未逐一核实。

已核实勘误四条（素材已实测，正文对应位置已注明）：

1. 「DeepSpeed 已明显降活」——**已被实测证伪**：commit 615→385→523 同比回升、
   月级 release 至 v0.19.7；真正休眠的是 torchtune（2026 全年 11 commit、
   最后 release v0.6.1/2025-04-07）。
2. 「DAPO/BAPO/GiGPO 都进了 verl 官方 recipe」——**只有 DAPO 成立**：
   verl-recipe 无 bapo/、无 gigpo/；GiGPO 属第三方 langfengQ/verl-agent，
   BAPO 截至 2026-10-12 未见官方 recipe。

   async DCP checkpointing、TitanRL async rollout。
4. 「Megatron hybrid parallelism manager」——**无对应物**：真实载体是
