# 训练生产排障手册：挂、慢、漏、存的命令级排查

> 分布式训练模块面向 AI Infra / 训练系统岗的生产侧补充篇。先说分工：
> **算法侧的收敛问题不归本篇**——grad norm 先行指标、SDC 坏卡定位、dataloader
> 四件套在[训练框架与稳定性](./训练框架与稳定性.md)第四节，监控告警与恢复
> 三件套在 [loss 稳定性专题](../训练与对齐/loss稳定性与数值精度专题.md)第九节。
> 本篇只写**训练系统侧的硬故障与性能病**：通信挂死、MFU 低、OOM、慢节点、
> 存储与 ckpt 事故、复跑不一致。读完拿到：① 挂/慢/错/漏总纲与工具箱速查；
> ② 七大症状五段式排查树；③ 两个可背诵的排障故事；④ 面试讲法与 20/80 口径。
>
> **口径说明**：命令与环境变量以 PyTorch 2.x / NCCL 2.2x 为准，字段在
> 小版本间有差异；文中故事为构造案例，不对应任何特定公司事件。

## 一、排障总纲：先把事故分成四类

训练事故上手第一件事不是敲命令，而是**归类**——四类事故的排查路径几乎
不相交，归错类浪费一半时间：

| 类 | 典型信号 | 第一入口 | 本篇章节 |
|---|---|---|---|
| 挂（hang） | 所有 rank 无输出、watchdog 超时 | NCCL 日志 + flight recorder | ≈a |
| 慢（slow） | tokens/s/GPU 掉、MFU 低于基线 | `nsys` 时间线分桶 | ≈b、d、g |
| 错（wrong） | loss 异常、grad norm 爆 | 数值分诊，**算法侧找已有文档** | ≈f |
| 漏（OOM） | `OutOfMemoryError`、reserved 打满 | `torch.cuda.memory_summary` | ≈c |

工具箱总表（每个都真实存在，建议背到能默写）：

| 工具 / 环境变量 | 看什么 | 一句话口径 |
|---|---|---|
| `NCCL_DEBUG=INFO` + `NCCL_DEBUG_FILE` | 每 rank 通信日志、拓扑、算法选择 | 挂死与通信回归的第一现场 |
| flight recorder（`TORCH_NCCL_TRACE_BUFFER_SIZE`） | 集合通信事件环形缓冲，定位缺哪个 rank | 2.4+ 超时自动 dump |
| `NCCL_ASYNC_ERROR_HANDLING=1` | 异步错误立即报错而非静默挂死 | 生产必开 |
| watchdog `timeout` / `TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC` | 集合通信与心跳超时 | 默认 10 分钟，心跳约 8 分钟 |
| `nsys profile` | GPU 时间线：kernel、通信、间隙 | MFU 分桶的唯一权威视图 |
| `torch.profiler` | 框架侧算子耗时与调用栈 | 抓单个算子回归用 |
| `py-spy dump --pid` | 主线程 Python 栈 | 不重启进程看卡在哪行 |
| `dcgmi` / dcgm-exporter | 降频、温度、ECC、PCIe 重传 | 慢节点硬件体检 |
| `ibstat` / `ibv_devinfo` / `perfquery` | IB/RoCE 端口状态与丢包计数 | 网络层的「血压计」 |
| `torch.cuda.memory_summary` | allocated / reserved / 碎片三块账 | OOM 分类的起点 |
| `PYTORCH_CUDA_ALLOC_CONF` | 分配器策略（`expandable_segments:True`） | 碎片型 OOM 的一键缓解 |

## 二、七大症状排查树

每个症状统一五段：**观测信号 → 排查命令 → 根因树 → 处置 → 预防**。

### a. 训练挂死（NCCL timeout）

**观测信号**：所有 rank 日志同时停住，若干分钟后 watchdog 抛
`Watchdog caught collective operation timeout`；超时时长来自
`init_process_group(timeout=...)`，默认 600 秒（10 分钟）。

**排查命令**：

1. `NCCL_DEBUG=INFO` + `NCCL_DEBUG_FILE=/path/rank-%h-%p.log` 拉每 rank 日志；
2. flight recorder：预先设 `TORCH_NCCL_TRACE_BUFFER_SIZE=1048576`，2.4 起超时自动
   dump 到 `TORCH_NCCL_DEBUG_INFO_TEMP_FILE` 目录，也可手动调 `_dump_nccl_trace()`；
3. `py-spy dump --pid <trainer pid>` 看主线程栈停在哪个 op。

**现场看什么**：flight recorder 按 `seq_id` 对齐所有 rank 的集合通信事件，找最后
一个「有的 rank 进了、有的没进」的 op——缺人的 rank 序号和缺的通信类型
（`AllReduce` / `AllGather`…）就是破案现场：都等同一 op 是对称慢，只有一部分进了是调用序列错了。

**根因树（四分支）**：

1. **慢节点拖尾**：某 rank 算得慢，其余在集合通信里等——对照症状 d；
2. **网络抖动**：RDMA 丢包、交换机拥塞或光模块 flap，配合 `perfquery`
   看端口 `XmitWait` / 重传计数，故障时刻与丢包尖刺对齐即实锤；
3. **非对称崩溃**：某 rank 先 OOM 或段错误退出，剩余 rank 永远等不到
   它——先查最早那条 rank 日志的异常，它才是真凶，watchdog 只是回音；
4. **代码调用序列不一致**：经典 bug 是 `if` 分支里藏 `all_reduce`，
   只有数据命中条件的 rank 走进集合通信；变体有各 rank 梯度累积边界
   不一致、动态长度分支只对部分 rank 触发 `barrier`。

**处置**：定到 rank 就隔离换机；网络证据齐就换端口并报网络组；
把 `timeout` 从 600s 提到 1800s 只是**止血**（掩盖慢节点），不是治疗。

**预防**：集合通信一律走统一 wrapper，禁止裸通信调用进条件分支；常驻
canary `all_reduce` 探活小 job；flight recorder 自动 dump 接入告警。

### b. MFU 低排查树

**观测信号**：tokens/s/GPU 比基线低、`nvidia-smi dmon` 里 SM 利用率锯齿
或长期在六七成；先看**通信等待占比**这个总开关再细分。

**排查命令**：`nsys profile -t cuda,nvtx,nccl -o trace` 抓 50~100 个 step，
用 NVTX 标出 step 边界；`torch.profiler` 的 chrome trace 补充框架侧栈。

**先看什么**：把时间线分成 kernel 在跑、kernel 间隙（bubble）、被
`ncclDevKernel` 占满三段，占比直接决定进哪个桶。

**根因树（四桶）**：

1. **通信等待桶**：kernel 间隙被 NCCL kernel 填满——TP 的 `all_reduce`
   太频繁（TP 跨节点了）、PP bubble 大（micro batch 数不够）、DP 的
   overlap 没生效（bucket 太大或没开 `overlap_grad_reduce`）；
2. **饿卡桶**：GPU util 呈规则锯齿、step 时间双峰——dataloader 供不上，
   查 `num_workers`、`pin_memory`、prefetch 深度和解码耗时；
3. **算子慢桶**：某 kernel 突然变慢——升级后 `FlashAttention` 回退到
   math 路径、`tf32`/`bf16` 没开、fused kernel 被环境变量关掉；
4. **配置错桶**：micro batch 太小使 launch 开销占比爆炸、full recompute
   白烧三成算力、并行配比放错（TP 跨节点是最常见配置事故）。

**处置**：只砍最大的那桶——修第二桶前先确认第一桶已不占时间线大头。
每桶解法对应[三维并行](./三维并行.md)与[zero 与显存优化](./zero与显存优化.md)。

**预防**：基线 profile 入库，任何镜像 / 框架 / NCCL 升级先跑 canary job
对比 kernel 级时间线再放量；MFU 面板按周巡。

### c. OOM 决策树

**观测信号**：`torch.cuda.OutOfMemoryError`；报错栈里已打印 allocated
与 reserved 两个数，分类从这两个数开始。

**排查命令**：`torch.cuda.memory_summary()` 打三块明细；快照级排查用
`torch.cuda.memory._record_memory_history()` + `_dump_snapshot()` 回放
分配火焰图；碎片场景用 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 对照。

**根因树（四分支）**：

1. **第一分支：allocated 偏高**——activation 账算错：seqlen 超标、该开的
   重计算没开、micro batch 超配；先核对显存拆账；
2. **第二分支：reserved 高而 allocated 偏低**——碎片：长短不一的分配释放
   把段切碎，首选 `expandable_segments:True`，其次统一 bucket 尺寸；
3. **第三分支：优化器状态爆**——ZeRO 该开没开或开错档，optimizer state /
   master 权重没按 DP 分片，每卡全量一份；
4. **第四分支：突发爆显存**——一直好着、某 step 起炸：数据长度画像漂移、
   ckpt 或 eval 时刻额外显存（gather 全量权重、eval batch 超配）。

**处置**：分支一降 micro batch 或开 selective recompute；分支二上
expandable segments；分支三改 ZeRO 档位；分支四修数据分桶或把 gather 挪 CPU。

**预防**：上线前用最长合法样本跑显存压测；reserved/allocated 比值漂移
入监控提前告警。

### d. 慢节点定位（straggler）

**观测信号**：step time 的 p99 明显大于 p50；集合通信等待集中在同一来源
rank；整 job 的 MFU 被一台机器拖低。

**排查命令**：各 rank 打点 iteration time 上报聚合（p50 / p95 / p99）；硬件侧
`nvidia-smi -q -d PERFORMANCE` 看 clocks 与 throttle reasons，`-q -d ECC` 看错误
计数；集群侧 dcgm-exporter 面板；网络侧 `ibstat` 看端口 `Rate` 是否掉档。

**根因树（四分支）**：

1. **热 / 供电降频**：SM clock 被拉到基频以下，throttle reason 给实锤；
2. **纠错降速型慢卡**：ECC 重试或 row remap 后的卡算力悄悄降级，不报错
   只变慢；
3. **网卡半伤**：400G 口掉到 200G/100G 不告警，通信型 job 首先感知，
   `ibstat` 的 `Rate` 字段一眼假；
4. **邻居噪声**：同 ToR 或同存储池的其他 job 抢带宽 / 抢 MDS——跟人
   无关、跟位置有关的慢。

**处置（换位实验法）**：怀疑节点与健康节点互换 slot 后重启 job——
**慢跟人走**就是节点坏，下线送修；**慢跟位置走**就是网络或拓扑问题。

**预防**：job 准入前跑 `dcgmi diag -r 3` 体检；per-rank step time 常态化
监控，p99/p50 比值超阈自动标记候选慢节点。

### e. ckpt 与存储事故

**观测信号**：写 ckpt 的 step 时间尖刺、MFU 周期性骤降；存储侧告警；
更隐蔽的是**续训后 loss 对不上**——能跑，但曲线接缝处台阶。

**排查命令**：`iostat -x 1` 看本地盘 util；对象存储网关日志看限流
（429/503、SlowDown）；并行文件系统看 MDS 负载；ckpt 目录按时间戳
核对各 rank 分片是否同一轮写出。

**根因树（四分支）**：

1. **同步写挡训练**：主线程等落盘，step 被 IO 拉长——该上异步 ckpt
   （先拷 pinned memory 再后台落盘）；
2. **对象存储限流 / 小文件风暴**：每 rank 一个分片、几千路并发写触发
   限流——聚合分片数、加前缀打散、退避重试；
3. **并行文件系统元数据热点**：大量小文件 create/stat 打爆 MDS——
   合并分片、目录分桶；
4. **复跑不一致**：dataloader state 或 RNG state 没存全（样本顺序变了）、
   optimizer state 精度或版本差、resume 代码路径与首训不一致——表现
   为接缝台阶而非崩溃。

**处置**：支一上 async save（DCP / Megatron async）；支二三降并发、
合分片、错峰写；支四补齐 state dict 并做一次「存档—kill—恢复—前一百步
loss 逐位一致」验收。

**预防**：ckpt 写入带宽与耗时入监控；恢复正确性纳入发版回归，别等线上
事故才发现 state 少存一项。

### f. 数值异常的快速分流

loss 异常本身归算法侧文档管，这里只给**五分钟分诊**，决定往哪边送：

1. **先看 grad norm 有没有先行抬头**——有则走 loss 稳定性专题的 spike
   流程；
2. **导出可疑 batch 查数据特征**——乱码、极端长度、标签错位；
3. **逐卡对比各 rank 的 loss 与梯度范数**——单卡离群是坏卡（SDC）信号，
   走训练框架与稳定性第四节的定位套路；
4. 以上都对不上，查 lr 调度 / 配置最近一次变更点。

分诊完把案子移交对应文档，本篇不展开数值侧的修复手段。

### g. MoE 训练慢 / 吞吐不达预期

**观测信号**：MFU 比同规模 dense 基线低一截、step time 整体上涨；
`nsys` 时间线上每个 MoE 层前后的通信窗口明显拉长——归「慢」类，
但桶不在 NCCL 集合通信，在 EP 的 all-to-all。

**排查命令**：

1. `nsys profile -t cuda,nvtx` 并在 MoE 层边界打 NVTX 标记，统计
   dispatch / combine kernel 的 wall time 占比和等它们的 bubble；
2. `torch.profiler` 展开 grouped GEMM 的逐条记录看实际形状——每个
   专家分到的 token 数是否悬殊（负载不均直方图），矩阵是否小到
   打不满 tensor core；
3. 同配置下**开关通信-计算 overlap 各抓一次 trace 做对照**——通信
   占比纹丝不动，说明 overlap 根本没挂上。

**根因树（四分支）**：

1. **专家负载不均**：热门专家分到的 token 数倍于均值，快卡等慢卡——
   看 per-expert token 分布，回查 aux loss 权重、路由 bias 与容量因子；
2. **专家批凑不齐的形状病**：负载抖动把 grouped GEMM 每个专家的矩阵
   切得又小又不齐，算子效率被摊薄——这是形状病不是通信病，别误砍
   通信；
3. **通信 kernel 版本与拓扑不匹配**：DeepEP 默认配置按官方集群调优，
   自家轨距 / QP 数 / SM 预算不对就跑不满——参照带是 **约 43~58 GB/s
   的跨机瓶颈带宽量级**（官方口径，H800 环境，数字见
   [通信与网络专题](./通信与网络专题.md) 第九节）；
4. **通信未做 overlap 的暴露**：dispatch / combine 串行占满时间线——
   batch 级 overlap 或双 batch 交替没生效，也可能是 SM 预算被通信
   kernel 挤过头、GEMM 反而变慢。

**处置**：负载不均调 aux loss 权重 / 容量因子、必要时 token drop 保底
（路由侧的取舍见 [MoE 架构专题](../llm基础/moe架构.md)）；形状病升级
grouped GEMM 实现或调 expert alignment；拓扑不匹配换 kernel 版本并在
自家集群重跑 auto-tune；overlap 失效按第九节的三层（内部 hook / 框架
调度 / TBO）逐层核对。

**预防**：MoE 压测基线（per-expert 分布、通信占比、MFU）入库进 CI，
路由与容量参数变更一律先过 canary job 再放量。

## 三、两个完整排障故事（背诵版）

### 故事一：千卡任务每六小时准时挂死

1. **首日报警**：千卡预训练每约六小时 watchdog timeout，flight recorder 显示某次 `AllGather` 缺了同一台机器的八个 rank。
2. **第一次误判**：换机重跑——六小时后又挂。**跟位置不跟人**，嫌疑从节点转向网络。
3. **对时间轴**：`perfquery` 拉同 ToR 端口计数器，整点附近 `XmitWait` 与重传尖刺同挂死时刻逐次重合。
4. **定根因**：同 ToR 另一租户每六小时日志回填打满上行；拥塞下 PFC 扩散、RDMA 大量
   重传，集合通信实际耗时超过默认 600 秒 watchdog——挂死是**拥塞加超时默认值太小**的合谋。
5. **处置**：短期 `timeout` 提到 1800 秒止血、回填任务限流错峰；长期按 rail-optimized 分平面、隔离租户。
6. **沉淀**：挂死的第一嫌疑永远是「谁在等谁」，flight recorder 先给答案，别重启碰运气。

### 故事二：升级镜像后 MFU 掉十五个百分点

1. **首日观测**：例行升级训练镜像后，同配置 job 的 MFU 从 47 掉到 40，loss 曲线正常——纯性能病，归入「慢」类。
2. **分桶**：`nsys` 时间线对比升级前后，通信等待占比从一成二涨到二成七，kernel 耗时没变——锁定通信桶。
3. **看日志**：`NCCL_DEBUG=INFO` 对比显示新版 NCCL 下 `AllReduce` 的算法与 channel 数选择变了，NVLink SHARP（NVLS）未启用。
4. **定根因**：NCCL 小版本升级后拓扑识别结论变化、`all_reduce` 算法切换，机内段不走 NVLS——慢在算法选择，不慢在硬件。
5. **处置**：显式 `NCCL_ALGO` 锁回旧算法验证 MFU 恢复，随后版本与拓扑参数双 pin；向 NCCL 提 issue 附两份 `INFO` 日志。
6. **沉淀**：任何依赖升级先过 canary job——同数据、同配置、对比 kernel 级时间线，性能回归在灰度里抓，不在生产里抓。

## 四、面试怎么讲

1. **二十 / 八十口径**：大规模训练里 loss 不对约两成是算法问题、八成是
   工程问题（数据、卡、通信、存储）——先亮口径，再展开任何细节。
2. **指标先行**：oncall 第一小时看四个数——grad norm、MFU、step time
   的 p99/p50、通信等待占比；不是先上 `print`。
3. **复现优先**：任何结论先在 canary job 上最小复现（同数据同配置、
   单机能复就不用集群），修好再回生产验证；「根因未复现 = 没修好」。
4. **一句收尾金句**：「我排查挂死的标准动作是先开 flight recorder 看
   哪个 rank 缺了哪次集合通信」——具体到命令名，比方法论可信。

## ▶ 面试题

**第 1 问（高频）：NCCL timeout 怎么排查**？

先分清「对称慢」与「不对称错」——开 `NCCL_DEBUG=INFO` 与 flight recorder，超时自动
dump 后按 `seq_id` 找缺 rank 的那次集合通信：缺人固定在几台机查慢节点与硬件；无规律
且网络计数器有尖刺查 RDMA 丢包与拥塞；调用序列不齐就是 `if` 分支藏 `all_reduce` 的
代码 bug。提 `timeout` 只能止血。

**第 2 问（高频）：MFU 掉了怎么定位**？

`nsys` 抓时间线把时间分三段——kernel、间隙、NCCL 占用，占比定桶：通信桶查 TP 放置
与 DP overlap；锯齿桶查 dataloader；算子桶对比升级前后 kernel 耗时（常见于 FA 回退、
`tf32` 被关）；配置桶查 micro batch 与重计算。只砍最大的桶，砍完再 re-profile。

**第 3 问（高频）：训练 OOM 分几种、分别怎么解**？

用 `torch.cuda.memory_summary` 的两行数分类：allocated 高是 activation 账错
（降 micro batch / selective recompute）；reserved 高 allocated 低是碎片
（`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`）；optimizer 状态爆查 ZeRO
档位；突发 OOM 查数据长度漂移与 ckpt / eval 时刻额外显存。

**第 4 问（中频）：怎么定位慢节点**？

各 rank 上报 iteration time，看 p99 对 p50 的离群 rank；硬件侧查降频与 ECC
（`nvidia-smi -q -d PERFORMANCE` / dcgm），网卡侧 `ibstat` 看 `Rate` 掉档；确认用
换位实验——慢跟人走下线，慢跟位置走查网络。

**第 5 问（中频）：断点续训 loss 对不上什么原因**？

三类：dataloader state 没存全（样本顺序变了）、RNG state 没恢复、optimizer state
精度或版本差。验收标准是存档后 kill 恢复、前一百步 loss 逐位对齐。

**第 6 问（高频）：oncall 第一小时干什么**？

十分钟归类（挂 / 慢 / 错 / 漏），看四个数（grad norm、MFU、step time p99/p50、通信
占比）；挂死拉 flight recorder 定位缺人的 rank，OOM 读 `memory_summary`，数值异常
分诊后移交；封存最近 ckpt 与现场日志，起 canary job 最小复现；恢复按三件套
（跳过坏 batch → 回退好 ckpt → 重启验证），写事故时间线。

## 口径与未核实说明

- **版本口径**：命令与环境变量以 PyTorch 2.x / NCCL 2.2x 为准。flight
  recorder 相关变量（`TORCH_NCCL_TRACE_BUFFER_SIZE`、`TORCH_NCCL_DUMP_ON_TIMEOUT`、
  `TORCH_NCCL_DEBUG_INFO_TEMP_FILE`）在 2.4 起可用，命名与默认值随小版本
  演进，落地前按所用版本官方文档复核；watchdog 默认 `timeout` 600 秒、
  heartbeat 约 480 秒，不同 minor 版本有调整。
- **故事为构造案例**：第三节故事融合公开故障复盘（拥塞导致集合通信超时、
  NCCL 升级引发算法切换）的模式改写，时间线与数字为教学构造，不对应
  任何特定公司或真实事件，面试引用时请声明为「典型案例」。
- **关于 dcgm 指标名**：随 dcgm-exporter 版本变化，文中只点名到工具层
  （`dcgmi` / dcgm-exporter / `nvidia-smi -q`），具体 metric 名以部署
  版本为准；`perfquery` 的计数器字段同理。
- **未展开项**：PFC / ECN 等 RoCE 拥塞控制细节、NVLS 启用条件、对象
  存储各厂商限流策略，均只在需要处点名，深入请走串联阅读。
