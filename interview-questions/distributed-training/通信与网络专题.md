## 一、一句话主线：带宽分层差一个数量级，而且还在拉大

一切并行放置规则、一切拓扑设计、一切通信优化，都可以从**一张带宽金字塔**
推出来：

- **机内**：NVLink 单 GPU 聚合带宽 **900GB/s**（H100，2022）→
  **1.8TB/s**（B200，2024）→ **3TB/s**（Vera Rubin NVL72，CES 2026 发布、
  2H2026 出货）；
- **同代 PCIe**：x16 单向 **63GB/s**（Gen5）→ **126GB/s**（Gen6）→
  **242GB/s**（Gen7 规范）——NVLink 是同代 PCIe 的 **12~14 倍**；
- **跨节点**：单张 400Gb/s NIC = **50GB/s**（Gb÷8=GB），只有单机 NVLink
  的 **1/18**。

结论先于一切细节：**TP 放机内（吃 NVLink）、DP 可跨机（吃 IB/RoCE）、
万卡集群按 rail-optimized 组网把 8 网卡聚成 400GB/s 名义出口**。后面每一节
都是这个不等式的展开。

## 二、硬件速查表：四代 NVLink、两代 NIC、一条换算铁律

### 2.1 NVLink 演进（单 GPU 聚合带宽，双向合计口径）

| 代际 | 代表卡 | 带宽 | 面试口径 |
|---|---|---|---|
| NVLink 1 | P100（2016） | 160GB/s | 历史背景 |
| NVLink 2 | V100（2017） | 300GB/s | 记"300" |
| NVLink 3 | A100（2020） | 600GB/s | 记"600" |
| NVLink 4 | H100/H800（2022） | 900GB/s | 记"900"，8 卡机内 3.6TB/s |
| NVLink 5 | B200/GB200（2024） | 1.8TB/s | NVL72 全架 **130TB/s** |
| NVLink 6 | Vera Rubin NVL72（CES 2026） | 3TB/s | 另一口径 3.6TB/s = 全双工计法 |

最后一行的**口径差**要能讲清：3TB/s 是"每向"或按厂商页口径，3.6TB/s 是把
收发两个方向加起来——被追问时主动说"这取决于按单向还是全双工记账"，直接
加分。

**GB200 NVL72** = 36 颗 Grace CPU + 72 颗 B200 GPU 的液冷整柜， NVLink
Switch System 把 NVLink 域从 8 卡扩到 72 卡，roadmap 上到 576 卡（Rubin
Ultra，2026）。NVIDIA 的对标阵营是 **UALink**（2024.5 成立，
AMD/Broadcom/Cisco/Google/HPE/Intel/Meta/Microsoft 九家，200Gbps/lane、
单 pod 1024 加速器，Rev 2.0 2026.4），NVIDIA 的回应是 **NVLink Fusion**
（2025 Computex，向半定制 ASIC 授权互联 IP）。

### 2.2 PCIe 与网卡：换算铁律 Gb÷8=GB

| 层级 | 带宽 | 备注 |
|---|---|---|
| PCIe Gen4 x16 | 31.5GB/s | A100 时代标配 |
| PCIe Gen5 x16 | 63GB/s | H100/400G NIC 入门线 |
| PCIe Gen6 x16 | 121GB/s | 首批硬件 2025.8 |
| PCIe Gen7 x16 | 242GB/s 单向 / 512GB/s 双向 | 草案→规范（2025） |
| IB HDR 200G | 25GB/s | 上代机房存量 |
| IB NDR 400G | 50GB/s | ConnectX-7，当前主力 |
| IB XDR 800G | 100GB/s | ConnectX-8 SuperNIC、Quantum-X800/Spectrum-X800（2024-2025） |
| Roadmap GDR/LDR | 1.6T / 3.2T | UltraEthernet 同期推进 |

"**8 网卡惯例**"：一台 8 卡训练机配 8 张 NIC，每 GPU 对位一张，
8×400Gb/s = **400GB/s** 名义节点出口。两个隐藏成本必须知道：

- 400G NIC 要 **PCIe Gen5 x16** 才喂得饱；ConnectX-8 800G 需要 Gen6 或
  **Socket Direct** 双 x16 拆分；
- NIC 插在哪个 PCIe root complex 上直接决定通信路径走不走 CPU
  inter-socket——这就是 PXN（第五节）存在的理由。

## 三、集合通信机制：Ring、Tree、分层，以及一张成绩单

### 3.1 Ring AllReduce 的 2Φ 推导（必须能手推）

设每 rank 数据量 m，共 n 个 rank。AllReduce = ReduceScatter + AllGather 两段：

- **ReduceScatter**：分 n−1 步，每步每 rank 收发 m/n，总流量 m(n−1)/n；
- **AllGather**：同理 m(n−1)/n；
- 合计每 rank 流量 **2m(n−1)/n ≈ 2m**——与集群规模几乎无关，这就是 Ring
  带宽高效、能线扩的根本原因。

α-β 时间模型：**t ≈ 2(n−1)α + 2m(n−1)/(nB)。**消息大时第二项主导
（Ring 优）；n 很大时第一项线性恶化（延迟爆炸），这就是 Tree 存在的理由。

### 3.2 Tree 与 Double Binary Tree

普通二分树 Reduce/Broadcast 把延迟压到 **O(2log₂n)，**但单树根节点附近
链路带宽打不满。**Double Binary Tree**（NCCL 2.4 引入，2019）构造两棵
互补树，每 rank 在两棵树里各当一半角色，延迟保持 log 级的同时恢复满
带宽。NCCL 选型逻辑：

- 拓扑探测自动选：**小消息 / 大规模 → tree，大消息 → ring**；
- 还有 CollNetDirect、**NVLS/NVLSTree**（NVLink SHARP，NVSwitch 芯片内规约）；
- 手动覆盖：`NCCL_ALGO`，例如 `NCCL_ALGO=allreduce:^tree` 禁用 tree；
- 截至 2026-09-17 NCCL 最新 release 为 **v2.32.3**。

### 3.3 busbw vs algbw：nccl-tests 成绩单的汇率

被问"实测带宽多少"前，先分清两个口径：

- **algbw = S/t**（算法视角：数据量 ÷ 时间）；
- **busbw = algbw × 2(n−1)/n ≈ 2×algbw**（总线视角：真实流量 ÷ 时间）。

"名义 400GB/s 的集群 nccl-tests 只打出 algbw 23GB/s"不矛盾：
busbw ≈ **46GB/s ≈ 92% 效率**（以单 NIC 50GB/s 对位计），这是相当健康的
成绩。面试里主动做这一步换算，就是老手信号。

### 3.4 分层（"2.5 层"）AllReduce

跨节点不走纯 Ring 的原因：让每 rank 都吃 IB 链路会把机间流量放大 n 倍。
分层做法三段：

1. **机内 ReduceScatter**（走 NVLink）；
2. **机间 AllReduce**（每台机器只出 1 个代表 rank，走 IB）；
3. **机内 AllGather**（走 NVLink）。

机间数据量从 Φ 降到 **Φ/机内并行宽度**，IB 带宽压力直接除 8。这也是
"TP 不出节点、分层通信"两条规则的同一条物理。

### 3.5 PXN、SHARP 与邻居库

- **PXN**（NCCL 2.12+）：消息经非本地网卡送出时，由"离目标 NIC 最近的
  本机 GPU"中转，避免跨 PCIe socket。`NCCL_P2P_PXN_LEVEL` 默认 **2**
  （总是聚合）。注意 `NCCL_NET_SHARED_COMMS` 默认 **1** 会降低包五元组
  熵 → 加重 ECMP hash 不均——这正是 Llama3 / MegaScale 多流调优的
  接口点（第四节）；
- **SHARP/CollNet**：交换芯片内做规约（IB Quantum 系），
  `NCCL_COLLNET_ENABLE` 默认 **0**（冷知识）；NVSwitch 内的等价物叫
  NVLink SHARP（NVLS）；
- 其他集合通信库一句话：**Gloo**（CPU 后端/控制面/fallback）、
  **RCCL**（AMD）、**HCCL**（昇腾）、**oneCCL**（Intel）、**TCCL**
  （腾讯）、**ACCL**（阿里）。

## 四、万卡组网：拓扑怎么选，RoCE 三件套怎么治

### 4.1 四种拓扑一句话定位

- **fat-tree / leaf-spine**：通用云默认，槽点是**超售比**——Llama3 论文
  自曝聚合层 **1:7**（arXiv 2407.21783，2024）；
- **rail-optimized**：每张 GPU 对位一张 NIC，按"导轨"双平面接入，AI
  训练集群默认形态；字节 MegaScale 即 8×200G 多轨道
  （arXiv 2402.15627，2024）；
- **阿里 HPN**（SIGCOMM'24）：2-tier dual-plane、单 Pod **15K GPU**、
  51.2T 交换芯片、**双 ToR 消灭单点**——论文实测单 ToR 故障对训练作业
  的代价是通用云的 **20 倍**，改造后吞吐 **+14.9%、96.3%** 的作业
  拿到最优网络；
- **dragonfly**（Cray Slingshot）：组内全互联 + 组间稀疏，省线缆但
  依赖 adaptive routing，常见于超算（Frontier 等）。

### 4.2 RoCE 三件套：ECMP 极化、incast、PFC

MegaScale 与 HPN 两篇 2024 论文不约而同地把工程重心放在这三件事上：

1. **ECMP hash 极化**：五元组 hash 在低熵（流少而大的集合通信）下失衡，
   少数链路被打爆。Llama3 的对策：E-ECMP 用多头 QP 字段参与 hash +
   **把一次集合通信拆成 16 条流**；
2. **incast**：AllReduce 同步相位天然带来多打一，缓冲区瞬时撑爆；
3. **PFC**：无损以太网的流控，不丢包但引入**队头阻塞与环死锁**。字节
   用 **Swift（RTT 驱动）+ DCQCN（ECN 驱动）混合 CC** 替代纯 PFC。

**RoCE 化是大趋势**：Llama3 24K H100 主力集群就是 **RoCE（Arista 7800）+ 400G** 而不是 IB；腾讯星脉 2.0（2024.7 发布）超 **10 万卡**、自研
交换设备与网卡、TiTa 协议 + TCCL，通信效率 **+60%、**训练效率
**+20%、**故障定位从天级到分钟级；IB 阵营以 Quantum-X800 /
Spectrum-X800（800G，2024-2025）应战。

## 五、故障是常态：训练侧的韧性工程

万卡训练不是"会不会坏"，而是"今天坏几次"。三组论文数字按心脏背诵：

- **Llama3 405B**（最高 24K H100，训练用 16K；arXiv 2407.21783）：54 天
  **466 次中断**（47 计划内 + 419 非预期），非预期中断 **~78%** 归因
  硬件、其中 GPU 占 **58.7%；**折算下来平均约 **每 2.8 小时一次**；
  只有 **3 次**需要人工干预（其余自动化重启 + checkpoint 回滚 + 备节点
  替换），有效训练时间 **>90%。**冷知识：NVLink 故障表现为 CUDA kernel
  内 load/store 挂起且**无错误码**——watchdog 只能告诉你"超时了"，不
  等于根因；
- **OPT-175B**（992×A100，Meta 2022 公开日志）：2 个月 **≥35 次人工重启**、
  更换 **100+ 台主机**；
- **字节 MegaScale**（12,288 GPU、175B）：MFU **55.2%，**为
  Megatron-LM 的 1.34×，数周内自动故障恢复 **100+ 次**。

排查工具链（能报出名字就是加分项）：

- **NCCL flight recorder**（torchex）：内核态环形 buffer 记录集合通信
  元数据栈，watchdog 超时自动 dump；
- Megatron-LM main 自带 **--log-straggler**（README_STRAGGLER.md）：
  按 TP group 比较迭代 RTT，输出 Mn/Mx Rtt/Tmp/Utl，支持 curl 端口
  动态开关；
- **排查分两层**：bootstrap 层 ETIMEDOUT（`NCCL_SOCKET_RETRY_CNT/SLEEP`
  默认 34 次约 60s、`NCCL_SOCKET_IFNAME`）vs 通信期间 hang——前者是
  建连/网络配置问题，后者才轮到 flight recorder 与拓扑排查。
  （完整的 timeout 排查弧见 [训练框架与稳定性](./训练框架与稳定性.md)，
  本文只给定位框架不重复展开。）

**一道现场判读题**（2026-09 landedjobs practice 题标本，非实报口径）：
四个对齐的 rank 输入等待 20/20/140/20 ms、每步计算 180 ms，集合在最后一个
rank 入场后 20 ms 完成——「该不该先动网络」？答：不该。**140 ms 的输入等待
就是唯一短板**：集合完成只比最慢 rank 入场晚 20 ms，说明集合通信本身健康，
先修输入侧（数据加载与预处理分片），网络排查（flight recorder、拓扑）往后
放——与 --log-straggler 的 Mn/Mx Rtt 读数是同一判断的两面。

## 六、推理侧传输：PD 分离的 KV 走什么路

▶ 背景：PD 分离概念本身见 [负载均衡专题](../inference/负载均衡专题.md)，
本节只回答"KV cache 用什么搬"——2025-2026 已收敛到**双轨**：

- **NIXL**（NVIDIA 开源，UCX 底座）：vLLM v1 KV connector
  `v1/nixl/`、SGLang `disaggregation/nixl/` 均已并入 main，NVIDIA
  Dynamo 官方传输层（均 2025-2026 实测）；
- **Mooncake**（Moonshot，GitHub star **6.7k**，2026-10 实测）：Kimi
  生产吞吐 **+75%；**2025-09 接入 SGLang HiCache，2025-12 vLLM 与
  TRT-LLM 双双内置 TransferEngine；同一套传输还用于 P2P 权重热更
  （1T 参数 **53s → 7.2s**，7×）与 2026-08 起的 RL rollout ↔ training
  传输；
- **NCCL/Gloo P2P 已退为 fallback**——vLLM main 已删除 p2p_nccl 目录；
  **DeepEP**（DeepSeek，star **10.2k**）主打低延迟 MoE All-to-All，
  v1.2.1 停在 2025-09，main 分支仍有 PP/CP/Engram 实验原语。

答题框架：训练侧 NCCL 是无可替代的地基；推理侧 P2P 传输已让位给
"RDMA 原语 + 显存直通"的专用栈（NIXL / Mooncake），NCCL 只做控制面与
兜底。

## 七、计算题模板：名义 vs 有效带宽（面试重头戏）

**通用公式**（梯度 AllReduce，分层简化版）：

```text
t_comm = 2Φ × dtype_size / (B_eff × N_NIC)
其中 B_eff = 名义带宽 × busbw 效率（经验 80~90%）
```

**完整代入**（70B、bf16、256 卡、8 NIC × 400Gb/s）：

```text
单份梯度 Φ = 70B × 2B = 140GB
每 rank AllReduce 流量 ≈ 2m(n−1)/n，节点级同理 ≈ 2 × 140GB
节点出口：8 × 50GB/s = 400GB/s 名义，按 85% busbw 效率 → 340GB/s
t_comm = 140 × 2 / 340 ≈ 0.82s

对照 step 时间（MFU 40%、单卡 bf16 800 TFLOPS、effective 6N FLOPs/token）：
tokens/s ≈ 0.4 × 800T × 256 / (6 × 70B) ≈ 186K tokens/s
global batch 2M tokens → step ≈ 10.7s
通信占比 ≈ 0.82 / 10.7 ≈ 7.7% → 可接受；超过 20% 就要考虑 overlap 或加带宽
```

"**为什么必须分层"的对照计算**：若不分层、每 rank 跨机 Ring，机间流量
是 Φ×2 级且全部挤 IB；分层后机间只有每机 1 个代表 rank 的流量，
**机间流量直接 ÷ 机内宽度（8）**——同一组数字，一个是步时间 +80%，
一个是 +10%，这就是分层的全部理由。（TP/DP 通信量推导基准见
[三维并行](./三维并行.md) 的 Ring AllReduce 2Φ 一节，本文不重复。）

## 九、DeepEP 机制拆解：MoE all-to-all 的专用答案

▶ 直觉层（为什么是瓶颈、双内核分治、非对称精度、EPLB）在
[MoE 架构专题](../llm基础/moe架构.md) 第五节，本节补**机制级拆解**——
两类 kernel 怎么分工、官方数字背哪几个、overlap 到底叠在什么上。
Momenta 二面原题「用了 DeepEP、但没学过怎么优化」就栽在这一层
（出处见[面经合集第五帖](../../interview-experiences/小红书社招面经合集-2026h2.md)）。

### 9.1 为什么 all-to-all 是 MoE 的通信大头

dense 模型的通信次数可预算：TP 每层固定几次 AllReduce、DP 每个 step 一轮
梯度同步。MoE 开 EP 后多出一对**结构不对称的原语**——dispatch 把每个
token 按路由结果发给 top-k 个专家所在的卡，combine 把专家输出加权收回；
前向一对、反向再来一对（dispatch 的反向就是 combine）。通信量正比于
token 数 × top-k × hidden × 精度字节数，且专家一散开**跨机 hop 不可免**，
落在只有机内带宽零头的 RDMA 上。所以 MoE 训练的通信窗口不在 NCCL 集合
通信里，而在每个 MoE 层前后的两次 all-to-all 上。

### 9.2 两类 kernel 的官方分工（官方口径，H800 环境）

DeepEP 的回答是**训练与 prefill 用一套、解码用另一套，各追一个指标**：

| 维度 | normal kernels | low-latency kernels |
|---|---|---|
| 场景 | 训练、推理 prefill | 推理 decode |
| 传输路径 | NVLink → RDMA 分级转发（机内先汇合再跨机） | 纯 RDMA 一击直达 |
| 追的指标 | 吞吐（带宽用满） | 延迟（百微秒级） |
| dispatch 与 combine | 两个独立 kernel，`async_finish` + EventOverlap 串依赖 | 同样分离，但收发经 hook 重叠 |
| overlap 挂点 | 事件挂在计算流上等结果 | 返回 recv hook，RDMA 后台跑、不占 SM |
| SM 占用 | 可配置（官方例程设 24 个 SM） | 通信 hook 零 SM，代价是 buffer 大得多 |

官方 README（v1.2.1，H800 机内 NVLink 上限约 160 GB/s、CX7 400Gb/s IB，
FP8 dispatch / BF16 combine，训练侧按 V3 预训练设定 4096 token/batch、
hidden 7168、top-4 组 top-8 专家）给出两组必背数字：

- normal：机内是 **约 153/158 GB/s 的 NVLink 瓶颈带宽量级**（dispatch /
  combine，EP8，官方口径）；跨机 EP32 是 **约 58/57 GB/s 的 RDMA
  瓶颈带宽量级**、EP64 掉到 51/50 上下（官方口径）——贴着 400G 网卡
  名义上限，说明分级转发把跨机段压到了近极限；
- low-latency（128 token/batch 的解码设定）：EP8 时 dispatch **约 77 μs
  起步的单层延迟量级**、combine **约 114 μs 量级**；EP128 时 dispatch
  涨到 192 μs、combine 369 μs（均官方口径，H800 环境）。

经验换算：一层跨机 all-to-all 的解码延迟在**百微秒量级**（上面 EP8–
EP128 那列就是参照带），几十层叠起来若完全不 overlap，decode 的 TPOT
会被通信吃掉大半。

### 9.3 三组必答的设计取舍

1. **非对称精度**：dispatch 支持 FP8 传输（token 先量化再发，scale
   factor 另传），combine 收的是加权求和结果、必须 BF16——传输字节数
   直接减半，9.2 的吞吐数字有一半从这里来；进一步压 NVFP4 在
   hybrid-ep 分支。
2. **算力侧 SM 是成本而非免费**：V2 官方原话是 EP dispatch 与 combine
   需要 GPU SM、不支持零 SM 的 RDMA EP（官方口径）。normal kernel 的
   SM 预算要留够（官方例程 24 个），给大了抢 GEMM、给小了带宽跑不满；
   low-latency 的 hook 路线才把通信真正挪出 SM。
3. **低延迟用显存换**：low-latency 的 buffer 按最坏情况预分配，官方
   建议每 rank 解码 token 容量 `num_max_dispatch_tokens_per_rank < 256`，
   且 QP 数必须等于每 rank 的本地专家数（官方口径）——「低延迟」三个
   字背后就是这组互换。

### 9.4 overlap 叠在什么上：训练侧与推理侧两本账

- **训练侧**：DeepEP 内部只提供 hook 与事件原语，**真正的 overlap
  结构在框架层**——DualPipe / batch 级 overlap 把相邻 micro-batch 的 attention
  计算与本批的 dispatch/combine 交错排布（Megatron v0.14 起有
  EP-A2A overlap，落点见 [Megatron 源码深度拆解](./megatron源码深度拆解.md)）；
  双 batch 交替则是把两个 micro-batch 的通信窗口完全错相。
- **推理侧**：解码用同一思想的**双 batch 重叠（TBO/DBO）**——A 批跑
  MoE GEMM 时 B 批的 all-to-all 在后台走，DeepEP 的 recv hook 就是为
  这个设计的零 SM 挂点（引擎接入与收益见
  [推理压测与容量规划专题](../inference/推理压测与容量规划专题.md)）。
- 一句话记分：**钩子归 kernel，调度归框架**——被问「DeepEP 怎么做
  overlap」，按「内部 hook 与事件 / 框架层 DualPipe 或双 batch /
  推理侧 TBO」三层展开。

### 9.5 Momenta 二面原题的收束答法

- **「EP 里 combine 和 dispatch 的 overlap 方式」**：训练侧答 batch 级
  overlap——dispatch 异步发出后先算当前 micro-batch 不依赖专家结果的
  部分（attention、共享专家），等 GEMM 真要数据再 wait；相邻
  micro-batch 错相，通信藏进计算。解码答 low-latency kernel 的 recv
  hook + TBO：RDMA 传输不占 SM，钩子挂到消费数据的那一刻。追问就补
  一句：dispatch 的反向是 combine，两个方向都要进时序图。
- **「有没有用 profiler 看 DeepEP 前后的通信占比」**：`nsys` 抓时间线，
  统计 dispatch / combine kernel 的 wall time 占比和等它们的 bubble，
  接入前后同一张图对比「占比从多少降到多少」；降完之后剩余的是
  形状问题还是负载不均，根因树在
  [训练生产排障手册](./训练生产排障手册.md) 的 MoE 症状条目。态度上
  **报得出通信占比变化的具体数字才算答完**——只说「接入后变快了」
  就是被点破的那种答法。
