## 一、直觉一句话：多模态请求 = 「prefill 极重、decode 不变」的偏载请求

纯文本时代，一个请求的成本大致随「prompt 长 + 输出长」对称变化。多模态
打破了这个对称性：图像、音频、视频进 LLM 之前先被编码成几百到上万个
token，**全部堆进 prefill 阶段**；而 decode 阶段与文本请求毫无区别——输出
还是那些文本 token，ITL 行为与纯文本同构。

把这个偏载看清，只需要三个数字锚：

- 单图 vision token：从几十（低分辨率档）到 **7290 token**（LLaVA-OneVision
  AnyRes-9 上限，arXiv:2408.03326，2024），再到 **16384 token**（Qwen2.5-VL
  单图上限，HF 模型卡，2025）——同一张图，不同档位 token 数可以差 10 倍以上；
- 视频是乘法：帧数 × 每帧 token。**32 帧 × 196 token = 6272**（LLaVA-OneVision，
  同上），1 小时长视频可到几万 token；
- prefill 的 FLOPs 与序列长度近似线性（attention 部分平方），KV cache 与
  总 token 严格线性——7290 个 vision token 在引擎眼里就是一篇 5–6K 英文词
  的文档被一次性塞进 prefill。

对应地，2024–2026 年工程侧收敛出三条主线，也是本文的骨架：

1. **内容哈希驱动的多级缓存**——把重复图像的编码与 prefill 成本摊掉
   （第四、五节）；
2. **EPD 三段分离**——把 Encode 从 Prefill/Decode 身边挪走，治队头阻塞
   （第六节）；
3. **token 预算治理**——从源头削 prefill，让成本可配、可计价（第七节）。

## 二、图片 token 化成本：三种切图策略

一张图花多少 token，不是模型脾气，是**架构选择**。三种主流策略的成本画像
完全不同，serving 侧的治理抓手也不同。

| 策略 | 代表模型 | token 公式 | 成本画像 | serving 抓手 |
|---|---|---|---|---|
| 连续档（native dynamic resolution） | Qwen2-VL / Qwen2.5-VL / MiMo-VL | ≈ (h/28) × (w/28)，默认 4–16384 | token 随分辨率**连续线性**涨到上限 | min/max_pixels 硬夹，官方平衡档 256–1280 |
| 阶跃 tile（dynamic tiling） | InternVL2.5 | 448×448 tile 整倍数 + 缩略图 | **阶跃跳档**：每多一个 tile 多一次 448² ViT 前传 | tile 数上限治理（max_num 常用 12） |
| 配额制（AnyRes + 分场景定额） | LLaVA-OneVision | 单图 729×(1+9)、多图 12×729、视频 32×196 封顶 | 各场景配额**刻意对齐**，成本可预期 | 配额即预算，治理最省心 |

### 2.1 Qwen 系：连续档，token 可被 serving 参数直接治理

Qwen2-VL / Qwen2.5-VL 不切 tile，把图 resize 到 28 的倍数直接进 ViT，
token ≈ (h/28) × (w/28)（14×14 patch 再经 2×2 merge）。单图默认范围
**4–16384 token**（HF Qwen/Qwen2.5-VL-7B-Instruct 模型卡，2025）——注意这是
Qwen2.5-VL 的口径，不要安给 Qwen2-VL。1024×1024 的方图约 **1296 token**。

Qwen2.5-VL 重训了 native-resolution ViT：window attention + SwiGLU +
RMSNorm（arXiv:2502.13923，2025），动机就是**把视觉编码计算开销本身**
降下来——「视觉编码成本成为一等优化对象」的标志性事件。MiMo-VL-7B 同属
这个家族（部署时直接对齐 Qwen2_5_VLForConditionalGeneration）。

成本画像：token 连续、随分辨率线性到上限，min_pixels / max_pixels 就是
成本阀门——官方给的平衡档是 256–1280 token，产品侧「低清 / 高清档」就是
在这上面定价的。

### 2.2 InternVL 系：阶跃 tile，每档多一次 ViT 前传

InternVL2.5 走 dynamic tiling：把图切成若干 448×448 tile，按最近长宽比选
tile 分布（min/max 默认 1–12），tile 数大于 1 时追加一张 448² 缩略图
（arXiv:2412.05271，2024）。pixel unshuffle 把视觉 token 压到原来的 1/4，
**约 256 token/tile**（按 1024 patch ÷ 4 推导，未见官方直接数字，见文末
说明）；高分辨率档 12 tile + 缩略图约 **3072 token** 量级。

成本画像：token 是**阶跃**的——每多一个 tile 多约 256 token 加一次 448²
ViT 前传，serving 侧做 tile 数上限治理即可。训练侧 tile 预算按场景分：
普通图 6–12 tile、多图/高分辨率 24–36 tile、视频每帧 max_num=1。

### 2.3 LLaVA-OneVision 系：配额制，成本可预期

LLaVA-OneVision 用 AnyRes 切网格，并且**刻意让各场景 token 配额对齐**
（arXiv:2408.03326 App. §D，2024）：

- 单图：SigLIP SO400M 吃 384×384 输入 = **729 token**，AnyResMax-9 上限
  729 × (1+9) ≈ **7290 token**；
- 多图：最多 12 张，各 pad 到 384²，12 × 729 ≈ **8748 token**；
- 视频：每帧 729 token 经 2×2 bilinear 插值压到 **196 token**，采样 32 帧
  共 **6272 token**。

配额制的好处是成本画像最平：请求一来就知道 prefill 量级，调度与计价都
省心——代价是细节上限被配额锁死。

### 2.4 成本三律与 KV 显存账

把三种策略收拢成三条规律，面试可以直接背：

1. **prefill 与总 token 近似线性**（attention 部分平方），所以「图数 ×
   每图 token」几乎线性决定 TTFT——Dynamo 实测聚合架构下 TTFT 随它陡增，
   EPD 分离后保持平坦（Dynamo 博客，2026-09）；
2. **KV cache 与总 token 严格线性**：每 token KV =
   2 × layers × kv_heads × head_dim × bytes。按 Qwen2.5-7B GQA 估算，一张
   高配额图的 KV 约 **0.4 GB 量级**（公式推导值，未按实际 config 实测，见
   文末说明）——7B 级模型单图就要百 MB 到 GB 级的 KV 预算；
3. **decode 与文本无异**：视觉 token 只在 prefill 出现一次，之后和普通
   token 一样躺着等 attend，ITL 不因多模态而特殊。

推论：多模态 serving 的优化战场**几乎全部在 prefill 侧**。这也是后面
缓存、EPD、预算治理三条主线全部指向 prefill 的原因。

## 三、音视频 token：乘法爆炸与帧聚合

音视频的 serving 问题与图像同构——**音频是「每秒多少个 token」，视频是
「图的成本 × 帧数」**，学会的图像治理手段原样复用。

### 3.1 音频：token 率收敛到 12.5–25 token/s

两条路线要分开记：

| 路线 | 代表 | token 率 | 机制一句话 |
|---|---|---|---|
| 理解侧（音频进 LLM） | Qwen2-Audio（arXiv:2407.10759，2024） | **25 token/s**（40ms/token） | Whisper-large-v3 编码 + stride-2 pooling |
| 生成/全双工侧（语音 codec） | GLM-4-Voice（arXiv:2412.02612，2024） | **12.5 Hz**（80ms/token，175bps 单码本） | 单码本低帧率 tokenizer |
| codec + 聚合 | MiMo-Audio-Tokenizer（2025-09） | 原始 **200 RVQ token/s**（25Hz × 8 层 RVQ），进 LLM 前压到 **6.25 Hz** | patch encoder 每 4 个时间步聚成 1 patch；patch decoder 自回归补回 25Hz |

量级直觉：**1 分钟语音 ≈ 1500 token（25Hz）或 750 token（12.5Hz）**。关键
工程洞察是 MiMo 那一行：**LLM 不吃 200/s**——codec 的原始帧率必须在进
LLM 前聚合降频，这是音频侧「token 预算治理」的标准动作。MiMo-Audio 宣称
预训练音频「超过一亿小时」——照引其 README 原文 "over one hundred million
of hours"（2025-09），口径以原文为准。

### 3.2 视频：帧数 × 每帧 token 的乘法

视频 = 抽帧 × 每帧 token，乘法怎么爆看三个实例：

- LLaVA-OneVision：32 帧 × 196 token = **6272 token**（每帧先压到 196 再乘，
  这就是「帧级 token 降维」的示范）；
- InternVL：视频每帧 max_num=1 只取单 tile，再乘帧数；
- Qwen2.5-VL：dynamic FPS 采样 + 每帧按图 token 公式计，宣称支持 1 小时+
  长视频（HF 模型卡）——必然撞上 token 总预算，vLLM 示例视频默认
  total_pixels 为 20480 × 28 × 28（vLLM 多模态输入文档）。

视频降本四连（顺序即优先级）：**帧采样 → 每帧 token 池化/插值 →
total_pixels 预算硬夹 → encoder 后 token pruning**。最后一刀是 2025 年的
新工具：vLLM 的 video token pruning 在 encoder 之后剪（EVS 默认 / VidCom2，
Qwen3-VL），形如 `--video-pruning-rate 0.75` 的剪枝率量级。长视频的位置
编码侧另配 YaRN / M-RoPE，属于
[长上下文推理与 KV 体系](./长上下文推理与kv体系.md)的地盘，本文不展开。

## 四、多模态 KV / prefix cache 的特殊性

### 4.1 机制前提：新的是「前缀的键」，不是 KV 本身

先立住一个最容易答错的点：**视觉编码器输出的是输入 embedding**（进 LLM
第一层的 hidden states），**不是 KV**。KV 仍然是 LLM 各层对视觉 token 段
算出来的，照样进 PagedAttention block，和文本 token 占 block 的方式一模
一样。所以 KV 侧没有任何新数据结构。

真正的新问题是 **prefix cache 的「键」**。纯文本里前缀的键就是 token id
序列的哈希；多模态里图像在文本侧只是 `<image>` 占位 token，**两张不同的
图占位符序列完全相同**——Dynamo 博客的原话大意是：没有图像内容哈希的
话，对 router 来说每张图都只是同一个占位符。所以必须把图像内容 hash（或
业务侧稳定 ID）混进 block 哈希链，否则两张不同图会互相错命中。

**同图不同档的追问**也要能接住：缓存键敏感于 processor 的展开结果——同
一张图换分辨率档、换 tile 数、换 fps，展开后的 token 序列变了，hash 就
不同，命中率直接掉。**档位治理同时是缓存命中率治理**，这个连锁关系是
加分点。

### 4.2 三引擎实源

| 引擎 | 机制 | 层级 |
|---|---|---|
| vLLM（stable 文档） | 媒体按内容哈希；`multi_modal_uuids` 业务侧稳定 ID 跨请求复用，命中后请求甚至可以不传原始媒体（image: None + uuids）；两级缓存：mm processor cache（省解码+预处理+ViT）+ prefix cache（省视觉 token 段 prefill）；视频另有 encoder 后 token pruning 开关 | 传输 + 预处理 + 前缀 |
| SGLang（main 分支源码） | 独立 server 级 `MultimodalCache`（`python/sglang/srt/mem_cache/multimodal_cache.py`）：按 mm item hash 存 vision embedding，LRU 淘汰，先查 combined hash（整组 tuple hash）miss 再回落单项 hash；`tokenizer_manager.py` 接受调用方传入 mm_hashes 并做合法性校验、malformed 输入内部重算兜底；radix/router 侧存在 mm hash 参与前缀调度的路径（具体路径以源码为准，见文末说明） | 预处理/编码 + 前缀 |
| Dynamo | KV-aware router 把媒体内容 hash 与文本一起参与路由（multimodal KV routing）；CPU DRAM embedding cache；`--frontend-decoding` 前端并行解码 | 路由 + 编码 |

一句话口径：**vLLM 偏功能面与预算治理，SGLang 把多模态做进了 cache /
router 体系而无特例，Dynamo 把媒体 hash 用到了路由层**。两家引擎的
roadmap 都在补 EPD。

### 4.3 与纯文本引擎的四点工程差异

1. **多一段预处理流水线**：tokenizer/scheduler 之前插入「媒体 fetch（图/
   音/视频 URL 超时 5s/10s/30s + SSRF 域白名单 `--allowed-media-domains` +
   sandbox 禁重定向）→ 解码（CPU/GPU：opencv / torchcodec / NVDEC）→
   processor 切块 → 占位符扩展为真实 token 数」；
2. **token 数运行时才知道**：动态分辨率下，scheduler 的 token 预算必须按
   processor 展开后的真实长度计，vLLM 用 `limit_mm_per_prompt` 在引擎侧
   兜硬上限；
3. **ViT 与 LLM 共享 GPU 的队头阻塞**：图重请求等 ViT，同 batch 文本请求
   被拖高——混合流量实测文本 TTFT 92.3 → 53.3ms（**降幅 42.2%，**Dynamo 博客，
   2026-09，50:50 混合、OSL 128 的测试环境），这是 EPD 的直接动机；
4. **失败面扩大**：图坏、视频截断需要 frame recovery（vLLM
   `--media-io-kwargs`），多模态网关有纯文本没有的安全与尾延迟面。

## 五、四级缓存省钱地图

「多模态缓存」不是一层，是**四级独立开关、独立命中率口径**的体系，
每一层命中免掉一段不同的上游成本：

| 层级 | 键 | 命中省什么 | 代表实现 |
|---|---|---|---|
| ① 传输层 | 业务 UUID / 媒体内容 hash | **连图都不用传**（命中后 image 可为 None） | vLLM `multi_modal_uuids` |
| ② 预处理层 | 媒体内容 hash | 下载、解码、切块、processor 展开 | vLLM mm processor cache；SGLang MultimodalCache（combined hash 优先、miss 回落单项） |
| ③ 编码层 | 图像 hash | **不重跑 ViT**（embedding 直接取） | Dynamo CPU DRAM embedding cache |
| ④ 前缀层 | 图像 hash 混进 KV block 哈希链 | 视觉 token 段的 prefill 本身 | vLLM prefix cache；SGLang radix（mm hash 参与命中） |

三个运营级要点：

- **四层命中率分开看**：传输层命中高说明客户端幂等做得好；④层命中高
  说明 prompt 模板把图放在了前缀稳定的位置。四层各有各的看板和容量规划。
- **缓存键的脆弱面**：键对 processor 展开结果敏感——客户端重压缩、改尺寸、
  换档位，hash 全变；图在 prompt 中的位置如果被中断段隔开，④层也吃不满。
  对策三件套：**业务 UUID 锚定 + 档位归一化 + 图像固定在 prompt 最前**。
- **为什么线上图重复率高、缓存收益仍有限**：重复的是「语义上的同图」，
  不是「字节/展开结果完全相同的图」——缓存只认后者。把这条想清楚，就
  知道该把命中率治理往客户端与网关推，而不是只调引擎。

## 六、EPD 分离：适用边界与全量数字

### 6.1 三种部署形态

| 形态 | 拓扑 | 适用 |
|---|---|---|
| 聚合（默认） | ViT 与 LLM 同进程同 GPU | 图少、输出长、大模型的场景；基线 |
| colocated | 同一张 GPU 上拆出 encoder worker 与 LLM worker，同构集群 | **同构集群首选**：不用专设 encoder 层 |
| 异构 disaggregated | 低端卡跑 encoder + NIXL 传 embedding（20Gbps 网络够用） | 图极多、需要独立扩 encoder 容量时 |

能拆的物理基础：ViT 产 embedding 不产 KV，**天然无状态**，embedding 走
NIXL/CPU DRAM cache 传输，不需要为 ViT 保留任何 KV。ViT 参数量占整机 **1.7%–7.2%** 不等（Dynamo 测试环境，随 LLM 从 4B 到 27B 递减），单塞一张卡
纯浪费算力——这就是为什么同构集群里 colocated 稳赢专设 encoder 层。

### 6.2 Dynamo 全量实测（2026-09 博客，测试环境限定）

这一节数字最值钱，全部来自同上 Dynamo 博客 Fig.4–11（Qwen3.5 122B NVFP4
\@GB200 等均为 Dynamo 测试环境型号），按主题分四组：

**TTFT 分解**：

- 多模态请求约 **43%** 的 TTFT 花在 ViT 开始之前（下载 + 解码 + 预处理）——
  EPD 不优化这一段，这段的杠杆在第七节（c）。

**EPD vs 聚合（10 图/请求、256 token/图、OSL 1024）**：

- TTFT：colocated **降 58%，**异构 **降 50%；**同 SLO goodput 提升 **70%；**
- 全网格热图 TTFT 改善 **25–93%，**最重的 cell 达 **92–93%** 一档（即「最高降
  93%」的出处）；
- 但 E2E 收益随 OSL 增大从 **+20.3%** 缩到 **+5.2%；**（异构）colocated 在
  OSL 2048 轻图档出现 -**2.5%** 的反噬——长输出摊薄 prefill 收益、分离的
  传输开销变成净成本。

**EPD 收益随模型形态变化**：

- goodput：4B **2.62×** / 9B **1.50×** / 27B colocated **0.65×**——ViT 参数
  占比 7.2% → 4.7% → 1.7%，**模型越大 EPD 收益越小，27B 已跌破盈亏平衡**；
- 只量化 LLM（BF16 → NVFP4）后 EPD goodput 从 **1.78×** 升到 **2.64×**——
  LLM 越快 ViT 占比越高，EPD 越赚，MoE 同理。

**混合流量**（50:50 文图混合、OSL 128）：

- 文本 TTFT 92.3 → 53.3ms（**降幅 42.2%）**：EPD 消除了文本请求被 ViT 队头阻塞；
- 图像 TTFT 289.9 → 200.6ms（**降幅 30.8%）**。

### 6.3 收益公式一句话

**图多（每请求视觉 token 量大）、输出短（OSL 小）、模型小/量化/MoE（LLM
侧快）——三个条件占得越多越赚；大 dense + 长 decode 会反噬。** 与 PD 分离
的「prefill 重就拆」同一条物理，EPD 只是把「E」也拆了出来。被问边界时
先把这条说出来，再上数字，段位就出来了。

## 七、工程议题五条

(a) **vision prefill 重的负载均衡**：聚合架构里图重请求既拖自己 TTFT 也
阻塞同 batch 文本。两条对策——路由层 media-aware routing（按 media hash
一致性路由到已缓存的 worker；Dynamo multimodal KV routing、SGLang radix
router），或者干脆按第六节拆 encoder。

(b) **token 预算治理是 cost SLO 一等公民**：min/max_pixels、tile 上限、
视频 total_pixels + fps 采样 + `--video-pruning-rate`、音频帧聚合。面试要
能把「**产品分辨率需求 → token 预算 → prefill 成本 → SLO**」一条链串出来
——同一张图不同档位 token 差 10 倍以上，档位不定，SLO 无从谈起。

(c) **流水线前段也可以是瓶颈**：43% TTFT 花在 ViT 之前，EPD 管不到这段。
杠杆是**把解码挪出 worker**：Dynamo `--frontend-decoding` 让 encoder 请求
均值延迟 -26%（281.3 → 207.0ms）、P99 -23%（Dynamo 测试环境）；vLLM 侧
可以用 GPU 解码后端（PyNvVideoCodec / DeepStream，走 NVDEC），但要为前端
解码单独预留 VRAM 预算。网络面：媒体拉取超时 5s/10s/30s 分媒体类型、
SSRF 域白名单、sandbox 禁重定向——多模态网关特有的安全与尾延迟面。

(d) **变长视觉 token 对 scheduler 的影响**：token 数运行时才知道，
admission control 与 token 预算必须基于展开后真实长度；图密请求混入
batch 会急剧改变 prefill 构成，chunked prefill 的 chunk 大小要考虑单请求
视觉 token 突增；引擎侧 limit_mm_per_prompt 兜硬上限。

(e) **SLO 与计费口径**（经验法则，非官方标准）：文本时代「input token 数」
不再是诚实的成本单位。产品解法是 **API 层固定档位**（低清/高清）、网关
按档位计价与限流、引擎兜上限——把不可预测的 token 量变成可定价的档位，
这是多模态计费的通行做法。

## 八、▶ 面试题十条（按频率排序）

| # | 频率 | 追问 | 答题要点 |
|---|---|---|---|
| 1 | ★ | 一张图进来到底要花多少 token？成本怎么算？ | 按三种策略给公式：Qwen 系 ≈(h/28)×(w/28)、4–16384 连续可调；InternVL 448² tile 阶跃、约 256/tile + 缩略图；LLaVA-OV 配额制 729 → 7290 封顶。成本三律：prefill 近似线性（attention 平方项）、KV 严格线性（单图百 MB 级）、TTFT 随图数×每图 token 线性陡增（Dynamo 实测）；decode 与文本无异。 |
| 2 | ★ | 多模态怎么做 prefix cache？两张不同的图占位符一样，会不会错命中？ | 会错命中——占位符序列相同，必须把图像内容 hash（或业务 UUID）混进 KV block 哈希链。四层命中口径：传输 UUID → processor cache → embedding cache → 前缀层。追问同图不同档：展开结果变则 hash 变、命中率掉，所以档位治理 = 缓存命中率治理。 |
| 3 | ★ | 视觉编码器和 LLM 要不要拆开部署（EPD）？ | 能拆：ViT 产 embedding 不产 KV、天然无状态，NIXL 传 embedding 即可。但收益有条件：图多、输出短、模型小/量化/MoE 时 TTFT 最高 -93%、4B goodput 2.62×；大 dense + 长输出反噬（27B colocated 0.65×、E2E 收益随 OSL 从 +20.3% 缩到 +5.2%）。同构集群 colocated 优于专设 encoder 层（ViT 仅占整机 1.7–7.2% 参数）。 |
| 4 | ★ | 视频为什么贵？怎么降？ | 帧数 × 每帧 token 乘法：LLaVA-OV 32×196=6272 起步，长视频几万 token，prefill 爆炸。降本四连：帧采样 → 每帧 token 池化/插值 → total_pixels 预算 → encoder 后 pruning（0.75 剪枝率量级，EVS/VidCom2）；长视频另叠 YaRN/M-RoPE。 |
| 5 | ★ | 音频 token 率多少？一分钟语音占多少 token？ | 两条路线：理解侧 25 token/s（Qwen2-Audio，40ms/token）；codec 侧 12.5Hz（GLM-4-Voice）/ 原始 200 RVQ token/s（MiMo-Audio），但 LLM 不吃 200/s，patch encoder 聚 4 帧降 6.25Hz 再进 LLM。一分钟 ≈ 750–1500 LLM token。 |
| 6 | ☆ | 图像 token 和文本 token 在 KV cache 里有区别吗？ | 没有。ViT 产输入 embedding 不是 KV；视觉 token 的 KV 由 LLM 各层照常生成、一样占 PagedAttention block。特殊性只在两点：前缀的「键」怎么定义（图像 hash 混链）、命中收益极大（省掉整段视觉 prefill）。 |
| 7 | ☆ | 多模态请求怎么拖垮混合流量 SLO？ | 队头阻塞：batch 里有图要等 ViT，文本 TTFT 被拖高（实测混合流量文本 92.3→53.3ms 的改善幅度 -42.2% 就是阻塞的量级）；图重请求还把 batch token 构成推向 prefill 主导，ITL SLO 受压。对策：media-aware routing、EPD 隔离、limit_mm_per_prompt、分辨率档位。 |
| 8 | ☆ | 动态分辨率是把双刃剑，serving 侧怎么治理？ | 训练侧要细节就加 tile/提分辨率；serving 侧 token 预算 = 成本与时延，必须可配（min/max_pixels、tile 上限、total_pixels）。同图不同档 token 差 10 倍以上，不治理 SLO 必失稳；档位要写进产品与计费口径，同时影响缓存命中率。 |
| 9 | ○ | 线上图重复率很高，为什么缓存收益仍有限？ | 缓存键敏感于 processor 展开结果：重压缩、改尺寸、换档、换 fps 都会换 hash；图在 prompt 中被中断段隔开也吃不满前缀层。对策：业务 UUID 锚定 + 档位归一化 + 图像固定 prompt 最前；把命中率治理推到客户端与网关。 |
| 10 | ○ | vLLM 和 SGLang 的多模态支持差在哪？ | vLLM 偏功能面与预算治理：processor cache + multi_modal_uuids + 视频 pruning + 多解码后端 + limit_mm_per_prompt。SGLang 把多模态做进 cache/router 体系无特例：MultimodalCache 的 combined hash 优先回落单项、radix router 原生接受 mm_hashes。两家 roadmap 都在补 EPD；Dynamo 把媒体 hash 用到了路由层。 |

每题展开素材对照上文对应章节；必背数字锚：**7290 / 16384 / 6272 /
25 token/s / 12.5Hz / 43% / -93% / 2.62× / -42.2% / 1.7%–7.2%。**

## 口径与未核实项说明

1. InternVL「约 256 token/tile」为按公开规格推导（1024 patch ÷ 4 pixel
   unshuffle），未见官方直引数字；高分辨率档「12 tile ≈ 3072 token」同为
   推导量级。
2. Qwen2.5-7B 单图 KV「约 0.4 GB 量级」为公式推导值
   （2 × layers × kv_heads × head_dim × bytes × n_tokens），未按实际 config
   实测。
3. 4–16384 token 是 Qwen2.5-VL 的口径，勿外推给 Qwen2-VL。
4. MiMo-VL-7B（arXiv:2506.03569，2025-06，35/40 任务胜 Qwen2.5-VL-7B）与
   GLM-4.1V-9B-Thinking（arXiv:2507.01006，v6 2026-01 更新，9B 模型 29 项
   榜胜 Qwen2.5-VL-72B）均为榜单口径；**两者官方均未发布 serving 吞吐
   benchmark**。
5. MiMo-Audio「超过一亿小时」照引其 README 原文 "over one hundred million
   of hours"（2025-09），未独立核实。
6. SGLang 侧「mm hash 混入 block 哈希链」为基于源码的合成推断；可确认的是
   代码中存在 mm_hashes 参与 radix 调度的路径，具体路径以源码为准。
7. 第七节（e）计费口径为经验法则，非任何官方标准。
8. Dynamo 博客全部实测数字（含 Qwen3.5 122B、4B/9B/27B 分档、\@GB200）均为
   「Dynamo 测试环境」口径，复现前注意硬件与配置差。
9. vLLM / SGLang 特性描述以 stable 文档与 main 分支为准，特性名不写死版本号。
