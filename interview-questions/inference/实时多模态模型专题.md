## 一、主线直觉：竞争从「延迟数字」下沉到三个硬问题

E2E speech-to-speech 这两年的演进，表面上是一串越来越小的毫秒数，
实际上竞争已经下沉到三件更硬的事：**离散化 codec、双流化架构、
服务化会话态**。一句话版主线：

- 全双工的首包延迟下限由 **codec 帧率**决定，不是由模型大小决定——
  帧是模型能看到声音的最小时间单位，拆延迟先拆帧率再谈优化；
- **每秒 token 密度**是语音比文本难 serving 一个数量级的根源：英语
  文本约三至四个 token/s，而 12.5Hz×8 码本的语音每秒约一百个
  AR 步，RTF<1 成了硬约束而不是优化目标；
- 会话即连接：full-duplex 服务是「长连接 + session 作用域状态 +
  每路独占流」的资源模型，与无状态 HTTP 按 token 摊销的成本曲线
  完全不同，主流推理引擎到 2026-10 仍未原生接住 omni 模型。

## 二、Audio tokenization：RVQ 谱系与速率账

### 2.1 SoundStream：RVQ 开山（2021）

**RVQ（Residual VQ）**是离散音频 codec 的底座技术：第一级量化器
压主干残差，后续每级只压残差中的残差，码率 = 级数 × 每级码本大小
× 帧率。开山之作 **SoundStream（Google，arXiv:2107.03312，2021-07）**确立的
配方是「全卷积 SeaNet 自编码器 + RVQ + 对抗损失」，三个工程结论
至今仍是面试锚点：

1. **量化器 dropout 让一个模型跑可变码率**：训练时随机丢量化级，
   一个权重集覆盖 **三点五至十八 kbps**（论文口径 3–18kbps）；
2. 主观评测 **三 kbps 胜过 Opus@12kbps**、逼近 EVS@9.6kbps
   （论文口径），证明神经 codec 对波形 codec 的跨代优势；
3. 因果卷积天然可流式、手机 CPU 即可实时——「可流式」从第一天起
   就是 codec 选型的一等公民。

### 2.2 EnCodec：谱判别器与熵编码（2022）

**EnCodec（Meta，arXiv:2210.13438，2022-10）**是 SoundStream 的
产品化升级版，两件事值得记：补上**多尺度谱判别器与 loss
balancer**（音质更稳）；以及用**轻量 Transformer 对量化后的
token 流再做熵编码**——码流本身存在统计冗余，熵编码再压约
**四成**（论文口径）。这给了后续 E2E 模型一个启发：token 流
的「编码冗余」和「语义结构」是可分离的。

### 2.3 Mimi：RVQ 的实时化改造与 split-RVQ（2024）

**Mimi（Kyutai，Moshi 论文 §3.3，arXiv:2410.00037，2024）**是被
拆成「为实时全双工而生」的版本，三组数字必须脱口而出：

- 采样率 **二十四 kHz** 输入 → latent 帧率 **十二点五赫兹**，下
  采样 striding 为 4、5、6、8 再乘二（latent 维度 512，投影到
  256 做 RVQ），帧长即 **八十毫秒**；
- **Q=8 个码本、各 2048 项**，合计码率约 **一点一 kbps**；
- **split-RVQ 结构**：语义信息通过 **WavLM 蒸馏**进一个独立的
  普通 VQ，与七级声学 RVQ 并行——即「一个语义 VQ + 七个声学
  RVQ」并行工作，训练用对抗损失加 feature matching。

为什么要 split-RVQ 这个看起来别扭的结构？Mimi 论文的消融实测：
把语义蒸馏目标直接加到 RVQ 第一层会与**重建质量冲突、伤音质**，
独立 VQ 是关键补救。主观质量上，Mimi 超过 50Hz/4kbps 的
SpeechTokenizer 与 50Hz/1.3kbps 的 SemantiCodec（论文对比口径）
——记住这个对比：**被超过的 baseline 才是五十赫兹，Mimi 自己
是十二点五赫兹**（勘误考点，见第十节）。

### 2.4 速率账：每秒约百个 AR 步（面试高频）

为什么 2024–2025 年两个独立团队收敛到同一流率？答案是
**AR 步数**这个硬约束，账分三笔：

| codec | 帧率 | 码本 | 码率 | 每秒语音 token |
|---|---|---|---|---|
| GLM-4-Voice tokenizer（arXiv:2412.02612，2024-12） | 12.5Hz | 单码本（约 2 的 14 次方，推导口径） | 175bps | 约 12.5 个 |
| Mimi（arxiv:2410.00037，2024） | 12.5Hz | Q=8×2048（论文口径） | 1.1kbps | 约 100 个 |
| 对照：英语文本（Moshi 论文 §3.4，2024） | — | — | — | 3–4 个 |

读法：GLM-4-Voice 的 **一百七十五 bps**（12.5Hz 乘每帧 14 bit）
信息量刚够音素加少量韵律，韵律的缺口靠 LLM 侧先验补齐；Mimi 的
**一点一 kbps** 用八码本换音质，代价是每秒约一百个 AR 步，这才
逼出后面 Moshi 的 Depth Transformer 分解。离散 audio token 对
推理引擎的三个直接后果务必记住：

1. **每秒 AR 步数被帧率钉死**（帧率乘码本数），RTF<1 是硬约束；
2. **多码本要么分层要么多轨**：RQ-Transformer 式分层建模，或
   多序列并行输出，引擎必须支持多序列混合 KV；
3. **codec 编解码是常驻流式状态**：因果卷积的内部状态与码本嵌
   入随连接存续，不能像文本 tokenizer 那样无状态调用——这一点
   是第六节会话态容量公式的根因。

## 三、E2E 架构谱系：三条已验证的开源路线

到 2026-10，经过完整论文加代码验证的 E2E 语音架构只有三条路线，
外加两个只给数字不给架构的闭源黑盒。

### 3.1 Moshi（Kyutai，2024-09）：双流并行 + 时间-深度分解

**Moshi（arXiv:2410.00037）**是第一个可实时全双工的开源
speech-to-speech 模型，三个设计关键词是**双流、分解、独白**。

**其一，Temporal + Depth 分解**。从 7B 文本 LLM（Helium，用
二点一万亿英文 token 预训练）出发：沿时间维建模跨步依赖的是
**Temporal Transformer 主干**；每个八十毫秒时间步内部建模八
个码本之间依赖的是一个独立小模型 **Depth Transformer**
（RQ-Transformer 式分解）。口径要精确：**七 B 只指 Temporal
Transformer 本体**——Depth 是独立的小模型，两者合计参数大于
七 B（勘误考点）。没有这一层分解，每秒一百个 AR 步根本流不
起来。

**其二，双流并行**。模型的输出语音与用户输入语音是两条独立的
token 流，没有显式的 turn 概念：重叠、插话、抢话、打断
（barge-in）**全部是分布内事件**，由训练分布直接建模（训练侧
用 Fisher 电话
数据做双声道分离）。这是 Moshi 与一切「chunk 流式」模型的
本质分界。

**其三，Inner Monologue（内心独白）**。生成时先预测与音频帧
**时间对齐的文本 token**（用 Whisper 词级时间戳对齐到 12.5Hz），
再预测音频 token，显著提升生成语句的语言质量；副产品是同一个
模型免费导出流式 ASR 与流式 TTS——流式 TTS（两秒 lookahead）
WER **百分之四点七对五点九**战胜 Vall-E，流式 ASR WER
**百分之五点七对 FastConformer 三点六**（论文口径）。

**质量-延迟旋钮**：声学 token 用「延迟 pattern」（每层码本延迟
k 步）调节，论文 §5 给三档实测：延迟零步等于八十毫秒可用；加一
步等于一百六十毫秒显著提质；加两步等于二百四十毫秒只剩边际提
升。**理论延迟一百六十毫秒、L4 实测二百毫秒**（官方 README
口径）。生态衍生：Hibiki（同传）、Kyutai TTS/STT
（Delayed Streams Modeling）。

### 3.2 GLM-4-Voice（THUDM，2024-12）：单流交错的极简路线

**GLM-4-Voice（arXiv:2412.02612）**用 **Whisper encoder 加 VQ
bottleneck** 得到 **一百七十五 bps、十二点五赫兹的单码本**
tokenizer（bit 账：12.5 乘和每帧 14 bit，约 2 的 14 次方码本，
推导口径），然后在 **GLM-4-9B** 底座上做语音-文本交错数据的
续训，扩到约 **一万亿 token**（论文口径）。一条序列交替输出
文本与语音 token，实现最简、部署心智成本最低；但本质是**轮次
制流式**——它能流式输出，不是全双工（勘误考点）。

### 3.3 Qwen Thinker-Talker（2025-03 / 2025-09）：分层复用隐藏状态

Qwen 系两代的共同骨架：完整 LLM 担当 **Thinker 主干**，负责
文本与高层表示；专门的 **Talker 侧** 是 dual-track AR
Transformer（受 Mini-Omni 启发），直接消费 Thinker 的隐藏表
示与历史上下文输出语音 token，两端到端联合训练。关键事实四连：

- **TMRoPE（时间对齐 RoPE）**：把 RoPE 拆成时间、高、宽三维，
  音频一个 temporal ID 等于 **四十毫秒**；带音视频按真实时间
  切 **两秒块**、块内先视觉后音频交错，保证唇音对齐
  （arXiv:2503.20215，2025-03）；
- **Qwen2.5-Omni 的 code→wav 用滑窗 DiT**：flow-matching DiT
  加改造 BigVGAN，感受野四 block——**回看二 block 加前看一
  block**，前看宽度直接进首包延迟（同上口径）；
- **Qwen3-Omni 换成因果 ConvNet**：多码本自回归加轻量**因果
  卷积网络**替代 block-wise diffusion，从第一个 codec 帧起即可
  播放，标注**冷启动理论首包二百三十四毫秒**（arXiv:2509.17765
  摘要，2025-09，官方明确标注 theoretical）；
- 官方基准口径：三十六项榜单拿下三十二个开源 SOTA、二十二个
  总 SOTA，覆盖文本一百一十九、语音理解十九、语音生成十种语
  言（arXiv:2509.17765 摘要，官方口径）。

### 3.4 闭源黑盒：能引的只有协议与响应数字

**GPT-4o / Realtime**：官方可引数字只有响应延迟——**最小二百
三十二毫秒、平均三百二十毫秒**（OpenAI 官方博客 Hello GPT-4o，
2024-05），对照旧 Voice Mode cascade pipeline 平均 **二点八秒
（GPT-3.5）与五点四秒（GPT-4）**（同上口径）；Realtime API 文档
确认协议形态：浏览器侧 WebRTC、服务端 WebSocket、ephemeral key
建 session、session 内维护会话状态与工具调用。**官方对 codec、
帧率、架构均未披露**——不得编造其内部 token 化方案（勘误考点）。

**Gemini Live**：官方文档确认「low-latency real-time voice and
vision」，协议为 **stateful WSS**，输入 sixteen 位 PCM 十六 kHz、
输出 PCM 二十四 kHz、图像每秒不超过一帧，特性含 proactive
audio 与 affective dialog（Google 官方文档，2026-10 抓取口径）
——**官方没有任何毫秒级延迟数字**，网传数一律不入正文。

## 四、延迟预算：确定性结构账先于实测优化

### 4.1 结构账四项拆法

E2E 模型的首包延迟可拆成四个**确定性分量**，先把结构账摆平
再谈实测优化：

1. **帧粒度**：Mimi 八十毫秒 / Qwen 音频编码四十毫秒——模型能
   看到声音的最小时间单位，这是下限的地基；
2. **声学 token 延迟**：Moshi 选加一步等于再加八十毫秒，这是
   质量-延迟旋钮选出来的项；
3. **模型 forward 与解码本身**：与 GPU 档位挂钩，L4 上 Moshi
   理论一百六十毫秒落地为实测二百毫秒；
4. **code→wav 首块**：Qwen2.5-Omni 的滑窗 DiT 要前看一
   block；Qwen3-Omni 的因果 ConvNet 第一个 codec 帧即出。

Qwen2.5-Omni 论文把 initial packet latency 显式拆成四项——多
模态输入处理、首文本 token 到首语音 token、首段语音 token 转
波形、架构固有开销——与上面的通用拆法同构，面试时任用一套。

### 4.2 理论值与端到端：口径先行，不互证

| 数字 | 口径 | 来源 |
|---|---|---|
| 232 / 320ms | **端到端生产口径**，含传输 | OpenAI 官方博客，2024-05 |
| 160ms | **理论/结构值** | Moshi 官方 README，2024 |
| 200ms | **L4 本地实测**，结构+推理 | Moshi 官方 README，2024 |
| 234ms | **冷启动理论值**，官方标注 theoretical | arXiv:2509.17765 摘要，2025-09 |
| 2.8 / 5.4s | 旧 cascade pipeline 平均延迟（对照组） | OpenAI 官方博客，2024-05 |

三个开源毫秒数（一百六、二百、二百三十四）全是**理论或结构值**，
GPT-4o 是含传输的端到端数——两组数**口径不同、不能互证**，
面试被问「GPT-4o 和 Moshi 谁快」先拆口径再回答。

### 4.3 声学 token 延迟旋钮是软的 SLA 调节器

Moshi 的延迟 pattern 本质是「语音版 lookahead」：八十、一百六、
二百四十毫秒三档质量-延迟 trade-off 是**软的、可 serving 侧动
态调节**的——按业务 SLA 选档，无需重训。这个视角能从纯八股
跳到系统设计的加分位。

## 五、barge-in 与状态机：模型内化 vs 应用层补丁

**辨析点（勘误级）**：Qwen2.5/3-Omni 与 GLM-4-Voice **都不是全
双工**。它们支持 chunk 化流式输入输出，但仍是轮次制交互，打断
处理在应用层；真正的模型级全双工开源参照只有 Moshi 系（及衍生
的 PersonaPlex）。社区把三者混称全双工是错误口径。

两条路线的本质分歧：

- **Moshi 双流（模型内化）**：打断、重叠、抢话全是同一 token 流
  的分布内事件，无需外部状态机；代价是模型**永远双开**（边听边
  说），每路会话独占一条生成流——架构优雅、资源账难看；
- **Thinker-Talker（应用层补丁）**：chunk 化 prefill 输入加流
  式输出，打断仍走应用层老三样——VAD 触发、撤回放、作废本
  turn 生成；这就是 [语音与voice-agent专题](../语音与voice-agent专题.md)
  里那套组合解，本篇不展开。

另一个深挖点：**慢思考与流式首包存在结构性矛盾**（Thinking
×流式冲突）。思考-说话并
行在双流架构里是免费的（Inner Monologue 本就是文本前缀），在
Thinker-Talker 里却有物理冲突——Talker 复用 Thinker 的隐藏状
态，意味着 Thinker 的任何「思考时间」都会直接传导到首包；
Qwen3-Omni 官方明说 Thinking 变体拉长首包，因为显式推理链延
迟了 Talker 的起始。**要慢思考还是快起播，必须在产品层先回答**。

## 六、serving 工程：会话态连接的资源模型

### 6.1 传输层：三家收敛到「长连接 + session 作用域状态」

- **OpenAI Realtime**：浏览器侧 WebRTC、服务端 WebSocket，
  ephemeral key 建 session，session 内维护会话状态与工具调用
  （官方文档口径）；
- **Gemini Live**：stateful WSS，十六 kHz PCM 入、二十四 kHz
  PCM 出，图像每秒不超过一帧（Google 官方文档，2026-10 抓取）；
- **Moshi demo**：WebSocket 加 WebRTC UI，自带回声消除
  （官方 README）。

没有任何一家用无状态 HTTP 做 full-duplex——**会话即连接**是
全行业的共识，剩下的问题是连接背后怎么排队上卡。

### 6.2 引擎缺口实测（2026-10）

这是本篇最「冷」但最值钱的一节——omni 模型的 serving 现状是
**多模型编排加常驻流式状态**，主流引擎的 continuous batching
抽象尚未原生覆盖：

- **Moshi 官方三套实现**：PyTorch（研究）、MLX（端侧 iPhone/Mac）、
  **Rust/Candle 定位生产**；README 明确二十四 GB 显存量级、L4
  单流实测口径（官方 README，2024 起持续维护）——生产不走
  vLLM 也不走 SGLang；
- **Qwen2.5-Omni**：官方 vllm serve **只支持 Thinker 文本输出**，
  语音输出要用官方指认的 fork（fyabc/vllm 分支，含
  thinker/talker/code2wav 多 GPU 拆分 demo，README 实测
  2026-10）——官方引擎只啃下了四段编排里的第一段；
- **Step-Audio 2**：官方提供 vLLM docker 镜像
  （stepfun2025/vllm:step-audio-2-v20250909），支持流式推理
  与多卡，是目前**最完整的开源 omni serving 参照**。

结论是：「encoder + thinker + talker + codec」四段各自有流式
状态与首包 SLA，把它编排成一条服务**就是企业自建 omni serving
的真实工作量**，而不是「等 vLLM 支持一下」。

### 6.3 会话态容量公式

资源模型一句话：**会话数等于流数，每路独占 KV 与 codec 状态**。
容量估算公式：

> 单卡并发流数 ≈ 单卡可用显存 ÷（模型显存每流分摊 + 每流常驻
> KV + 每流 codec 状态）

与无状态 HTTP 服务的差异三点：不能按 token 摊销成本；KV 与
codec 的因果卷积状态随连接常驻、无法页表换出复用；连接的生命
周期（秒到分钟级）远大于一次请求的 batch 窗口。这就是
[语音与voice-agent专题](../语音与voice-agent专题.md)里「每路
独占流」成本结论的机制成因，显存每流的拆账模板见
[显存计算专题](../显存计算专题.md)。部署级选择题还有 WebRTC
网关、模型 worker、codec worker 是否**同卡共置**：省通信与争抢
显存带宽的取舍，按流量形态决定。

### 6.4 Step-Audio 2 mini 的工程取向与 star 水位

Step-Audio 2 mini 从 Qwen2-Audio 加 Qwen2.5-7B 初始化，主打
工具调用与 RAG（含**音频检索换音色**），配套 StepEval 系列基准；
开源 repo 截至 2026-10 实测 **一千五百二十六 star**，而早期
Step-Audio repo 仅 **四十三 star**（与语音专题口径一致，主线
已迁 Step-Audio2）。全量 star 水位见数字锚总表附录。

## 七、面试可深挖的六个工程 trade-off

1. **单码本对多码本**：GLM-4-Voice 一百七十五 bps 极简，AR 步
   少、码本嵌入小，但韵律容量受限；Mimi 一点一 kbps 音质好，
   代价是每秒约百个 AR 步、必须 Depth Transformer 分解。选的
   本质是「LLM 先验补多少信息」的哲学差异。
2. **语义蒸馏进 codec 的副作用**：Mimi 论文实测语义蒸馏目标与
   重建、对抗损失冲突导致音质下降，split-RVQ 是工程补救；纯声
   学 codec 加文本孪生（GLM 单流交错、Qwen Talker 吃 Thinker
   文本）是另一条路。选边取决于 codec 要不要兼任「输入理解侧
   的 token 化」。
3. **声学 token 延迟旋钮**：Moshi 延迟 pattern 是软的质量-延迟
   trade-off（八十至二百四十毫秒三档），serving 侧可按业务
   SLA 动态调——语音版 lookahead。
4. **引擎缺口即工作量**：vLLM 官方只啃下 Thinker，说明四段编排
   每段各有流式状态与首包 SLA，这正是落地 omni serving 的真实
   排期内容；Step-Audio 2 官方 vLLM docker 是最完整参照。
5. **会话态容量模型**：并发流乘常驻 KV 加 codec 状态；共置与否
   是部署级选择，没有全局最优解。
6. **Thinking 与流式的根本矛盾**：Qwen3-Omni 官方把 Thinking
   变体与二百三十四毫秒首包写在同一份技术报告里，但两者物理
   冲突——推理链不跑完 Talker 动不了。选型时「慢思考还是快起
   播」必须先在产品层回答。

## 九、▶ 面试题

1. **Moshi 的一百六十毫秒是怎么凑出来的？你负责的环节能压掉
   哪一段？（高频）** 先拆结构账：八十毫秒 Mimi 帧粒度加八十毫秒声学
   token 延迟（官方 README，2024）；能压的环节是延迟 pattern 档
   位选择（八十可用、一百六提质、二百四十边际）与 code→wav 首
   块（因果卷积即出第一帧），帧粒度本身不可压。深度提示：再进
   一层讲 Depth Transformer 为什么必要——每秒约百个 AR 步不分
   解根本流不起来，这是「160ms 可信」的工程前提。
2. **为什么这两年大家都收敛到十二点五赫兹？让你设计下一代
   codec 流率定多少？（高频）** 答收敛逻辑：AR 步数被帧率乘
   码本数钉死，文本只需三至四个 token/s，语音十二赫兹乘八码本
   已经约百个；bit 账如斯：单码本十二点五乘十四 bit 等于一百
   七十五 bps、八码本共一点一 kbps。设计问题落在**帧率与码本
   数的二维 trade-off**：语义靠 LLM 先验补就走单码本，保音质
   就多码本分层。深度提示：说出 split-RVQ 为什么把语义蒸馏放
   进独立 VQ（直接蒸进重建路径伤音质，论文消融证实）即超纲加分。
3. **Thinker-Talker 和 Moshi 双流在 barge-in 上的本质区别是
   什么？（高频）** 核心辨析：Thinker-Talker 与 GLM-4-Voice 都是
   chunk 化输入加流式输出的**半双工**，打断走应用层（VAD 触发、
   撤回放、作废本 turn）；Moshi 双流里 barge-in 是**分布内事
   件**，无需外部状态机，代价是模型永远双开、每路独占生成流。
   深度提示：补 Qwen3-Omni 官方明说的 Thinking 变体拉长首包
   （Talker 复用 Thinker 隐藏状态导致思考时间传导），与第七题
   打通。
4. **设计一个千路并发的 full-duplex 语音服务，资源模型怎么估？
   为什么不用现成 vLLM？（高频）** 资源模型：会话数等于流
   数，单卡并发流约等于可用显存除以「模型显存每流分摊加每流
   KV 加 codec 常驻状态」，按连接生命周期核算而非按 token 摊
   销。不用 vLLM 的理由是 2026-10 实测：Qwen 官方 vLLM 只支持
   Thinker 文本输出、Moshi 生产走自研 Rust/Candle、continuous
   batching 抽象没盖住四段编排。深度提示：主动提出 WebRTC 网
   关、模型与 codec worker 同卡共置的取舍。
5. **GPT-4o 的三百二十毫秒和 Moshi 的二百毫秒能直接比吗？
   （中频）** 不能。三百二十毫秒是含传输的端到端生产口径
   （官方博客 2024-05），二百毫秒是 L4 本地「结构加推理」实测
   口径；Qwen 的二百三十四毫秒更是官方标注的 cold-start
   theoretical。口径先行，数字不互证。深度提示：还能指出
   Gemini Live 官方根本不给毫秒数，凡给数必问口径。
6. **Talker 侧为什么要复用 Thinker 隐藏状态，而不是重新编码
   文本当输入？（中频）** dual-track AR 直接消费隐藏表示
   与历史上下文，省一次文本复读的 forward，同时保住语义对齐；
   代价正是思考时间的传导（Thinking 变体首包变长）。
7. **流式语音模型里 reasoning 能力怎么放进来？（中频）**
   双流架构靠 Inner Monologue 免费获得文本前缀的思考-说话并行；
   分层架构里思考与首包物理冲突，产品层必须先选「慢思考还是
   快起播」。这是 2025-09 之后的新考点，答上即区分度。
8. **Mimi 是五十赫兹还是十二点五赫兹？GPT-4o Realtime 用的什
   么 codec？（低频，勘误陷阱题）** Mimi 是十二点五赫兹，五十
   赫兹是它对比超越的 baseline（SpeechTokenizer、
   SemantiCodec）；GPT-4o Realtime 的 codec 官方**从未披露**，
   唯一能引的是响应延迟数字与协议形态。考官拿这两问试探你是
   否读过原文还是刷的二手摘要。

## 十、口径与未核实说明

**勘误类（正文已按修正后口径书写）**：

- 「Qwen2.5/3-Omni、GLM-4-Voice 是全双工模型」系错误口径：三
  者是 chunk 化流式加轮次制交互，打断在应用层；模型级全双工
  开源参照只有 Moshi 系及衍生 PersonaPlex。
- 「Mimi 是 50Hz codec」系错误：Mimi 为十二点五赫兹；五十赫
  兹是被超越的 baseline（SpeechTokenizer 50Hz/4kbps、
  SemantiCodec 50Hz/1.3kbps，Moshi README 口径，2024）。
- 「GPT-4o Realtime 用了 Mimi 或某种公开 codec」无任何官方证
  据：OpenAI 从未披露 codec、帧率或架构，官方可引数字仅二百
  三十二与三百二十毫秒响应（2024-05 博客）加协议形态。
- 「Moshi 深度模型是 7B」口径须精确：七 B 只指 Temporal
  Transformer，Depth Transformer 是独立小模型，合计大于七 B。
- 「Gemini Live 有官方延迟数字」查无：官方文档（2026-10 抓取）
  只有 low-latency 定性表述与协议格式细节，网传毫秒数一律不引。

**未核实单列（不作为正文事实引用）**：

- Qwen2.5-Omni Talker 侧 codec token 的具体帧率与码率：论文
  （arXiv:2503.20215）摘要与正文片段只给 DiT 滑窗感受野与
  flow-matching 加 BigVGAN 结构，未见明确 Hz；只能表述为「论
  文给了滑窗机制但未在摘要披露 token 帧率」。
- Step-Audio 2 的音频 token 帧率：arXiv:2507.16632 摘要与官方
  README 均未给 Hz/bps 数字。
- Moshi 在高端 GPU（H100 级）上的单卡并发流数：README 只有
  L4 二百毫秒实测与 Rust 后端定位，容量估算只给公式不给背书
  数字。
- Gemini 2.x Live 各模型版本（native audio / half-cascade）的
  命名与架构差异：功能列表已核实（proactive audio、affective
  dialog、live transcription/translation），内部架构非官方披露。
- PersonaPlex 的 arXiv 编号（2602.06053）系沿用语音专题口径
  （repo README 所引，未逐页核对）。
