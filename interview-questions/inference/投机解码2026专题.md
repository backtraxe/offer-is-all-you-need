## 一、主线直觉：用小钱换大步，但大钱在高并发处会亏本

decode 是串行的、memory-bound 的：每步前向把全部权重读一遍，只为产出
一个 token。投机解码的全部故事一句话：**用小钱（draft 算力 / 参数）
换大步（一次前向验掉多个 token）**。draft 阶段产出候选 token 序列
（链或树），target 一次并行前向把整段验掉，数学上用 rejection
sampling 保证输出分布与无投机严格一致。

谱系的演进方向就一条轴：**主线是 draft 不断贴近主干**。外置小模型 → 主干
挂多头（Medusa）→ 复用主干特征（EAGLE）→ 把 draft 训进主干（MTP）
→ 2026 年块级并行 draft（DFlash / DSpark）+ 自适应验证预算
（adaptive verification）。**核心公式是 draft 从哪来决定成本与接受率
天花板，verify 怎么验决定分布无损与工程兼容性**——这条主线是答一切追问的
骨架：接受率问的是前半句，兼容性红线与无损论证问的是后半句。

为什么 2026 这篇要单开：以前 spec decode 是「低负载专武」——batch
一大收益就掉、吞吐反而转跌。2026 年的两件事直接打在这个短板上：
draft 端块级并行（串行步数归零）+ verify 端预算化（按请求动态分配）。
面试官从「讲原理」转向「什么时候用、配多大、和什么不兼容」，这篇的
素材就围绕这三个新考法组织。

## 二、统一骨架：draft → verify → 截断 → bonus token

所有投机方法共享同一套骨架，先把骨架背熟再谈谱系：

1. **draft 阶段**：用某种便宜机制产出候选 token 序列（链或树）；
2. **verify 阶段**：target 对这些候选做一次并行前向——链式候选直接
   逐位并行，树形候选配 **tree attention mask** 保证各分支互不串扰；
3. **rejection sampling 逐位裁决**：每个位置以
   min(1, p_target(x)/p_draft(x)) 的概率接受，遇到第一个被拒的位置
   就截断，其后全部作废；
4. **bonus token**：在截断位置用残差修正分布（p_target 与 p_draft
   的正差归一化）补采一个 token——所以哪怕 draft 全被拒，这一轮也
   至少前进一个 token，**期望接受长度恒大于 1 才谈得上赚**；
5. **回滚**：被拒位置的 KV 不保留（实现上 tree mask 天然没写入互串
   的部分），进入下一轮。

**无损论证的三段声明**（vLLM 官方文档明确列出，面试可直接引用）：

- **理论无损**：rejection sampling 的接受/修正规则数学上保证输出
  分布与 target 直接采样一致，差异只在数值精度限制内；
- **算法无损**：实现侧有 rejection sampler 收敛测试与 greedy 等价
  测试覆盖（vLLM 仓 tests/spec_decode/e2e）；
- **logprob 不保证稳定**：batch 数值非确定性（batch-invariant 之外
  的实现）会让 logprob 有微小漂移——如果你要严格复现输出，这一点
  要主动声明。

一句速记：**验证段从 2023 到 2026 没有变过**（tree attention +
rejection sampling），变的一直是 draft 端。这也是为什么谱系按
「draft 从哪来」切分最干净。

### 边栏：字节级精确的工程变体（TensorFold，2026-10 新项目口径）

上面「logprob 不保证稳定」的注意事项有一个工程反例：TensorFold
（本地推理引擎，2026 新项目）的投机解码宣称**草稿输出与串行解码
字节级完全一致**——草稿 token 一次前向验证，只接受`与串行解码
会采样出的完全一致`的 token，加速不改变任何一个采样字节。对
coding agent / 评测流水线这类**把 LLM 输出当确定性工件**的场景，
这个性质比速度本身更刚需。

- 实测（项目自报口径，未独立复测）：DGX Spark 上比 vLLM（MTP=3）
  同 checkpoint 解码快 1.6–3.1 倍；Mac M5 Max 上 Nemotron 3.5
  Lightning 30B 跑到 188–206 token/s（mlx_lm 同模型 138 token/s）；
  Qwen3.8-27B + DFlash2 drafter 代码任务 189 token/s vs 不开草稿 26。
- 工程取舍同样值得记录：**只做四个模型家族的手写 kernel 包**
  （Metal lane / CUDA 引擎），GPTQ、AWQ、NVFP4 下载前直接拒绝——
  窄换字节级精确与调优深度，代价是名单外模型用不上、新架构要等
  手包更新；prefix-cache 落盘按 agent 流量设计（续轮只 prefill 后缀、
  服务端重启不丢）。
- 使用边界：本地/主权推理 + Apple Silicon/DGX Spark 重心；数据中心
  多租户、模型杂、要 AMD/TPU 仍是 vLLM 的地盘。**选它就是选深度
  不选广度**，benchmark 全为项目自报，按「有潜力的年轻项目」看待。

## 三、谱系深挖：draft 从哪里来

### 3.1 Vanilla draft model：另养一个小模型

祖师形态：独立的 0.1B–1B 级小 LM 自回归**串行**猜 k 步，每步产一个
token，拼成链交给 target 验。账很直白——成本 = 一个完整小模型的
前向 × k 步；小模型自己也 memory-bound，draft 阶段本身就吃掉一部分
换来的时间。且「另养一个模型」意味着训练 / 部署两份资产，draft 与
target 的分布对齐靠蒸馏，接受率天花板是谱系里最低的一档。典型加速
**约 1.5–2.5×（旧文口径量级，2023–2024）**。

### 3.2 Medusa：一次前向挂 k 个头

Medusa 的思路是把 draft 的串行步数压成 1：target 一次前向，主干
hidden 接 k 个**独立 LM head**，第 i 个头只猜 t+i，各头自己的
top-k 展开成候选树，tree attention 一次验掉。

- 优点：draft 阶段一次前向完成，不用单独小模型服务；
- 代价一：各 head **互不通信**，组合出自相矛盾路径的多，靠树宽
  补救；
- 代价二：词表大时每个头一份完整 LM head，参数量不可忽略
  （Victor-sized 词表上每头都是几亿参数）。

**生态信号**：官方仓库 FasterDecoding/Medusa 实测 **2774 stars
（gh 实测，2026-10）**，创建于 2023-09-10，**最后 push 停在
2024-06-25**——项目已停更，与「Medusa 已不是当前主力」这一社区
判断互证。面试被问 Medusa 现状，这个停更事实比背原理更显跟踪深度。

#### 3.2+ 边栏：IBM MLP Speculator——Medusa 的生产化改进

IBM 把 Medusa 思路做成了生产版（Wertheimer et al.,
arXiv:2404.19124；jarvislabs 实测文转述，2026-09）：

- **架构**：多阶段多头 MLP 直接挂在 target 的上下文嵌入（内部
  状态 Z）上——1 号头看 Z 猜 t+1，2 号头以 Z+t+1 的预测猜 t+2，
  依次条件化；target 冻结，参数量约为 target 的十分之一甚至更少；
- **逐头 loss**：每个预测步**单独算一份交叉熵**——近端（t+1）
  易学快收敛，远端（t+3）依赖前几步猜测、曲线整体更高；分开
  跟踪防止近端误差被远端噪声淹没；
- **两阶段训练**：阶段一**输入对齐**（标准文本批次，学会把
  target 嵌入映射到有效后继）；阶段二**输出对齐**（改用 target
  自己生成的输出当真值，蒸馏对齐到 target 的「脾气」）——与
  6.1 节「响应必须 target 自产」的铁律互为印证；
- **支持现状（坑位）**：vLLM 0.12.0 稳定版里独立 draft model 与
  MLP Speculator 的实现**尚未完全支持**（jarvislabs 因此未实测
  它）——面试官问「vLLM 支持哪些方法」，MLP speculator 在方法
  清单里但成熟度要打折讲。

### 3.3 EAGLE-1 / EAGLE-2：在特征层做小自回归

EAGLE 不满 Medusa 的「各猜各的」：在**特征层**做自回归——draft
模块输入主干倒数第二层 hidden 序列 + 前移一位的 token embedding，
逐步迭代出草稿树，再复用主干 LM head 出分布。参数量约**一层
transformer 量级 + 共享 LM head**，比 Medusa 每头一份 LM head 省，
且因为逐步迭代时能看到自己上一步的决策，一致性远好于多头独立猜。

EAGLE-2 的增量是**动态树**：按全局接受率统计决定树的展开形状，
「分歧小的地方多扩」，把验证预算花在回报高的分支上。官方仓库
SafeAILab/EAGLE 实测 **2549 stars（gh 实测，2026-10）**；学术线
EAGLE-1（ICML'24）、EAGLE-2（EMNLP'24）、EAGLE-3（NeurIPS'25），
发表节奏均来自官方仓库描述。

### 3.4 EAGLE-3：直预测 token + TTT，draft 训练的 scaling 路线

EAGLE-3（arXiv:2503.01840，2025-03-03 提交）动了两个关键刀：

1. **放弃 feature prediction 回归目标，直接预测 token**。作者的论证
   是：特征回归约束是 scaling 瓶颈——EAGLE 加训练数据收益有限，
   根因就在让 draft 复刻主干中间特征这个不必要的目标上。放开之后
   draft 训练能吃数据红利；
2. **训练时融合低 / 中 / 高三层特征**，替代只用顶层特征；
3. 整体技术命名为 **Training-Time Test（TTT）**：训练时就模拟测试
   时的多步 draft 展开，做 **on-policy** 训练——draft 在自己真实
   会犯的错上被纠正，而不是在主干的「标准答案」分布上拟合。
   （SGLang 官方文档口径：EAGLE-3 removes feature prediction
   objective, incorporates low and mid-layer features, trained
   in an on-policy manner。）

代表性数字：**加速比最高 6.5×，比 EAGLE-2 高约 1.4×（arXiv:2503.01840
论文，2025）**；工程口径见第四节 SGLang 实测表。

### 3.5 MTP（DeepSeek-V3）：draft 与主干「同根生」

MTP（arXiv:2412.19437，2024-12）是谱系目前的内化终点：训练时主干
后挂 D 个**顺序** MTP 模块，每个模块共享主干 embedding 层与输出
head，逐深度维持因果链预测 next-k（论文原文 causal chain，
"similar to that of EAGLE"）。训练时它是辅助 loss——防止模型只盯
相邻一步的短视目标；推理时退化为 spec decode 的 draft 头，**零额外
模型资产**。

与外挂 draft（含 EAGLE）的本质区别：**起点不同，MTP 的 draft 与主干
同参数、同训练信号**，外挂 draft 则是蒸馏对齐。同根生意味着分布天然
贴近，接受率天花板不同——这也是下面这组数字的结构性原因：**数字是
MTP 第二 token 接受率 85%–90%（跨生成主题）、整体 1.8× TPS
（DeepSeek-V3 论文，2024）**。这个 85–90% 是外挂方案按场景下浮后
很难追平的一档。

### 3.5+ 边栏：Gemma 4 MTP——独立打包、共享 KV 的中间形态

vLLM 官博客（2026-08，AMD 实测文）把 MTP 家族又细分出一档，值得
单列——**Gemma 4 MTP**：draft 组件是**与 target 模型配对的独立
checkpoint**（要单独下载、单独加载显存），但推理时**共享 target
模型的 KV cache、直接消费 target 的 activation**，不需要自己重算
已接受 prefix 的上下文。它卡在两个极端之间：

| 形态 | 权重 | KV cache | 代表 |
|---|---|---|---|
| Native MTP | 嵌在 target 里，零额外资产 | 天然共享 | DeepSeek-V3 系 |
| **Gemma 4 MTP** | **独立 checkpoint** | **共享 target KV** | Gemma 4 E2B/E4B/12B/26B-A4B/31B 的 Assistant checkpoint |
| 专用 speculator | 独立 checkpoint 独立网络 | 部分特征复用 | EAGLE-3 / DFlash / DSpark |

vLLM 配置上的细节：Gemma 4 Assistant checkpoint **走 `mtp` 方法
路径**——尽管它是通过 `model` 字段外部提供的；vLLM 会把
assistant 组件接到 target 上并放开 KV 共享。发布方是 Google
官方，覆盖 Gemma 4 全尺寸（vLLM 官博客，2026-08）。

### 3.5++ 两轴分类法：把所有 draft 方法一秒归位

同一篇 vLLM 官博客给了一个比时间线更好用的分类骨架——所有
drafting 方法只看两个轴：

1. **draft 从 target 拿到什么信息**：当前隐藏表示 / 选定若干层的
   hidden states / KV cache / 多层特征融合；
2. **候选怎么生成**：串行（逐 token 依赖上一个）还是并行
   （一次前向产一整块）。

按这两轴归位：**native MTP 与 Gemma 4 MTP 是「当前隐藏表示 ×
串行」；EAGLE-3 是「三层 hidden states 融合（靠近开头/中间/结尾
三段）× 串行」；DFlash 是「融合特征注入每层 × 并行」；DSpark
是「同 DFlash × 并行+轻量顺序修正」**。分类描述的是 draft 组件的
架构，与 target 模型家族正交——同一个 target 可以同时拥有原生
MTP 和单独训练的 EAGLE-3/DFlash/DSpark 多套 draft 资产。
时间线谱系讲「为什么长成这样」，两轴法讲「面试时怎么 30 秒
对比任意两个方法」，两个都背。

### 3.6 无 draft 一支：n-gram 与 suffix decoding

谱系别忘了还有「根本不训 draft」的一支：

- **n-gram / prompt lookup**：从 prompt 或已生成文本的 n-gram 缓存
  里匹配续写，命中即草稿；
- **suffix decoding**：全局后缀自动机 / trie，跨请求共享，vLLM 默认
  max_tree_depth=24、缓存上限 10000 请求（vLLM 文档口径，2026-10）。

零训练成本、零显存增量，适合代码编辑、agent 多轮回填这类**高重复
生成**场景；代价是通用场景增益中低。工程位置：常作为 warmup 或
与有 draft 方案的组合项存在。

#### 3.6+ Suffix Decoding 机制深挖（Oliaro et al., arXiv:2411.04975）

「零权重免费加速」是有机制的，面试被追问要能拆到这一层
（jarvislabs 实测文口径，2026-09）：

- **双后缀树缓存**：本地树（per-request）收当前请求的 prompt 与
  已生成 token，捕获**会话内自我重复**；全局树收服务处理过的
  **所有历史请求输出**，提供跨请求的统计规律——agent 循环（反复
  读自己历史）里全局树是接受率的顶梁柱；
- **模式匹配**：取当前序列末尾 p 个 token 沿两树下行走位，命中
  节点 Np 下的所有路径都是可能延续；
- **贪心扩展建推测树**：不铺全部分支，只用两个分数长最可能的路
  ——步概率 C(N)（该 token 紧随前 token 出现的可能性）与路径
  置信度 `D(N) = D(父) × C(N)`（整条路径正确的可能性，根为
  1）；从 Np 起反复把置信度最高的叶节点并入推测树，直到规模
  上限 **MAX_SPEC（自适应调整）**；
- **工程特性**：匹配与起草**全程 CPU**，不占显存不算力；MAX_SPEC
  随模式匹配长度**自适应**——命中越长猜得越多，避免短命中时
  浪费 target 验证算力；
- **与 n-gram 的分野**：同为回看历史，n-gram 线性扫描窗口窄，
  suffix 的树结构让长历史查找占优——这就是实测里 n-gram 普遍
  比 suffix 慢 20–25 个点的结构原因（见 4.3 矩阵）。

### 3.7 2026 块级并行 draft：DFlash / DSpark / LiLiCorr / UNO

2026 年 draft 端的主线是**把串行步数归到零**：

- **DFlash**：block / 扩散式草稿——一次前向产出整个线性 block，
  不再逐 token 自回归；验证走 **block verification**（逐前缀检查、
  保留最长可接受前缀，配修正分布保持 target 采样分布）。SGLang 与
  vLLM 均已支持 DFLASH 算法（两引擎文档，2026-10）。
  机制细节（vLLM 官博客 AMD 文，2026-08）值得展开三点：
  **① anchor token**：每个 draft block 第一个位置放一个**已被
  target 确认过的已知 token**（后续轮次里通常就是上一轮 verify
  返回的 bonus token），DFlash 不预测它，只给后续被 mask 的位置
  一个已知起点；**② 融合特征的去向与 EAGLE-3 相反**：EAGLE-3 把
  三层 hidden states 融合后**在 draft 输入端与 token embedding
  拼接一次**，DFlash 则把融合特征**转成额外的 Key/Value，注入
  draft 网络的每一层**——被 mask 位置的 Query 每层都能同时
  attend target 派生的 KV 和 block 自身的 KV，target 上下文
  「全程在线」而非只在入口处露一面；**③ 代价**：同一次前向里
  靠后的位置**不以靠前位置的采样结果为条件**（逐 token 反馈被
  移除），块越长、后段位置的有效性越依赖 checkpoint 质量与具体
  负载——这是并行块方法的天性税；
- **DSpark**：在 DFlash 之上做两个加法（vLLM 官博客，2026-08）：
  **① 轻量 Markov head（顺序修正）**——并行 backbone 独立预测
  每个位置会出「每位合理、联合不连贯」：比如 `"of course"` 和
  `"no problem"` 各自合理，独立采样却拼出 `"of problem."`；
  Markov head 在 backbone 产出全部 base logits 后**从左到右跑
  一遍轻量顺序头**，每位置只用紧邻前一个已选 token 生成一个小
  bias 修正 logits——块内后续 token 得以依赖已选 token，又不必
  为每个位置重跑完整 draft 网络；**② confidence head**——训练出
  的逐位置接受概率估计，为 adaptive verification（第五节）供概率，
  也可用来截短提交给 target 验证的前缀；vLLM 示例用
  DeepSeek-V4-Flash-DSpark checkpoint 配 7 个投机 token（vLLM
  adaptive verification 文档，2026-10，V4 相关口径见文末未核实节）；
- **LiLiCorr**（SGLang 文档引 arXiv:2608.20530）：DFlash drafter 按
  边际分布逐位训练，会出「每位合理、联合不连贯」的草稿；LiLiCorr
  保留每位 top-k 候选，用两层 transformer 对整格**联合打分**后贪心
  提交。verify 路径完全不动，所以输出仍然无损，代价只花在草稿质量
  上（约 +6% 接受率、+6% 端到端，块时长代价 <1%，SGLang 文档
  转述口径——未经论文原文核验，亦见文末说明）；
- **UNO**（SGLang 集成，2026-10 文档）：target 复用式 draft——不走
  独立 draft 模型，同一 transformer + 一个 LoRA 充当 draft 权。
  已验证 Qwen3-8B，Linear 8/1/8、Tree 8/32/8 两种配置；硬约束是
  要求 CUDA + FA3、TP=PP=1。

一句收口：**趋势是 draft 从「逐 token 串行」走到「一次前向产一块」，
verify 从「定长验 k 个」走向「按概率分预算」**——这就是 2026 主题。

MiMo×DFlash 实测口径（小米官方博客，2026-10 UltraSpeed 披露）：
draft 全部采用 SWA、与 MiMo-V2 系列自身 SWA 设计对齐——draft 不再
依赖完整前缀，单次预测算力从随上下文线性增长变为常数级；Muon 二阶
优化器+模型自蒸馏保证小 mask 块接受率，块大小限 8（压验证开销、提
并发）；训练时 mask 信号采样下沉 GPU 本地分片，一条序列单步即可产出
覆盖不同上下文位置的数万级独立训练信号。实测接受长度：**Coding
6.30 / Math-Reasoning 5.56 / Agent 4.29**（每轮 8 个 draft token
接受 6–7 个）；通用对话场景接受率尚低。官方定性：并行块 draft 在
agent 与 coding 高价值场景收益显著——与上文「块越长后段越依赖
checkpoint 质量与负载」的天性税互为印证：**场景要选块状性强的**。

## 四、2026 支持矩阵与兼容性红线（两引擎文档实测）

本节全部条目以 **2026-10 抓取的 vLLM / SGLang 官方文档**为准。支持
矩阵的读法：方法名能对上不稀奇，**红线条目才是面试加分项**——它
证明你把文档读到了「不能怎么用」那一层。

### 4.1 vLLM 侧

**方法清单（method 取值）**：EAGLE / EAGLE3 / MTP / draft model /
PARD（并行 draft）/ MLP speculator / n-gram / suffix decoding /
DFlash / DSpark / LiLiCorr / custom proposer（experimental）。另有
两个场景级特性：**动态投机（Dynamic SD）**，面向 QPS 波动场景
（典型如 RL rollout）；另一个是**自适应验证（adaptive verification）**（第五节详拆）。

**传参方式**：单一 `--speculative-config` JSON，关键键值得背：

| 键 | 语义 | 备注 |
|---|---|---|
| method | 方法名 | eagle / eagle3 / mtp / draft_model / ngram … |
| model | draft 模型路径 | assistant checkpoint 期 Gemma 4 走 mtp 专用路径 |
| num_speculative_tokens | 每轮最多投机几个 token | 静态预算；自适应验证下退化为上限 |
| draft_tensor_parallel_size | draft 独立 TP 切分 | 大 draft 才用得上 |
| rejection_sample_method | standard / synthetic / block | block 对应块级验证 |
| parallel_drafting | 并行草稿 | 仅 EAGLE / draft_model 兼容 |
| use_heterogeneous_vocab | TLI 跨词表 draft | 只允许 greedy draft 采样 |

**兼容性红线（文档原文口径，2026-10）**：

1. **pipeline parallelism 不可与 spec decode 组合**（as of
   vllm<=0.15.0）——这是最常见的一条追问，「你们 70B 上 PP 怎么开
   投机」的正确答法是先指这条限制；
2. draft models 在 vllm<=0.10.0 不受支持（版本下限）；
3. **adaptive verification 要求 full CUDA graphs**（传
   --enforce-eager 会在启动直接拒掉）；
4. adaptive verification **不支持 LoRA、不支持 PP**——注意这和
   「UNO 用 LoRA 当 draft」是不同层面的两个开关，不要混；
5. attention backend 必须容忍 **device-decided query lengths**
   （验证阶段每个请求的有效 query 长在 kernel 侧才能定）；
6. MTP 页确认 Gemma 4 assistant checkpoint 的专用路径：assistant
   层与 target **共享 KV cache**；MiMo-7B 是文档的例行示例。

### 4.2 SGLang 侧

**方法清单（--speculative-algorithm 取值）**：EAGLE / EAGLE3 /
NEXTN（EAGLE 别名）/ STANDALONE / NGRAM / DFLASH / UNO。DeepSeek
系的 MTP 经由 spec 工作流接入（文档示例 XiaomiMiMo/MiMo-7B-RL，
DeepSeek-V3.2 系见 cookbook §4.2.3）。

**自动默认值（背下来直接答「draft 参数怎么配」）**：

- Llama / Grok 系：**默认 steps=5、topk=4、draft_tokens=8**；
- 多数其他模型：**默认 steps=3、topk=1、draft_tokens=4**；
- 联动规则：topk=1 时 draft_tokens 自动调为 steps+1（链式草稿
  不需要树宽）。

**坑位清单（每条都是实测过的）**：

1. **overlap scheduler 仅兼容 topk=1**——topk>1 直接报错；尤其要
   防 auto-tuning 悄悄选出 topk>1 的配置，生产上须显式锁定 topk=1
   再开 overlap；
2. **NGRAM 与 DFLASH 禁用 overlap scheduler 和 mixed chunked
   prefill**，且不支持 DP attention；
3. **STANDALONE 不支持 DP attention**；
4. **UNO 要求 CUDA + FA3、TP=PP=1、禁 mixed chunked prefill**；
5. page_size>1 且 ngram 宽度>1 时必须用 flashinfer backend；
6. **OOM 调参顺序（官方 recipe，按序执行）**：先降
   --mem-fraction-static → 再砍 CUDA graph 最大 batch → 再缩
   draft 树（num-steps / topk / num-draft-tokens）→ 最后限并发。

- **`num_speculative_tokens` 的最优值按负载扫描，峰值通常落在
  4–7（官方口径）**；同系列的 Qwen3.6-27B 与 35B-A3B 最优 N 都
  不同——Dense 与 MoE 的接受模式不一样，照抄推荐值必踩坑；
- 落地姿势：**先跑通 checkpoint 官方支持的配置，再用位置级接受率
  （per-position acceptance）把 N 收到峰值**——看接受率曲线收敛
  比拍脑袋调参快一个量级。

vLLM 0.12.0，N-gram/Suffix/EAGLE/EAGLE-3 四法对决）——它回答的

读矩阵的三层格局（选型框架，面试直接背）：

1. **8B 是计算受限**：权重舒服进显存，瓶颈在算力——draft 的额外
   计算直接与 target 抢 GPU 周期，所以**低开销的启发式赢**：代码
   场景 Suffix 1.45× 压过 EAGLE-3 的 1.03×（EAGLE-3 在 8B+刚性
   任务上开销超过收益）；
2. **70B 是显存带宽受限**：每步贵在搬权重——**预测越准 = 越少
   搬权重**，收益被放大，EAGLE-3 双场景拿下 1.57×/1.60×；标准
   EAGLE 在 70B 上几乎与基线打平（1.01–1.02×），说明**老 draft
   头架构跟不上大模型，升级到 EAGLE-3 是必要条件**；
3. **Suffix 是全档位的免费地板**：四个格子永远前二，不要训练、
   不占显存——落地公式：**先用 Suffix 摸自家负载的天花板，70B+
   追极致再为 EAGLE-3 付配置与调优成本**；
4. 顺带坐实 3.6 的结构判断：**n-gram 普遍比 Suffix 慢 20–25 个
   点**（窄窗口线性扫描 vs 树结构长历史查找）。

SGLang 官方明确警告投机增加显存占用，账按这三笔记：

1. **draft 参数本身**：EAGLE draft 头约一层 transformer 量级 + 共享
   LM head；词表大时 Medusa 每头一份 LM head 不可忽略；MTP 的
   draft 参数嵌在主干里，增量最小；
2. **draft 树的 KV 与 verify buffer**：候选树每个位置都要
   attention 参与，树越宽 buffer 越大；
3. **CUDA graph 图谱**：投机的 graph 拓扑比无投机多一档（draft 步
   + verify 步都要 capture），graph 池本身吃显存——这也是 SGLang
   OOM recipe 把「砍 CUDA graph 最大 batch」排在第二顺位的原因。

## 五、工程账：大 batch 收益衰减与 adaptive verification

### 5.1 衰减机制：memory-bound 到 compute-bound 的交叉点

vLLM adaptive verification 文档给的一手表述（2026-10）：

- **bs=1 时** GPU memory-bound、算力闲置，draft token 近似免费——
  反正 target 那一次前向的算力本来就用不满，多算几个候选几乎不
  花 wall time；
- **bs=256 时** 进入 compute-bound，draft token 与真实 token 抢
  同一份算力，**每个被拒 token 都是纯浪费**；
- 且**逐位置接受概率衰减很快**：第 1 位 85% 不代表第 6 位还有
  85%——各位置接受概率的连乘才是「整段存活率」，所以期望接受
  长度随树深快速失血。

两件事合成一条下降曲线：单请求量级 2–6× 的收益，到 bs=64 只剩
**1.38×（EAGLE 论文 + SGLang 实测，2025）**，再大 bucket 甚至转跌。
**交叉点随负载与任务接受率移动**——代码补全接受率高交叉点靠后，
开放闲聊靠前。

### 5.2 为什么静态配置救不了：这就是自适应的动机

既然交叉点在动，**没有任何一个静态 num_speculative_tokens 能覆盖
全部并发档**：低负载配 5 个投机 token 是对的，高负载配 2 个都嫌
多，而线上 QPS 在昼夜之间、突发流量之间来回穿越。2026 之前工程上
的妥协是「凭感觉配一个折中值 + 高 QPS 手动关投机」；adaptive
verification 就是把这件事自动化。

### 5.3 预算分配机制（能讲清这块就是深档选手）

vLLM 现行文档口径的机制四步：

1. **逐 slot 打分**：每个 (request, position) draft slot 按**生存
   概率**打分——该请求逐位接受估计的连乘积，位置越深连乘越小；
2. **概率从哪来**：DSpark 直接用训练出的 confidence head；其余
   方法在 draft logits 上套一个**小 logistic 模型在线重校准**
   （用线上真实接受与否做校准信号）；
3. **全局预算内择优录取**：不是所有 slot 都验——在总验证预算内
   按生存概率选最高的一组；
4. **预算从哪来**：启动时剖析的 **step 成本模型**（测一次真实
   step 的算力成本曲线），目标是最大化「**每秒期望接受 token
   数**」。

配套硬约束（第四节已列，这里复读一遍因为它们就是落地门槛）：要
full CUDA graphs、不支持 LoRA、不支持 PP、attention backend 要容忍
device-decided query lengths。支持 EAGLE / MTP / DFlash / DSpark /
standalone 全谱系（vLLM 文档，2026-10）。

**预算方法的面试答法模板**：

| 场景 | 判断 |
|---|---|
| 低 QPS、延迟敏感 | 开，静态多配几个投机 token 即可 |
| 高 QPS、吞吐敏感 | 不开，或上 adaptive verification 把预算压小 |
| QPS 波动大（RL rollout、突发流量） | Dynamic SD / adaptive verification 的主场 |
| 温度高、开放闲聊 | 接受率天然低，收益打折，先看任务再开 |
| 代码编辑 / agent 回填等高重复场景 | n-gram / suffix 零成本低收益，先试这个 |

准确话术：**这句 2026 共识——静态 num_speculative_tokens 无法覆盖全
并发档——要能脱口而出**。主动报这句，就是把回答从背书升级到工程判断。

## 六、训练侧资产：draft 是一等工程方向

2026 年 spec decode 的训练生态三家对标：

|---|---|---|---|

| speculators | vLLM 团队（含 RedHat） | **871★**，2025-04-08 创建，活跃 | vLLM 侧统一 draft 训练 / 评估 / 分发库；HF 上有 RedHatAI speculator-models 系列 |

DeepSpec 的信息量最大：**其 7205★ 是前两家之和的 3.6 倍**，且出自一
线模型厂——说明 spec decode 已从「推理引擎的可选优化」升格为
「模型厂的一级工程方向」，draft 训练与模型发布捆绑（DeepSeek-V3

训练路线的一句话总结：EAGLE-3 用**放弃 feature prediction + TTT
on-policy** 打开了 draft 训练的 scaling 路线；MTP 证明 draft 可以
作为主干训练信号的一部分自然长出来；DSpark 再把「逐位置接受概率」
也变成可训练资产（confidence head）供验证侧消费。**总趋势是 draft
训练与主训练流程合并，而不是另起炉灶蒸馏对齐**。

### 6.1 训练 speculator 的工程工作流（vLLM Speculators 实践口径）

被问「给你一个内部模型，怎么从零配一个 draft？」时按这五步走，
每步带一个坑：

1. **准备代表性 prompt**：chat/数学/代码/工具调用按预期负载配比，
   单独留一组评估专用；
2. **用 target 模型自己生成响应**——**最大的坑在这里**：把
   target 的 tokenizer/chat template 套到别的模型生成的响应上，
   并不能让数据变成 target-specific；tokenizer、chat 模板、
   thinking mode、采样配置都必须与目标部署一致（vLLM Speculators
   文档强调口径）。数据分布错了，接受率天花板直接砍半；
3. **选 hidden-state 供给模式**：

   | 模式 | 工作方式 | 什么时候选 |
   |---|---|---|
   | 在线 | 训练时由运行中的 vLLM server 现生成现丢 | 磁盘紧张，但 GPU 要同时扛推理+训练 |
   | 离线 | 训练前全部生成落盘 | 之后 GPU 全留给训练，代价是大存储 |
   | 混合 | 第一个 epoch 生成并缓存，后续复用 | 只付一次生成成本，无独立预处理阶段 |

4. **对齐训练配置**：speculator 的 hidden size、词表、tokenizer、
   选定 target 层必须与 target 一致——**自定义了 target layers，
   训练配置里就必须用同一组层选择**；
5. **测对的指标**：**训练 loss 不算数**，看 accepted length、
   acceptance rate、draft 延迟、显存增量、端到端吞吐；接受率
   偏低时回去调 prompt 混合比例或训练配置重跑。

## 七、▶ 高频面试题

**Q1：spec decode 原理？为什么输出分布无损？**——**极高频**

- 浅档：讲清「draft 猜 → target 并行验 → 第一个被拒处截断 →
  残差补一个 bonus token」的骨架，点出验证仍是同一次 target
  前向，不是小模型说了算。
- 深档：写出接受概率 min(1, p_target(x)/p_draft(x)) 与残差修正
  分布（p_target − p_draft 正差归一化），再补 vLLM 三段无损声明
  （理论无损 / 算法无损含 e2e 测试 / logprob 不保证稳定）。
  收尾一句：无损的无是指分布，不是指逐 token 复现。

**Q2：Medusa / EAGLE / EAGLE-3 / MTP 的 draft 各从哪来？训练成本
与接受率怎么排？**——**高频**

- 浅档：按「外置小模型 → 主干挂多头 → 复用特征自回归 → 训进
  主干」排序，接受率与贴合度递增、额外资产递减。
- 深档：EAGLE-3 为什么放弃 feature prediction——特征回归是
  scaling 瓶颈，放开后能直预测 token 吃数据红利；TTT 是训练时
  模拟测试时的多步展开做 on-policy。MTP 与外挂的本质差是同参数
  同训练信号 vs 蒸馏对齐。补 Medusa 仓库停更（2024-06，2774★）
  与 DeepSpec 7205★ 两个生态作信号对比。

**Q3：为什么 batch 大了投机收益掉甚至转跌？**——**高频，2026 升温**

- 浅档：低负载 memory-bound 时 draft 近似免费，高负载
  compute-bound 时被拒 token 是纯浪费。
- 深档：三重机制一起讲——算力交叉点随负载与任务接受率移动；
  逐位置接受概率连乘衰减（第 1 位 85% 撑不到第 6 位）；数字锚
  bs=64 仍有 1.38×（EAGLE-3 论文）。然后自然引出 Q4。

**Q4：线上到底开不开投机？怎么开？**——**高频（工程判断题）**

- 答法是场景矩阵：低 QPS 延迟敏感开；高 QPS 吞吐敏感不开或开
  自适应；QPS 波动用 Dynamic SD；高重复场景先试 n-gram。
- 控场金句：「静态 num_speculative_tokens 无法覆盖全并发档」
  是 2026 共识。能讲到 adaptive verification 的「生存概率连乘
  打分 + 全局预算择优 + 启动剖析成本模型」三步即到深档。

**Q5：MTP 和外挂 draft 的本质区别？**——**中高频**

- 同参数同训练信号 vs 蒸馏对齐；MTP 训练时是辅助 loss（防短视），
  推理时复用为 draft 头，一套参数训练推理两用。
- 接受率天花板的结构性原因在此：85–90%（DeepSeek-V3 论文）
  是外挂方案蒸馏对齐后很难追的一档。
- 1.8× TPS 捎带报出（同论文口径）。

**Q6：tree 验证 vs chain 验证怎么选？**——**中高频**

- 同一次验证预算，tree 覆盖更多位置、分支共享前缀，期望接受
  长度更高；代价是 tree attention mask 的复杂度与显存（树宽
  直接撑 verify buffer 与 KV 占用）。
- 工程口径：SGLang 默认值给了答案——Llama 系 steps=5/topk=4
  走树，多数模型 3/1/4 走近似链；topk=1 时自动退化成链且
  draft_tokens=steps+1。

**Q7：PD 分离 / prefix cache / chunk prefill 下 spec 怎么配？**——
**中频，2026 工程向**

- 能答的红线：SGLang overlap scheduler 仅 topk=1；NGRAM/DFLASH
  禁 mixed chunked prefill 与 DP attention；vLLM 侧 PP 不兼容
  （≤0.15.0）、adaptive verification 需 full CUDA graph 且不支持
  LoRA/PP。
- 诚实边界：两大引擎文档都未给「PD 分离 + 投机」的官方组合
  矩阵，面试时说「实测前不下结论」反而是加分答案（见文末
  未核实节第 7 条）。

**Q8：draft 参数怎么调？OOM 了先动哪个？**——**中频**

- SGLang 三参数语义：steps（draft 自回归步数）、topk（每步树宽）、
  draft_tokens（每轮总预算），联动规则 topk=1 → draft_tokens=
  steps+1；
- vLLM 侧 num_speculative_tokens 静态预算，自适应验证下退化为
  上限；
- OOM recipe 顺序：先降 mem-fraction-static → 砍 CUDA graph
  最大 batch → 缩 draft 树 → 最后限并发。顺序本身比参数值更是
  考点。
