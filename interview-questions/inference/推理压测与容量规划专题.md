## 一、主线：压测不是跑分，是容量规划的取证环节

面试官问「线上要扛 X QPS，给多少卡」，外行答「我压一下看看」，内行答的是一
条**闭环**：先声明流量画像（ISL/OSL 分布、峰谷、prefix 命中率），再用对的
负载模型（泊松，不是恒定并发）扫出吞吐–延迟曲线，用 knee 点定单实例的真实
上限，乘上 headroom 折算实例数，上线后用监控三板（KV 占用、SM 利用率、队
列长度）盯住画像漂移，引擎一升级就回灌重扫。这条闭环的每一个环节都有专属
工具、专属坑、专属一手出处——本篇就是按闭环顺序组织的。

三个先立的观念：

1. **单机上限是测出来的，不是算出来的**：KV 容量公式只给理论并发上限，
   SLO 内的 goodput 拐点（knee）才是实际上限，两者经常差好几倍。
2. **压测报告的价值 = 元信息完整度**：数据集全名、随机种子、ignore_eos
   与否、采样参数、档位、时长、warmup 剔除方式、prefix hit rate——缺一
   项，数字就没有可复现性，面试里先报这份清单就是高分动作。
3. **容量假设的保质期很短**：引擎版本迭代动辄 +
   **47% 每卡吞吐（vLLM wide-EP 博客，2025-12）。** 历史容量结论不重扫
   就是白配卡。

## 二、压测工具栈横评（2026-10 口径）

### 2.1 工具谱系总表

| 工具 | 维护方 | 定位 | 负载模式 | 一句话备注 |
|---|---|---|---|---|
| `vllm bench serve`（原 benchmark_serving.py） | vLLM | 生态事实标准 | 泊松（gamma burstiness）/ inf / 恒定并发 / ramp-up | 2026 已并入 `vllm bench` CLI 子命令 |
| bench_serving 四件套 | SGLang | 引擎自带分层 | 恒定 rate / 恒定并发 | 从 kernel 到在线四层，官方稳态判据 num-prompts ≥ 5× 并发 |
| genai-perf → **AIPerf** | NVIDIA | LLM 专用跨服务器客户端 | 并发 / request-rate / 双控 / trace replay / adaptive | genai-perf 官方宣布停止新特性开发，新项目迁移 AIPerf |
| GuideLLM | vLLM 项目（原 Neural Magic / Red Hat） | SLO-aware 扫参平台 | synchronous / concurrent / throughput / constant / poisson / sweep | 自带 warmup/cooldown 剔除与 over-saturation 判停 |
| k6 / Locust + LLM 封装 | Grafana / 社区 | 通用 HTTP 负载 | k6: closed（constant-vus）/ open（arrival-rate） | 不懂 TTFT/ITL，SSE 指标要自己解析 |
| inference-perf / genai-bench / llmperf | k8s-sigs / sgl-project / ray | 生态杂牌军 | 见 GuideLLM README 对比表 | 选型时提一嘴做对照 |

选型金句：「**引擎内对比用 SGLang bench_offline，在线 SLO 用 vllm bench
serve 或 AIPerf，找 SLA 边界用 GuideLLM sweep，全链路（网关+鉴权+限流）
才上 k6。**」（综合各官方文档定位，2026-10。）

### 2.2 vllm bench serve：gamma 三参数与官方用例表

2026 形态：`vllm bench serve` CLI（benchmarks/ 旧脚本迁出），配套
`vllm bench throughput`（离线）、`vllm bench latency`，以及
`vllm bench sweep serve`——**每次跑比重置服务器缓存，一刀切掉 prefix
cache 污染（vLLM Benchmark CLI 文档，2026）。**

负载参数三件套，面试要能不假思索说出：

- `--request-rate`：默认 inf = 启动时全发，测裸吞吐（打满态）；
- `--burstiness`：到达间隔服从 Gamma 分布，变异系数 **CV = 1/√burstiness
  ——0.1 是高突发（CV≈3.16），1.0 是泊松（CV=1，自然流量），2.0–5.0 趋
  均匀（vLLM 文档公式，2026）。**
- `--max-concurrency`：客户端背压，模拟网关限流，报告里单列
  `client_queue_time`。

官方用例表直接可当面试答法：Maximum Throughput = {rate=inf，限并发}；
Realistic = {burstiness 1.0，rate 5–20}；Stress = {burstiness 0.1–0.5，
高 rate}；Capacity Planning = {1.0，扫 rate，限并发}；SLA Validation =
{1.0，目标 rate，SLO 限并发}。容量规划时 **`--max-concurrency` 设到启动
日志报告最大值的 80–90%（vLLM 官方建议，2026）。**

官方 Warning 级警告（「压测四坑」之首的一手出处）：同一服务器重复压会
命中 prefix cache 抬高吞吐；synthetic random 数据集固定 seed=0 可复现；
不想被缓存污染就换 seed、重启服务，或用 `vllm bench sweep serve` 在
run 间重置缓存。

2026 可提一笔的加分项：`--ramp-up-strategy linear/exponential` 爬坡找最
大吞吐；`--probe-request-rate` 旁路探针（主负载打大图请求时用单 token
文本探针测干扰）；`--plot-timeline` / `--plot-dataset-stats`；数据集支持
ShareGPT、custom jsonl、random、多模态 random-mm（bucket 配置图片分辨率
分布）、BFCL 工具调用负载、timed_trace（Mooncake conversation_trace 回
放）、prefix_repetition（前缀重复合成）。

### 2.3 SGLang 四件套：从 kernel 到在线的分层打

| 工具 | 过 HTTP？ | 过调度器？ | 用途 |
|---|---|---|---|
| bench_serving | 是 | 是 | 在线 serving 指标（TTFT/TPOT/ITL），默认用它 |
| bench_one_batch_server | 是（单批） | 是 | 单批 E2E 含开销；非稳态指标有偏 |
| bench_offline_throughput | 否 | 是（进程内 Engine） | 无网络开销的最大吞吐 |
| bench_one_batch | 否 | 否（直调 ModelRunner） | 固定静态 batch 的 kernel 级 profile |

两条必须背的官方判据（SGLang Benchmark and Profiling 文档，2026）：

- **稳态判据：`num-prompts >= 5 × max-concurrency`，**否则曲线前段被
  prefill 簇与启动瞬态污染；bench_one_batch_server 的权威指标只有
  overall_throughput 一个。
- 真实 prompt 回放要 `--disable-ignore-eos`：否则 decode 越过 EOS 往垃
  圾分布上偏，吞吐数字虚高。该模式下报告自动给出「稳态窗口列」（从最
  后一条请求首 token 到第一条请求结束之间的窗口）。

PD 分离模式 profiling：prefill / decode worker 要分开
`--profile-prefill-url` / `--profile-decode-url`，两参数互斥。

### 2.4 genai-perf 退役与 AIPerf 接棒（2026 换代考点）

genai-perf（2024 起，Triton perf-analyzer 家族）在其 **官方 README 顶部明
确宣布停止新特性开发、新项目请用 AIPerf（genai-perf README 弃用声明，
2026）。** 面试答 2026 口径要会主动说这句，而不是还拿 genai-perf 当最新
工具。

genai-perf 时代建立、AIPerf 继承的口径：

- LLM 指标表 = TTFT / Time to Second Token / ITL / Output Token Throughput
  Per User / Request Latency / ISL / OSL / 全局吞吐 / request throughput；
- synthetic 输入默认 **ISL 均值 550、正态 stddev 可调（genai-perf 文档，
  2026）；**
- OSL 用 `--output-tokens-mean`，但**不保证达到**——除非 `ignore_eos` /
  `min_tokens`。这是「输出长度不可控」坑的一手出处，两家文档都明写；
- 温机：`--warmup-request-count`；稳态判定继承 perf-analyzer 公式：以最
  近 3 次 measurement-interval 的 infer/s 与延迟的 max/min 比值判定稳
  定，`--stability-percentage` 默认 999（基本不关窗），正式压测建议设
  5–10%；
- goodput 约束语法：`-g 'time_to_first_token:100 inter_token_latency:
  3.40'`，key:value 列表可多个约束；
- GPU 遥测全家桶：同机 DCGM exporter 自动采样 power、SM util、显存、时
  钟、throttle 时长。

AIPerf（ai-dynamo/aiperf，2025–2026）新增的考点：

- benchmark 模式五档：concurrency / request-rate / 双控 / trace-replay /
  **adaptive-scale（单次运行内自动发现 SLA 边界并维持，AIPerf README，
  2026）；** 另有 Bayesian 搜参；
- 到达模式三选：constant / poisson / gamma；warmup 阶段、multi-run
  confidence intervals、timeslice 分片指标（看漂移）；
- 姊妹指标 **good_request_fraction = good_count / (request_count +
  error_count)，分母故意含错误请求（AIPerf goodput 教程，2026）。** ——
  压测中 429/超时也算未达 SLO，不能靠抛负载刷出高分；CI 用法是 grep
  JSON 判 frac ≥ 0.99 给退出码；
- 搜索配方 `max-goodput-under-slo`：以 good_request_fraction ≥
  attainment 门限为可行域，Bayesian 优化 goodput；
- 已知坑：`--output-tokens-mean` 不保证（同 genai-perf）；高并发 >15k
  可能端口耗尽。

### 2.5 GuideLLM：SLO-aware 扫参平台

一句话定位：「其他工具压的是 endpoint，GuideLLM 压的是 LLM」——TTFT/ITL
全分布 + token 级统计是卖点（GuideLLM README，2026）。

- profile 六种：synchronous / concurrent / throughput / constant /
  poisson / sweep（自动扫梯度找最大性能与最大安全 rate）；
- 工程细节可背：并发模式 warmup/cooldown 支持按百分比剔除
  （`streams=16, warmup=0.1, cooldown=0.1`）；constraint 支持
  max_duration / max_requests / max_errors / **over_saturation 判停**——
  饱和检测，曲线不要再往上扫；
- 数据集：HuggingFace 直接拉、synthetic_text（定长 in/out）、trace 回放
  （Mooncake/Weka/OTEL）、合成图像/视频给 VLM；
- README 内置与 inference-perf（k8s-sigs）、genai-bench（sgl-project）、
  llmperf（ray）的对比表，选型面试可直接引用。

### 2.6 k6 / Locust：open vs closed 这个框架必须会

k6 官方文档把负载模型分两类（一手概念，讲「泊松 vs 恒定并发」必须引）：

- **closed model**（constant-vus / Locust 固定用户数）：下一次迭代等上一
  次完成才开始——**到达率被响应时间绑架**：服务端越慢，压测器自动「轻载」，
  看起来 p99 还行，实际是请求的排队被压测器藏掉了，这就是
  **coordinated omission（协同遗漏，k6 Open vs Closed 文档，2026）。**
- **open model**（constant-arrival-rate / ramping-arrival-rate）：到达率
  与响应时间解耦，配 preAllocatedVUs 兜底。

答法：测 LLM serving **默认用 open model**（泊松到达 × 目标 RPS）；
closed 恒定并发只用来测「打满态」吞吐上限，不做延迟结论依据。vLLM 的
`--request-rate=inf + --max-concurrency` 本质就是 closed 打满态；有限
rate + burstiness=1 就是 open 泊松——两类模型在一个工具里实现了统一。

k6/Locust 本身不懂流式 token 指标：要么写 SSE 解析算 TTFT/ITL，要么在
引擎侧埋 OpenTelemetry。所以工程分工是：**延迟分布交给 LLM 专用客户端
（vllm bench / AIPerf），k6 只验证网关背压、限流与全链路。**

## 三、指标口径分叉：同名不同公式

> 核心金句（vLLM 文档原文忠告可引用）：**指标名跨压测工具不标准，比较
> 结果必须比测量点与公式，不能只比名字（vLLM Benchmark 文档，2026）。**

### 3.1 三个延迟族，ITL 有两派公式

- **TTFT**：发送请求到收到第一个流式输出。三家口径基本一致，但注意
  Reasoning 时代的坑：vLLM openai-responses backend 下 reasoning delta
  会被算进 TTFT——不给 `include_reasoning:false`，整个推理阶段被吸收
  进 TTFT，数字直接没法看。
- **ITL（Inter-token latency）**：相邻流式输出事件之间的时间差，逐样本
  聚合。两派公式**不可互比**：
  - **vLLM 口径**：按「流式输出事件」记 gap；投机解码下一个事件带多个
    token，**同 event 内的 token 不产生 ITL 样本（vLLM 文档，2026）。**
    所以 spec-decoding 开启时 ITL ≠ TPOT；
  - **genai-perf 口径**：相邻 response 间隔**除以该 response 内生成的
    token 数**——同事件多 token 会被摊薄，系统性偏小。
- **TPOT**：per-request 定义 TPOT = (E2E − TTFT) / (输出 token 数 − 1)，
  再请求级聚合。标准解码（每 event 一 token）下 ITL ≈ TPOT；spec
  decoding 下分叉——vLLM 文档给了具体算例：两个 ITL 样本各 40ms，均值
  40ms；TPOT = (180 − 100) / (5 − 1) = **20 ms/token，两者相差一倍
  （vLLM 文档算例，2026）。**

面试答法：先声明引擎与解码方式，再报数。被问「为什么两份报告 ITL 对不
上」，就是这两派公式。

### 3.2 吞吐族与 goodput：比率口径才防刷分

- Output token throughput（tok/s，全局输出 token / 总时长）vs Output
  token throughput per user（tok/s/user，剥掉 TTFT 后的 decode 速率，即
  interactivity）。SemiAnalysis InferenceMAX 的 Pareto 图横轴就是后者；
- Request throughput（req/s）；
- **goodput**：满足声明 SLO 约束的请求/s。必须声明约束集才有意义——
  AIPerf 的完整口径是同时给 Goodput(req/s) 和 good_request_fraction，
  **分母含错误请求，被服务甩掉的负载也算没达标（AIPerf 教程，2026）。**

与 SLO 运营文档的衔接：那边说「goodput 必须声明 SLO」，这边补「分母要
含错误」——两条合起来才是 2026 的完整口径。

### 3.3 EOS 与采样参数的暗坑

- OSL 不可控：vLLM synthetic random 与 genai-perf output-tokens-mean 都
  只能逼近；真要定长输出需 `--ignore-eos` 或 `min_tokens`（两家文档明
  写）。**用定长 OSL 压出的吞吐是上限，不是真实生产值。**
- SGLang 反向坑：真实 prompt 回放要 `--disable-ignore-eos`，否则 decode
  越过 EOS 往垃圾分布偏移（§2.3）。
- 采样参数（temperature / top-p / top-k）影响输出长度分布 → 压测报告必
  须记录；vllm bench serve 显式支持透传。
- prefix cache：所有引擎 KPI 里最大的「隐性作弊变量」，vLLM 官网给到
  Warning 级。

## 四、负载建模：让流量长得像生产

### 4.1 到达过程选型表

| 模式 | 参数实现 | 场景 | 注意 |
|---|---|---|---|
| closed 恒定并发 | vllm rate=inf + `--max-concurrency`；k6 constant-vus | 打满态、吞吐上限 | 受协同遗漏影响，延迟数据本身失真 |
| open 泊松 | vllm `--request-rate R --burstiness 1.0`；GuideLLM poisson；k6 arrival-rate | SLO 验证、容量规划 | Little's law 连接 R 与并发分布 |
| open gamma 突发 | vllm burstiness 0.1–0.5（CV 3.16–1.4） | 韧性与 429 测试 | 验证限流与降级链路 |
| open 均匀 | burstiness 2–5 | 延迟 profiling | 排除到达抖动看引擎内 delay |
| ramp-up | vllm linear/exp ramp；GuideLLM sweep | 找最大 goodput / knee 横坐标 | 每档需要独立稳态窗 |
| 时变/正弦 | Dynamo sin_load_generator → AIPerf payload | 削峰、autoscale 联动 | 需引擎侧同步采样水位 |

时变负载的一手实现：Dynamo 的 sin_load_generator 生成
`request_rate(t) = (min+max)/2 + (max−min)/2 · sin(2π/period · t − π/2)`
——相位移让 t=0 从谷值起步；ISL/OSL 双预设组合也可正弦扫比率（Dynamo
sin_load_generator README，2026）。输出 Mooncake jsonl 格式，三家客户端
都能回放。

### 4.2 ShareGPT 口径：建立量级直觉，不当规划依据

- **ShareGPT 分布的祖宗**：vLLM 论文（SOSP'23）用 ShareGPT（约 53k 条
  清洗后会话）+ Orca 作负载，ShareGPT 请求**平均输入 ≈161 token、平均
  输出 ≈338 token，输出为重尾分布（vLLM SOSP'23，2023）；**在 LLaMA-7B
  + A10G 上吞吐相对 HF Transformers 最高 **24×（vLLM 原始博客，2023-06）。**
  今天绝大多数引擎博客仍把 ShareGPT 当「参考会话分布」。
- 分布对结果的影响（可直接背的结论链）：
  1. ISL 拉高 → TTFT 拉长（prefill 时长 ∝ prompt 长度，prefix 命中率折
     减），KV 需求按 ISL 线性涨 → 同 QPS 下 batch 变小、吞吐降；
  2. OSL 拉高 → 请求滞留时间 ∝ OSL（Little：并发 = R × duration），KV
     占用时间拉长，打满态下吞吐按 OSL 反比缩；
  3. 重尾输出使 p99 E2E 与 mean 差一个量级 → **压测必报尾部分位**；
  4. 双峰画像（长输入短输出的 RAG + 短输入长输出的 chat 混合）不能用单
     一 ShareGPT 代表——要么按 bucket 分别扫（vLLM random-mm bucket 思
     想），要么拿生产 trace 回放。
- 生产 trace 已是 2025–2026 一线做法：Mooncake 的 conversation_trace
  （kvcache-ai 发布，FAST'25 格式）被 genai-perf / AIPerf / GuideLLM /
  vllm timed_trace 四家支持回放；另有 BurstGPT（突发流量真实 trace）、
  SageMaker capture 回放、AIPerf 的 Bailian trace。

结论金句：**ShareGPT 的历史价值是建立量级直觉（数百 token 输入），容量
规划请永远对着自己的流量画像，不要用 ShareGPT 的均值凑数。**

### 4.3 温机与稳态判据：防「压测无效」的第二条命门

温机三件事，每一条都有工具实现：

1. 引擎侧 CUDA graph capture / kernel autotune（vLLM FlashInfer autotune
   要在启动后首次压测请求前跑完）；
2. prefix cache 与 KV 池冷启动；
3. 客户端连接池 / HTTP keep-alive 预热。

工具对应：genai-perf `--warmup-request-count`、AIPerf warmup phase、
GuideLLM warmup=0.1（按 profile 的 10% 剔除）、vllm bench sweep 在 run
间重置缓存。

稳态判定三条一手口径：

- SGLang：num-prompts ≥ 5 × max-concurrency（§2.3）；
- perf-analyzer / genai-perf：最近 3 个 measurement-window 的 infer/s 与
  延迟的 max/min 比值 ≤ stability-percentage（默认 999% 几乎不关，正式
  压测设 5–10%）；
- AIPerf：分 timeslice 看吞吐/延迟随时间漂移 + multi-run confidence
  intervals 看 run 间方差。

**样本量**：长尾分布下 p99 需要 N ≫ 1000——100 条请求的 p99 就是第 99
条，噪声极大；5× 并发只是下限，出 p99 结论建议 ≥5k 条或扫多 run。

### 4.4 压测报告元信息清单（面试一口气报完即高分）

数据集全集名 + 随机种子、ignore_eos 与否、采样参数、并发/rate 档位、每
档时长、warmup 剔除方式、prefix hit rate、引擎版本与启动参数。这份清单
的每一项都对应一个已知的「压测造假/失真」方式，缺一项就留一个质疑口。

## 五、容量公式链：从 QPS 到卡数

> 目标：面试官问「线上要扛 X QPS，给多少卡」，你 3 分钟内写出整条推导
> 链 + 申明每条假设。与 SLO 运营文档互补：那边拆预算，这边算卡数。

### 5.1 五步推导链（面试版）

1. **声明画像**：ISL/OSL 分布（均值 + 尾部分位）、峰谷系数、prefix 命
   中率、调用结构。缺画像不估价。
2. **单实例上限测出来**：对目标模型 + 并行方式，跑并发/rate 梯度扫描
   （vllm bench serve 扫档或 GuideLLM sweep），以 SLO（TTFT p99 / TPOT
   p99）为门限，取满足 SLO 的最大 goodput = 一实例的可持续容量。
3. **QPS → 并发（Little's law）**：L = λ × W，W = TTFT + OSL × TPOT。
   例：RAG 画像 ISL=2000 / OSL=300，W ≈ 0.8s + 300 × 0.03s ≈ 9.8s，
   20 QPS → 平均并发 ≈ 196，峰值按 1.5–2× 放大到 ~300–400 并发。
4. **并发 → KV 需求 → 卡数**：每请求 KV 字节 = 2 × n_layer × d_kv ×
   精度字节 × (ISL + OSL)。以 Llama-3.1-70B 为例（80 层、GQA 8KV 头
   ×128 dim = 1024 kv_dim、BF16）：2 × 80 × 1024 × 2B ≈ **0.33 MB/
   token；ISL+OSL=2300 token → 每请求 ≈0.75 GB，300 并发 ≈225 GB KV
   （显存计算口径，2026）。** 单 H200 141GB 权重 TP4 后每卡剩 ~90GB 可
   用 KV → 理论并发上限约 480——**但钉死并发上限的是 goodput 扫描里的
   knee，不是 KV 理论容量**（见 §5.3）。低于理论值就按 headroom 扩容。
5. **实例数 = ⌈峰值并发 ÷ 单实例 SLO 内并发⌉ × 峰值系数 1.5–2×**，
   系数的三个来源见 §5.4。

### 5.2 PD 配比：速率平衡，没有常数比

直觉锚（SGLang 96×H100 DeepSeek 复刻博客，2025-05，2000-token 输入场
景）：prefill 4 节点 EP32 vs decode 9 节点 EP72，prefill 每节点 5.03–
5.77 万 input tok/s，decode 每节点 2.23 万 output tok/s。配比跟着**需求
两侧的 tok/s 速率比**走：

```
N_p : N_d ≈ (R × ISL ÷ 单 P 节点吞吐) : (R × OSL ÷ 单 D 节点吞吐)
```

对上例：ISL:OSL = 2000:100，输入速率大 20 倍，但 P 节点吞吐只大 ~2.3 倍
→ P 侧反而要多配。DeepSeek 官方部署表（同 blog 附录引用）在 kv_len≈5k
时 decode 用了 16–18 节点，印证「decode 吃显存吃 batch、prefill 吃算力」
的资源直觉随画像漂移。

工程经验两条：① ISL 重（RAG/Agent）→ P 侧加保险，TTFT p99 服从 P 排队；
② OSL 重（reasoning/长链）→ D 侧受限，TPOT 服从 D 的 batch 上限。配比要
按画像赛季性重调，所以编排件（Dynamo / llm-d 一类）把配比做成可热改参
数。

「什么比例优」的面试答法：**没有一个常数比。正确答案是按画像做速率平衡
——prefill 池与 decode 池的 tok/s 留出同量级 headroom，D 侧以 TPOT SLO
的 knee 为上限、P 侧以 TTFT 排队预算为上限。** DistServe（OSDI'24）的
goodput 收益 **7.4×（推理调度专题已展开）** 就是「情绪化配比」的反例来
源，本篇不重复推导。

### 5.3 vLLM 官方口径：KV 理论上限 vs knee 实际上限

vLLM 启动日志直接打印两个数（vLLM Benchmark CLI 文档，2026）：

```
GPU KV cache size: 15,728,640 tokens
Maximum concurrency for 8,192 tokens per request: 1920
```

关系式 `max_concurrency = kv_cache_size / max_model_len`。官方建议：
Capacity Planning 把 `--max-concurrency` 设到报告最大值的 **80–90%；**
SLA Validation 时报告的最大值就是 SLA 限。但注意这是 **KV 装得下的理论
并发限**——真正的上限在 §6 的 knee：SLO 约束下 goodput 开始跌的那一档
并发，通常远低于理论值。**理论上限看显存，实际上限看 knee，两者都要报。**

### 5.4 headroom 1.5–2× 的量化来源

面试被追问「为什么是 1.5–2 倍，拍脑袋吗」，给全三个理由：

1. **泊松到达 + 重尾 OSL** 的稳态并发本身有涨落，p99 峰谷比经验 1.5+；
2. 日常要滚动升级 / N−1 冗余；
3. KV 冲突、慢节点、压测与生产的图偏移各打 10–20%。

与 SLO 运营文档的运维水位 **ρ ≤ 60%（即 1/1.67 ≈ 0.6）互相印证**——两
个独立出处收敛到同一个数字区间，这就是 headroom 口径敢写进文档的原因。

成本侧的商业锚：容量规划的成果以 tok/$ 交付——SGLang 自部署 DeepSeek 合
**$0.20/1M output tokens，约为官方 Chat API 的 1/5（SGLang 博客，
2025-05）。**

## 六、曲线解读：knee、Pareto 与上限信号

### 6.1 吞吐–延迟曲线三段式

标准图形：横轴并发（或 QPS），纵轴吞吐；第二条曲线画 p99 TTFT/TPOT。
三段式：

1. **线性区**：batch 未打满，吞吐近线性、延迟平；
2. **knee**：KV 读取 / 调度开销开始非线性，goodput 收益递减——knee 的
   roofline 推导（step 时间 = 权重摊销 + KV 读取，B≈32 弯平）已写在
   SLO 运营文档，本篇补**扫法**：并发梯度 1→2→4→…→2^n，每档收
   p50/p90/p99，**knee = TPOT p99 超过 SLO 线的前一档并发**；
3. **崩溃区**：排队爆炸、p99 陡崖、吞吐不再涨甚至降——SLO 合格的
   goodput 已开始跌。

**Per-user vs per-GPU Pareto frontier**（SemiAnalysis InferenceMAX 方法
论核心，2025-10）：横轴 interactivity（tok/s/user），纵轴 tok/s/GPU，
同一引擎扫并发就是画这条 frontier。比较两组配置（Hopper vs Blackwell）
的正当方式是比 frontier 而不是比单点——**官方话术锚就是「单点
benchmark 是撒谎」（InferenceMAX 方法论，2025-10）。**

配套的三场景 ISL/OSL 格子可以直接搬作己方「压测标准画像」：**三组
1K/1K（chat）、1K/8K（reasoning）、8K/1K（summarization）（InferenceMAX，
2025-10）。**

### 6.2 已达上限的六个信号

| 信号 | 语义 | 对策锚 |
|---|---|---|
| GPU KV cache usage ≈ 上限，调度器无法 admission | 显存/KV 约束先撞墙 | KV 量化降档 / 降 max_model_len / offload，或扩容 |
| 排队请求数持续 >0 且 TTFT p99 阶梯状抬 | 到达率 > 服务能力（M/M/1 爆炸） | 限流 429 + 扩容 / 分流长 prompt |
| decode batch 恒定上限、SM util 高、TPOT 平 | 已达稳定 knee，健康上限 | 不要硬加并发，走扩容（EP/DP 维度） |
| SM util 不满但 TPOT 在涨 | 通信 / CPU 开销 / 调度瓶颈 | async-scheduling、TBO/DBO、查调度器 |
| KV utilization 高但 TTFT 跌不动 | prefix 命中太低或前缀异质 | 前缀亲和路由、KV 复用 |
| power/thermal throttle、nvlink CRC 增长 | 硬件层到顶 | 降频排查、换 SKU |

一句话答题：**打满看 KV 占用与 SM 利用率哪个先到顶——KV 先满是容量瓶
颈、SM 先满是算力瓶颈、两者都不满但延迟涨是调度或通信瓶颈。** 工具出处：
genai-perf 的 DCGM 遥测（功耗、SM、显存、时钟、throttle 时长）自动记录。

### 6.3 batch 打满与 MoE/EP 特例

- decode batch 打满（max_num_seqs）后吞吐平台化、延迟直线恶化——vLLM
  打满态测法 `--request-rate=inf --max-concurrency=<limit>` 是官方钦定。
- **MoE/EP 特例——「expert 不均衡」本身就是上限信号**：SGLang 实测
  EPLB on/off，大规模下 prefill **1.49×**、decode **2.54×** 吞吐差
  （SGLang 博客，2025-05）；balancedness（平均/最大 token 数比）与吞吐
  强相关。vLLM 的 EPLB 三旋钮：window size / rebalance interval / 冗余
  专家数。
- TBO/DBO 的批次符号反转：prefill +27–35%（SGLang，16k token/device，
  native 8k OOM 封顶），decode 在 batch 64–128 以下收益为负甚至 −27%
  ——**同一个优化在不同 batch 段符号不同，是曲线解读最容易踩的地雷
  （SGLang 博客，2025-05）。**

## 八、▶ 面试题

**Q1【高】让你给线上模型设计一次压测，怎么做？**
五步口述：① 画像先行——从生产日志统计 ISL/OSL 直方图（双峰打散成
bucket）、QPS 日曲线、prefix 命中率，没有生产数据就用 ShareGPT 量级 +
InferenceMAX 1K/1K、1K/8K、8K/1K 三格子兜底；② 选工具——引擎内对比
SGLang bench_offline，在线 SLO 用 vllm bench serve（泊松 burstiness=1）
或 AIPerf，找 SLA 边界 GuideLLM sweep / adaptive-scale，全链路 k6
arrival-rate，并说明 closed model 协同遗漏为什么不取；③ 扫曲线——并发
梯度 × 三画像格子，每档 ≥5× 并发请求量 + warmup 剔除，报 p50/p90/p99
TTFT/TPOT + 声明 SLO 的 goodput，扫到 over-saturation 为止；④ 盯三个上
限信号——KV usage、SM util/throttle、队列长度；⑤ 交付容量结论——单实
例 SLO 内 goodput 与 knee、实例数（Little's law + 1.5–2× headroom 拆分
理由）、PD 配比理由、回测频率（引擎升级即重扫）。（§二、§四、§五）

**Q2【高】100 QPS 需要多少卡？**
当场推 §5.1 五步链：声明画像 → Little's law 求并发（W = TTFT + OSL ×
TPOT）→ 单请求 KV 字节 × 并发求 KV 需求 → 用压测 knee（而非 KV 理论容
量）定单实例并发 → 实例数 × 峰值系数。收尾补一句：公式链每一步都要落
到可观测——并发由队列长度验证、KV 由引擎 usage 指标验证、goodput 由
p99 SLO 验证。（§5.1）

**Q3【高】为什么压测报告吞吐很高，上线就炸？**
四个经典失真：① prefix cache 污染（同服重复压命中缓存，vLLM 官方
Warning 级）；② 定长 OSL 上限失真（ignore_eos 压出的是上限不是生产值）；
③ closed model 协同遗漏（服务端越慢压测越轻，p99 假好）；④ 没打画像
双峰（单一 ShareGPT 代表不了长输入 RAG + 长输出 chat 的混合）。每个给
修复：sweep 重置缓存 / 真实分布或 trace 回放 / open model / bucket 分扫。
（§2.2、§3.3、§2.6、§4.2）

**Q4【中】ITL 和 TPOT 有什么区别？为什么两份报告对不上？**
TPOT 是 per-request 公式 (E2E − TTFT)/(输出 token − 1)；ITL 是事件间
gap 的逐样本聚合。标准解码下两者近似；投机解码下分叉且两派 ITL 公式
不同：vLLM 按事件记 gap（同事件多 token 不出样本），genai-perf 把间隔
除以该 response 的 token 数（摊薄）。vLLM 官方算例下两者差一倍。答法：
先声明引擎与解码方式再报数。（§3.1）

**Q5【中】k6 能不能直接压 LLM？**
能压 HTTP 但不懂 token 指标：要么自己解析 SSE 统计 TTFT/ITL，要么引擎
侧 OpenTelemetry。一般做法：延迟分布交给 LLM 专用客户端，k6 只验证网
关背压、限流与全链路（鉴权、日志链路）。（§2.6）

**Q6【中】TTFT p90 稳、p99 炸，怎么排查？**
长尾 ISL 撞大 prefill 的排队雪崩：长 prompt 到达在小瞬间挤占 prefill，
队首阻塞传导成全队列 TTFT 阶梯抬升。对策：prefix cache / 长 prompt 分
流 / PD 分离（TTFT 排队预算挪给 P 池）。验证：看排队请求数与 TTFT p99
是否阶梯状相关（§6.2 信号表第二行）。（§6.2）

**Q7【中】SM util 才 60%，机器还有余量吗？**
不一定：调度器 / CPU 开销 / 通信都可能先行到顶。正确证实方式是扫并发
曲线看 knee，不是看利用率——**60% 利用率但 TPOT 已涨，就是调度或通信
瓶颈**（查 async-scheduling、TBO/DBO）。工具锚：genai-perf DCGM 遥测 +
vllm bench 梯度扫描。（§6.2）

**Q8【中】PD 分离里 prefill 和 decode 节点按什么比例配？**
没有常数比，按需求两侧 tok/s 速率平衡：N_p : N_d ≈ (R×ISL ÷ 单 P 吞吐)
: (R×OSL ÷ 单 D 吞吐)。SGLang 96×H100 实测 2000-token 输入是 P4:D9，
官方在 kv_len≈5k 时 D 用到 16–18 节点——配比随画像漂移，要按赛季重调
并做成可热改参数。ISL 重保 P（TTFT 服从 P 排队），OSL 重保 D（TPOT 服
从 D 的 batch 上限）。（§5.2）

**Q9【中】headroom 留 1.5–2 倍是拍脑袋吗？**
三个可辩护来源：泊松 + 重尾 OSL 的并发涨落（p99 峰谷比经验 1.5+）、滚
动升级与 N−1、KV 冲突 / 慢节点 / 压测-生产图偏移各 10–20%；且与运维水
位 ρ ≤ 60%（1/1.67 ≈ 0.6）独立互证。（§5.4）

**Q10【低】genai-perf 和 AIPerf 现在（2026）是什么关系？**
genai-perf 官方宣布停止新特性开发，新项目迁移 AIPerf（ai-dynamo/
aiperf）；指标口径（TTFT/ITL/ISL/OSL、output-tokens-mean 的不可控坑、
warmup 与 stability 判据）被继承，AIPerf 新增 adaptive-scal、Bayesian
搜参、good_request_fraction（分母含错误）与 timeslice 漂移观测。答 2026
口径要会主动说「genai-perf 已退役」。（§2.4）
