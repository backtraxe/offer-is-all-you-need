## 一、主线：调度器从「排队员」变成「分配者」

单租户时代的推理引擎很好写：FCFS 排队，先到先服务，大家攒满 batch 就发车。
**FCFS 的单租户引擎是理想世界**——因为不存在「服务谁、亏待谁、向谁收费」
的问题。多个租户共用一台引擎之后，答案全部变了：

1. **谁优先**——两个租户同时打进来，batch 只剩一个位，先放谁？（隔离与
   调度问题）
2. **谁欠账**——一个租户白天刷爆队列，晚上空着；另一个租户稳定的低流量
   被挤得 TPOT 劣化。「平均下来大家都够」的说辞在 p99 面前不成立。
   （公平问题）
3. **谁付钱**——同跑一次 32K prompt，A 的命中 prefix cache、B 的没有，
   TTFT 差十倍，账单按什么记？（归因问题）

还有一个省钱的第四个问题：**什么时候让离线 batch 进来填谷**——在线利用率
通常 30–60%，低谷期的闲置 GPU 秒是纯浪费，把「可等待」的负载填进去，
$/token 直接腰斩。2024–2026 年公有云把这件事商品化成 API 上的 tier 档：
Batch/Flex 减五成，Priority 加七成五到两倍——填谷权本身成了可买卖的商品。

## 二、多租户隔离：四层栈，每层一个落点

### 2.1 隔离的四个层次

面试先铺框架再进细节。多租户隔离不是单点特性，是**四层栈**：

| 层 | 机制 | 落点 |
|---|---|---|
| 准入层 | API key 认证、quota、rate limit（RPM/TPM/并发） | 网关（LiteLLM proxy、Kong、自研 gateway） |
| 排队层 | 优先级队列、公平队列、抢占 | 引擎调度器（vLLM --scheduling-policy priority、VTC） |
| 执行层 | batch 混合编排（prefill/decode 互相干扰的治理） | 引擎（chunked prefill、连续 prefill 上限） |
| 状态层 | KV cache / prefix cache 的共享与隔离 | 引擎 cache（cache_salt、per-tenant namespace） |

硬隔离的极端形态是物理切分：每租户独占实例 / MIG 切片 / MPS 时间片，成本上
等于放弃共享红利，所以生产主流是「共享引擎＋软隔离」。本篇全部建立在软隔离
基础上——硬切分只在「给一个金主租户保底」这种红线场景上桌。

### 2.2 准入层：quota/rate limit 是企业私有化的事实标准

参照系是 LiteLLM proxy 的 virtual keys 体系
（docs.litellm.ai/docs/proxy/virtual_keys，2026-10 版）：

- 每把 key 可挂：models 白名单、rpm_limit、tpm_limit、max_parallel_requests、
  max_budget＋budget_duration、expires。
- **分层继承**：key ← user ← team，key 继承 owner 的 tpm/rpm/max_budget；
  服务账号 key（user_id=null）只挂 team 限额。
- 管理默认值双保险：default_key_generate_params 填默认值，
  upperbound_key_generate_params 设上界——超上界的申请直接 400，**不做
  clamp**（不是悄悄压平，是明确打回）。
- spend 追踪落到三张 Postgres 表：key/user/team 的 spend 随每次
  completion_cost() 累计，USD 口径。

有个条款值得单独记：**overwrite_user_with_key_hash 把转给上游的 user 字段
强制写成 key 的 sha256——计费归因在多级代理下只认 key，不认请求体里用户自
填的身份。** 这防的是「租户伪造 end-user 身份把成本转嫁给别人」，多级代理
链上每一跳都可能改写 user，只有 key 是转不过去的锚。

### 2.3 RPM 限流的代价：work-conserving 丢了

rate limit 看着是隔离的万能药，实测不是。VTC 论文（arXiv 2401.00588）§1 的
真实轨迹实验（Llama-2-13B/A100）给出了硬数字：按 RPM(5) 把空头客户限死，
**集群聚合吞吐只有 ≈340 输出 tok/s，而同负载下 VTC/FCFS 能到 ≈779 tok/s**
——RPM 限流不是 work-conserving，限死的租户占着配额不动，剩下的配额也不
会拨给别人。

再往细里看（同一组实验）：限速越严集群吞吐越低，从 RPM(5) 的 ≈340 tok/s
升到 RPM(30) 的 ≈747 tok/s，但 RPM(30) 的响应时间曲线已基本收敛到 FCFS——
公平收益也消失了。**限速旋钮上公平和效率是同一条曲线的两端，不存在无成本
的甜点。** 所以 rate limit 是准入层兜底（防刷爆、挡账单事故），不能当
调度器用——公平是第三节的事。

### 2.4 vLLM 优先级调度：2024→2026 一手 PR 时间线

vLLM 的 priority scheduling 是「单引擎多租户」在开源栈里的第一个一等公民
能力。时间线全部可在 GitHub vllm-project/vllm 查到：

- **PR #5958**「[Core] Adding Priority Scheduling」开于 2024-06-28，合入
  2024-09-25（V0 引擎）。
- PR #8850（2024-09-27）把优先级带进 async engine；PR #8965（2024-10-01）
  把 priority 参数暴露到 OpenAI API（请求体的 priority 字段）与 embedding。
- **PR #19057「[Core] feat: Implement Priority Scheduling in V1 Engine」
  合入 2025-06-23**——V1 引擎全面支持优先级，这是「2025 落地」的锚点。
- 语义：`--scheduling-policy={fcfs,priority}`；priority 为整数，数值越小越
  优先，同优先级内 FCFS。
- 加固链（2025–2026 密集修补）：#20608「aging factor」（2025-07，优先级
  ＋等待时长混合加权，防久等请求饥饿）；#23713 修 V1 priority preemption
  崩溃（2025-08）；#40087（2026-04）/#54530（2026-08）支持 **waiting 队列
  中的高优先级请求在 max_num_seqs 占满时抢占 running 中的低优先级请求**；
  #47837「Priority-aware KV cache eviction」（2026-07）——KV block 淘汰
  也看优先级；#58078（2026-09 进行中）给 finished-request metrics 打
  priority bucket 标签，按 tier 拆 latency/throughput 观测。

这条时间线本身就能答「vLLM priority 成熟了吗」：核心 2025-06 落地，但抢占
语义、KV 淘汰策略、观测三件套到 2026 年还在密集修——**生产用需要版本锁
与自测，不是开个 flag 就完事。**

还有一个工程语义要拿好：V1 的抢占只有 recompute 模式（丢 KV、回队重算），
不像 V0 有 swap。被抢请求的已算 prefill/decode 全部作废——这是「幽灵成本」
（GPU 秒花了但没有 token 发给用户）的来源，第四节计费时还会回来碰它。

### 2.5 执行层与状态层：噪声邻居与 cache_salt

**噪声邻居的三种形态**：① prefill 打爆 decode——一条 32K 长 prompt 的
prefill 抢占大量 step 时间，同引擎所有 decode 的 TPOT 集体劣化；治理是
chunked prefill（vLLM 的 max_num_batched_tokens 封顶单步 prefill token 量），
SGLang 2026 主线仍在发射同类 PR：#34058「scheduler: bound consecutive
prefills to protect decode」（2026-08）限制连续 prefill 步数，#31395
「Interleave decode passes between mixed prefills」（2026-07）。② quota
刷爆型租户——单一客户端高 RPM 压垮共享队列，VTC 论文的 core abuse 场景：
FCFS 下一个激进 client 能把其他 client 的响应时间拉长数倍。③ KV 占位型
租户——长上下文请求占满 KV block，触发对其他租户的抢占（recompute）。

prefix cache 在多租户下有两副面孔：

- **共享红利**：RadixAttention（SGLang，arXiv 2312.07104）把 KV 复用从
  「同请求内」提到「跨请求同前缀」，agent/多轮/少样本场景 SGLang 报告吞吐
  最高 6.4× 提升。但全局共享意味着**一个大租户的高复用 prefix 会帮自己
  省钱省时延，也会挤占别人的 KV 空间**——cache 既是红利也是噪声通道。
- **安全隔离**：vLLM PR #17045「[Core] Prevent side-channel attacks via
  cache salting」（2025-04-23）引入 cache_salt——prefix block 的 hash 掺入
  租户提供或平台注入的 salt，跨租户内容相同也不命中同一块 cache。动机是
  侧信道：多租户环境下「你的请求 TTFT 突然变快」可以反推「有别人发过
  逐字节相同的前缀」。#20981（2025-07）随后扩展到 /v1/completions 与
  /v1/responses。

面试加分句记好：**prefix cache 默认共享语义在多租户场域不是性能问题而是
安全漏洞，cache_salt 把它从偶发越权复用改成显式命名空间。** 附带第三副
面孔是计费耦合：命中 token 与未命中 token 必须按租户分开计量（DeepSeek
API 的 usage 就返回 prompt_cache_hit_tokens / prompt_cache_miss_tokens
两字段，命中价与未命中价分档）——这是归因管线的必需维度，第四节详说。

## 三、公平调度：RPM 不是答案，VTC 是理论锚

### 3.1 为什么经典公平算法搬不过来

经典网络队列调度（DRR/CFS 一支）假设的是包交换世界。LLM serving 换了三处
博弈结构（均出自 VTC 论文 §2.3 的论证）：

1. **作业长度未知**——输出 token 数事先不可知。DRR 的决定式是「本轮
   quantum＋历史 deficit ≥ 包长」才放行；LLM 里「包长」是个变量，DRR 没法
   判断一个请求该不该被本轮排进去。
2. **成本非线性**——一个 token 一份成本，不成立。decode 是
   memory-bandwidth-bound，prefill 是 compute-bound；论文 profiled 数据：
   同等 token 总量下，纯输出场景的 decode 时间是纯输入场景 prefill 时间的
   2–5 倍。**按 token 数 1:1 记账会系统性亏待长输出租户。**
3. **batch 耦合**——请求不是独占资源而是共享 batch：服务 A 的同时也在服
   务 B，经典「分时独占」模型直接失效。

### 3.2 max-min 公平：什么叫「公平的调度」

论文给公平下的标准是经典 max-min：n 个活跃客户端共享引擎，每个至少拿到
1/n 份额，空闲容量按需求最小的先满足。一个调度器要算公平，必须同时满足
两条性质：

- **isolation**——受某个过量客户端攻击时，其他 client 的份额不被侵蚀；
- **work-conserving**——有空闲容量就服务，不空耗。

对照读法：RPM 限流有 isolation 没有 work-conserving（340 vs 779 就是代价）；
FCFS 有 work-conserving 没有 isolation（激进租户拖垮众人）。**公平调度要
解的工程动机，是同时在一张调度器里把两条都拿到。**

### 3.3 VTC（Virtual Token Counter）：机制与数字

一手信息源：arXiv 2401.00588（Sheng/Cao/Li 等，SGLang/S-LoRA 团队后续作，
2023-12 v1、2024-06 v2），artifact 仓库 Ying1123/VTC-artifact 构建于
S-LoRA 之上。

机制三行版：

1. 每个 client 维护一个 virtual counter c_i，**以服务成本记账**——每处理
   一个 input token、每生成一个 output token，都按成本函数 h(n_p, n_q)
   累加；主分析用线性成本，附录 B.2 用 profiled 二次成本函数做了泛化验证。
2. 每步组 batch 时，**优先从 counter 最小的 client 挑请求**（min-heap），
   counter 随处理进度更新。新加入 client 给一个 counter lift（吸收旧
   client 的欠债差值），系统重启不清 counter（防止欠债清零失效）。
3. 输出长度未知的解法：请求入队先按预测长度记账，实际生成结束后**多退少
   补**——预言器失准不影响公平解近性（附录 C.1 给出与输出预测挂钩的通
   用形式）。

理论结论可写白板：**两个 backlog 客户端的服务差有 2× 紧上界，且调度保持
work-conserving。** 2× 是严格证明出来的，不是经验值。

实验数字（Llama-2-13B＋A100-80GB，22/27 client 真实轨迹）：

- 高负载下 VTC 的服务差几乎线性回落到 0 附近，FCFS 不退。「一个 client
  滥用」的合成场景里 FCFS 让受害 client 延迟成倍增长，VTC 维持低响应时间。
- 对照 RPM：VTC 吞吐 ≈779 tok/s 与 FCFS 持平——**公平性的吞吐代价约等于
  零**，RPM(5) 只有 ≈340。
- 8 client 压测表 5/表 6：VTC 的 work difference 与 FCFS 拉开数量级差距。

论文给出的等价视角也很妙：附录 C.2 的 adapted DRR 把「包长」换成「预测服
务成本」，预测记账、事后多退少补，deficit 最高的 client 恰是 VTC 里
counter 最小的 client。**简报口径：VTC 可以看成长度未知世界里的
DRR/CFS——min(counter) 选边就是 Linux CFS 的 min(vruntime) 选边**（论文
§4 明言与 CFS 同源）。

### 3.4 落地现状：主流引擎没收编，老老实实说组合拳

重要事实核查（别把论文当 feature）：

- **vLLM 主线没有接入 VTC**，走的是 §2.4 的 priority＋准入层 rate limit 两
  条产品线。VTC 停在「论文＋S-LoRA-based artifact」层。
- **SGLang 主线也没有 per-tenant 公平调度器**（2026-10 检索）：只有 cache
  感知的路由/调度策略（fcfs/lpm/dfs-weight）与 decode 保护类 PR，没有 VTC
  实现在主线。LMDeploy 同样检索不到公平调度主线特性。

论文工程限制（论文自陈）：分布式部署需跨引擎同步 counter——hierarchical
virtual counter 还是 open problem；输出长度预测在长推理任务上失准会削弱
公平性。

2023 年发表到 2026 年主流引擎仍未收编，本身就是面试时间线上值得点名的
现状。正确讲法是：**VTC 是 fair-serving 的理论锚（2× 界、等价 DRR/CFS），
工程落地形态是准入层 rate limit（LiteLLM tpm/rpm/并发）＋排队层 priority
（vLLM --scheduling-policy priority）＋aging 防饥饿的组合拳。**

## 四、成本归因工程：从集群平均到请求级账单

### 4.1 归因总线：每个已完成请求都要落账

finops 篇的 $/M token 是集群平均口径；多租户归因必须落到 per-request 粒度。
最小数据集（一个请求跑完就该有一条账）：

```
tenant_id, key_id, model, endpoint, request_id,
input_tokens, output_tokens, cached_input_tokens, cache_write_tokens,
queue_ms, prefill_ms, decode_ms, ttft_ms, tpot_p50_ms,
gpu_node_id, preempted_count, finish_reason, ts
```

注意最后两行的四个字段：cached/cache_write 记录缓存动的账，preempted_count
记幽灵成本的账。落账位置在**网关不在引擎**——LiteLLM 的 completion_cost()
把每张模型价表查成 USD 累计写回 key/user/team 三张表。可以这么记：每张票
出站时刷卡记账，不是月底估算。OpenRouter 走另一路：响应 usage 字段＋异步
审计端点 /api/v1/generation，按 generation id 事后回追成本，适合审计与
对账。有一个口径细节别放过：**token 计数按上游 native tokenizer、不走归一
化 tokenizer——tokenizer 差异可以是 1%–30% 的账单差异**（OpenRouter API
参考页口径）。多模型路由平台对账的第一现场就是这个。

### 4.2 TTFT/TPOT 与成本结构的映射：output 为什么贵 4–5 倍

价格表是成本结构的影子。一手价锚（2026-10 抓取口径）：

- Claude Opus 4.5：input $5/MTok、output $25/MTok——**5 倍**
  （docs.claude.com/en/docs/about-claude/pricing）。
- OpenAI gpt-6-astra：input $10/MTok、output $50/MTok——**5 倍**；cached
  input $1/MTok——是 input 的 0.1 倍（platform.openai.com/docs/pricing）。

物理解释是可以自己推的（这是面试问的「为什么」）：prefill 是
compute-bound，token 在 batch 内摊薄算力；decode 是
memory-bandwidth-bound，每个 token 都要把全部权重从 HBM 过一遍，batch 摊薄
效率低一个数量级。VTC 的 profile 给出实测锚：**decode 的每 token 时间成本
约为 prefill 的 2–5 倍**，与价表 4–5 倍的价差互相印证。记一句总口径：
**input/output 价差不是定价习惯，是 prefill/decode 算力特性的直接映射。**

TTFT 的映射同理：TTFT 贵的那部分是 prefill 计算；cache 命中把 prefill 变成
查表，所以 cached input 价是 input 价的约 1/10——错位来自成本结构。Anthropic
的 prompt caching 更直给：5-min cache 写收 1.25× input 价、1-h 写收 2×；
读取 0.1×；Opus 5.5/Sonnet 5.5 读 0.05×、Fable/Mythos 5.1 读 0.025×。
写也要收费的逻辑记好：**cache 写发生在 GPU 上（额外算＋KV placement），
写价覆盖的是写入期的算力与存储期 TTL 的机会成本。**

### 4.3 计价 pipeline：model×tenant×endpoint 四层

生产级成本归因管线分四层：

1. **计量层**：引擎按请求返回 usage——input/output/cached 三段分计量，
   OpenAI/Anthropic/DeepSeek 已成事实标准字段。stream 模式要在网关侧补
   token 计数兜底：连接中途断掉的「幽灵 token」引擎可能没记上。
2. **计价层**：价表 = f(model, tier, endpoint, 地域, 特性)。2026-10 观察
   到的一手价格维度矩阵：Anthropic = f（模型，tier：fast 2×/batch 0.5×，
   cache：写 1.25×–2×/读 0.1×，地域：us 1.1×）；OpenAI = f（模型，context
   长短档位，cached 0.1×，flex=batch 价，data-residency＋10%，FedRAMP
   ＋10%）；Bedrock = f（provider/model，tier：Priority＋75%，Flex/Batch
   −50%）。**级联是乘法**——Batch×caching×地域可以一路乘下去。
3. **对账层**：key/user/team 三级 spend 表＋异步审计（OpenRouter
   /api/v1/generation）；多级代理下还有折算率问题——Anthropic Claude
   Platform on AWS 把 token 计费按标准价折成 USD，再以 $0.01/CCU 转换上报
   AWS Marketplace。**计费口径先在 Anthropic 侧定，AWS 账单上只有一个 CCU
   行项目——多级归因的下钻尽头是供应商的折算率。**
4. **展示层**：showback（可见性）/ chargeback（真扣钱），与 finops 篇衔
   接；本篇的增量是「到租户到请求」的粒度，不是组织预算流程。

### 4.4 KV cache 占用怎么计价：这是最容易漏的分项

先算物理账（可白板手推）：Llama-3-70B bf16 每 token KV ≈ 80 层 × 2(K/V)
× 8 KV head × 128 dim × 2B ≈ **328 KB/token**；一个 128K 上下文请求
≈ 42 GB KV。KV 是 time×bytes 的稀缺资源——**GPU 上的第二房租**。业界三
条计价答案：

1. **折算成时间维度**（主流云产品线）：KV 持有不出现在价表，出现在
   TTL＋写价/读价组合——Anthropic 5min/1h 两档、DeepSeek 把 KV 落磁盘只
   按命中 token 分档计价。「命中折扣」就是 KV 租金的商品化形态，租户无感。
2. **折算成算力复用**（推理平台/引擎私有实现）：PD 分离＋外部 KV 池
   （vLLM KV connector、Mooncake 体系；vLLM 2026-05 有 Mooncake Store 集
   成博客）让 KV 在 GPU 间共享，省的是 prefill 算力；是否向租户收费各平
   台自行决定，暂未见到公有云把跨请求 KV 复用单列到账单。
3. **学术定价是开放题**：VTC 的 cost function h(n_p, n_q) 是抽象接口，论
   文明言真实生产的 cost function/pricing model 留未来工作。面试可以反将：
   真实系统里 KV 占用按「排他性字节秒 × 机会成本」计价，近似存在但无人
   透明披露；DeepSeek 的命中折扣是它最接近的商品化形态。

另一个归因冷点拿好：**被抢占请求的幽灵成本归平台不归租户**——用户按
usage 付款，recompute 作废的 GPU 秒在成本中心口径里单开一行。这既是
showback 的干净度，也是比谁多算一步的加分点。

## 五、tier 定价与混部填谷：把「可等待」卖成钱

### 5.1 为什么混部是省一半钱的杠杆

逻辑链：单租户在线推理的利用率通常 30–60%；低谷期的闲置 GPU 秒是纯浪费。
离线 batch 是「任何时候跑都行」的负载——把它填进低谷，利用率拉升，
$/token 直接腰斩。2024–2026 年公有云把这件事商品化成 **tier 制**：把「可
等待」显式写进 API，等于把填谷权从平台卖回给了你（或者说，把「不可等待」
明码标价卖给你）。

### 5.2 tier 制的一手数字锚（2026-10 抓取口径）

| 厂商 | tier | 价格 vs standard | 时延/可用性口径 |
|---|---|---|---|
| OpenAI | Batch API | **50% 折扣** | 24h 窗口内完成；独立更高 rate-limit 池（单批 50K 请求/200MB/2K 批每小时） |
| OpenAI | Flex | 与 Batch 同价 | 同步调用＋更慢时延＋可能 429（429 不计费）；建议超时提到 15 分钟 |
| OpenAI | Priority→Fast | 2026-07-30 改名 Fast mode | 低时延保证（**具体溢价倍数官方价表页未披露，不写数字**） |
| Anthropic | Batch API | **50% 折扣**（输入输出同折） | 异步；可与 prompt caching 乘叠 |
| Anthropic | Fast mode（research preview） | Opus 5.5：$8/$40 vs $4/$20，**溢价 2 倍** | 显著更快输出，不与 Batch 兼容；缓存/地域乘法可叠 |
| AWS Bedrock | Priority | **＋75%** premium vs Standard | 更高优先级 |
| AWS Bedrock | Flex / Batch | **−50%** | 总体同「可延迟」语义；另有第四个 tier Reserved（预留容量，文档仅列名） |
| OpenRouter | :batch 模型变体 | batch 价版独立条目 | 路由语义变体：:nitro 按吞吐排序、:floor 按价格排序、:exacto 工具可靠优先 |

规律可背：「**能等的减五成，急用的加七成五到两倍**」——业界把时延梯度
商品化成 3–4 倍的价带。面试答题句式：**tier 制是 SLO 分层在价表上的投
影：Priority 卖给 SLO 紧的在线，Standard 是主力，Flex/Batch 拿来填谷；一
个 MaaS 的成本结构 = Σ（各 tier 用量占比 × tier 单价），自营＋云桶混合之
后这个公式直接决定混合均价。**

### 5.3 spot 混部：学术上限与工程现实

SpotServe（arXiv 2311.15566，2023-11）回答的是「抢占式实例上怎么稳定
serve」：

- 三大坎：spot 随时被抢＋迁移成本＋并行化重配置。
- 方案三件套：动态 parallelization 适配可用实例数（TP/PP 重配置）；迁移规
  划建成二分图匹配（KM 算法）最小化通信成本；stateful inference recovery
  把推理进度细粒度 commit，借云厂商 grace period（AWS 2 分钟）低成本续算。
- 数字锚：**P99 尾延迟比现有系统降 2.4–9.1 倍；与纯 on-demand 相比省 54%
  成本。** 这是「spot 混部省钱」目前最干净的一手理论上限。

工程现实别吹过头：**spot 适合作业级负载**（离线评测、RL rollout、批量生
成），不适合 p99-SLO 在线链路。生产形态通常是「on-demand 主池＋batch/flex
池填谷＋spot 只承载可重放批次」。OpenAI Flex 的「429 不计费、可重试」就
是这套语义的产品化影子。

### 5.4 自管集群的 SLO 分层混部形态（设计题骨架）

自己管 GPU 时，同一台引擎上落地混部的标准答案：

1. **在线 tier**（chatbot/agent）：独占资源池或 priority=0（vLLM priority
   数值越小越优先），SLO 按 [推理服务slo与运营](./推理服务slo与运营.md)
   的口径盯 TTFT/TPOT p99。
2. **离线 tier**（eval、合成数据、RL rollout、批量摘要）：priority 数值
   挂大，安静吃空闲容量；2026 年的 vLLM 已支持 waiting→running 的优先级
   抢占（PR #40087/#54530），离线请求撞见在线高峰直接让位。
3. **队列衔接**：Batch 语义在网关层实现（作业文件＋24h 窗口＋output/error
   文件），引擎层只是给 batch 请求打低优先级——别在引擎里发明新语义。
4. **可观测**：SLO-burn-rate alert 只盯在线 tier 的 TTFT/TPOT；离线 tier
   只盯吞吐与完成窗口。两条告警链物理分开，否则离线抖动天天误报。

## 六、产品实践：云 MaaS 怎么设计，私有化怎么抄

### 6.1 公有云 MaaS 的 tier 与计费设计（对照表）

- **OpenAI**：五维级联——模型档位、context 长短档位（短/长两档价）、
  cached input（0.1×）、服务 tier（default/flex/priority-fast）、地域
  （data residency＋10%、FedRAMP＋10%）。级联乘法。价表页另有选型信号：
  fine-tuning 平台转向新用户不可入、存量迁移——自建模型池是未来重点。
- **Anthropic**：用法级特性显式计价——prompt caching（5min 写 1.25×/
  1h 写 2×，读 0.1×，新模型 0.025–0.05×）、工具定义 token 按模型费率计
  （sonnet 系主工具 system prompt 约 286–804 tokens/请求，浏览器工具约
  6,600 tokens）、web search $10/1K 次；Batch 与 caching 可叠低至名义
  input 的 0.05×；US 地域 1.1×；rate limit 按 Start/Build/Scale 三档成长
  型 tiers。有一个信号值得单独记——
  **agent 时代的 runtime 也进了价表**：Managed Agents 有 session runtime
  收费 $0.08/小时。
- **Bedrock**：多云代理形态＋tier 四分法（Standard/Flex/Priority/Reserved），
  Flex/Batch −50%、Priority＋75%。核心价值是把多 provider 计费归一到 AWS
  账单（Claude CCU：$0.01/CCU 兑换率＋私有 offer 折扣）。
- **OpenRouter**：不自营算力的纯路由——不涨价（no markup），收费点在购
  额度的 fee；BYOK 免 $25K/月，超出部分 5%（按同模型同 provider 在
  OpenRouter 的正常成本折算）；/api/v1/generation 异步审计＋provider 路由
  变体。给私有化的启示：**MaaS 路由层的计费与路由策略是一体两面，路由
  变体本身就是定价维度。**

### 6.2 私有化多租户的标准三层图

一个可以直接画在白板上的答案（综合 LiteLLM 文档＋vLLM 能力＋K8s 实践）：

```
       [Tenant Apps]
            │ API key
   ┌────────▼────────┐
   │ Gateway 层       │ 认证/授权、per-key rpm·tpm·并发·预算
   │ (LiteLLM/自研)   │ 路由（模型映射/池别名）、计量落账
   └────────┬────────┘
            │ priority·cache_salt·tenant tag
   ┌────────▼────────┐
   │ Engine 层        │ vLLM/SGLang 集群
   │ priority 调度    │ max_num_seqs 语义＋优先级抢占
   │ prefix cache     │ cache_salt 命名空间隔离
   │ prefill 治理     │ chunked prefill 防长 prompt 打爆 decode
   └────────┬────────┘
            │ usage events (input/output/cached)
   ┌────────▼────────┐
   │ Billing 层       │ showback 报表、chargeback、预算熔断
   │ (spend tables)   │ key/user/team 三级聚合
   └─────────────────┘
```

选型三问三答：全开源栈 = 网关 LiteLLM（key/quota/spend）＋引擎 vLLM
（priority/cache_salt）＋Prometheus/Grafana 观测；全买 = OpenRouter 或云
MaaS，代价是计费口径透不出来（真实成本→标价毛利不可审计）；混合 = 核心
模型自部＋长尾/突发走云。**混着用时铁律一条：成本核算跟着 key 走不跟
endpoint 走——网关层的 key↔tenant 映射是所有账的唯一对账基础。**

money 层的私有化细节（从 LiteLLM 提炼）：upperbound_key_generate_params
设默认上限（max_budget 100、budget_duration 10d），防新 key 开出无限预算；
temp_budget_increase＋temp_budget_expiry 支持促销期临时加码；auto rotate
的 grace_period 保证换 key 不停服；end_user 层成本追踪仍在演进（docs 明示
跟 issue 状态）。

## 七、面试题答法清单（按主题）

1. ▶ **多个租户共用一个 LLM 服务，怎么保证互不影响？（高频）**——铺四层
   隔离栈：准入/排队/执行/状态，每层举一个一手机制：LiteLLM key 配额、
   vLLM priority＋aging、chunked prefill、cache_salt。收尾点一句：硬隔离
   （MIG/独占实例）是放弃共享红利的底线方案。
2. ▶ **FCFS 调度有什么坑？公平调度怎么做？（高频，论文型面试官）**——先
   答 RPM 丢 work-conserving（340 vs 779 tok/s 一手数字），引出 max-min
   公平定义（isolation＋work-conserving 双性质），落 VTC：成本函数记账＋
   min counter 选边＋2× 紧上界。诚实交代 VTC 未进主流引擎，生产组合是
   rate limit＋priority＋aging。
3. ▶ **为什么 output token 价格是 input 的 4–5 倍？（高频）**——prefill
   compute-bound/decode bandwidth-bound；VTC profile 2–5 倍实测对账价
   表 4–5 倍；cache 命中把 prefill 变查表，所以 cached input 是 0.1×。
   再补一句 Anthropic 的 cache 写价玄机（写发生在 GPU 上，收写入算力＋
   TTL 机会成本）。
4. ▶ **设计一个私有化 LLM 平台的计费系统。（高频）**——§6.2 三层图＋
   §4.3 四层 pipeline（计量/计价/对账/展示）＋key↔tenant 唯一对账基础；
   强调 usage 三字段（input/output/cached）必须分流落账，stream 模式网关
   侧补 token 计数。
5. ▶ **prefix cache 在多租户有什么安全问题？（中）**——跨租户侧信道：
   同前缀 TTFT 变快暴露他人 prompt；机制是 vLLM cache_salt（PR #17045，
   2025-04）。顺手补：命中率本身也必须按租户归因，账单才可解释。
6. ▶ **云厂那套 Batch/Flex/Priority 定价背后的逻辑？（中）**——tier 制
   ＝SLO 分层商品化；−50%／＋75%／2× 的价带是「可等待度」的市场标价；
   自营集群的对应物是 interactive/batch 混部＋priority 抢占。
7. ▶ **KV cache 占用怎么向租户收钱？（中）**——摊开物理账（70B 模型
   ≈328 KB/token、128K 上下文 ≈42 GB）；业界两种折算：TTL＋写价/读价
   （Anthropic）或磁盘缓存＋命中折扣（DeepSeek）；学界开放（VTC 留
   future work）；目前没有公有云把 KV 字节秒单列计价。
8. ▶ **离线推理能省多少钱？怎么混部？（中）**——SpotServe 省 54%（学术
   上限）＋OpenAI/Anthropic Batch 五折（产品化口径）；spot 不碰在线 p99；
   vLLM 2026 的 waiting→running 优先级抢占让离线 tier 安静吃谷电。
9. ▶ **被抢占的请求成本算谁的？（低频，但答出来是加分）**——recompute
   ＝已花 GPU 秒没出 token，是平台幽灵成本；计费上归平台（用户按 usage
   付款），成本中心单开一行，归因比人多算了一步。
10. ▶ **100 张卡要支持 50 个团队怎么规划？（变形设计题）**——metric
    first：流量画像×tier 占比反推各池卡数；池间用 priority＋抢占做软
    边界；预算按 key 落账；留 10–20% headroom。
