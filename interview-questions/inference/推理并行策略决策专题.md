# 推理并行策略决策专题：DP/TP/PP/CP/EP/混合，每种只治一种瓶颈

> 面向已经读过 [vLLM 与推理加速核心](./vllm与推理加速核心.md)、知道
> prefill/decode 两阶段的读者。训练侧的并行请看
> [三维并行](../distributed-training/三维并行.md)——本篇只解决**推理部署**
> 的并行选型：多卡不是大卡（4 块 GPU 是 4 个独立内存空间 + 4 个处理器，
> 任何跨卡依赖都付一次传输或集合通信），六种并行策略各切一个维度、
> 各治一类瓶颈、各引入一种通信模式。读完获得：① 拆任意策略的「五问
> 框架」；② 每种策略的检查点与失败信号；③ 自上而下的决策顺序
> （最小 TP → 再 PP → 最后 DP）；④ 8 道可直接对答的面试题。
>
> **口径声明**：框架与规则整理自公开推理并行教程（2026-10 转述），
> 不含特定 benchmark 数字；merge 数学与 Megatron 切分为教科书口径。

## 一、评估任意策略的五问

| 问题 | 在问什么 |
|---|---|
| 切分了什么状态？ | 权重 / 请求 / 层 / 序列位置 / expert |
| 复制保留了什么？ | 副本成本直接决定显存门槛 |
| 什么数据跨互联？ | 激活 / KV / partial 结果 / token 路由 |
| 传输频率多高？ | 每 token、每层、每请求、还是每 stage |
| 改善的是显存、延迟还是吞吐？ | 三者互斥居多，先确认治的是哪个 |

先把资源瓶颈列全：**参数显存**（模型放不放得下）、**KV 显存**（能常驻
多少 token、撑多少并发）、**GPU 计算时间**、**通信时间**。指标侧对齐
产品目标：TTFT / TPOT / 请求与 token 吞吐 / goodput（只算满足 SLO 的
请求），且**一律报分位数**——平均 TTFT 会把排队长尾洗没；没有延迟
约束的 tokens/s 会误导人（饱和服务报的 TPS 很高，其实请求都在排队）。

## 二、DP：切请求——吞吐工具，不是延迟工具

每个副本存**完整模型** + 独立调度器与 KV cache，路由器决定请求进哪个
副本队列。训练侧 DP 的梯度同步在推理里不存在。

- 适用：单副本已满足延迟目标、但扛不住请求速率；两副本吞吐近翻倍。
- 检查点一：每个副本仍要装下完整布局——**DP 只在模型已放下后可用**，
  解决不来「放不下」。
- 检查点二：路由规则。round-robin 无视两副本的队列与 KV 水位差；工程
  规则按**队列延迟、可用 KV 容量、预估输出 token 数**路由。
- 检查点三：准入预留。请求到达时只占少量 KV，decode 生成后越占越多；
  不预留会接进「现在放得下、稍后放不下」的请求。
- **失败信号**：低流量期第二副本闲置；单请求延迟毫无改善——拿 DP 治
  延迟就是误诊。

## 三、TP：切权重大矩阵——先解决「放不下」，顺带降计算

Megatron 经典构造：两段投影的 MLP，第一个矩阵按**列切**（各 rank 算
不同中间特征），第二个按**行切**（各消费自己的特征切片），每段本地
矩阵乘后 **all-reduce 合并**——collective 完成前本层走不下去。
Attention 同理（Q/K/V 按 head 切，输出投影再合并）。activation 的
partial 求和在浮点容差内与未切分逐元素一致（numpy 可 20 行自验）。

- 检查点一：模型是不是真的放下了。TP 只切被选权重；部分参数、临时
  buffer、CUDA graph、KV cache 可能仍在每卡复制——**要实测峰值显存，
  不是估**。
- 检查点二：**每层内部都有 collective**，慢互联会被逐层放大；NVLink
  机内与跨节点完全两个世界。
- 检查点三：每 rank 还剩多少计算量。TP 越高本地矩阵越小，GPU 靠大
  矩阵吃满，小到一定程度利用不足；**decode 比 prefill 更早触限**（单
  token 的矩阵活远小于长 prompt）。attention head 数与量化布局也会
  卡住切分度数。
- 经验规则（核心）：**用满足显存与延迟的最小 TP 度数**——多出来的卡
  拿去开第二个副本（DP），不是继续堆 TP。
- 失败信号：TP 上调后 decode 反而变慢（collective 参与者翻倍、本地
  活见底）；峰值显存没降多少（复制部分吃掉收益）。

## 四、PP：按层分组——低频传输跨过慢速互联

层分组为 stage，stage 间传 hidden states；权重不离开本设备。推理没有
反向，continuous batching 又让多组请求同时在流水线里流动。通信频率
远低于 TP 的逐层 collective，所以**PP 是跨节点 / 无高速 P2P 场景的
候选**，但不降单请求计算延迟。

- 检查点一：流水线填满度。warm-up 与 drain 阶段 stage 空闲，microbatch
  太少推高空闲比例（气泡）。
- 检查点二：stage 均衡按**实测时间与显存**，不按层数均分——embedding
  与输出层的占用和中间层完全不同。
- 检查点三：activation 缓冲。请求在 stage 间流动期间 activation 一直
  存活、占显存。
- 失败信号：流量不够时气泡占比飙升；层数均分后慢 stage 拖着整条
  流水线。

## 五、CP：切序列位置——两种独立机制，各治一种长上下文病

**PCP（prefill 上下文并行）切 prompt 计算**：各 rank 拿一段 prompt
算 Q/K/V；路线一是每 rank gather 全部 K/V 后对全局做 attention（放得
下才行），路线二是 ring-attention 风格循环传 KV chunk、合并 partial
（不物化全序列但多轮通信）。**实践关键是找临界点**：长 prompt 的
attention 计算量足以摊掉通信才有净收益，短 prompt 上 PCP 是纯开销——
按 prompt 长度实测 TTFT 曲线决定开不开。

**DCP（decode 上下文并行）切 KV 历史**：各 rank 只对自己那段历史做
attention，然后合并 partial 输出——合并数学就是 log-sum-exp 重缩放：
每个 partial 上报本地最大值、指数和、加权 value 和；取全局最大值，
各贡献按 exp(local_max − global_max) 重缩放后归约（减最大值是为数值
稳定，结果与完整 attention 一致）。

- 检查点一（DCP）：切分前后分别记录**常驻 KV token 数与最大并发数**，
  收益要用这两个数兑现。
- 检查点二（DCP）：**每个 decoder 层都要合并 partial**，TPOT 会涨；
  只有瓶颈明确是 KV 显存时才值。
- 注意区分：Megatron 系 sequence parallelism 是在 normalization 等
  算子周围切 activation，相关的另一回事。
- 落地形态（常见）：普通流量跑 TP/DP 基准布局，超长上下文请求路由到
  启用 CP 的专门布局——**PCP 治长 prompt 计算、DCP 治 KV 存储，两个
  独立决策**。
- DCP 的工程深挖（vLLM 官方 benchmark：8 卡 B200 吞吐超 3 倍、
  MLA/GQA 两后端约束公式）见
  [DCP 解码上下文并行专题](./dcp解码上下文并行专题.md)。

## 六、EP：切 expert——省显存，把 all-to-all 放上关键路径

只适用 MoE。把不同 expert 放不同 rank；路由把 token 表示发给持有
对应 expert 的 rank，产生 **all-to-all 流量**，算完经 combine 返回。

- 省的是 expert 权重显存；代价是**数据相关的动态流量进了请求关键
  路径**（不像 TP 的字节数固定）。
- 检查点一：共享的 attention/embedding/buffer/KV 在各 rank 仍放得下。
- 检查点二：负载倾斜是尾部问题——collective 等最慢的 rank；看平均
  负载会掩盖掉队者，**必须测每 expert 最大 token 数、本地 expert 计算
  时间这类尾部指标**。
- 灵活性：dense attention 与 expert 层**不必同一切分**——attention
  走 DP/TP，expert 层走 EP。
- 失败信号：路由倾斜时尾延迟爆炸；all-to-all 带宽吃掉省下的显存
  收益。

## 七、混合并行：乘积计数与构造顺序

- 计数规则：对 dense 组，**总 worker 数 = DP × PP × TP**（如 8 =
  1×2×4：一个副本、两个 stage、每 stage 四卡 TP）。部分 CP 复用已有
  rank，expert 组可能与数据组交互，按语义另算。
- 拓扑匹配（铁律）：**频繁的逐层 collective 留在节点内高速链路，只有
  stage 边界的 activation 跨慢速网络**。8 卡双节点的两个典型布局：
  节点内 TP4 + 节点间 DP2，或节点内 TP4 + 节点间 PP2——TP 始终不出
  节点。
- 构造顺序（防乱堆）：**先最小 TP（每 stage 放得下）→ 必须跨慢速
  边界才加 PP → 完整实例放下后才加 DP**。在搞清每个维度治哪种瓶颈
  之前就乘起来，是最常见的错误。
- PD 解耦（prefill/decode 分池）是**独立的一维**：两阶段硬件或扩缩
  节奏不同时分池（prefill 池偏矩阵算力、decode 池偏访存），但每个池
  内部仍需自己的 TP/PP 放置方案。
- **混跑干扰的定量直觉**（为什么解耦值这么多）：Cerebras 的示例账——
  5 块 GPU 每块 80% 时间跑 prefill、20% 跑 decode，则一个活跃响应的
  token 只在它所在的 GPU 做 decode 步时才前进，**decode 实际只吃到
  1 块卡的量**；理想解耦恰是把这 1 块的活交给专用 decode 池、4 块专做
  prefill——GPU 花在 prefill 的时间占比越高，解耦增益越大。反过来，
  如果负载本来就在 decode 上花大头，能挤出的干扰就少。
- **解耦的成本三件套**（决定「什么时候解耦反而亏」）：KV cache 跨池
  搬运的网络与协调开销（同机房 vs 跨地域完全两回事）；两池容量配不齐
  时一池闲一池忙；多养一套控制面的运维成本。所以解耦**在规模上最划算**：
  并发足够大时，独立配比与独立调度省下的才超过搬运与双池成本——Cerebras
  官方甚至宣称异构解耦（prefill 上合作伙伴加速器、decode 上 WSE 带宽
  怪兽）早期测试同卡数吞吐 5 倍、token 速度不降（2026-10 厂商口径，
  未经第三方复测；其商业面见 [推理专用硬件专题](../推理专用硬件专题.md)）。
- 与 Agent 负载的契合：多轮长上下文任务每步延迟累加，TTFT 与流式速度
  同时决定体感——这正是解耦把两阶段调度权拆开解耦后最能兑现的场景。

## 七·增、A/F 分离与 AFD：PD 之后的下一个切分维度

### 7·增一、PD 分离的干扰账

- 共存时大 prefill 要么暂停 decode、要么与 decode 混批，decode 的 TPOT
  剧烈抖动；资源还要按两阶段最坏情况共担预算，导致超配。
- 解耦只做一件事：两个 GPU 池，各自搜 GPU 数量与并行策略，分别满足
  TTFT 与 TPOT。指标是被架构造出来的：不在同一张卡上，才自然分开测。
- 数字：burst 场景共存 vs 分离，decode 延迟差 **2–30×**（DistServe
  口径）；SGLang 96×H100 部署 DeepSeek-R1，每节点 **52.3k input TPS /
  22.3k output TPS**；vLLM + llm-d 96-way EP 每 H200 约 **2k tok/s**。
- 代价：重构整个 serving 栈；只有 SLO 变成业务生死线、模型大到必须
  跨数百卡时才付得起。

### 7·增二、A/F 分离：attention 与 FFN 各找各的硬件

- decode 里 attention 访存密集（KV 大）、FFN 计算密集（权重大但恒定），
  分硬件可各取高 MFU；每层要搬两次激活，dense 模型原本不划算。
- MoE 改变了这笔账：EP 下每个 decode step 本就有两轮 all-to-all，把
  A/F 边界对齐过去，额外传输近乎免费。**A/F 目前只在 MoE 上验证**，
  dense 仍是开放问题。
- 面试一句：PD 分离按「阶段」切，A/F 按「层内模块」切；前者解决干扰，
  后者解决 MFU，两者可叠加。

### 7·增三、AFD：长上下文把 MoE batch 饿死

- 病根不在 expert 数，在 batch：上下文变长 → 每请求 KV 涨 → KV 上限
  压低 active batch → 每 expert 分到的 token 变少 → grouped GEMM 变小、
  MFU 断崖。EP 治不了：它只减少每卡 expert 权重流量，不改 MoE 总计算量。
- 分离边界：Attention worker 持 KV、attention、路由、采样；FFN worker
  收路由后的 token 做 expert GEMM；FFN 池从多个 Attention worker 聚合
  token，固定 FFN 卡数时每 expert batch 变大。
- 必须掩盖通信：每层 M→N dispatch、N→M combine；DeepEP 风格通信、
  MegaMoE 把 dispatch+GEMM+combine 融成一个 kernel、zero-overhead 调度、
  microbatch ping-pong。
- 数字：GB200 NVL72 上 Qwen3-235B 8K/16K **1.41×/1.44×**、
  MiniMax-M2.5 **1.45×/1.35×**；Attention GPU 卸掉 90%+ 权重，KV 容量
  **1.5×**；MegaMoE 融合让 8 节点 decode step 延迟 **-44%/-42%**；
  attention 侧边界 kernel 只占 148 SM 中的 **24 个**。
- 边界：只在同一 NVLink 域成立；三条件——A/MoE 计算量平衡、单次通信
  短于流水线周期、microbatch 足够大。不追求 T_a≈T_e，选 T_e≤T_a 的最大
  M，用有界 FFN 空闲换鲁棒。

### 7·增四、DeepSeek 多节点：MLA 不能按 head 切 TP

- 起手是 DP 而非 TP：多个独立 engine 实例各持请求，网关按前缀做 KV
  reuse 路由；实例不跨节点，节点内可选 TP 切 attention。
- MLA 的 TP 是残缺的：q/kv 先压到 latent，所有 head 共享同一 latent，
  latent 无法按 head 切；每个 TP rank 复制投影与整份 KV cache，只省
  一部分计算。所以 attention 走 DP（+可选 TP），MoE 走 EP，且
  **EP = DP × TP**；16 机 EP128 = DP32 × TP4。
- 数字：128×H100 对单节点 8×H200，EP128 吞吐最高 **5×**（EP8 基线）；
  单 MoE 层 H100/TP1/batch128：NoOverlap 2667µs、DispatchOverlap
  2651µs（-0.6%）、MicroBatch **1896µs（-29%）**；同 batch EP8 vs
  EP128 GroupGEMM **555→270µs**，但通信多 213µs；microbatch 在每卡
  batch<32 时 -5%~-40%，≥32 才 +10%~35%。
- 边界：5× 依赖自研 AllToAll 写对、显存预算留足；每卡 batch=64 时
  单节点反而略高，拓扑不是单向胜利。

### 7·增五、A2 速记：两条并行增量

- **CTA 级跨 GPU 空间流水（55）**：只注入 prologue/epilogue，tile 级
  跨卡流水；vs micro-batch **-31.8%**、vs TP **-29.6%**。
- **模型-GPU 协同设计（99）**：按 G/Hsz/序列长度对齐 tile 与并行度；
  G 翻倍 decode 减半、prefill 对 G<1% 不敏感；Hsz=128/256 是甜点。

## 八、决策框架（自上而下，每次只解一个瓶颈）

1. 单卡能否保留 KV 容量放下完整副本？能 → 单副本起步，流量上来加 DP；
2. 放不下 → 找最小 TP 度数并实测 decode 延迟达标；
3. 必须跨节点 → TP 留节点内，PP 跨节点；
4. 长 prompt 的 TTFT 不达标 → 评估 PCP；KV 限制并发/长度 → 评估 DCP；
5. MoE 且 expert 权重是显存主因 → 在跟踪路由尾部指标的前提下上 EP。

两条总原则：**只有测量指出某资源是瓶颈，才启用对应那种并行**；每次
切分引入的通信/同步/调度开销，必须小于省下的显存与算力——最简单且
达标的布局就是最好的布局，并行是放置决策，不是堆卡数量的设置。

## 九、▶ 面试题与追问

**Q1【高】给你 8 卡放 70B，怎么选布局？**
先实测：单机 8 卡 TP8 能放下但 decode 会被逐层 collective 拖；更优
是 TP4 × DP2（模型 4 卡放得下时）或跨双节点时节点内 TP4 + 节点间
PP2/DP2。判断顺序：最小 TP 让单实例达标 → 剩余卡换吞吐（DP）而非
继续切（TP）——**TP 治放置，DP 治吞吐，别拿 TP 治吞吐**。

**Q2【高】为什么 TP 不能超过某个度数？为什么 decode 比 prefill 更
早触限？**
两层原因：通信频率——每层一次 all-reduce，度数越高参与者越多、
等待越明显；计算密度——每 rank 的矩阵随度数线性缩小，GPU 大矩阵
才吃得饱。decode 每步只有 1 个 token 的计算量，prefill 是整个
prompt，所以 decode 的算通比先到下限。

**Q3【高】PCP 和 DCP 分别解决什么？合并 partial attention 的数学
怎么写？**
PCP 切 prompt 计算治「长输入的 TTFT」，DCP 切已存 KV 治「长历史
的显存」。合并：各 partial 上报 (local_max, exp_sum, weighted_v)，
全局 max 后各项乘 exp(local_max − global_max) 重缩放，分子分母
分别求和相除——就是 online softmax 的分布式版本。

**Q4【中高】为什么不直接全上混合并行？DP×PP×TP 拉满不好吗？**
每加一维都引入自己的通信/调度/调度复杂度，且让归因变难——吞吐
掉了你不知道是哪一维拖的。正确姿势是自上而下每次只启用被测量
证实能解决当前瓶颈的一维，benchmark 达标就停。

**Q5【中高】EP 和 TP 的流量性质差在哪？为什么 EP 更要看尾部？**
TP 通信字节数固定（与激活形状绑定、逐层发生）；EP 的 all-to-all
字节数随 token 路由结果动态变化，且 collective 等最慢的 rank——
负载倾斜时平均值毫无参考意义，必须测每 expert 的最大 token 数与
尾延迟。

**Q6【中】PP 的负载均衡为什么不能按层数均分？**
layer 数 ≠ 时间：embedding、输出头、带 MoE 的层、带大 KV 的层耗时
和显存都不同。按实测 stage 时间重新切边界，否则慢 stage 决定整条
流水线的节拍，气泡全部堆在它前面。

**Q7【中】PD 分离和 TP/PP 是什么关系？**
正交的两维：PD 解耦决定「prefill 与 decode 是否分池、各自扩缩容」；
TP/PP/CP 决定「每个池内部模型怎么放」。解耦后每个池内部仍需放置
方案——比如 prefill 池 TP4（矩阵大、吃算力），decode 池 TP2（访存
为主、算通比早触限），这正是两阶段布局可以不同的原因。

**Q8【中】DP 副本间怎么路由？为什么 round-robin 不合格？**
round-robin 默认两副本等价，无视队列长度与 KV 水位差；正确输入是
队列延迟、可用 KV 容量、预估输出 token 数（准入还要为 decode 增长
预留）。与 [负载均衡专题](../负载均衡专题.md) 的网关层接力：副本内
引擎再按自己的调度器排。
