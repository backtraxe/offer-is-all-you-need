## 〇、先立规矩：旧框架已过时，本篇只讲窗口期增量

旧文 [vLLM vs SGLang 深度对比](./vllm与sglang深度对比.md) 的对照框架
「V1 两刀 vs 三刀」在 2026 已基本过时，三组硬证据：

- vLLM **V0 engine 代码全删**（v0.11.0，2025-10-02），V1 成为唯一 engine；
- vLLM **MRV2 成为全模型默认 Model Runner**（v0.29.0，2026-09-09），
  「V1 架构」本身的 runner 又换了一代；
- SGLang **scheduler 前半 Rust 化、radix 核心进 Rust**（v0.5.21，
  2026-10-02），「三刀流水线」前两刀正在被重写。

所以本篇的旧文策略是**只串联、不重复**：两刀 vs 三刀的进程切分、APC vs
Radix 的命中逻辑、retraction 的调度细节，请回旧文看；这里只回答一个问题
——旧文写完的这一年，地基又被换掉了多少。面试照着旧架构图背会被当场
追问，本篇就是你的补钉。

## 一、节拍器：两周一版本身就是信号

先看版本密度，再看技术内容——**发版节奏本身就是军备竞赛的证据**：

| 引擎 | 窗口起点 | 窗口终点（最新） | 节奏 |
|---|---|---|---|
| vLLM | v0.10.0（2025-07） | v0.31.0（2026-10-05） | 21 个 minor，约两周一版 |
| SGLang | v0.5.9（2026-02） | v0.5.21（2026-10-02） | 12 个 minor，同样两周一版 |
| Dynamo | v1.0（2026-03） | v1.5.1（2026-10-07） | 月更，已自称第 18 个 feature release |
| NIXL | — | v1.5.0（2026-09-30） | PD 传输底座，随三家同步发版 |

两个推论：

1. **你的「最新知识」保鲜期约等于一个发版周期（两周）**。面试前不扫一遍
   最新 release notes，讲的任何「现状」都可能已经在被修的路上；
2. 版本密度的另一面是**默认开关在快速换代**：去年还是实验特性的东西
   （异步调度、CUDA graph 全覆盖、统一 radix tree），今年大多已默认开启。
   背「XX 特性需要手动开」要格外小心。

## 二、vLLM：三代翻篇与 KV 四级化（v0.10.0 → v0.31.0）

### 2.1 架构线：V0 全删，MRV2 全模型默认

三个版本走完两代：

- v0.11.0（2025-10-02）**V0 engine 代码全删**，V1 唯一；同版 CUDA graph
  默认 FULL_AND_PIECEWISE、CPU KV offload 进主线、DBO 双 batch overlap；
- v0.12.0（2025-12-03）**Model Runner V2 实验首发**：GPU 常驻 block
  table、去掉重排 bookkeeping、Triton 原生 sampler；v0.27 扩到
  embedding / pooling，v0.28 补齐 E/P/D 分离与多层 MTP KV；
- v0.29.0（2026-09-09）**MRV2 全模型默认**——V0 → V1 → MRV2 三代翻篇。

面试口径：被问「vLLM V1 架构长什么样」，2026 的正确答案是
**V1 的进程外壳 + MRV2 的 runner 内核**，而不是旧文那张 V1 图。

### 2.2 KV offload：六个版本连续发力，四级成事实标准

这是 vLLM 在窗口期**投入密度最高的一条线**：

| 版本 | 增量 |
|---|---|
| v0.26（2026 年中，具体日期未核） | 打基础：指标埋点、对象存储二级层、DP 副本感知 |
| v0.27.0（2026-08-10） | P2P 二级层、可插拔驱逐策略 |
| v0.28.0（2026-08-26） | **磁盘层落地**，tiered 体系闭环 |
| v0.30.0（2026-09-22） | **HiSparse host 级稀疏 KV 层**：sparse-MLA 场景 KV page 溢出到 pinned host 内存 |
| v0.31.0（2026-10-05） | **背压检测**：offload 抢资源时知道收手 |

结果：**GPU → Host → Disk → 对象存储四级 KV 分层**成为事实标准。配套
的另一个关键动作是 v0.28 起可用 module_path 注册二级存储管理器——
connector 从单点实现长成了**分层加外接插件**的形态。

负优化意识（追问伏笔）：offload 的收益 = 省下的重新 prefill 算力 vs
传输带宽 × 命中概率；短 prompt 重算本来就便宜、host 带宽被 NUMA / RDMA
争抢、offload 与 decode 抢 HBM copy 引擎时，四级是负优化——v0.31 的
背压检测和 HiSparse 的「只溢出稀疏 KV」都是这个答案的工程化。

### 2.3 PD 与 connector 体系

- v0.27.0（2026-08-10）**NIXL PD 打通 hybrid MLA+SSM**：混合模型、P/D
  两端异构 block size 首次可传；同版 Fault Tolerance 框架（DP+EP）、
  FA4 SM100 FP8 KV、Rubin sm_107 适配；
- v0.26 NIXL 支持流水并行 prefill push；
- v0.30.0（2026-09-22）encoder cache 经 NIXL / Mooncake 共享；
- v0.31.0（2026-10-05）修复 KV connector + MTP 在 **KV 压力下的死锁**
  ——这条修复本身就是一道面试题：spec decode 占用 KV 与 connector 传输
  争抢时，老版本会死锁。

### 2.4 Spec decode / MTP：EAGLE 独大阶段结束

- v0.28.0（2026-08-26）draft spec decode **自动开异步调度**；
- v0.29.0（2026-09-09）per-request 接受率指标；
- v0.30.0（2026-09-22）**在线接受率估计的自适应验证** + Gumbel-max 水印；
  同版 MRV2 跑通 MTP / EAGLE3 / DFlash / DSpark；
- v0.31.0（2026-10-05）**MRV2 草稿模型 spec decode** 补齐，MRV2 的
  spec 路径完整。

一句判断：**DSpark / DFlash 块级半自回归草稿已同时进两家主线**（出处
只引 LMSYS blog 2026-07-06，是否有 arXiv 论文未核实），EAGLE 一家独大的
阶段过去了。自适应验证窗（按置信度 / 在线接受率动态调整）成为标配。

黑历史值得一提：v0.10.2 / v0.11.0 时期 async scheduling 在 preemption
下输出乱码，是 release note 明文警告的已知问题；v0.28 起 draft 默认自动
开异步调度，可视为已稳定。这个弧线说明——**默认开关背后都是修出来的**，
面试讲「开 async scheduling」时把这段带上。

### 2.5 RL 配套与重启归零

- **sleep mode**：/wake_up 接口 2025 年已具备（首次落地版本未核实，按
  降级口径不写死），v0.27 起持续修复（#41602），2026 年进入 RL 配套
  主线；
- v0.29.0（2026-09-09）**sharded_rdt 权重热同步**：按 TP / EP 分片、经
  NIXL 或 Ray Direct Transport 拉权重——RL colocate 下权重更新不再靠
  整模型重载；同版 FlashInfer all-reduce 默认开；
- v0.30.0（2026-09-22）**weight-cache daemon**：--load-format
  ipc_cache，量化后权重常驻，重启走 CUDA IPC 映射；
- v0.31.0（2026-10-05）**CRIU engine snapshot**：vllm preload CLI +
  vllm snapshot create/restore，直接恢复一个完整初始化好的 TP1 引擎。

意义：**引擎冷启动从分钟级压到秒级**，服务对象非常明确——RL colocate
的训推切换，和 serverless 推理。这是「重启/弹性成本归零」主题的 vLLM
半边。

### 2.6 其他值得带上的锚点

- v0.28.0 max_num_batched_tokens 默认 **8192 提到 16384**；
- v0.29.0（2026-09-09）**prefix cache hash 默认可复现**（NONE_HASH
  确定性化）——分布式 KV 共享不再需要 pin PYTHONHASHSEED；
- v0.31.0（2026-10-05）**每请求多模态 kwargs 默认拒绝**（安全收紧）。

## 三、SGLang：Rust 化与 HiCache 纵深（v0.5.15 → v0.5.21 + SMG）

### 3.1 HiCache：从单机 radix 到全局内存池

首发按降级口径写**2025 上半年**（雏形 PR #2693，精确首发版本未核）。
窗口期增量一版一个台阶：

| 版本 | 增量 |
|---|---|
| v0.5.16（2026-07-25） | **UnifiedRadixTree 对 SWA / Mamba / DSA 默认**；DSA cache 按 CP 分片（每 rank KV −74%，官方口径） |
| v0.5.17（2026-08-08） | **session 感知 radix cache**：/close_session，agentic / RL 长会话防误驱逐 |
| v0.5.19（2026-09-05） | **统一 radix tree 全模型默认 + HiCache L3 运行时挂载/卸载**（不重启挂 L3 存储） |
| v0.5.20（2026-09-18） | **分支点缓存**：DSV4 共享 system prompt 命中率 43.8%→60.8%、TTFT 1.57s→1.07s（官方口径）；树外接 Mooncake / UMBP 全局池 |
| v0.5.21（2026-10-02） | **prefix cache 核心迁 Rust，默认开启** |

官方文档已配套 HiCache Best Practices / 系统设计 / 运行时挂载三个专页，
面试前连夜补 HiCache 的最低成本路径就是这三页。

### 3.2 PD：角色热切换正面回答静态配比之痛

- 传输层 **Mooncake / NIXL 双线并行**：v0.5.20 在 8×B300、256K 输入下
  同时验证两条路径；
- v0.5.21（2026-10-02）**PD 实例可热切换 prefill / decode 角色不重启**
  ——对静态 PD 配比（P:D 定死后流量波动只能硬扛）这个老痛点的正面回答；
  同版 DSV4.1 长 prompt TTFT −22%（官方口径）；
- EPD 有独立文档页，多模态岗要单独看。

### 3.3 Spec：DSpark 首发、DFlash2 跟进、线性注意力验证省显存

- v0.5.16（2026-07-25）**DSpark 首发**：块级半自回归草稿 + 按草稿置信度
  动态定验证窗；DSV4-Pro 在 B300 上 bs=1 达 383.7 tok/s、accept ≈5
  （官方口径，出处 LMSYS blog 2026-07-06）；
- v0.5.19（2026-09-05）**DFlash2**：局部卷积 + 候选选择器，bs=1 加速
  3.43x、并发 64 时比 DFlash 再快 +24%（官方口径）；同版 DeepEP
  v2 ElasticBuffer、AMD Lean attention 1.52x（官方口径）；
- v0.5.16 线性注意力 spec 验证显存 11.5GB→1.8GB（ReplaySSM ring，
  官方口径）；v0.5.21 PP × spec 兼容。

工程追问点提前备好：draft 的 CUDA graph 兼容、DP / PP 下接受率一致性、
logprobs 支持——这三件是 spec 从「能跑」到「能上生产」的差距。

### 3.4 Breakable CUDA graph：与 vLLM 平行同向

v0.5.15（2026-07-10）**Breakable CUDA Graph 默认开**，prefill 全程
CUDA graph（实验）；此后每版大量修复与扩展（PP、DP-attention、memory
borrow pool）。与 vLLM 的 FULL_AND_PIECEWISE 默认是**同一道题的两个
平行答案**：CUDA graph 能覆盖的都覆盖，覆盖不了的 break 掉，而不是退
回 eager。

### 3.5 Rust 化：旧文的三刀正在被重写

- v0.5.17（2026-08-08）**Rust frontend 初始落地**，Python 只保留 GPU
  调度之后的部分；同版 DCP 可插拔通信后端、weight-cache daemon、
  MoE 加载 35min→6m20s（官方口径）；
- v0.5.21（2026-10-02）**radix 内核进 Rust**：三刀流水线前两刀
  （TokenizerManager、Scheduler 前半）被 Rust 接管，旧文进程图需重画；
- 路由侧 SMG gateway v0.3.1（2026-01-09）**cache-aware 路由提速
  10–12x**、每节点内存 −99%（180KB→1.4KB，官方口径）+ JWT / OIDC——
  路由层的 Rust 化加企业化。SMG 与旧 router 的品牌沿革未核实，本篇只
  摆功能锚点、不编时间线。

动机一句话：前处理（tokenize、多模态解码、路由）CPU 密集且并发拉到万级
QPS 时，Python GIL 与每请求开销就是硬瓶颈；GPU 调度与 kernel launch
仍贴 Python / CUDA，所以短期是三头都收敛到**前半 Rust 后半 Python**
的混合架构。

### 3.6 启动与 RL：和 vLLM 同一道题

- v0.5.18（2026-08-22）**checkpoint staging 与 CUDA graph 捕获重叠**：
  启动快 2.38x（官方口径）；同版 torch 2.13；
- v0.5.17（2026-08-08）weight-cache daemon（与 vLLM v0.30 同名同思路）；
- v0.5.20（2026-09-18）**RL sampling mask 回放**：吞吐 +52% @ bs64
  （官方口径）——本质是 rollout 可复现性机制的副产品收益。

## 四、Dynamo：从外挂到平台（v1.3.0 → v1.5.1）

### 4.1 定位与锁版：不再是谁的插件

Dynamo 的定位已经翻篇：不再是「vLLM 的 PD 外挂」，而是有独立发行节奏
的**分布式推理平台**（v1.5.0 自述第 18 个 feature release）。锁版口径：

- v1.3.0 锁住 vLLM v0.23 / SGLang v0.5.14 / TRT-LLM 1.3.0rc19；
- v1.5.0 / v1.5.1 升到 vLLM v0.28 / SGLang v0.5.18 / TRT-LLM 1.3.0rc25，
  依赖 NIXL v1.3.x–v1.4.0。

TRT-LLM 的独立演进本篇未调研，须要对比时只报锁版内的版本号，不要外推。

### 4.2 KV-aware routing：从「猜谁有缓存」到「消费 KV 事件」

- v1.3.0（2026-07-22）**Branch-Sharded KV Indexer**：压缩 radix tree 做
  热路径，事件处理 28x（官方口径）；工具调用 / 推理 parser 分层；
- v1.4.0（2026-08-15）**跨数据中心 KV 路由**：sequenced KV relay、
  reservation replay、按租户 cache-salt 隔离；tokenizer prefix cache
  默认开；
- v1.5.0（2026-09-21）**router 直接消费 Mooncake 共享缓存事件与 vLLM
  磁盘层 KV 事件**——路由能看到 L2 / L3 命中；router 插件化
  scorer / picker；KVBM 弃用；sidecar 模式落地。

演进判断：**KV 路由从近似猜测演进为多级 KV 事件驱动**——vLLM KV
events、SGLang HiCache 事件、Dynamo KV Indexer 三条线同源，「控制面
能看到 KV」是 2026 的标配能力而不是噱头。

### 4.3 EPD：多模态推理的第三段

- 首次引入版本未核实（v1.0 前已存在，按降级口径不写死）；v1.1.0 统一到
  Qwen3-VL 示例；
- v1.3.0（2026-07-22）**SGLang 多模态 PD 分离接入**；
- v1.5.0（2026-09-21）**EPD 成熟期**：图像在 Frontend 只解码一次
  （libjpeg-turbo / FFmpeg），像素经单次 NIXL 传给 encode worker；
  视频走 video-aware KV hash 路由；
- v1.4.0（2026-08-15）**vLLM-Omni NIXL RDMA 多节点**：AR → diffusion
  首次真多节点。

权衡点（多模态岗必考）：encoder 独立成段换来弹性伸缩，代价是传输体积
（传像素还是传 embedding）与 encode 位置的决策。

### 4.4 平台化：GMS、Snapshot、TITO、sidecar

- v1.3.0（2026-07-22）**GPU Memory Service 生产可用**：多 worker 共享
  GPU 常驻权重；RL 支持 TITO、原地权重更新、sleep / wake；
- v1.5.0（2026-09-21）**Snapshot 独立 operator** + sidecar 模式（引擎
  不改代码、保留原生 serve 命令）；SGLang RL 契约（实验）。

## 五、收敛趋势：七条

1. **PD 分离 → EPD 三段是共同终局形态**——多模态流量下 encode 必然
   独立成段；
2. **prefix cache 多级化 + KV 事件驱动路由成标配**——KV 缓存从单机
   状态变成跨层、跨实例、可被控制面感知的分布式资产；路由从猜谁有缓存
   变成消费 KV block 事件索引；
3. **spec decode 从 EAGLE 单点走向块级半自回归 + 自适应验证**——
   DSpark / DFlash2 同进两家主线，验证窗按置信度 / 在线接受率动态调；
   spec 与 PP / DCP / PD / Mamba 的组合兼容成为常规修补项；
4. **Rust 重写控制面是共同动作**——vLLM Rust frontend（v0.26 起）、
   SGLang Rust frontend + radix 内核 + SMG、Dynamo 本就 Rust；动机一致：
   Python / GIL 扛不住万级 QPS 的前处理与路由；
5. **为 RL 而生从边角变一等公民**——vLLM sharded_rdt、SGLang sampling
   mask 回放 + session radix、Dynamo TITO + 原地权重更新 + sleep /
   wake；共同痛点是 colocate 训推下的权重更新、显存让位、rollout 可复现；
6. **重启 / 冷启动成本归零**——两家 weight-cache daemon + CRIU /
   checkpoint staging、Dynamo GMS + Snapshot；serverless 推理的
   基础设施在引擎层被补齐；
7. **未收敛的差异点仍然真实**——vLLM 强在模型覆盖面、RL 生态对接
   （veRL / Slime）、connector 插件化；SGLang 强在 radix / HiCache 系统
   纵深、DSpark spec 首发、国产卡与 AMD 调优密度；Dynamo 强在多机 PD
   编排、KV 路由、K8s 平台化。选型问题仍有真实 trade-off，但底层技术
   在持续互抄——**结论可以不变，论据必须每年更新**。

## 六、▶ 面试题与追问

**Q1【高】你两年前选的 vLLM / SGLang，放到 2026 还成立吗？**
标准答法：**结论可以不变，论据必须更新**。选型 trade-off 本身还在
（第七节的差异点），但支撑论据全部换代：vLLM 侧 V0 已删、MRV2 默认、
KV 四级 offload 成主干；SGLang 侧 radix 内核已 Rust 化、HiCache 可
外接全局池、DSpark 让 spec 不再只有 EAGLE。把「我当时为什么选」与
「这一年双方各自补了什么」分开讲，就是高分答案。

**Q2【高】PD 分离在 2026 还有什么没解决的问题？**
至少四个：① P/D 静态配比——SGLang v0.5.21 的在线角色切换是正面回应
但未成共识；② hybrid / 线性注意力模型的 KV 异构传输——vLLM v0.27 才
打通；③ KV 压力下 spec decode 死锁——v0.31 刚修；④ 多模态 encode
段的位置——Dynamo v1.5.0 才把「前端只解码一次」工业化。

**Q3【高】prefix cache 怎么从单机走向多级？L3 命中怎么参与调度？**
分层答案：GPU radix → host pinned → disk / 对象存储；调度答案：控制面
消费 KV 事件做路由（Dynamo v1.5.0）。追问三连：事件一致性（写后读
可见性）、过期与失效、多租户 cache-salt 隔离（Dynamo v1.4.0）。

**Q4【中高】EAGLE 和新的块级 spec（DSpark / DFlash）差在哪？**
EAGLE 是逐 token 自回归草稿 + 固定 / 树形验证；DSpark 是块级半自回归
草稿 + 按置信度动态定验证窗（383.7 tok/s @ accept ≈5，官方口径）。
工程重点不在算法名，而在 draft 的 CUDA graph 兼容、DP / PP 下接受率
一致性、logprobs 支持。

**Q5【中高】KV offload 到 host / disk 收益怎么算，什么时候是负优化？**
收益 = 省下的重新 prefill 算力 vs 传输带宽 × 命中概率。负优化三种：
短 prompt 重算本来就便宜；host 带宽被 NUMA / RDMA 争抢；offload 与
decode 抢 HBM copy 引擎。精化案例两个：vLLM v0.31 的背压检测、
SGLang HiSparse 只溢出稀疏 KV。

**Q6【中】引擎怎么支持 RL rollout？colocate 时显存怎么腾？**
三件套：sleep / wake（CuMem 级显存让位）+ 原地权重更新
（sharded_rdt / TITO）+ 权重常驻 daemon 快速重启。可复现靠 sampling
mask / 精确 logprob 回放。再往下追一层是训推精度差（batch-invariant
kernel 配套方向）。

**Q7【中】为什么大家都用 Rust 重写前端 / 路由？**
前处理（tokenize、多模态解码、路由）CPU 密集 + 高并发，Python GIL
与每请求开销是瓶颈；GPU 调度与 kernel launch 仍贴 Python / CUDA，
所以短期是前半 Rust、后半 Python / C++ 的混合架构——SGLang 的「三刀
前两刀 Rust 化」是最完整的样本。

**Q8【中低，多模态岗为高】EPD 和 PD 差在哪？encode 放哪最合理？**
EPD 把 encoder 独立成段、经 NIXL 传 prefill；Dynamo v1.5.0 的答案是
图像在前端只解码一次、encode worker 只收像素。权衡点在 encoder 弹性
vs 传输体积（像素 vs embedding）——没有唯一解，看图像尺寸分布与
encoder 算力占比。
