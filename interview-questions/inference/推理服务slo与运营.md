## 〇、从 bench 到生产还差三件事

压测报告上「p99 TTFT 180 ms、吞吐 2000 tok/s」不等于服务可以上线。bench 到
生产的缺口只有三件事：

1. **容量**：压测是一次性快照，生产要承诺「峰值流量下、任意时刻」都满足
   SLO——这要求从流量画像反推卡数，并留出冗余；
2. **成本**：吞吐数字必须除以卡时才值钱——同样的 goodput，184 张卡跑和
   96 张卡跑是完全不同的生意；
3. **稳定性**：压测没有 OOM、没有慢节点、没有流量突刺——生产有，且按 p99
   的口径「每小时抖一次」就已经是事故。

整篇文档就围绕这三件事展开，最后用 Incident Playbook 收尾——因为面试官的
潜台词永远是那句：**「这套东西真交给你运维，你睡得着吗？」**

## 一、SLO 的定义与拆解

▶ 面试题：你们线上 SLO 怎么定的？为什么这么定？——**高（二面必问）**

### 1.1 SLO 三件套与为什么必须带分位数

一条可执行的推理 SLO 长这样：

| 指标 | 示例 SLO | 是对谁的承诺 |
|---|---|---|
| TTFT p99 | ≤ 1.5 s（prompt ≤ 4K 时） | 用户「卡住感」的上界 |
| TPOT p99 | ≤ 60 ms | 流式阅读不卡顿（人眼 ~15~20 tok/s 舒适线之上留余量） |
| 请求成功率（可用率） | ≥ 99.9% | 含 429/超时/Volcano 重试后的最终口径 |

为什么必须带分位数——均值在长延迟分布下没有意义（长尾把 mean 带飞），
**SLA 是按尾部碎的，不是按平均碎的**；这一点需要脱口而出的推导与压测口径
见计算题专项第九节，不再展开。

### 1.2 流量画像：SLO 的一半写在这张表里

先记住一句话：「没有流量画像的 SLO 是空头支票」。同样的 QPS，两个画像
的容量差可以到一个数量级。

画像里必须拍下来的四件事：**输入/输出长度分布**（lognormal、双峰、超长
尾巴）、**峰谷系数**（白天集中/夜间碎片、活动尖峰）、**prefix 命中率**
（多轮对话/Agent 场景显著抬高）、**调用方结构**（独占大客户 vs 长尾小
租户）。文章下面所有估算都以「显式声明画像」开场——面试官盯着的就是
这一步声明习惯。

### 1.3 把业务 SLO 拆成引擎预算

**直觉**：一个请求的时间 = 排队 + prefill + decode × N。SLO 的每一毫秒都要
有「下属」认领，没人认领的部分最终会以事故形式被认领。

三份预算的归因与杠杆（答的时候按这个顺序报）：

| 预算 | 归因公式 | 主要杠杆 |
|---|---|---|
| **排队预算** | TTFT SLO − prefill 耗时 | 水位控制（ρ ≤ 60%）、优先级、PD 分离隔离 |
| **prefill 算力预算** | ≈ 2·P·S / (算力 × MFU) | prefix cache（命中≈免算）、chunked prefill、prefill 集群配比 |
| **decode 带宽预算** | TPOT ≈ (权重 + Σ KV) / 有效带宽 | batch 上限 B_max、KV 量化、TP 度与带宽摊分 |

来源推导：prefill 2·P·S 与 decode 带宽账见
[计算题专项第五节](./infra面试计算题专项.md#五prefill--decode-耗时推算)；
PD 分离为什么要拆，见 [PD 分离一节](./vllm与推理加速核心.md#七pd-分离prefill-和-decode-为什么要拆成两套集群)。

### 1.4 SLO 违反的事故等级

把「违反 SLO」本身分级，运维面最爱考你对破坏面的量化直觉：

- **P3 预警**（单实例/单租户级）：某个实例 p99 超标 3× 中位数、单租户
  连续 429 → 触发自动扩缩或故障摘除可自愈，不升级；
- **P2**：全局某 SLO 指标 5 分钟级超阈值（如 TTFT p99 > 2× SLO）、可用率
  跌破 99.9% 但仍 > 99% → oncall 介入，流量调度/降级；
- **P1**：可用率 < 99%、全链路超时雪崩 → 全量降级保底态（小模型/短
  输出/高优租户保留），事后必须复盘。

等级表的意义在于**触发判据必须是机器读的**：p99 的告警要带持续时间窗口
（防止一次性抖动误报），且每个等级挂一个被演练过的 SOP（见第七节）。

## 二、容量估算：从 SLO 反推卡数

▶ 面试题：70B 模型，峰值 30 QPS，TTFT p99 ≤ 1.5 s、TPOT p99 ≤ 60 ms，
要多少台 H800？——**高（字节/腾讯原题套路）**

### 2.1 答题链条（五步不断链）

```text
峰值 QPS × 输出长度 → decode 在途并发（Little's Law）
                    → 单节点可承载并发 B_max
                    → 节点数 × 冗余系数 → GPU 总数
                    → 显存核对（必须走一遍，链条不闭环不收尾）
prefill 侧单独按 FLOPs 走一遍同链条 → PD 配比
```

*（车型、模型、画像、SLO 全部显式声明，让面试官看到你主动框定了问题。）*

### 2.2 完整算例（70B · H800 · PD 分离）

**声明假设**：70B GQA（80 层、8 KV head、head_dim 128、BF16，权重 140 GB）；
H800 8 卡台，TP = 8，有效带宽按 70% = 2.35 TB/s，MFU 按 35%；流量画像
prompt 4K / output 512，峰值 QPS = 30，见上一节的 SLO 三件套。

**Step 1 — 单序列资源账**

```text
KV/token = 2 × 80 × 8 × 128 × 2 B ≈ 320 KB
平均 ctx ≈ 4K + 256 ≈ 4.25K → KV ≈ 1.36 GB/seq
单卡权重 = 140 GB / 8 = 17.5 GB
```

**Step 2 — decode 侧 B_max 由 TPOT 预算定**

每个 iteration 每卡搬 = 权重 17.5 GB + B × 1.36 GB。给 p99 留一半余量
（防 prefill 干扰与突发），单程预算 26~30 ms：

```text
B_max ≤ (30 ms × 2.35 TB/s − 17.5 GB) / 1.36 GB ≈ 39 → 工程取 B = 32
B = 32 时 step ≈ (17.5 + 43.5) GB / 2.35 TB/s ≈ 26 ms ✓ 预算内
```

**Step 3 — decode 侧节点数（Little's Law）**

```text
单请求占用卡槽 ≈ TTFT(1s) + 512 × 26 ms ≈ 14.3 s
在途并发 ≈ 30 × 14.3 ≈ 430 条
节点数 = 430 / 32 ≈ 13.4 → 14 台
冗余系数 1.3（N+2、水位压到 60~70%）→ ≈ 18 台 = 144 卡
```

**Step 4 — prefill 侧节点数（FLOPs 账）**

```text
单次 prefill FLOPs ≈ 2 × 70e9 × 4096 ≈ 5.7e14
单台 H800 有效算力 ≈ 8 × 989 TF × 35% ≈ 2.77 PFLOP/s
→ 0.21 s/req → 单机 ≈ 4.8 req/s → 30 / 4.8 ≈ 7 台
TTFT 排队预算 = 1.5 s − 0.21 s ≈ 1.3 s → 水位 ρ ≤ 0.6 再补 1 台 → 8 台
```

**Step 5 — 显存核对 + 结论**

```text
每台 decode 节点 KV = 32 × 4.25K × 320 KB ≈ 43.5 GB / 8 ≈ 5.4 GB/卡
权 17.5 + KV 5.4 ≈ 23 GB ≪ 80 GB ✓
```

**结论**：decode 18 台 + prefill 8 台 ≈ 26 台 ≈ **208 张 H800**，配比约
**2:1**。边界三问（都要主动说）：

1. **扩一批 prompt 翻倍就重算**——本例 prefill:decode = 7:13 的机器配比
   对输入长度敏感（进 prompt 16K，prefill 侧就要 28 台）；
2. **B_max 不是显存定的（5.4 GB ≪ 80 GB），是 TPOT 定的**——显存富余正是
   后文讲混部/超卖敢上空间的依据；
3. MFU 与有效带宽是最脆弱的两个假设，必须报出「我按 35% / 70% 估的」。

### 2.3 Knee point：容量拐点的直觉

整台机器的 goodput 曲线长这样：B 从 1 起涨，权重读取被 batch 摊薄，
goodput 近乎线性上升；过了某点 KV 读取开始主导 step 时间（每加一条请求
既多吐 token 又多搬 KV），曲线弯平；再往上 queue 延迟使 p99 撞穿 SLO，
**SLO 合格吞吐（goodput）不升反降**。那个弯就是 knee。

knee 的物理位置本例可直接算：step 里 KV 占比 = 1.36B / (17.5 + 1.36B)，
在 B ≈ 32（KV ≈ 71%）时曲线已开始弯平——所以工程上 knee point 常用
「batch 上限 = 公式反解 + 10% 试探压测」双确认，它不是查表常数：长度
分布变了、KV 量化档切了、prefix 命中率变了，knee 都会跟着挪。

### 2.4 集群公式一句话背下来

```text
nodes = ceil( 峰值并发 / B_max ) × 冗余系数          （decode 侧）
nodes = ceil( 峰值 QPS × 单次 prefill 时延 ) / 水位上限 （prefill 侧）
```

冗余系数怎么取值：N+2 容错 + 60~70% 水位上限（见 §4.3）→ 1.3~1.4；
可用率承诺 99.9% 以上再叠多地域存活冗余。

*（如果考官追问卡时成本：把 §6.1 的公式原地代入即可，不用慌。）*

## 三、削峰与混部/超卖

▶ 面试题：为什么要混部？代价是什么？——**高（Moonshot/字节 JD 关键词）**

### 3.1 全局队列 + 优先级：削峰的第一道闸

削峰不是把请求打回去，是**把「炸的时点」往后推、让每一档资源按优先级
尝到水**：

- 多级队列 + 同档 FIFO（三级队列：付费实时 > 在线 > 离线批）；
- 高优抢占低优 KV 槽位（抢占上限次数，防饿死）；
- 队列长度 × 单请求占用 → 动态预估等待时间，透传给网关侧 429/降级判断，
  **绝不让队无限长**——队一旦长成「所有请求都超时重试」就是重试风暴。

以上是节流「入口」，下面的混部与超卖是节流「出口」——让削不掉的波谷
资源也有活干。

### 3.2 离线混部：在线保证 SLO、离线吃满碎片

离线任务（评测、数据集生成、RL rollout、checkpoint 导出）天然
throughput-oriented、不挑延迟，是在线波谷的填充物。关键三条：

1. **硬隔离打底**：cgroup/MIG/MPS 划份额，离线不能借抖动传回在线；
2. **秒级驱逐**：在线水位上来，离线 10 s 级 kill/preempt，不灰在线 p99；
3. **离线自己也挑食**：驱逐成本高的（长 checkpoint）排在波谷区段，
   追求 GPU-hour 单价，不压任何 SLO。

system-design 篇第五节已列了 JD 关键词与三件套口径，此处不再重复联动，
本文讲它更深的一层——**混部对容量公式的改写**：波谷时段离线吃掉的
「可动用 GPU-hour」要记入成本池（§6.3），因为它直接摊薄单卡成本。

### 3.3 GPU 超卖的尺度与反噬

超卖 = 承诺给租户的并发配额之和 > 物理并发容量。在 CPU 微服务里这是
惯例，在 LLM 推理里它格外凶残：

- **为什么不超白不超**：上面算例 B_max = 32 时 KV 只用 ~7 GB/卡，显存
  大量富余；若按「名义 KV 满打满算」签合同永远不撞车，就是白扔卡；
- **反噬的貌**：并发真撞上来时排队 → p99 TPOT 抖动；短窗口内看不出，
  长期「间歇性 p99 拉高」——这是超卖反噬最典型、也最难排查的指纹；
- **尺度经验口径**：仅当有「画像可同质化的同类租户」（错峰明显）可卖，
  超卖系数经验取值 1.2~1.5；**纯在线独享型大客户的裸模型实例不碰**。

### 3.4 弹性伸缩的触发水位与预热延迟

LLM 实例不是冷启毫秒级服务——预热延迟决定了扩容策略的形状：

| 预热阶段 | 量级 | 说明 |
|---|---|---|
| 实例拉起/镜像 | 秒~分钟 | 取决于镜像分发链 |
| 权重加载 | 140 GB：本地 NVMe ~30 s；走对象存储分钟级 | 权重预热池是必选项 |
| CUDA graph capture | 秒~一分钟 | 枚举 batch 档提前烧热 |
| prefix cache 冷启动 | 与业务预热流量成正相关 | 新实例捞不出 prefix 命中，早期 TTFT 偏高 |

结论两条：**扩容不能在「已经过载」时触发**——触发水位提前量 ≥ 预热延迟
× 当前增速（典型是提前到 60% 水位触发），**水位维持 + 定时扩缩 + spot
预池**三件套的动机正来自这张表；缩容要 drain（停止接新、在途跑完），
drain 不掉的在途请求会按 SLA 直接算违规。

## 四、多租户与配额

▶ 面试题：几十个租户打一个 70B，怎么限流？——**中高（网关+运营交叉题）**

### 4.1 限流的三个维度

| 维度 | 粒度 | 用途 |
|---|---|---|
| **租户配额** | 每租户 token/s 与并发槽 | 防单一租户挤占；合同级 |
| **模型配额** | 70B/8B/embedding 各自池子 | 防大模型挤垮小模型供给 |
| **优先级拦截** | 请求头 priority + 预占水位 | 高优请求能给排队侧开后门 |

### 4.2 公平性 vs 利用率：孤儿的座位

经典矛盾：严格公平（各租户静态分份额）→ 碎片；全力利用率 → 弱租户
饿死。**标准答法 = 「预留 + 借用 + 记账」三段制**：

1. 每租户保底份额（保证最劣 SLO 的下界）；
2. 空闲份额可被借用，借用有记账；
3. 借用者直接承受被驱逐的 p99 抖动，租户配额表里明确写出。

### 4.3 级联故障隔离

推理服务的级联路径很短——**共享层意味着一病俱病**：

- 网关层按租户熔断（某租户超发即 429，不传遍集群）；
- 引擎层单实例异常不回流全局队列（摘除 + 重路由重算 prefill）;
- 慢节点从调度视野里越快移除越好——p99 是尾部的指标，**坏节点的
  每一秒都在直接吃 SLO 预算**；
- 模型版本灰度独立 KV 目录，避免新旧模型「同卡共享 KV 页表」的串扰。

## 五、成本控制

▶ 面试题：单 token 成本怎么算？怎么压？——**高（运营面灵魂拷问）**

### 5.1 tok/s 成本核算口径

公式一步写完，面试时先报公式再报数：

```text
单 token 成本 = 卡时成本 ÷ 实际可持续 goodput（tok/s）
              = 每小时卡数 × 每卡小时价 ÷ (goodput × 3600)
```

> 注：必须用 **goodput**（SLO 合格部分），不是裸吞吐——超 SLO 后刷出的
> token 业务不收钱，只能摊成本。

代入 §2.2 算例（各自声明假设）：decode 集群 18 台 × 8 卡，每卡时 12 元
（伪教学价，仅为演示公式），单台在 B = 32、step 26 ms 下聚合输出
≈ 32 / 26ms ≈ 1230 tok/s：

```text
每小时 goodput ≈ 18 × 1230 × 3600 ≈ 8.0e7 out-tokens/h
每小时成本 ≈ 144 卡 × 12 元 ≈ 1730 元
单百万 output token 成本 ≈ 21.6 元（≈0.0216 元/K tok，数量级锚点）
```

边界：以上**未计 prefill 侧 8 台**、未计波谷空转与混部收入摊销（见 §6.3
的完备口径）；数量级感记一个锚点——70B 级 BF16 自营百万 output token
量级在「几元到几十元」区间，与档位强相关。

### 5.2 成本三板斧

| 斧 | 做什么 | 数量级 | 代价 |
|---|---|---|---|
| **量化降档** | BF16 → FP8/INT4（KV 也跟着量化） | throughput ×1.5~2.5 | 精度回归、长 ctx 需评估 |
| **模型路由（大切小）** | 简单 query 走 8B/14B，难的进 70B | 大头流量分流后成本直接砍半起步 | 需要路由器质量与分级评测 |
| **缓存命中** | prefix cache 命中率从 30% 拉到 70% | TTFT 与 prefill 卡时近乎腰斩 | 不能解决 decode 成本 |

三板斧的顺序有讲究：**第一斧是「性能换钱」，后两斧是「业务换钱」**——
降档先砸在精度预算能覆盖的档位上，路由先砸在 「分级置信度高」的请求
类别上。细节衔接：系统级降本手段（PD 分离异构配比、spot 吃 prefill、
离线混部填谷）已在
[设计分布式推理服务第五节](../../system-design/设计分布式推理服务.md#五弹性伸缩与-gpu-超卖)
定调，本文不再重复；这里补的是**量化口径下的账本身**。

## 六、Incident Playbook（事故 SOP 表）

▶ 面试题：线上 p99 抖动怎么排？KV 打满怎么办？——**高（运维面分水岭）**

下面这张表建议**按「征兆 → 止血 → 根因 → 预防」四列报**，不要背口诀；

| 事故 | 征兆 | 止血（先救火） | 根因（再刨坟） | 预防 |
|---|---|---|---|---|
| **显存 OOM/碎片** | KV 分配失败，抢占风暴、吞吐直降 | 降 `max_num_seqs`、提高抢占阈值、滚动重启 | 长度分布漂移 / 页表碎片 / 大请求滞留 | 长度画像周报、碎片率告警、长请求分桶 |
| **KV 打满 · 排队雪崩** | TTFT p99 阶梯式上升，then 全面超时 | 限流 429 + 高优抢占，直接截断队列 | 突发流量超 knee point，或画像漂移 | 水位 ρ ≤ 60% + 提前扩容（§3.4） |
| **慢节点拖尾** | 单实例 TPOT 3× 中位数，聚合 p99 拉高 | 摘流量 + drain；别重启先看 XID | ECC/降频/慢盘/邻居租户抢占 | DCGM 健康分进调度；硬件分级利用 |
| **发布/灰度异常** | 灰度组 TTFT 上浮 >20%、输出回归集跌分 | 一键回滚 + KV 目录隔离 | kernel 回归/权重热替换/截断对齐问题 | 灰度判据写成表：指标 +幅度 +窗口 |
| **级联雪崩** | 一处超时→上游重试风暴→更广超时 | 网关侧熔断 + 重试带 jitter 限幅 | 重试策略错误放大负载 | 重试预算、舱壁隔离（§4.3） |

**复盘四要素**（答出这一条可以和「救火派」立刻拉开）：

1. **时间轴**：What → When → 触发告警 vs 人工发现（越早发现越有话语权）；
2. **影响面**：SLO 违反时长 × 影响请求占比 × 涉及租户；
3. **根因链**：5-why，每层写或然证据；
4. **行动项**：落到监控告警、容量水位、SOP 增改三类，带 owner 与截止。

## 七、▶ 本专题高频追问（五条）

| 追问 | 答法 |
|---|---|
| **SLO 怎么定？** | 从业务侧反推：交互体感线（TPOT 60 ms ≈ 15~20 tok/s）+ 画像（长度分布/峰谷/prefix 命中）+ 分位数约定（p99）+ 违反分级（P1/P2/P3 机器可读触发判据）。「SLO 不是拍的最优值，是写进告警的最小可防守值」 |
| **容量怎么估？** | 五步链条：画像 → 单卡 B_max（TPOT 反解）→ Little's Law 并发 → 节点数 × 冗余 → 显存闭环。每步报假设，冗余系数由 N+2 容错与 60% 水位联动推。必须能现场再算一次，不能只报总数 |
| **为什么要混部？代价是什么？** | 在线波谷的 GPU-hour 不卖给离线就是纯蒸发——「在线保证 SLO、离线吃满碎片」是集群毛利率主来源。代价：隔离成本（cgroup/MIG）+ 驱逐延迟 + 在线 p99 尾部风险暴露面变大，所以**只在错峰画像成立、且隔离可秒级落**的前提下做 |
| **p99 抖动怎么排？** | 套路：先分「是否单节点指纹」（看单实例 TPOT 分布，3× 中位数即嫌疑）→ 再看「是否画像漂移」（长度分布/峰谷/prefix 命中率对比）→ 最后看「是否级联」（上游重试风暴 × 排队雪崩）。止血三件套：摘节点、限流 429、抢占低优；事后补画像周报 |
| **成本怎么压？** | 报公式（卡时 ÷ goodput）→ 三板斧（量化降档 / 大切小路由 / 缓存命中），量化先谈精度预算、路由先谈分级置信度、缓存先谈命中画像；再把离线混部的 GPU-hour 收入摊进来，给出「看得着的单价」 |
