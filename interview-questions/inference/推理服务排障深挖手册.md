# 推理服务排障深挖手册

> ▶ 面向：被面试官追问「线上 p99 毛刺你怎么排」的读者。
> 读完获得：每个症状的「观测信号 → 排查命令 → 根因树 → 处置 → 预防」排查链。
> 分工口径：[推理服务 SLO 与运营](./推理服务slo与运营.md) 第六节的
> Incident Playbook 是五大事故的 SOP 总表（征兆 → 止血 → 根因 → 预防），
> 本文是它往下一层的「命令与指标细节」——症状在控制台里长什么样、每条根因
> 用什么命令证伪或证实。文中命令与指标字段以 vLLM 0.6+ 与 DCGM 主流版本
> 为准，个别字段随版本改名，部署与面试引用前以所用版本为准自查。

## 一、排障总纲

### 1.1 症状四分：慢、错、挂、贵

| 症状 | 典型表象 | 第一落点 |
|---|---|---|---|
| 慢（延迟） | TTFT 毛刺、TPOT 抖动、goodput 下滑 | Prometheus 引擎看板 |
| 错（质量） | 复读、乱码、答非所问、评测集跌分 | 回归评测 + 单请求重放 |
| 挂（崩溃） | 实例 503、CUDA error、进程退出 | 实例日志 + `dmesg` + XID |
| 贵（成本） | 单位 token 成本爬升、GPU-hour 翻倍 | 卡时 ÷ goodput 对账 |

四分法的用处是**定看板顺序**：慢先看引擎指标，错先看输入与版本，挂先看硬件与日志，贵先看长周期画像漂移。混在一起排就是纯玄学。

### 1.2 排查三板斧

1. **指标先行**——先在 Prometheus 看形状：是全集群、单实例，还是单请求指纹？形状不同，后面两条完全不同路。
2. **实例下钻**——锁定嫌疑实例后，引擎日志、`nvidia-smi dmon`、`dmesg` 三件套同时捞，一定在止血前留证据。
3. **隔离复现**——单请求重放（固定 seed + greedy），把线上症状复刻到最小输入集上，复刻成功才算根因闭环。

两条铁律贯穿全文：**先指标后假设**（不看板不下锅）、**先止血后刨坟**（摘流量、限流、回滚都排在 5-why 前面）。

### 1.3 推理服务必盯指标清单

| 指标 | 代表什么 | 在哪看 |
|---|---|---|---|
| `vllm:time_to_first_token_seconds` | TTFT 直方图，取 p50 与 p99 | vLLM `/metrics` 端点接入 Prometheus |
| `vllm:time_per_output_token_seconds` | TBT/TPOT 直方图 | 同上 |
| `vllm:num_requests_running` / `vllm:num_requests_waiting` | 执行中与排队中的请求数 | 同上 |
| `vllm:gpu_cache_usage_perc` | GPU KV pool 水位 | 同上 |
| `vllm:num_preemptions_total` | 累计抢占计数，看 rate | 同上 |
| 前缀缓存命中率 | prefix cache 命中比例 | 同上，字段名有版本差异（见症状 g） |
| GPU util 与 SM 活跃、降频、功耗 | 卡忙不忙、健不健康 | `nvidia-smi dmon`、`dcgmi dmon` |
| XID 与 ECC | 硬件错误事件 | `dmesg -T`、`nvidia-smi -q`、`dcgmi health` |
| NVLink 计数 | 跨卡链路错误与带宽 | `dcgmi nvlink`、`nvidia-smi nvlink` |

看板叠看提一句：waiting、KV 水位、抢占 rate、命中率四条曲线放同一面板，
形状相加就是诊断——等待涨且水位贴顶是排队雪崩，等待涨但水位低、命中率
跌是前缀失效，等待平但吞吐跌是 batch 构成漂移。单看任何一条都会误判。

## 二、八大症状排查树

每个症状统一格式：观测信号 → 排查命令或字段 → 根因树 → 处置 → 预防。

### 症状 a：TTFT 毛刺与 p99 阶梯上升

- **观测信号**：`vllm:time_to_first_token_seconds` 的 p99 一级一级抬高；同刻 `vllm:num_requests_waiting` 抬升、`vllm:gpu_cache_usage_perc` 逼近 0.9；`vllm:num_requests_running` 反而横盘——说明引擎在排队而不是在算。
- **排查命令**：`rate(vllm:num_requests_waiting[1m])`、`vllm:gpu_cache_usage_perc`、`rate(vllm:num_preemptions_total[5m])` 三条曲线放在同一面板叠看。
- **根因树**（4 条）：
  1. 突发流量越过 knee point——到达率 > 服务率，队列雪崩；证实：waiting 曲线与网关 QPS 曲线同频共振。
  2. 长度画像漂移——输入变长，单请求 KV 占用抬升，KV 池提前见底；证实：请求输入长度直方图与昨日同时段对比。
  3. 抢占风暴牵连——反复重算占掉 prefill 算力；证实：抢占 rate 持续上涨，跳到症状 c。
  4. 前缀命中率骤降——prefill 计算量翻倍、服务率直接腰斩；证实：命中率字段回落，跳到症状 g。
- **处置**：网关限流 429 止血，长尾超长请求单独分桶；确认画像漂移后扩容。
- **预防**：水位按 ρ ≤ 60% 留余量，knee point 写进压测报告，长度画像出周报。

### 症状 b：吞吐骤降但 GPU util 仍高

- **观测信号**：output token 吞吐腰斩，`nvidia-smi dmon` 的 sm% 还在 90+ ——卡在忙但产出少，这是「忙错方向」的经典指纹。
- **排查命令**：`nvidia-smi dmon -s pucm` 看功耗与降频排除硬件；再对比当前 batch 的输入输出长度构成与历史基线。
- **根因树**（3 条）：
  1. batch 构成变了——长输出请求占比上升，decode 步均吞吐被拖长，util 高但每步只前进一个 token；证实：输出长度分位数上移。
  2. 抢占重算白烧算力——`vllm:num_preemptions_total` 的 rate 抬升，被抢占请求重新 prefill 的算力计进 util 却不计进 goodput。
  3. 投机解码失效——draft 接受率塌了（接受率字段名以所用版本为准），draft 前向白跑，util 反而更高。
- **处置**：次优先级流量限流保长输出租户的 TPOT；确认抢占则按症状 c 处理。
- **预防**：goodput 与 util 双指标同板监控，二者背离超过阈值即告警。

### 症状 c：KV 打满与抢占风暴

- **观测信号**：`vllm:gpu_cache_usage_perc` 贴住 1.0，`vllm:num_preemptions_total` 持续上涨，TTFT 全线毛刺。
- **排查命令**：上述三项指标叠看；引擎日志检索 `Preempted`、`Aborted` 字样（日志文案随版本略有出入，以所用版本为准）。
- **根因树**（3 条）：
  1. `max_num_seqs` 与 KV 池 token 容量的账没对齐——并发上限高，池子却装不下这么多请求的自留地；证：单请求实际长度 × `max_num_seqs` 超过池容量。
  2. `max_model_len` 虚高或长请求比例抬头——预算按长上下文留了，实际静态余量被吃死；证：输入长度漂移。
  3. 页表碎片与长会话滞留——老会话占着页不撒手，碎片化分配失败；证：空闲 token 仍有但连续分配持续失败。
- **处置**：先降 `max_num_seqs` 与并发准入线止血；滚动重启回收碎片是最后手段，别一上来就用。
- **预防**：长度分桶调度、碎片率与抢占率双重告警、`max_num_seqs` 纳入容量对账表。

### 症状 d：OOM

- **观测信号**：进程退出或 `CUDA out of memory`，要第一时间分清启动期还是运行期——两者的账完全不同。
- **排查命令**：启动期核对 `gpu_memory_utilization` 与静态账（权重 + 激活 + KV 池预算 vs 物理显存）；运行期周期性 `torch.cuda.memory_summary()` 落盘做时间序列对比。
- **根因树**（3 条）：
  1. 启动期静态账爆了——权重与 KV 预算就装不下，模型还没接到第一个请求；多见于 `max_model_len` 或 `max_num_seqs` 调大之后首启。
  2. CUDA graph 捕获垫高——capture 阶段瞬时多吃显存，日志里卡死在 capturing 环节；vLLM 0.6+ 的 capture 行为随版本变化，以所用版本为准。
  3. 运行期慢泄漏与碎片——memory_summary 里 reserved 持续增长而 allocated 横盘，二者剪刀差就是碎片或泄漏。
- **处置**：启动期直接回退参数；运行期先降并发，重启前把 memory_summary 快照留档。
- **预防**：capture 预留量写进容量表，memory_summary 周期采集并设增长率告警。

### 症状 e：输出质量事故

- **观测信号**：指标面板一切正常，但回归评测跌分、用户报复读或乱码 ——四条实验能确认是「服务侧回归」而非「模型本来的能力上限」。
- **排查命令**：固定 seed + 零温度 greedy 的单请求重放，与基线版本逐 token 对比 logprobs；chat template 做 `git diff`；权重文件 `sha256sum` 对账。
- **根因树**（4 条）：
  1. 量化回归——新量化档在某类 prompt（长上下文、低资源语种、代码）先塌；证：同权重不同量化档的 logprobs 分叉。
  2. chat template 变化——jinja 模板 diff 后发现 system 前缀或特殊 token 变了；证：渲染后 prompt 字符串逐字节对比。
  3. rope scaling 与上下文外推配置错配——长输入退化，短输入无恙。
  4. 权重版本错——sha 对不上，或热替换只换了一半分片。
- **处置**：一键回滚 + KV 目录隔离；质量事故的血是「错误答案在流」，回滚优先级高于一切排查。
- **预防**：发布单必填回归集得分、模板渲染快照、权重 sha 三件套。

### 症状 f：慢节点与硬件

- **观测信号**：单实例 TPOT p99 是同集群中位数的 3 倍；`nvidia-smi dmon` 显示时钟降频；TP 组「一卡慢全组慢」。
- **排查命令**：`nvidia-smi dmon -s pucm` 看功耗、时钟、温度、降频标志；`dmesg -T | grep -i xid` 捞硬件错误；`dcgmi health -s a` 跑健康检查；`dcgmi nvlink` 与 `nvidia-smi nvlink` 看链路计数（子命令形式随版本略有差异，以所用版本为准）。
- **根因树**（3 条）：
  1. 硬件故障——ECC、降频、掉卡，看下面的 XID 码表；
  2. 混部邻居抢占——同机离线任务把功耗墙或盘 IO 抢光；
  3. 慢盘与 IO——checkpoint 加载或 swap 路径挂在机械盘上。

常见 XID 码表（来源为 NVIDIA 官方 XID 文档，见文末口径）：

| XID | 含义 | 嫌疑归属 |
|---|---|---|---|
| 13 | 非法指令或显存越界 | kernel 软件嫌疑大 |
| 31 | GPU MMU page fault | 多为驱动或 kernel 问题 |
| 48 | 双比特 ECC 错误 | 硬件确凿，卡需下线 |
| 79 | GPU fallen off the bus | 供电或 PCIe 级致命故障 |
| 94 | contained ECC error | 已被遏制，可观察运行 |

- **处置**：摘流量 drain。切记不要先重启——`dmesg` 与引擎日志先备份，重启一按证据没了，根因分析直接断链。
- **预防**：DCGM 健康分接入调度器，慢节点先 drain 再诊断写进 SOP。

### 症状 g：前缀缓存命中率骤降

- **观测信号**：命中率指标回落，TTFT 与 prefill 排队同步上升；命中率字段名有版本差异——部分版本为 `vllm:gpu_prefix_cache_hit_rate` 一类的 gauge，较新口径改为 `vllm:prefix_cache_hits_total` 与 `vllm:prefix_cache_queries_total` 的计数对，以所用版本为准。
- **排查命令**：命中率曲线对上发版时间线；实例间命中率分布对比；对线上 prompt 前缀做抽样 diff。
- **根因树**（3 条）：
  1. 路由不带会话亲和——同一会话多轮被散到不同实例，本地 KV 复用失效；证：实例间命中率方差拉大；修：网关侧一致性哈希。
  2. system prompt 抖动——时间戳、追踪 ID 混进前缀头部，每条请求的前缀都不同；证：对 prompt 前 256 token 做聚类 diff。
  3. 截断策略变化——prompt 截断点改动，KV 与历史前缀对不上。
- **处置**：亲和路由上线与回滚上游抖动字段二选一，先恢复命中率。
- **预防**：静态前缀前置（可变字段永远放 prompt 尾部），模板渲染输出纳入发版 diff 清单。

### 症状 h：引擎崩溃复现

- **观测信号**：实例 503，日志现 `CUDA error: an illegal memory access was encountered` 或进程被 kill。
- **排查命令**：`CUDA_LAUNCH_BLOCKING=1` 重放，让异步错误同步到发射点精确定位；`ulimit -c unlimited` 保证 core dump 落盘；`dmesg` 先排除 XID 13 与 31 的硬件嫌疑。
- **根因树**（3 条）：
  1. 自定义 kernel 越界——特定输入形状触发，用最小复现请求集二分定位到触发序列长度或 batch 形状。
  2. 驱动与运行时版本错配——灰度发版后首崩高度指向这一条。
  3. 硬件故障伪装成软件错——XID 79 或 48 后的非法访存是次生症状。
- **处置**：从引擎日志捞崩溃前最后 N 条请求，固化成最小复现请求集；该集合直接进回归测试。
- **预防**：崩溃用例库随时间增长，每次升级必须与回归集对跑一遍。

## 三、两个完整排障故事

以下案例为能力演示所构造，时间线格式为 T 标法——对面试官的加分点。

### 故事一：高峰期 TTFT 翻三倍

- T0（20:04）：告警触发，`TTFT p99 > 1.5 s 持续 5 分钟`，影响面约三成请求。
- T+3min 指标确认：waiting 队列持续膨胀，running 横盘，KV 水位仅 0.5，GPU util 钉在 95%——算在烧但算错了地方；同一面板看到命中率从 62% 掉到 4%，时间锚点上移十分钟有一发上游发布。
- 定位（3min）：跳转症状 g 路径；抽样 prompt 前缀 diff，发现上游 19:58 的发布把 `session_id` 与追踪时间戳塞进了 system prompt 头部，前缀全量失效，prefill 算力需求直接翻倍。
- 处置：网关先行改写洗前缀止血，上游随后回滚该字段；T+25min 命中率回到 60%，T+30min TTFT 全面回落。
- 复盘行动项：system prompt 前缀 sha 进监控告警；发布单加入模板渲染 diff 检查点；本案例固化进应急预案演练库。

### 故事二：夜班吞吐腰斩

- T0（02:17）：一组 TP8 实例 goodput 掉 50%，聚合 TPOT p99 涨到原来的三倍。
- T+3min 指标确认：8 个实例中 1 台的 TPOT p99 是同集群中位数的 4 倍 ——TP 组内一卡慢全组慢，单实例指纹成立。
- 定位（5min）：下钻该实例，`dmesg` 捞到 XID 48（双比特 ECC），`nvidia-smi dmon` 确认该卡已降频保护；DCGM 健康分转红。
- 处置：摘流量 drain → 备机顶上，T+40min 恢复；关键动作是重启前备份 `dmesg` 与引擎日志——前一晚另一个值班的直接 `reboot`，XID 证据清零，硬件厂商以此拒修了。
- 复盘行动项：XID 告警前置到「变慢」而非「崩溃」；DCGM 健康分进调度门限；慢节点自动 drain 流程落地。

### 三·增、Xid 31 的 PDE/PTE 三种变体

Xid 31 是 GPU MMU fault，但根因不止一种，排障要按三种变体分：

- **FAULT_PDE**：大块页表项被解映射（常见于大块显存释放/迁移），表现为
  整段地址失效；修法是按页表粒度重新映射，别把大块直接 unmap。
- **PTE invalid**：页表项无效，通常是驱动/分配器状态不一致；要查
  `nvidia-smi -q` 的 ECC/MMU 计数与最近一次显存分配。
- **DLPack 跨分配器共享所有权**：两个分配器（如 PyTorch 与自定义池）
  共享同一块显存，一方释放后另一方仍持有悬垂指针；修法是统一分配器或
  显式引用计数。
- 数字：原文把每天 **28 次** Xid 31 降到 **0**，处理 7000+ 视频、
  630 videos/min；关键是区分「大块解映射」与「悬垂指针」，不要一律重启。
- 面试句：Xid 31 不是「GPU 坏了」，先看 PDE/PTE 与跨分配器所有权，
  再决定重映射、回滚还是换卡。

## 四、面试怎么讲

排障题的回答框架用 STAR+R：

- Situation：给业务规模感，例如「70B BF16，TP8 × 10 实例，峰值 QPS 200」。
- Task：报 SLO 红线（TTFT p99 ≤ 1.5 s）与当前违反程度。
- Action：按三板斧顺序展开，命令和字段名要说得出——「我先在 Prometheus 看 `vllm:num_requests_waiting` 的形状」这种颗粒度才是加分段。
- Result：SLO 恢复时长、影响请求占比、止血动作清单。
- 复盘：行动项落监控、容量、SOP 三类，各带 owner。

两条原则贯穿始终：**先指标后假设**——不看板不开口猜；**先止血后刨坟**——摘流量、限流、回滚永远排在 5-why 之前。面试官追问细节时，往「症状 → 指标 → 命令」的下钻链条上挂，不要往概念上飘。

三个常见扣分点一并避开：

1. 只背术语不报命令——说出 `nvidia-smi dmon` 与 `dmesg` 才算干过；
2. 一上来就重启——等于告诉对方你不懂得固定证据；
3. 没有影响面与时长——「SLO 破了几分钟、多少占比」是 STAR 的 R 的及格线。

## ▶ 面试题

Q1「线上 p99 毛刺怎么排？」 A：三板斧——先在 Prometheus 分形（全集群、单实例、单请求），再下钻实例三件套（日志、dmon、`dmesg`），最后单请求重放闭环。毛刺形态决定分支：waiting 队列膨胀按症状 a，单实例慢按症状 f，抢占 rate 抬升按症状 c。

Q2「GPU util 很高但吞吐骤降，说明什么？」 A：卡在忙错方向。三选一排查：batch 构成漂移（长输出占比上升）、抢占重算白烧算力（看 `vllm:num_preemptions_total` 的 rate）、投机解码接受率崩塌。goodput 与 util 必须同板对比，背离即告警。

Q3「KV 打满抢占风暴怎么止血？」 A：先降 `max_num_seqs` 与并发准入线把待分配压力卸掉，再查账：并发上限 × 实际长度是否超池容量、`max_model_len` 是否虚高、页表碎片是否让连续分配失败。滚动重启是最后手段而非第一步。

Q4「启动期 OOM 与运行期 OOM 怎么区分？」 A：时间锚——第一请求前崩是启动期，静态账（权重 + 激活 + KV 预算）与 `gpu_memory_utilization` 对账；运行中慢涨是运行期，周期 dump `torch.cuda.memory_summary()`，看 reserved 与 allocated 的剪刀差定位碎片与泄漏，CUDA graph 捕获垫高另算一类。

Q5「灰度发布后输出质量塌了，如何定位是哪一环？」 A：四类分叉同时取证：零温度重放逐 token 对比 logprobs 判定量化回归；渲染后 prompt 逐字节对比判定模板变化；长短输入错位退化判 rope 配置；`sha256sum` 对账判权重版本。回滚优先于任何定位。

Q6「单实例变慢，怎么证明是硬件问题？」 A：三条证据链——`dmesg` 捞 XID（48 需下线、79 致命、13 偏软件嫌疑）、`nvidia-smi dmon` 看降频与功耗、DCGM 健康分红。 TP 组内一卡慢全组慢是落指纹放大器；重启前固定证据再处置。
