## 〇、第一性问题：调度 = 性能上限之争

推理引擎的性能上限由一个朴素问题决定：**谁能把 decode batch 开到更大，同时不破坏
decode 延迟**。拆开看，这其实是两个正交的子问题：

- **能不能塞下（内存线）**：KV Cache 占显存的大头，旧式连续预分配浪费 60%–80%，
  等效卡死了 batch 上限。这条线由 PagedAttention 解决。
- **塞进来后怎么排（调度线）**：batch 内 prefill 和 decode 互相挤占、长 prompt 把
  decode 挡死数秒、KV 耗尽时踢谁。这条线由 ORCA → Sarathi → 今天的 vLLM V1
  一步步解决。

金句先记住：**PagedAttention 解决能不能塞下，ORCA→Sarathi 解决塞进来后怎么排。**
两条线正交，vLLM 是把两者焊在一起的第一代引擎（SOSP'23）。本文主线是第二条线。

回答「CB 为什么提升吞吐」时一定不要停在「残批利用率高」四个字，要落到 roofline：
decode 是带宽 bound，batch 内权重只读一份，batch 越大权重摊销越充分——GPU 利用率
和 decode batch 大小近线性，所以让 decode batch **永远攒满**就是吞吐的全部秘密。
decode batch 上限受双约束钳制：**KV 显存容量**（决定再大可塞多少）和 **TPOT SLO**
（再大每步变慢）。全部调度技术本质上都是在这两个约束里折腾。

## 一、三代调度范式：FT → ORCA → Sarathi

### 1.1 第一代：请求级整批（FasterTransformer，2019）

NVIDIA FasterTransformer（2019 年开源）采用请求级批处理：凑满一整批一起 prefill、
一起 decode，整批跑完才放下一批。两个结构性问题：

- **批内气泡**：批内各条输出长度不等，先完成的干等最后一条——卡槽被占着空转；
- **批间等待**：新请求必须等整批收尾才能进。

在这个范式下「TBT 好看、吞吐崩」是宿命：Sarathi-Serve 把它归类为 decode-prioritizing
（TBT 优先、牺牲批满率）。2023 年 TRT-LLM 跟进 iteration 级能力时换了个名字叫
in-flight batching——本质是同一动作。

### 1.2 第二代：iteration-level scheduling（ORCA，OSDI'22）

ORCA（OSDI'22，Yu et al.）把调度粒度从「请求」降到「一次 forward iteration」，配
合 selective batching（matmul 类算子跨请求共批，attention 按请求各自算），请求可以
随时进出 batch。收益落在 roofline 上：decode batch 永远攒满 → GPT-3 175B 相同延迟
档下吞吐 **36.9×**（ORCA vs NVIDIA FasterTransformer，OSDI'22）。

但 ORCA 只解决了一半：它仍是 **prefill-prioritizing**——长 prompt 进来整块 prefill
硬插在 decode 前面，所有在跑的 decode 被一个 8K/30K 的 prefill 挡死（generation
stall）；PP 部署下 prefill/decode 的 micro-batch 时长不齐还会打出 PP 气泡。这两个
窟窿就是第三代要补的。

### 1.3 第三代：chunked prefill + stall-free（Sarathi → Sarathi-Serve）

Sarathi（arXiv 2023-08）和 Sarathi-Serve（OSDI'24）的解法定型了今天所有主流引擎的
默认形态，三点核心：

1. **chunked prefill**：把长 prompt 的 prefill 切成 chunk，切进 decode iteration 混排；
2. **decode-maximal / stall-free**：每步先装满 running decode，再续半成品的 prefill
   chunk，新请求按剩余 budget 插 chunk——decode 永不被大块 prefill 挡死；
3. **token budget 钳死**：每次迭代 token 总量被预算钳死 → 每步时长可预测 →
   TBT/ITL 的 p99 稳。

在相同 SLO 下 Sarathi-Serve 可服务的容量是 vLLM（2024 形态，prefill-prioritizing）
的 **2.6×/3.7×/5.6×**（Mistral-7B 单 A100、Yi-34B 双 A100、Falcon-180B 8×A100 PP，
OSDI'24）。2024 年后 chunked prefill 成为所有主流引擎的默认；vLLM V1 直接把它做成
「decode 优先 + 塞不下自动切块」的内建行为。

## 二、PagedAttention：调度器的内存底座

分页类比和「20%~40% 有效占用」的直觉在基础篇讲过，本文只补三笔和调度器直接挂钩
的账（全部引 vLLM 论文，SOSP'23）：

- **浪费上界**：旧系统 KV 有效占用仅 **20.4%–38.2%（60%–80% 是预留与内外部
  碎片）**，PagedAttention 把浪费压到 ≈0（每请求最多浪费最后一个不满块的 <1
  block）。显存省出来等效多塞 **2.2×–4.3×** 并发 → 同延迟吞吐 **2–4×**（vLLM
  vs FT/Orca，OPT-13B 同延迟 2.2×/4.3×，更大并发档）。注意：**2–4× 的基线是
  FT/Orca，和 ORCA 的 36.9× 基线不同，两组数字不能串乘**。
- **共享 = 调度 capacity**：parallel sampling 共享 KV 省显存 **6.1%–9.8%（Alpaca）**
  与 **16.2%–30.5%（ShareGPT）**，beam search 省 **37.6%–55.2% / 44.3%–66.3%（同
  为 SOSP'23 口径）**。省下的显存全部折算回 batch 并发——这才是 Prefix Cache 后来
  成为 TTFT 主武器的原因。
- **块大小是调度参数不是玄学**：块大 kernel 并行度好但内部碎片多、跨请求共享率降；
  块小 block table 变长、索引开销大。论文推荐 16，vLLM 沿用为默认。

调度器配套三条专属规则（都来自论文）：**FCFS**（论文明确把「先到先完成、防饿死」
列为目标）、**LIFO 逐出**（KV 耗尽时逐出**最晚加入**的请求）、**all-or-nothing +
sequence group gang-scheduling**（一条请求的 KV 要么整组放得下要么不进，beam
search 的候选按 group 整组调度）。

## 三、Chunked Prefill 深入：stall 怎么来的、budget 怎么定

### 3.1 Stall 的根因：两种性质的前向挤在一条时间里

prefill 一次算数千到数万 token，compute-bound；decode 一步只算一个 token，带宽
bound。硬把整块 prefill 插进 decode 流（2024 前 vLLM 默认 prefill-prioritizing），
后果可量化：一次 generation stall 可以长达**数秒**（Yi-34B，2×A100，128 并发，
Sarathi-Serve OSDI'24 Fig.1a）；朴素 hybrid batching 相对 decode-only 的 TBT 恶化
上界 **28.3×**（同上 §4.2）。

### 3.2 Sarathi 的算术直觉：decode 是「带宽小偷」，prefill chunk 是「算力甜点」

decode 的 arithmetic intensity 极低，GPU 算力根本吃不饱；prefill chunk 恰好是算力
甜点。同批混排后**prefill 占算力、decode 白蹭带宽**——各取所需，这就是
decode-maximal batching 的全部分母。Sarathi 前作的量化收益：LLaMA-13B decode
**10×**、端到端 **1.33×**；GPT-3 PP 场景气泡减 **6.29×**、端到端 **1.91×**
（arXiv 2308.16369）。

### 3.3 Token budget：吞吐-延迟的单一主旋钮

每次迭代允许进入 batch 的 token 总量（running decode 已发 token + prefill chunk
token 之和）被 budget 钳死。Sarathi-Serve 两个档位要记住：**512（strict，P99 TBT=
100ms 的严 SLO）vs 2048（relaxed，SLO 松则开大，LLaMA2-70B 的 relaxed 档用
1536）**（同上 §5）。严 SLO 下 capacity 做到 vLLM 的 **3.5×**（P99 TBT=100ms，
Mistral-7B，同上 §5）。

### 3.4 Tile quantization 陷阱：257 不是 256

GPU kernel 按 tile（典型 128/256）分块执行，token 数不对齐会多占一整个 tile、拖
跨整个 step：chunk **257 vs 256 的 prefill 时间差 +32%（tile quantization，
Sarathi-Serve §4.3）**。落地结论：budget 和 chunk size 一律对齐 256 的倍数
（256/512/1024/2048），profiling 里见到非对齐值直接当 bug 修。

### 3.5 分块的代价：KV 被重复读

切成 chunk 后，先算的 chunk 的 KV 要被后续每个 chunk 重复读——这是 chunked
prefill 的内生开销。量化口径：chunk=512 时总 overhead 控制在 **25% 以内**、2048
量级时可忽略（同上 §5.4）。所以「切多小」是 stall 平滑度与 overhead 的对账，不是
越小越好。

## 四、抢占与恢复：V1 为什么只剩 RECOMPUTE

**触发**：running 请求扩张 KV 时 free block 不足 → 调度器按 LIFO 逐出最后加入的请求，
回收其块给其他请求续命。

**恢复的两种姿势**（V0 都有）：

| | SWAP（V0 遗留） | RECOMPUTE（V1 唯一） |
|---|---|---|
| 动作 | KV 整块搬进 CPU pinned 内存，召回再搬回 | 召回时把 prompt + 已生成 token 拼成新 prompt，一次 chunked prefill 全算完 |
| 代价 | 占等量 CPU 内存池 + 双向拷贝干扰解码带宽 | 一次 prefill 的算力 |
| V1 名下 | 已删 | 默认 |

V1 只留 RECOMPUTE，docs 的原话是 recomputation has lower overhead in the V1
architecture，白话拆三条 why：① V1 chunk + decode 优先的调度让重算天然亲和——
重算本身就能当一次 chunked prefill 排进去；② swap 的双向拷贝与 DMA 会干扰 decode
的带宽敏感路径；③ prefix caching 默认开，重算大多命中缓存，「重算」往往是查表。
swap vs recompute 更系统的因子对账（带宽距离、前缀长度、在线负载三因子）见
[长上下文推理与 KV 多级体系](./长上下文推理与kv体系.md#四kv-多级存储体系2026-工程主线)，
本文只串联不展开。

**生产护栏**：抢占次数有 Prometheus 指标，频繁抢占不是正常工况而是容量信号——
调大 gpu_memory_utilization、调小 max_num_seqs / max_num_batched_tokens、或加
TP/PP。两个补救钉：watermark（预留一部分 free block 防预占领发）与整 prompt
放得下方可 admit 的准入开关（对应配置项就是防「切成 chunk 跑到一半没块」）。

## 五、公平性与优先级

默认 FCFS，论文级目标就是防饿死。v0.9.2 起支持 priority 调度：**priority 值小者
优先、同值 FIFO**——但它只定入队顺序，不是真抢占，不给高优请求腾 KV。高优进来
靠的是低优请求被 LIFO 逐出 + watermark 预留的组合。

starvation 的两个真实成因，答出来即区分度：

1. **低优请求被连续插队**：priority 调参不当 → 解法是 aging（等待越久优先级自动
   抬升）——这个 Mechanism 的名字当面说出来；
2. **超长 prompt 永远拼不进 token budget**：decode 优先策略下 running decode 先装满，
   剩余 budget 不够超长短 prompt 的第一块 → 解法是单独给 long prompt 一个 cap
   （对应 long_prefill_token_threshold 一类配置），保证它迟早被切进去。

## 六、2025+：异步调度与「Python 才是最后一个瓶颈」

GPU 前向被压到 ~**5ms/步**（Llama-8B 单步，H100，vLLM V1 alpha blog，2025-01-27）
之后，scheduler 的 Python 循环、KV manager 记账、block table diff 这些 CPU 开销开始
吃掉 decode 间隔——**2025 年推这些到底是优化什么？答案是 CPU 侧——Python 才是
最后一个瓶颈。**

解法链是逐步「调度与 GPU 执行重叠」：

- **v0.6.0（2024-09）**：API 层多进程，API 开销退出 Engine 关键路径；
- **V1 EngineCore（2025-01-27 alpha，v0.8.0 2025-03-18 转默认）**：EngineCore 独立
  进程，每步「先 schedule → launch → 立刻开始下一步的 schedule」，吞吐 V1 vs V0
  **1.7×**（同上 blog）；
- **async scheduling（v0.10.0，2025-08，experimental）**：乐观预测——调度第 N 步时
  第 N−1 步还在 GPU 上跑，假设无早 stop 直接预排下一步，采样回来再修正。代价明
  确：流式输出晚一拍、依赖采样结果的特性（如某些 spec decode 变体）难支持。

SGLang 的对应物是 overlap scheduler + Router Rust 化（2026 版本线见
[推理引擎 2026 新进展](./推理引擎2026新进展.md)）；设计层面 Vidur 这类 simulator
也在把调度策略做成可离线寻优的对象，面试提到存在即可。

## 七、DP/PD 下调度器在哪里

TP/PP 是单 EngineCore 统管所有 worker 同步执行；DP attention / DP 部署是**每 rank
各带独立 scheduler + KV pool**，前端 DP coordinator / Router 分发请求；PD 分离则再往
上一层：

- **各自为政**：P 池和 D 池各自独立的 scheduler 与 KV pool，P 池的调度目标是
  TTFT/吞吐、D 池是 TPOT/ITL——**配比是调度问题不是容量问题**（两段资源形态、
  并行度、延迟约束完全不同，这是 DistServe 的核心洞察），DistServe 凭每段既定的
  tailored 并行度 + 调度拿到 **7.4× goodput**、或同等 goodput 下 SLO 收紧
  **12.6×**（DistServe，OSDI'24）。配比算例与反推公式挂
  [infra 面试计算题专项 - PD 分离配比](./infra面试计算题专项.md#六pd-分离配比)。
- **proxy/router 角色感知 admission**：请求在 P 端算完 prefill 后 KV 经 connector
  （NIXL / Mooncake / LMCache 等）投递到 D 端，再由 D 端调度器接管 decode。
- **KV 亲和路由**：每 DP rank 独立 KV pool 后，请求路由去哪台直接决定 prefix cache
  命中率——调度逻辑正在从「单引擎内」上移到「admission + routing + KV-aware 集群
  层」，2026 的 vLLM Router/Dynamo KV-event aware routing 是佐证锚点。

spec decode 与调度器的耦合在 V1 里被抽象得很漂亮：V1 调度的输出就是
{request_id: num_tokens}，不区分 prefill/decode——spec decode 只是 num_tokens>1，
prefix cache、chunked prefill、spec 全在这个抽象下无侵兼容。代价藏在资源侧：draft
越激进每步要预留的 KV 槽位越多，接受率波动还会打到 token budget——「spec decode
免费提速」是市场话术，工程上 KV 与 budget 都要多花钱。

## 九、调度旋钮清单（vLLM V1 v0.8+ 为参照，按 SLO 目标分组）

先记住金句：**max_num_batched_tokens 就是吞吐-延迟的主旋钮**——开大吞吐/TTFT 好
但 ITL 毛刺，开小 ITL 平、decode 干净但 prefill 慢。Sarathi-Serve 512 vs 2048 的实
验就是这条曲线的论文版；预算必须对齐 tile（256/512/1024/2048，257 是 **+32% 的
反面教材**）。

- **吞吐优先**：budget 开大（docs 官方建议吞吐导向 >8192）、max_num_seqs 开大
  （V1 默认 1024 量级）、gpu_memory_utilization 0.9→0.95、prefix caching 开、
  async scheduling 开。
- **TTFT**：budget 开大（一步塞更多 prefill；offline 场景默认值在 16384 量级、API
  server 默认值在 8192 量级）、prefix caching 开（命中跳块，miss 时吞吐损失 <1%）、
  多模态再配 processor cache + 非阻塞预处理。
- **TBT/ITL**：budget 关小（2048 量级——docs 原文 Smaller values achieve better ITL
  because there are fewer prefills slowing down decodes）、给 long prompt 单独 cap、
  stream_interval 收 1、async scheduling 开、避免 PP（通信进 decode 路径），TP 或
  同节点 EP。
- **防饥饿**：FCFS 默认、priority 租户化、watermark 0.01–0.05 预留、整 prompt 放得
  下才 admit、配 max_num_queued 类上限卡住等待队列。
- **KV 压力大**：gpu_memory_utilization 开大、max_num_seqs 关小、FP8 KV、prefix
  caching 开、极端情况加 PP 腾显存。

## 十、工程议题 8 条（生产视角，逐条可当案例讲）

1. **调度 CPU 开销成新瓶颈**：GPU ~5ms/步之后，scheduler Python 循环 + KV manager
   记账 + block table diff 会吃掉整个 decode 间隔——gc 抖动也要算。解法链见第六节。
2. **抢占的级联抖动**：preemption 指标飙升是容量不足的信号，不是「调度器在工作」。
   线上要的是 admission control 把请求挡在门外，而不是看着它抢。
3. **优先级不是真抢占**：priority 只定入队顺序；真腾让靠低优被 LIFO 逐出 +
   watermark 预留，两者必须配套。
4. **PD 配比是调度问题不是容量问题**：P/D 资源形态、并行度、延迟约束完全不同，
   配比由 SLO + prompt:output 长度比反推（算例见计算题专项第六节）。
5. **DP 下的 KV 亲和路由**：每 rank 独立 KV pool 后，请求去哪台决定 prefix cache
   命中率——调度已上移到 admission + routing 层，这是 2026 新增佐证点。
6. **长 prompt × chunked prefill 的踩坑**：整 prompt 放不下才 admit 这条开关默认
   存在，就是因为「切成 chunk 后跑到一半没块」——decode 被咬 + prefill 报废。
7. **Starvation 的两种真实场景**：priority 低优被连续插（aging）与超长 prompt 在
   decode 优先下拼不进剩余 budget（long prompt 独立 cap）。
8. **spec decode 的 KV 预留**：draft 越激进每步预留 KV 槽位越多、接受率波动打到
   budget——不是免费提速，而是用钱换延迟。

## 十一、▶ 面试题 10 条（★ 星级 + 一口答案）

1. **★★★★★ CB 为什么提升吞吐？** —— 落 roofline：decode 带宽 bound，batch 越大
   权重读摊销越充分；ORCA 让 decode batch 永远攒满，同延迟 **36.9×**（OSDI'22）。
2. **★★★★★ V0 默认调度 vs V1 差别？** —— V0 整块 prefill + prefill-prioritizing；
   V1 decode 优先 + chunked prefill 默认开 + {request_id: num_tokens} 抽象。
   stall-free 才是生产 SLO 的解。
3. **★★★★ chunked prefill 和 prefix caching 矛盾吗？** —— 正交互补：前者管单次
   prefill 怎么插进 decode 流，后者管跨请求不重复算 prefix；V1 默认都开。
4. **★★★★ KV 不够为什么不能抢最老请求？** —— FCFS 的目标是「先到先完成」，抢最老
   等于剥夺它的完成时间保证；所以 LIFO 逐出 + all-or-nothing。
5. **★★★★ 抢占后怎么恢复？swap vs recompute？** —— V1 只剩 RECOMPUTE：prompt +
   已生成 token 拼新 prompt，一次 chunked prefill 全算完；swap 占等量 CPU 内存 +
   双向带宽；prefix caching 使重算更便宜。
6. **★★★★ max_num_batched_tokens 怎么调？** —— 吞吐/TTFT 开大（>8192）、ITL 开小
   （2048 量级）；必须对齐 tile 倍数（257 vs 256 慢 **32% 以上**）；生产靠一次
   profiling 定档，不靠手感。
7. **★★★ ORCA 为什么只解决一半？** —— iteration-level 解决残批（吞吐）但
   prefill-prioritizing 让长 prompt 挡死 decode（stall 数秒）、PP 气泡不齐；
   Sarathi-Serve 补齐这两块（**2.6–5.6×** 容量）。
8. **★★★ TBT/ITL 压不住，第一步看哪？** —— 先查 budget 是不是太大 → chunked
   prefill / long prompt cap 关没关 → preemption 率 → async scheduling 没开没。
9. **★★★ PD 分离里 scheduler 放哪？** —— P/D 各自独立 scheduler + KV pool，
   proxy/router 角色感知 admission + KV 亲和路由；DistServe **7.4×** goodput。
10. **★★★ spec decode 起来后调度要不要改？** —— V1 抽象 {request_id: num_tokens}，
    spec 只是 num_tokens>1；代价在 KV 预留与 budget 波动——抽象设计好之后功能都
    是参数问题。
