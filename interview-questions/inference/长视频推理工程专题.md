## 一、主线直觉：视频的 token 是乘法，而乘法没有免费的压缩

一句话主线：**视频的 token 数是乘法——帧数 × 每帧 token，而这个乘法没有
任何压缩是免费的**。文本里你压缩的是信息量；视频里你压缩的首先是**时间
分辨率和空间分辨率两个轴**——采样率 FPS 决定你能看到多快的事件，每帧
token 数决定你能看清多小的东西。工程化长视频推理，就是在这两个轴上做预算
分配（采样与合并），再把省不动的部分转移到系统侧（KV 分层、剪枝、流式
检索）。

为什么说是「长上下文问题在视觉域的重现」？帧间高冗余、attention 平方
开销、KV 线性增长——这三件事文本长上下文全都有，所以 2025–2026 视频
侧的解法谱系（稀疏 / 压缩 / 检索 / 分层）与文本长上下文高度同构，只是
多了「时间轴」这一维。面试里碰到视频题，第一反应应该是先算乘法账，再
把文本长上下文的武器库平移过来对号入座。

## 二、一小时视频的 token 账：五档代表方案

先把全篇最重要的数字放在最前面。统一口径：**一小时视频按 1fps 采样，共 3600 帧**。
五种方案的每帧 token 与一小时总账（全部按各官方/论文口径，推导值已标注）：

| 方案 | 每帧 token | 1h @1fps 总账 | 口径与来源 |
|---|---|---|---|
| LLaMA-VID | **每帧仅 2 个**（2023-11） | **仅 7200 token**（推导） | arXiv:2311.17043 |
| Gemini 3 | **默认 70**、高档 280（2026-10） | **总量 25.2 万** | Google Cloud 官方文档 |
| Qwen2.5-VL | **约 192–256**（推导） | **约 69–92 万**（推导） | HF 模型卡 2025-01 公式推导 |
| LLaVA-OneVision | **整帧 196** | **总量 70.6 万**（推导） | 配额制口径 |
| Gemini 3 之前 | **固定 258**、低分 66 | **总量 92.9 万**（推导） | Google Cloud 官方文档 2026-10 |

把总账再折成「上下文窗口能装几分钟」，就是面试里的直读计算题：

- **128K 窗口**（70 token/帧）：128000 ÷ 70 ≈ 1828 秒 ≈ **三十分钟左右**；
  Google 官方口径写作 **128K 约等于 25 分钟视频**（2026-10 文档，官方预留
  了非视频 token 的余量，两个口径都要会说）。
- **128K 窗口**（258 token/帧，Gemini 3 之前老口径）：128000 ÷ 258 ≈ 496
  秒 ≈ **八点三分钟**。
- **128K 窗口**（Qwen 256 token/帧）：同上量级，约 **八点三分钟**；按
  192 token/帧则约 **十一分钟**。
- **LLaMA-VID**（2 token/帧）：128K 能装 **约 17.8 小时**，一小时视频连
  零头都用不完——代价后面第三节专门讲。
- **硬塞派顶点 LWM**：1M 上下文模型，约 **3900 帧 × 256 token ≈ 装满
  1M 窗口**（1M 上下文与「1 小时 YouTube QA」为论文/repo 口径
  arXiv:2402.08268，2024-02；帧 × token 乘积为调研推导）。

口径隔离提醒（面试里千万别混）：Gemini 的「token per frame」是**媒体
tokenization 单位**，Qwen 的「28×28 像素折 1 个 token」是 **ViT patch
口径**，两者不能直接对数比大小；Gemini 3 从 258 到 70 是 **tokenization
换代**（固定长度 → 可变序列长度），不是单纯的「压缩率赢了 3.7 倍」。

## 三、token 从哪来：理解路径与生成路径两本账

### 3.1 路径 A（VLM 理解）：按「帧」对齐文本 token 预算

主流 VLM 把视频解码成帧序列，每帧过一个 image ViT，**每帧 token 数 =
每帧像素 ÷（patch² × merger²）**。以 Qwen2.5-VL 口径为锚（HF 模型卡，
2025-01）：**每 28×28 像素折 1 个 token**，单图 token 范围 **4–16384**，
视频支持动态 FPS 采样。两个推导锚点：**按 448×448 的帧约 256 token**、
官方示例 `max_pixels=360×420` 对应**约 192 token/帧**（均为调研按官方
公式的推导值，官方未直接给这两个分辨率的数字）。

于是 1 小时 @1fps = 3600 帧 ≈ **69–92 万 token**——远超 128K，这就是
「视频题先是计算题」的原因。

### 3.2 路径 B（生成/世界模型）：按「时空 patch」追求物理压缩率

生成侧不看「每帧多少 token」，而是让连续/离散视频 tokenizer 直接在像素
立方体上做时空压缩。标尺是 NVIDIA Cosmos Tokenizer（arXiv:2501.03575，
2024-12；README 2025-02 核验）：空间压缩 **8 倍或 16 倍**、时序压缩
**4 倍或 8 倍**，总压缩率最高 **2048 倍（即 8×16×16 的乘积）**，比
此前 SOTA **高 8 倍、快 12 倍**。

两条路径的差异本身就是面试考点：理解路径按「帧」对齐文本 token 预算，
工程重心在采样与合并；生成路径按「时空 patch」追求物理存储压缩率，
工程重心在 tokenizer 训练与重建保真。被问「视频 token 怎么算」时先问
一句「理解还是生成」，直接分出深浅。

## 四、省 token 三板斧之一：帧采样发生在 CPU 解码层

最朴素的是**均匀采样 / 固定 FPS**——Gemini 默认 **1fps**，官方文档可设
自定义 FPS，长视频建议 **低于 1fps**（Google Cloud video-understanding
文档，2026-10 核验）。进阶是**基于内容的关键帧选择**：镜头切换 / 光流 /
帧间相似度挑帧，省的是「静止镜头被反复编码」的浪费。

工程现实里最容易被忽略的一点：**采样发生在 CPU 解码层，不在模型侧**。
也就是说省 token 的第一刀在 mp4 还没变成 tensor 之前就落下了——这决定
了解码本身是 serving 侧的显式资源项（详见第六节 vLLM 四解码后端与
NVDEC 显存预算），而不是免费的预处理。面试答「怎么降视频成本」如果
张口就是量化，多半会被追问「你帧是在哪一层采的」。

## 五、省 token 三板斧之二：visual token 合并的谱系

采样砍的是时间轴的帧数，合并砍的是空间轴（以及跨帧）的 token 数。谱系
按压缩激进度排：

1. **ToMe**（arXiv:2210.09461，2022；ICLR 2023 Oral）：证明 ViT 内逐层
   bipartite matching 合并相似 token，可 **2 倍提速**、掉点仅
   **0.2–0.3 个百分点**，且视频上能跨帧合并同一物体——「相似 token
   本来就该被合并」的开山之作。
2. **VideoLLaMA3**（arXiv:2501.13106，2025-01，阿里 DAMO）：relevance
   驱动的中间态，按 token 相似度减少视频视觉 token 数量，追求「更
   精确且更紧凑」的表示。
3. **LLaMA-VID**（arXiv:2311.17043，2023-11）：走到极端，**每帧只留
   2 个 token**——context token 按用户 query 编码全局、content token
   保留帧内线索；1 小时 @1fps 只要 **7200 token**，号称支持小时级视频。
   这是「压缩率 vs 细节保留」轴的极端点：**对 OOV 细节问题必然掉精度**，
   面试里要主动说出这个代价，否则等于没读过原论文的立场。

合并路线的统一代价记一句话：**采样丢动作（时域事件），合并丢小目标
（空域细节）**——选哪板斧取决于业务在意哪个轴。

## 六、省 token 三板斧之三：KV 压缩与分层检索

帧与 token 都省完之后，省不动的部分转系统侧。两层做法暗合文本长
上下文：

- **prefill 后压缩：VidKV**（arXiv:2503.16257，2025-03）做 video LLM
  的 **1.x-bit KV 量化**，即插即用路线（本调研仅核验标题与年份，内部
  增益数字未读原文，不引细节）。
- **训练-free 检索式：ReKV**（ICLR 2025；GitHub Becomebright/ReKV
  2026-09 仍在更新）：流式视频 QA 场景，把视频 KV 滑窗留在 GPU、余量
  落 RAM/磁盘；query 到达时用检索器把相关帧的 KV 拉回 GPU，实现
  「**视频分析与问答分离到不同进程/GPU**」。ReKV 是整个谱系里唯一
  值得画完整系统图的代表作：它把长视频问题从「塞进去」转换成
  「**存得久、查得回**」——本质就是 RAG 的思想用在了 KV 上，可叫
  RAG-of-KV。

白板题预警：能把 ReKV 的「滑窗 attention → KV 落盘 → 检索拉回 → 跨
进程/跨 GPU 生成」四段完整画出来，是 streaming QA 题的深档分水岭。

## 七、时空位置编码：M-RoPE → 绝对时间 → Interleaved

文本 RoPE 只有一维，视频有两到三维（时间/高/宽）。三代演进：

1. **M-RoPE**（Qwen2-VL，arXiv:2409.12191，2024-09）：位置拆成
   时间/高/宽 三组，进 RoPE 的不同频段。
2. **绝对时间对齐**（Qwen2.5-VL，2025-01）：在时间维度做绝对时间
   编码——动态 FPS 采样下模型仍知道「第几秒」，这是**秒级事件定位**
   能力的结构性来源。
3. **Interleaved-MRoPE + Text–Timestamp 对齐**（Qwen3-VL，2025-09
   首发；论文 arXiv:2511.21631，2025-11）：原生 **256K 上下文**、
   可外推到 **1M**，官方口径支持小时级视频全召回与秒级索引。

深档工程细节（极适合被追问）：Qwen2.5-VL 长输入用 **YaRN 斜坡**（
`mrope_section: [16,24,24]`，factor 4），但**官方模型卡明说 YaRN
显著损害时空定位任务**，长视频建议直接调大 `max_position_embeddings`
（如 64k）——因为 MRoPE 的频段拆分对 position id 更经济。回答范式：
「外推方法不是免费的，YaRN 保文本困惑度但伤时空定位，视频场景改用
增大位置编码上限」。标准 RoPE/ YaRN 基础见
[位置编码与norm](../llm基础/位置编码与norm.md)，本篇不重复。

## 八、生产参数面：vLLM 视频管线与坑位（2026-10 docs 口径）

这一节是全篇的工程重心，也是社招 infra 面最爱追问的部分。完整数据流：

上传 mp4 → 解码抽帧（四后端可选）→ 动态 FPS + pixel 预算 → ViT + merger
出 vision token →（可选）视频 token 剪枝 → 拼接进 prefill → KV 侧可选
量化 / ReKV 式分层 → decode 输出（decode 侧与纯文本同构，见
[多模态推理专题](./多模态推理专题.md)）。

### 8.1 解码：四种后端与 GPU NVDEC 显存预算

vLLM 已支持**四种视频解码后端**（vLLM docs，2026-10 核验）：
`opencv` / `torchcodec` / `pynvvideocodec` / `deepstream`。要点：

- CPU FFmpeg 解码在**大视频轻推理场景**（典型如视频打标）会成为瓶颈，
  官方因此提供两档 GPU NVDEC 后端——**解码消耗已经是 serving 侧的
  显式资源项**，不是免费预处理。
- GPU NVDEC 解码需要 **MPS** 与独立显存预算，参数为
  `--mm-ipc-gpu-memory-gb`。
- `pynvvideocodec` **默认并发解码位为 2**，每增加一位吃额外显存预留。

### 8.2 token 预算参数：max_pixels 与 total_pixels

Qwen 系参数面用 `max_pixels`（单帧上限）与 `total_pixels`（整段视频
上限）控预算。vLLM docs 示例预算值 `total_pixels = 20480×28×28`，即
**约 2 万 token/视频**——这是「上传端不限、引擎侧硬顶」的工程兜底，
生产上一定要设，否则一条 4K 长视频就能把 prefill 队列打爆。

### 8.3 视频 token 剪枝：evs / vidcom2 与 CUDA graph 的冲突

vLLM 内置 `--video-pruning-rate` / `--video-pruning-method evs|vidcom2`
（docs，2026-10）：

- **evs**（默认）：按**帧间时间相似度**丢 token，**首帧全保留**——
  首帧是后续所有帧的时间参照，这条细节本身就是考点。
- **vidcom2**：按视频级/帧级特征中心分配预算，**每帧至少留 1 个
  token**，避免整帧被抽空导致时间轴断档。
- 共同副作用：**即 encoder CUDA graph 被禁用**。也就是说剪枝省 prefill
  算力的同时，放弃了 encoder 段的 graph 加速——这是典型的「省 token
  vs 保执行效率」取舍，vLLM 官方把 pruning 的目的写明为「**降 prefill
  时间与 KV 占用**」，选不选它要看你的瓶颈在算力还是在 graph 收益。

### 8.4 丢时序坑：media_io_kwargs 必须传

客户端抽帧传 base64 JPEG 会**丢失时间信息**——模型拿到的是一堆无序
图片。vLLM 要求补 `media_io_kwargs.video` 字段（`fps` /
`frames_indices` / `total_num_frames` / `duration`）以保持时序理解
（docs，2026-10）。生产上「模型时序感突然变弱、不会答第几秒发生的事」，
**先查这里**，再怀疑模型能力。

### 8.5 成本曲线：TTFT 与帧数的关系

面试标准答法：**两段分开说——encoder 段线性、LLM prefill attention
段超线性**。TTFT 与帧数近乎线性（吃在 ViT prefill + LLM prefill 的
token 数线性
增长），attention 项再叠平方。所以「帧数翻倍 TTFT 怎么变」要分两段答：
ViT 段约 2 倍，LLM prefill 段超过 2 倍，且 KV 占用线性翻倍。这也是为什么
pruning 与采样首先砍帧——帧是乘法里更贵的那个因子。

### 8.6 引擎对比与部署代表作

- **vLLM**：视频已是产品化一等公民——解码后端、pruning、UUID 缓存、
  media kwargs 全套参数面。
- **SGLang**：多模态模型矩阵含 Qwen3-VL / LLaVA-OneVision 等（repo
  docs/supported-models/multimodal_language_models.mdx，2026-10），
  README 还把 Diffusion 做成内建视频生成引擎；但**视频理解侧参数面
  明显薄于 vLLM**——公开 docs 层面未检索到 pruning 等价的公开参数
  （仅公开文档口径，未逐文件源码核实，见口径节）。引擎总体对比见
  [vllm与sglang深度对比](./vllm与sglang深度对比.md)。
- **部署代表作 Qwen3-VL-235B-A22B-Instruct**：SGLang / vLLM 双引擎
  cookbook 均存在（2026-10）；fp8 权重官方同步放出（Qwen3-VL 新闻，
  2025-10-04）。

## 九、2025–2026 代表作与榜单锚

- **LLaMA-VID**（HKU 等，2023-11，arXiv:2311.17043）：每帧 2 token 的
  祖师爷，小时级视频 benchmark 超越先前方法（原文口径），本谱系必背
  起点。
- **LWM / Large World Model**（UC Berkeley，2024-02，arXiv:2402.08268；
  repo LargeWorldModel/LWM，star 数 **7426**，2026-10 核验）：**用 1M
  上下文**训出的 7B「世界模型」，README 明示可对 1 小时 YouTube 视频做 QA——
  「硬塞派」的顶点。
- **Qwen2.5-VL**（2025-01 发布；tech report arXiv:2502.13923，2025-02；
  合并仓 **20059 stars**，2026-10）：动态分辨率 + 动态 FPS + 绝对时间
  编码，官方口径支持超 1 小时视频与秒级事件定位；VideoMME **无字幕
  73.3 / 有字幕 79.1**（72B，模型卡实测表，2025-01），LVBench **47.3**。
- **Qwen3-VL**（2025-09-23 首发 235B-A22B，2025-10 补齐 2B–32B + FP8）：
  原生 **256K**、可外推 **1M**；Interleaved-MRoPE + DeepStack +
  Text–Timestamp 对齐，官方口径小时级视频全召回与秒级索引。
- **Qwen3-Omni**（2025-09-22，arXiv:2509.17765；repo **4043 stars**，
  2026-10）：Thinker-Talker MoE，文/图/音/视频单模型统一且各模态不
  降级（原文口径）。注意其 **234ms 首包延迟是「理论值」口径**，对比
  时不可与端到端数字混用——[实时多模态模型专题](./实时多模态模型专题.md)
  既有口径已做同样勘误，本篇在此对齐。
- **GLM-4.6V**（Z.ai，zai-org/GLM-V **2396 stars**，README 2026-10
  核验）：**提供 128K 多模态上下文**，覆盖长视频分段与事件识别任务线；
  国产中等规模 VLM 的工业参数面代表。
- **NVIDIA Cosmos Tokenizer**（arXiv:2501.03575；repo **1728 stars**）：
  **2048 倍总压缩率**，生成/世界模型侧标尺。
- **榜单锚**（均论文原文口径）：VideoMME（arXiv:2405.21075，2024-05）
  **900 支视频 / 254 小时 / 2700 题**，11 秒到 1 小时分档，2024 年初版
  中 Gemini 1.5 Pro 为最强商用（**得分 75.0、有字幕 81.3**）；
  LongVideoBench（arXiv:2407.15754，2024-07）**共 3763 支视频、6678 题**，
  最长 1 小时，referring reasoning 任务式。

## 十、▶ 高频面试题（8 条，含深度提示）

视频题是 infra 面里「计算题 + 系统设计」的双料题，模型面则是「压缩与
位置编码」题——考的是你能不能把「为什么这么贵」拆成可算、可对比、可
调参的三层。

**Q1 为什么视频占用远超文本？**（频率：极高；浅档必答）
答：乘法结构（帧数 × 每帧 token）+ 帧间高冗余但 encoder 不知道冗余——
冗余要靠时序合并/采样才兑现。追问：冗余率怎么估？（相邻帧 patch 相似
度、镜头内静止占比。）

**Q2 计算题：128K 上下文能装几分钟视频？**（频率：极高）
给每帧 token × FPS 直接算：**按 70 × 1fps 约三十分钟**（官方口径约
25 分钟）；追问 **老口径 258 token/帧约八点三分钟**；再追问「要装下
1 小时需要多少压缩比」：92.9 万 ÷ 128K ≈ **7.3 倍**（按 258 口径）。
答不上乘除直接出局。

**Q3 帧采样 vs token 合并砍预算，怎么选？**（频率：高）
答：两条不同轴——采样丢**时域事件**（动作、瞬间），合并丢**空域细节**
（小目标、文字）。业务看动作选合并，看细节选采样；都保就上 KV 分层。

**Q4 视频 KV 能压缩吗？有哪些派别？**（频率：高；深档）
三派：**量化派** VidKV（1.x-bit，2025-03）；**检索/分层派** ReKV
（滑窗加 RAM/磁盘分层、按 query 拉回，ICLR 2025）；**剪枝派** vLLM
evs/vidcom2
（训练-free，2026-10 docs）。追问各派代价：量化有损解码质量、检索依赖
召回质量、剪枝禁 encoder CUDA graph。

**Q5 M-RoPE 是什么？Qwen2.5 与 Qwen3 时间轴处理差异？**（频率：高；深档）
答：三维拆分（时间/高/宽 × 频段）→ Qwen2.5 **绝对时间 ID**（动态 FPS
下仍知第几秒）→ Qwen3 **Interleaved-MRoPE + Text–Timestamp 对齐**。
深档追问：YaRN 为什么伤视频？——官方口径 YaRN 显著损害时空定位，
长视频改调大 `max_position_embeddings`（如 64k），因为 MRoPE 对
position id 更经济。

**Q6 TTFT 与帧数的关系？**（频率：中高）
答：encoder 段**线性**、LLM prefill attention 段**超线性**（token 数
线性 + attention 平方项）。追问 evs 为什么首帧全保留——首帧是后续
帧的时间参照系。

**Q7 长视频如何做 streaming QA？**（频率：中高；深档白板题）
答：滑窗 attention 出局部 KV → KV 落 RAM/磁盘池 → query 到达后检索器
（外部或 Video-LLM 内部参数）拉回相关 KV 段 → 跨进程/跨 GPU 生成。
能把 ReKV 四段完整画出来即过深档。

**Q8 1M 上下文模型（LWM）为什么没成为视频理解主流？**（频率：中）
答：训练成本与数据配比是硬门槛；且「装进去」**不等于「看得清」**——
视频 benchmark 仍是瓶颈，1M 全量注意力不解决帧内细节分辨率问题。
现代答案是把「硬塞」换成「采样 + 合并 + KV 检索」的组合拳。

**深浅自评线**：会背「帧数 × 每帧 token」乘法账、记得 **2 / 70 / 258**
三档代表值、知道默认 1fps ——到浅档及格线；能讲清 YaRN 损伤时空定位
的替代方案、pruning 禁 encoder CUDA graph 的取舍、GPU 解码要 MPS 且
独立显存预算这三处暗坑，并能白板 ReKV ——到深档。
