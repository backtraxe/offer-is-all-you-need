# Kernel 工具链选型专题：从 cuBLAS 到 Mojo 的五层控制阶梯

> **面向**：求职「推理引擎 / kernel 优化 / Infra 平台」岗的候选人。
> **读完获得**：把「模型代码到 GPU 之间那摞工具」整理成一道**五层
> 控制阶梯**——每层给到什么、拿走什么；TVM/XLA/Triton/Mojo 各自
> 的生态位与硬伤；一套「该怎么选」的决策四问；以及 Mojo/MAX 用
> MLIR 把阶梯压平的全栈路线的原理与现状。
> **口径**：素材转述自 Modular 官方 handbook（2026-10），属厂商
> 视角文档——对 Mojo/MAX 的表述按「官方口径」标注，竞品层的
> 评价需与自家面试经验交叉验证。

## 一、直觉：真正的选择发生在「模型与 GPU 之间的那摞工具」上

今天很少有人从零手写 CUDA kernel。实际问题是：**要让推理 kernel
更快，先动哪一层？** 把工具链想成一道控制阶梯，越往下走三件事
同时发生：

- 对分块、内存搬运、执行细节的**控制力 ↑**；
- 需要的 GPU 专业能力与工程时间 **↑**；
- 免费拿到的**可移植性 ↓**。

| 层 | 代表 | 你得到 | 你付出 |
|---|---|---|---|
| L1 厂商库 | cuBLAS / cuDNN（cuBLASLt） | 多年架构专属调优，开箱即用 | 只覆盖 NVIDIA 选择开放的算子目录；锁 NVIDIA |
| L2 AI 编译器 | TVM / XLA(OpenXLA) | 图级融合/布局/调度自动化，跨后端 | 峰值常落后手写；自动调优成本高；跟不上新算子 |
| L3 内核 DSL | Triton（tile 级 Python） | 自己写 kernel 但不管 threadIdx/warp 细节 | 块划分/流量/occupancy 仍要自己懂 |
| L4 手写内核 | CUDA C++（FlashAttention 的诞生地） | 全部控制权 | 开发/维护成本、硬件锁定 |
| 压平层 | **Mojo + MAX** | 一种语言写全栈，一份 kernel 跨 NVIDIA/AMD | 生态年轻；官方口径需验证 |

分界线一句话：**标准是负载是否标准**——标准算子交给库，图级融合
交给编译器，要写 kernel 但不想碰 CUDA C++ 时用 Triton，关键瓶颈
要最大控制权才手写。

## 二、L1 厂商库：快起点的边界

cuBLAS/cuDNN 把高度调优的 kernel 藏在稳定 API 后面；PyTorch、
TensorRT-LLM 与多数推理栈底层都靠它们。一个常被忽略的点：**上一代
能跑的 kernel 不会自动在下一代跑到峰值**——新 GPU 的内存层级、
Tensor Core 行为、调度细节、指令集全变，厂商库团队逐代重调，这份
投入多数团队自己做不起（这解释了为什么 cuBLAS 长期是性能基准线：
[Blackwell GEMM 实战专题](blackwell-gemm实战专题.md) 里手写八步
也只追到 0.97）。

三处硬伤：

1. **覆盖面只到已知模式**——新注意力变体、模型专属融合不会自动
   获得支持，模型演进时常滞后；
2. **跨算子优化弱**——关键路径横跨多算子、最优解是新融合 kernel
   时，单次库调用不够；
3. **锁生态**——性能收益搬不到 AMD 或其他加速器。

## 三、L2 AI 编译器：自动化的上限

职能：把「matmul+bias+activation」这类链式小算子**融合成一个
kernel**，让中间数据留在片上、少跑 HBM——这是图层收益的本质
（详见 [AI 编译器专题](ai编译器与torch-compile专题.md) 对
torch.compile 四段式的深挖）。

标准流水线五步：导入模型 → 图级优化 → 算子级优化 → 代码生成
（LLVM/CUDA/自定义 kernel）→ 运行时执行。

**TVM 的四个现实挑战**（面试被问「为什么 TVM 没统治世界」用）：

- 难触峰值：Tensor Core 与复杂内存行为面前，自动生成常落后厂商
  库与手写实现；
- 生态碎片化：TVM 是实现不是标准，硬件厂各自分叉，长期维护重；
- 跟不上负载演进：擅长稳定算子模式，FlashAttention 式的新算法
  出现时覆盖滞后；
- 自动调优贵：数千上万种 tiling/调度逐个基准测试，编译时间长。

**XLA 的两个边界**：硬件抽象的代价正是控制力（生成式负载要的
细粒度内存/数据类型控制给不了）；GPU 上的峰值仍靠回调 CUDA 库
而非纯编译器生成。生态位：TPU/JAX/TF 栈内最强，栈外递减。
注意**内部 XLA（TPU 用）与 OpenXLA 开源栈并不相同**，共享
StableHLO 等组件但后端成熟度各异。

## 四、L3 Triton：降门槛，但不假装问题变简单

Triton 的位置在裸 CUDA 与全自动编译器之间：**仍是自己写 kernel，
但写的是 tile 级编程模型**——用 `tl.arange`/`tl.load`/`tl.store`
显式搬数据，不直接管 `threadIdx`/`blockIdx`。适合自定义注意力、
融合逐点操作、库目录之外的研究型 kernel。

三条边界要背：调试依然难；性能调优不是自动的（访存流量、
occupancy、tile 形状与负载的相互作用仍要自己懂）；主后端之外的
可移植性取决于各家后端成熟度。Triton 帮的是「已经会写 kernel 的
人」，没有取消 kernel 工作本身——生产案例见
[FBTriton 实战专题](fbtriton与稀疏算子kernel实战专题.md)。

## 五、L4 手写内核：前沿路径与规模化难题

FlashAttention 就是在这条路径上诞生的：**库滞后、编译器优化不了
时，自定义 kernel 是前沿唯一解**。LLM 推理尤为典型——新架构
不断带来新注意力变体、新张量布局、新融合机会。三座成本大山：

- **开发贵**：GPU 架构（线程/warp/内存层级）、算力与带宽平衡、
  分块与避坑——专业能力稀缺；
- **难维护**：模型或硬件一变，kernel 里固化的假设（布局、tile
  尺寸、指令）就可能失效；
- **硬件锁定**：CUDA 写的 kernel 迁 AMD 要重写，团队被绑在单一
  生态。

本仓的三篇实战正好是这层的教材：[GEMM 优化阶梯（AMD）](gemm优化阶梯专题.md)、[Blackwell GEMM 实战](blackwell-gemm实战专题.md)、[GQA decode kernel 实录](gqa-decode-kernel调优实录专题.md)。

## 六、压平阶梯的尝试：Mojo + MAX（官方口径）

Modular 的路线是**不把 kernel/编译器/运行时当独立的层**，垂直
整合成一个栈：

- **Mojo**：语法接近 Python、构建在 **MLIR** 之上、原生 GPU 编程
  的语言；主张「熟悉的风格写高层代码，需要时逐步引入底层控制，
  全栈只用一种语言」；
- **可移植性的机制**：同一份 kernel 代码经 MLIR 分别落到 NVIDIA/
  AMD/Apple 等后端——warp 同步、Tensor Core 指令、内存层级细节
  由编译器按 `comptime if is_nvidia_gpu() / is_amd_gpu()` 派发
  成各家指令（官方示例里一个 `syncwarp` 原语分别编出
  `nvvm.bar.warp.sync`、`amdgcn.wave.barrier`、`air.simdgroup.barrier`）；
- **MAX**：建在 Mojo 上的执行与编译层，API 近 PyTorch，负责
  模型定义 → MLIR 图编译 → 硬件上生成并执行 kernel——卖点是
  **优化可以跨层进行**，而不是 PyTorch+vLLM+CUDA+手写 kernel
  缝合栈里每层各自为战。

**适用画像**（官方口径）：混合 GPU 集群、硬件成本敏感、被 CUDA
维护负担拖住的团队。保留三分怀疑：生态年轻、生产级大规模案例
公开有限，「一份代码多后端峰值」需要逐案例验证——但它确实指向
一个真问题：**L4 的控制力与 L1 的可移植性能不能不再二选一**。

## 七、决策框架：四个问题定位你该动哪层

1. **算子是标准的还是新的？** 标准 → L1 库；全新变体 → 准备下
   台阶；
2. **更在意单后端峰值，还是跨后端可移植？** 前者容忍 CUDA 锁定，
   后者考虑编译器/DSL/Mojo；
3. **团队有什么专长？** 编译器专长 → L2；kernel 专长 → L3/L4；
   都没有 → 留在 L1+L2，别硬写；
4. **在建通用产品 infra 还是前沿模型 kernel？** 通用 infra 优先
   稳定覆盖；前沿 kernel 接受手写成本换时间优势。

配套的「多数团队默认路径」：**不从栈底开始**。先框架/引擎里的库
kernel；图层能消内存往返时加编译器；要写 kernel 但想要更好的
表达时 Triton；要跨硬件又要控制时评估 Mojo/MAX；只有关键瓶颈
确实需要最大控制权时，手写 CUDA 才划算。再补一条顺序：先吃
batching、量化（8/4bit）、投机解码、编译器融合、前缀缓存这些上层
杠杆，写 kernel 只在它们都到顶后才划算。

## 八、▶ 面试题

**Q1【高】cuBLAS 已经很成熟了，为什么行业里还在手写 GEMM/
attention kernel？** 答：三类情况。① 算子目录之外：新注意力
变体、模型专属融合模式，库不覆盖或滞后；② 跨算子关键路径：
最优解是横跨多算子的新融合 kernel，单次库调用拼接不出来；
③ 新硬件窗口期：新架构（如 Blackwell 的 TMEM/tcgen05）特性
刚落地时，库调优未吃满，手写能暂时领先。手写不是反库运动，是
**在库覆盖的缝隙里补洞**——而且手写成果常被反哺回库里。

**Q2【高】TVM/XLA 这类 AI 编译器为什么很难打到手写峰值？**
答：目标是自动化通用，而峰值来自负载专属。手写 kernel 可以针对
具体 shape、数据分布、硬件微架构做激进假设（FlashAttention 的
在线 softmax 就是算法-硬件协同设计）；编译器要在保证正确性的
前提下搜调度空间，搜索成本随空间指数涨，且对新算子模式（新
稀疏、新量化、新注意力）没有先验。GPU 侧还多一层：峰值常靠
Tensor Core 等专用单元的特殊编程路径，自动代码生成覆盖这些
路径本身就要逐代重写。所以编译器的定位是「把 80 分自动化」，
不是「把 100 分民主化」。

**Q3【中】Triton 和 TVM/XLA 的本质区别是什么？** 答：抽象的落点
不同。Triton 是**kernel 编写模型**——开发者仍自己写 kernel 逻辑、
显式控制 tile 级数据搬运，抽象掉的是线程/warp 级细节；TVM/XLA 是
**编译器层**——输入是计算图，尝试自动完成跨算子的融合、下沉与
调度。前者帮你写得快，后者替你决定怎么跑。被追问「Triton input
是 kernel 还是 model」就稳了：是 kernel。

**Q4【中】Mojo/MAX 想用一条链解决什么问题？原理是什么？**
答：想消解「控制力 vs 可移植性」这个老矛盾。传统选项里手写
CUDA = 有控制无移植，TVM = 有移植无峰值；Mojo 建在 MLIR 上，
同一份 kernel 源码在编译期按目标硬件派发（`comptime if` 选后端
指令），warp 同步、Tensor Core、内存层级各后端分别落地，目标
是一份代码在 NVIDIA/AMD 上都拿到贴近硬件的性能；MAX 再把模型
图到 kernel 的整条推理链收进一个栈，让优化跨层进行。按官方
口径成立；工程上要盯生态成熟度与逐案例实测。

**Q5【中】什么信号说明你该从库里走出来、自己写 kernel 了？**
答：四个可观测信号。① profile 显示关键路径时间花在库 kernel
之间的往返（中间结果反复落 HBM），融合预估收益大于开发成本；
② 业务负载的 shape/分布在库 kernel 的调优盲区（比值异常低）；
③ 模型设计要用的算子组合没有现成实现且是差异化竞争力所在；
④ 硬件平台迁移，库在新平台缺位。反信号也要会说：**收益预期
没有数量级空间、团队没有 kernel 专长、需求是通用产品稳定性**——
三条占任何一条，留在库里。

**Q6【低】为什么「厂商库逐代重调」对推理 infra 是个重要事实？**
答：它解释了性能基准线的形成。cuBLAS 之所以是 GEMM 的标尺，
背后是 NVIDIA 库团队对每一代架构（内存层级、Tensor Core 行为、
指令集）的专门调优——这不是免费午餐，是厂商护城河。推论有两条：
① 自研 kernel 的合理目标是追平/略超 cuBLAS 并在专属 shape 上
建立优势，而不是全面碾压；② 把推理栈绑定在单一库生态上，迁移
成本会在换硬件时一次性兑现，这正是 Mojo/MAX 与各家国产栈都在
讲「可移植」叙事的原因。

## 十、口径与未核实说明

1. 本文层级框架、TVM/XLA/Triton 边界描述转述自 Modular handbook
   （2026-10）；其中对 Mojo/MAX 的能力描述为**厂商官方口径**，

   结论；个别编译器路径在特定负载上确实能反超手写，表述时留余地。

   建议以自家负载的小规模 PoC 为准，勿直接引用本文作架构决策。
