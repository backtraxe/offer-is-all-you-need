# Agentic RAG：把检索流水线改造成决策循环

> 本篇面向已经掌握 [RAG 全链路](./rag全链路.md) 的读者：你知道
> 索引/检索/重排/生成怎么做，现在想搞清楚 2026 升温的 Agentic RAG
> 和普通 RAG 到底差在哪、什么时候值得多付几倍延迟。
> 读完你会获得：一张「DAG vs loop」的心智图、按层对比表、
> 多跳问题的实例拆解、选型口诀与面试标准答。

## 一、一句话定义

**Agentic RAG = 把 RAG 的「检索-生成」从固定流水线改造成由 LLM
自主决策的动态过程。**

普通 RAG 是自动售货机——投币（query）→ 固定动作（embed → top-k →
拼 prompt）→ 出货（答案），流程写死在代码里，模型只在最后一步出场。

Agentic RAG 把流程里每个「如果…怎么办」都交还给模型：

```text
这个 query 需要检索吗？还是直接答？        ← 路由决策
该查哪个库？向量库 / SQL / 网页 / 私有 API？ ← 源选择
一次检索不够，要不要换个写法再查？          ← 迭代改写（query rewriting）
检索结果靠谱吗？不相关就丢弃重查            ← 相关性评估（self-grade / CRAG）
答案里每个断言都有证据吗？                  ← 自校验（Self-RAG 反思 token）
```

本质一句话：**普通 RAG 是 DAG（有向无环图），Agentic RAG 是 loop
（带反馈的循环）**——它是「RAG 的每个阶段都变成一个可被 agent 调用
的工具，然后套一层 [ReAct](../agent/agent基础与规划.md) 循环」。

## 二、按层对比

| 维度 | 普通 RAG | Agentic RAG |
|---|---|---|
| 流程 | 固定流水线：检索→拼接→生成，一次走完 | 动态循环：模型决定检索几次、查什么库、何时停 |
| 检索次数 | 恰好 1 次 | 0 到 N 次（判断不需要时**可以不查**） |
| 检索源 | 单一向量库 | 多源路由（向量/SQL/API/网页/个人记忆） |
| Query 处理 | 原始 query 直接 embed | 可改写、可拆解（多跳问题拆成子问题逐个查） |
| 质控 | 无（检索到什么用什么） | 可自评：相关性过滤、答案-证据一致性校验 |
| 失败模式 | 检索差 → 硬着头皮答（幻觉） | 检索差 → 换策略重查 / 承认不知道（可拒答） |
| 延迟/成本 | 一次检索 + 一次生成，可预测 | 多轮模型调用，倍数级且不可预测 |
| 可调试性 | 流水线各阶段输入输出明确 | 决策在模型行为里，要靠 trace 审计 |

一个直觉化例子。问「去年营收最高的子公司，它所在城市的天气对物流
影响」：

- **普通 RAG**：拿整个长 query embed 一次，召回一堆四不像，硬答；
- **Agentic RAG**：拆成两步——先查 DB「去年各子公司营收」→ 拿到
  「华东子公司」→ 再查「该城市天气与物流」→ 合并作答。
  **多跳推理是 Agentic RAG 最无可替代的场景。**

## 三、优势

1. **复杂问题能力质变**：多跳、对比型、需要计算的查询，普通 RAG
   单跳检索天然答不了；
2. **该不查就不查**：闲聊、模型已知的问题不再强行检索——省成本
   也减少「检索噪声带歪答案」；
3. **自纠错**：检索质量差时能换 query 重查，而不是「垃圾进垃圾出」
   （CRAG 的核心收益）；
4. **多源融合**：把企业里散落的 DB/API/文档统一在「工具」抽象下，
   模型自主选源——这其实是向 Agent 演化的自然一步；
5. **可信度提升**：带引用的自校验（Self-RAG 系）让「每个断言有证据」
   可检查，幻觉率显著下降（对照 [幻觉与事实性](./幻觉与事实性.md)）。

## 四、劣势

1. **延迟与成本不可控**：循环次数不确定，P95 延迟可能是普通 RAG 的
   3-10 倍——C 端实时场景往往是硬伤；
2. **复杂度爆炸**：普通 RAG 的失败模式一只手数得过来（召回差/切分差/
   幻觉），Agentic RAG 叠加了**所有** agent 的失败模式（路由错、
   循环不收敛、工具误用、注入面扩大——见
   [工具调用与 MCP 的注入防护](../agent/工具调用与mcp.md)）；
3. **评估难度翻倍**：不能只评「最终答案」，还要评**决策轨迹**
   （该检索时没检索？查了五次还没停？）——对照
   [评测与建库工程](./评测与建库工程.md)；
4. **对模型要求高**：路由和自评步骤用弱模型等于「让不懂的人做裁判」，
   反思环节往往输出「看起来很自信的错判」；
5. **漂移调试难**：同一 query 两次运行走不同路径，复现 bug 需要完整
   trace。

## 五、选型口诀

```text
问题单跳、库单一、延迟敏感（客服问答/站内搜索）
  → 普通 RAG，把省下的钱投在切分和重排上
问题多跳/要多源/质量比延迟重要（深度研究、企业知识助理）
  → Agentic RAG，但给循环加预算护栏（max-steps、token 上限）
不确定 → 从普通 RAG 起步，把「路由/改写/自评」做成可插拔节点，
          一步步开——这正是 Agentic RAG 的渐进落地路径
```

一句话定调：**Agentic RAG 不是 RAG 的替代品，是把 RAG 的全部组件
降级为工具之后的一种 Agent 应用形态——你付的是延迟和可控性，
买的是复杂问题的上限。**

## 六、▶ 面试挂钩

**问题 1：Agentic RAG 和普通 RAG 区别？**
「普通 RAG 是写死的 DAG：一次检索、一次生成。Agentic RAG 把每个
阶段变成 agent 可调的 tool，套决策循环：先判断要不要检索（路由）、
要查哪个源（多源选择）、结果不好要不要改写重查（自评纠错）、
答案断言有没有证据（自校验）。收益是多跳/多源问题的上限和
『该不查就不查』的成本节约；代价是延迟成本不可控、评估和调试
难度翻倍。」

**问题 2：什么时候不该用 Agentic RAG？**
「三种：单跳查询为主（客服问答），杀鸡用牛刀；延迟敏感的 C 端
实时场景，P95 可能翻十倍；以及团队还没有普通 RAG 的评测基建——
没有答案级和轨迹级 review 就上循环，等于放飞不可调试的黑盒。
正确路径是普通 RAG 起步，把路由/改写/自评做成可插拔节点逐个开。」

**问题 3：Agentic RAG 怎么评估？**
「两层评估：答案层沿用 RAGAS 类指标（忠实度、相关性）；**轨迹层**
新增决策质量指标——该检索未检索率、无效检索率、循环收敛率、
平均每问检索次数与成本分布。上线前用固定问题集回归，重点盯
『决策抖动』：同一个问题两次跑路径差异大，说明路由过拟合于
采样随机性，要加约束或换路由模型。」

**问题 4：自校验（self-grade）靠谱吗？**
「能显著提升但不能全信：反思 token（Self-RAG）和 CRAG 的
相关性打分在模型能力强时有效，弱模型会输出『自信的错判』。
工程上加两道保险：引用一致性用 NLI/检索证据复述校验做第二道
程序化检查；高价值场景把自评降级为『信号』交给规则或人工复核，
不让模型既当运动员又当唯一裁判。」
