> 向量索引、Query 改写、权限召回这些应用岗加试题。前篇 [RAG 全链路](./rag全链路.md)

## 一、Embedding 模型选型与维度

> ▶ 面试题：Embedding 怎么选？维度怎么定？垂域术语效果下降怎么办？ —— **高**

### 1.1 Embedding 在干什么

把文本映射到向量空间，让"语义近"的文本在向量空间也近。检索时用
**cosine similarity / 内积**算 query 和每个 chunk 的距离，取最近的 top-k。
它是双塔架构：文档侧离线批量算好存库，query 侧在线算一次。

### 1.2 选型看什么

1. **榜单不如自测**：MTEB/C-MTEB 能筛候选，但最终要用**自己的评测集**测——
   榜单上是通用语义，你的库里是专有名词；
2. **维度**：维度高表征更细、存储和检索更贵。常见 512/768/1024/1536/3072。
   经验法则：**先上 768~1024 档**，库到百万级再抠维度；有的模型支持
   Matryoshka 截断（同一向量取前 N 维仍可用），是降本的优雅解；
3. **语言与垂域**：中文检索选中文优化的模型（BGE 系、M3E 等是常用基线）；
   代码检索用 code embedding；跨语言用多语言模型；
4. **推理成本**：在线 query embedding 是 P99 延迟的一部分，模型越大越准也越慢。

### 1.3 垂域术语效果下降怎么办（高频追问）

通用 embedding 没见过"IVF_FLAT""HNSW"这类术语，向量空间里它们挤成一团。三板斧
按序升级：

1. **混合检索兜底**：术语、编号、缩写走 BM25（字面匹配天然免疫语义盲区）——
   这是成本最低也最该先做的；
2. **继续预训练领域语料**（continued pretrain 一个垂域 embedding），或用少量
   「query-正确 chunk」对做对比微调；
3. **Query 扩展/术语词典**：检索前把"宝宝"扩成"婴儿/幼儿"，把行话翻译成
   同义表述再编码。

## 二、向量索引原理：为什么 top-k 不用全库扫描

> ▶ 面试题：向量库选型：Milvus / ES / HNSW / IVF_FLAT 原理与场景？ —— **中**

百万级 chunk 全量算相似度是 O(N·d) 次乘加，扛不住并发。**ANN（近似最近邻）**
用一点点精度换掉几个数量级的时间。两大代表：

### 2.1 HNSW（分层可导航小世界图）

- 把向量组织成**多层图**：上层稀疏（大步跳）、下层稠密（细搜），像高速公路→
  国道→小区路；
- 查询从顶层贪心走到最近邻居，逐层下降，局部搜索；
- **特点**：召回率和延迟都最好，**内存最贵**（图邻接表 + 向量本体）；
  适合对延迟敏感、库容量中等的在线服务；Milvus/Faiss/ES 都支持。

### 2.2 IVF_FLAT（倒排文件 + 平坦存储）

- 先用 K-means 把全库聚成 nlist 个簇，每个向量挂到最近簇心下；
- 查询时先找最近的 **nprobe 个簇**，只扫这几个簇里的向量（暴力精确扫）；
- **特点**：内存省、建库快；**召回率靠 nprobe 调**——nprobe 小则快但漏，
  nprobe 大则准但慢；适合海量库、可接受少量漏召回。

### 2.3 对比表

| 维度 | HNSW | IVF_FLAT |
|---|---|---|
| 检索质量 | 高且稳定 | 可调，nprobe↑则召回↑延迟↑ |
| 延迟 | 低且平稳 | 取决于 nprobe，波动大 |
| 内存占用 | 高（图结构开销大） | 低 |
| 建库/更新 | 插入较贵（要维护图） | 快（挂簇即可），但类间漂移要重建 |
| 调参 | M（每点边数）、efSearch | nlist、nprobe |
| 适用 | 在线低延迟、中小库、高并发 | 海量库、批量检索、内存敏感 |

**选型一句话**：要求 P99 稳、并发高 → HNSW；库里千万以上、内存紧、可微调召回 →
IVF 系。再往下就是 PQ 量化、IVF_PQ、磁盘索引这些"省到极致"的玩法，和推理篇的
量化是同一种思路：拿精度换成本。

## 三、BM25 + 向量：为什么混合检索是标配

> ▶ 面试题：混合检索：BM25 + 向量怎么融合？RRF 怎么用？ —— **极高（京东/钉钉/字节）**

### 3.1 两条路的盲区正好互补

| 路 | 强项 | 盲区 |
|---|---|---|
| **BM25（稀疏检索）** | 专有名词、产品型号、错误码、人名、缩写——字面命中即正义 | 同义改写（"多少钱"vs"定价"）、语义改写后字面零重叠 |
| **向量（稠密检索）** | 语义等价、跨语言表达、口语→书面语 | 术语扎堆没区分度、数字/编号被平均掉、罕见词向量不可靠 |

单独用任何一路，都会在某些 query 上系统性漏召。混合检索的命中率提升几乎是
"免费午餐"——这是各家面经里被反复验证、也是生产系统的默认配置。

### 3.2 BM25 公式（写对就行，细节不考）

$$
\text{score}(q,d) = \sum_{t \in q} \text{IDF}(t) \cdot
\frac{f(t,d) \cdot (k_1 + 1)}{f(t,d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}
$$

其中 $f(t,d)$ 是词频，$|d|$ 是文档长度，$\text{avgdl}$ 是平均文档长度，
$k_1、 b$ 是经验常数（常用 $k_1 \approx 1.2 \sim 2.0$，$b \approx 0.75$）。
记住三个直觉就够面试：**词出现得多加分但会饱和（$k_1$）、长文档要打折扣（$b$）、
稀有词更值钱（IDF）**。

### 4.2 加权融合

把两路分数各自归一化（min-max 或 z-score，因为 BM25 和 cosine 量纲完全不同），
再加权求和：

$$
\text{score} = \alpha \cdot \hat{s}_{\text{vector}} + (1 - \alpha) \cdot \hat{s}_{\text{BM25}}
$$

- 优点：直觉、可调（术语多的场景调大 BM25 权重）；
- 缺点：**归一化敏感**——某一路分数分布极端时会带偏整体；每加一个召回路数，
  权重就要重调。

### 4.3 RRF（Reciprocal Rank Fusion，倒数排名融合）

**不看分数，只看排名**：

$$
\text{RRF}(d) = \sum_{i} \frac{1}{k + r_i(d)}
$$

$r_i(d)$ 是文档 $d$ 在第 $i$ 路召回里的名次（第 1 名 $r=1$），$k$ 是平滑常数，
惯例取 **$k = 60$**（原始论文的经验值，防止第 1 名一家独大）。

举个例：某 chunk 在向量路排第 2、BM25 路排第 50，则
$\text{RRF} = \frac{1}{60+2} + \frac{1}{60+50} \approx 0.01613 + 0.00909 = 0.02522$。

- 优点：**免调参、对分数分布免疫**，多路扩展直接加项，生产默认选它；
- 缺点：丢掉了分数的"差距信息"（第 1 名和第 2 名在 RRF 里只差固定的一步）；
  极端依赖某一路质量时不如加权限重可控。

**答法要点**：先说"默认 RRF"，再说"业务有明显权重偏好（如术语密集型）时换加权
并配评测集调 $\alpha$"——这就是"会选型"和"背过名词"的差别。

## 五、Rerank：为什么需要，什么时候可以不接

> ▶ 面试题：为什么需要 Rerank？什么时候可以不接？ —— **极高（京东/快手）**

### 5.1 为什么需要

召回用的是**双塔/稀疏**模型：query 和文档各自编码，只在线算一次点积——快，
但两个塔之间没有逐 token 交互，语义判断粗糙。Rerank 用 **cross-encoder**：
把 `[query, chunk]` 拼一起喂进 Transformer，全注意力交互后打个相关性分数——
准，但每个候选都要过一次大模型，贵。

所以标准架构是**粗排 + 精排**：召回取 top-30~50（宁可错杀召回阶段也要多），
cross-encoder 精排出 top-5~10 进上下文。召回管"别漏"，Rerank 管"别乱"。
常用模型：BGE-Reranker 系列、Cohere Rerank，垂域同样可微调。

### 5.2 什么时候可以不接

- **库小且 query 规整**（几百 chunk、标准 FAQ）：向量召回本身够准；
- **P99 延迟红线**：cross-encoder 一次几十毫秒×30 个候选，撑不住就不接，
  或降级成更小的 reranker / 用召回分数直接截断；
- **上下文预算充足**：反正 top-20 全能塞下，精排省下的只是 token 而非质量——
  但注意长上下文下"中间遗忘"，乱序塞比少塞更伤；
- **已经在用 LLM 做阅读重排**（如让模型自己从 30 条里选）时，独立 reranker 可省。

**别把追问答反了**："不接 Rerank 是优化"的前提是评测集证明去掉后指标不掉，
否则就是偷懒。

### 5.3 嵌套追问：召回 30 条但上下文只放得下 6 条怎么取舍？—— 中（字节）

1. Rerank 取 top-6 是最直接的答案（这正是精排的存在意义）；
2. 截断按 **rerank 分数 + 多样性** 双重约束：同一文档的多个相邻 chunk 合并，
   避免 6 条全是同一段的重复表述（MMR 思路）；
3. 分数断层检测：top-6 和第 7 名之间有明显分数悬崖时，宁可少塞也别硬凑；
4. 真放不下时，把"被挤掉但分数接近"的 chunk 摘要化/只留引用线索，二轮再取。

## 六、Query 改写：检索质量的上半场比赛

> ▶ 面试题：Query 改写/问题拆分？模糊提问怎么识别？ —— **中高（携程/美团）**

用户原话直接 embedding 是新手第一个坑。Query 侧优化通常比折腾索引见效快：

1. **Query 改写（rewrite）**：口语→检索友好表述。"那个蓝色的咋退" →
   "蓝色款商品退货流程"；
2. **查询扩展（expansion）**：加同义词、上下位词、拼写纠错；
3. **问题拆分（sub-query）**：复合问题拆成多个独立检索："对比 A 和 B 的退款政策
   并告诉我哪个划算" → 拆成「A 退款政策」「B 退款政策」两路并行召回，最后汇总；
4. **HyDE（Hypothetical Document Embeddings）**：先让 LLM 写一篇**假设答案**
   （不管真假），用假设答案的向量去检索——答案和文档在同一"文体空间"，
   比问题空间更接近；适合开放问题、零样本场景，代价是多一次 LLM 调用；
5. **Step-back prompting**：把具体问题抽象一层再检索（"iPhone 15 发热怎么办"
   →"锂电池高温保护机制"），拿到原理再回答具体。

### 多轮对话改写（高频追问）

"那这个呢？""为什么要这样？"——多轮下的指代和省略让原始 query 无法检索。标准做法：
**用一个（小的）LLM 把历史 + 当前问题改写成独立完整 query** 再进检索。
注意两点：改写要**保留用户的领域用词**（别把术语"润色"丢了）；改写失败/歧义大时
宁可带历史检索两次，也别生成一个不存在的实体去检索。

## 七、带权限召回：ACL 先过滤还是先召回（字节纵深题）

> ▶ 面试题：带权限知识库：ACL 先过滤再召回 vs 先召回再过滤？ —— **中，字节纵深追问**
> 这类题面试官要的不是答案，是**分析框架**。

### 两种方案

**方案 A：先过滤再召回（pre-filter）**
检索时把 ACL 条件下推给向量库：只在该用户有权限的分区/带权限 metadata 的
chunk 范围内做 ANN。

**方案 B：先召回再过滤（post-filter）**
先全局召回 top-k，再按权限逐条剔除，留下的进后续流程。

### 分析框架（四维对比）

| 维度 | 先过滤（A） | 先召回再过滤（B） |
|---|---|---|
| **召回质量** | 好：搜索空间里全是可见内容，top-k 实实在在 | **致命短板**：top-k 里大部分可能无权，剔完只剩 1~2 条甚至 0 条——小权限用户召回质量雪崩 |
| **安全边界** | 索引层就隔离，越权 chunk 根本不参与计算，安全性强 | 无权 chunk 会进 ANN 计算甚至进 rerank——分数、中间日志可能泄露存在性；真要挑刺，rerank 也都是接触点 |
| **性能** | 权限分区多时检索空间碎、ANN 图碎片化；metadata 过滤有额外开销 | 全局索引一次查，性能最好、实现最简单 |
| **工程复杂度** | 权限变更要同步进索引（重建/软删），一致性复杂 | 权限判断在内存里做，权限实时生效，最简单 |

### 生产上的答案：分层混合

没有纯 A 或纯 B，而是**按过滤的选择性分层**：

1. **物理/租户隔离**：多租户系统按租户拆库或拆 collection，这是最强的"先过滤"；
2. **过滤下推 + 过采样**：在召回阶段带上权限 filter（主流向量库 Milvus/Qdrant/
   ES 都支持 filtered ANN），同时 **top-k 过采样**（要 10 条召 50 条）给过滤留余量；
3. **后置兜底校验**：生成前再验一次权限，防索引内 metadata 滞后；
4. **权限变更的同步**：权限改动走消息/事件同步更新索引 metadata，并接受一个
   短暂的一致性窗口（或者高敏场景走实时反查原文库权限）。

**答题话术**：先点破 B 方案"top-k 剔除后召回不足"这个核心矛盾，再给 A 方案
"权限变更一致性"的代价，最后落到"selectivity 决定过滤放哪层 + 过采样兜底 +
权限事件同步索引"的混合架构——纵深题要的就是你能自己往下走三层。

## 八、面试高频追问速查

| 面试题 | 频率 | 一句话抓手 |
|---|---|---|
| BM25 和向量为什么互补 | 极高 | 字面匹配管术语/编号，语义向量管改写/同义，盲区正交 |
| RRF 公式里 k 是什么 | 高 | 平滑常数，惯例 60，防止第一名碾压；只看排名不看分数 |

## 九、手撕/练习建议

- `coding/`：**手写 RRF 融合函数**——输入两路 `(doc_id, rank)` 列表，输出融合
  排名；再写一个加权融合版本，用同一份模拟数据对比差异；
- `coding/`：**BM25 最简实现**——对 20 篇小文档建倒排、算 IDF 和打分，
  亲手验证"词频饱和"和"长度惩罚"两个直觉；
- `coding/`：**余弦相似度 + top-k 暴力检索**，再用 `heapq` 优化——体会为什么
  百万级必须上 ANN；
- 练过这三个，混合检索一节的所有名词你都"摸过"了，面试展开的底气来自这里。
