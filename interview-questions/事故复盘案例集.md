## 怎么用这本案例集

面试官问「讲一个棘手问题」，要的不是答案，是你处理事故的**秩序感**。
每个案例按六拍讲，顺序本身就是评分点：

1. **背景一两句**：系统规模、你的角色、任务的关键约束。控制在两句
   以内——「我负责的 3000 卡预训练平台，我是训练框架侧的 owner」。
   背景讲长了会显得没有经过取舍。
2. **现象与影响面**：必须给数字。影响多少请求或多少卡、损失多少时
   长、慢了多少倍。没有数字的现象描述等于没说。
3. **发现路径**：这是全篇最容易被漏说、也最值钱的一拍。问题是怎么
   进入你视野的——监控告警先响、用户投诉先到、例行巡检翻出来、
   演练暴露，还是复盘会上被问出来。说清楚发现路径，等于告诉面试官
   「我的团队有可观测体系与质量机制」，比根因本身更证明实力。
4. **复现与定位**：最小复现是什么、排除法按什么顺序砍。不能复现的
   根因只是猜想，这句话说出来就赢了半程。
5. **解决与验证**：先讲五分钟内能止血的动作，再讲根治与灰度对照。
   顺序反了会显得没上过生产。
6. **教训与预防**：落进监控、流程、SOP 的具体行动项，以「后来我们
   把 X 加进了 Y」收尾。讲不出行动项的复盘只是故事会。

练的时候不要背全文，背每张卡片的**数字骨架**：影响面数字、发现
路径一句话、复现手段、根治动作、沉淀的机制。五个钩子记住了，细节
现场都能现挂。

## 训练栈案例（7 例）

### 案 1：并行配比被静默接受，预训练 loss 平台期三天

- **背景**：3000 卡的 70B 预训练，我负责训练框架与 launcher。集群
  从 2000 多卡扩到 3000 卡的同一周，launcher 模版也换了版本。
- **遇到的问题**：任务能起训、无报错，但 loss 从 2.4 降到 1.9 后
  躺平三天，按基线此时应到 1.6 上下。grad norm 正常，MFU 只比基线
  低几个点，没有任何告警。数学上 TP 乘 PP 乘 DP 正好整除
  `world_size`，校验通过——但新 launcher 的 rank 映射变了，数据
  sampler 仍按老的 DP 数切分，同一批样本被重复消费，等效
  global batch 翻倍、有效学习率被稀释了一半。
- **如何发现的**：不是告警发现的，是对照实验。我拿同框架同 launcher
  跑一个 7B 小模型复验，loss 曲线与历史基线对不上、同样出现平台
  期；把小模型的卡数减半重跑，曲线恢复正常。这一步把嫌疑从数据和
  超参整体排掉，锁定 launcher 与并行拓扑这一层。
- **如何复现的**：在 8 卡 canary job 上用同一 launcher 启动，把
  rank 到 data shard 的映射表打出来，一眼看到重复分片；再把
  sampler 的切分参数改回正确值，重复消失、loss 恢复下降。一张
  映射表就是全家复现集。
- **如何解决的**：止血是回退 launcher 版本并按正确 DP 数重切
  sampler，从三天前的 ckpt 重启，损失三天算力；根治是给 launcher
  加启动期校验——并行配比、DP 数与 sampler 参数必须三方一致，不
  一致直接拒起；每次拓扑或 launcher 变更必须过 canary 复核。
- **教训与预防**：能起训不等于配置正确，并行配比是典型的静默错误
  类型；后来把「小模型复验」写进了变更 SOP，任何调度或框架模版
  变更先用 7B 对照 loss 曲线再放大。
- **面试讲法**：适合回答「讲一次你排查过的、最难发现的配置或基础
  设施错误」，亮点在发现路径不是告警而是对照基线的工程习惯。

### 案 2：集群换拓扑后 ZeRO-3 存档无法恢复，deadline 前的聚合救援

- **背景**：70B 的 SFT 任务跑在 ZeRO-3 上、128 路并行；平台侧把
  一批 8 卡机换成了 4 卡机，新任务的世界规模随之从 128 路变成
  96 路。当时离模型交付还有 36 小时。
- **遇到的问题**：旧存档在新拓扑下直接起不来——optimizer state
  分片按 128 路切的，新世界 96 路对不齐，加载即报错。如果恢复不
  了，等于重训一整周。
- **如何发现的**：这次要强调的发现路径本身就是加分项——不是事故
  逼出来的，是例行恢复演练暴露的。团队每月做一次存档恢复演习，
  换拓扑后的第一次演习就复现了加载失败，还留出了处置窗口。真正
  在 deadline 前撞上的概率被演练提前消耗掉了。
- **如何复现的**：演练脚本本身就是最小复现：同一份存档在新拓扑的
  world size 下加载必现报错；救援方案出来后，再用同拓扑的小模型
  做一次「存档、聚合、重切、恢复、前几十步 loss 逐段对齐」的端到
  端验收，验证了再上大模型。
- **如何解决的**：止血是用框架自带的聚合工具（DeepSpeed 的
  `zero_to_fp32` 思路）把 128 路分片离线聚合成完整 fp32 状态，
  再按新并行格式重切，整个转换与恢复约 4 小时，loss 曲线接续无
  台阶；根治是存档元信息写入世界规模与并行配比，拓扑变更流程
  强制先跑一次存档格式转换演练，恢复演习制度化到每月。
- **教训与预防**：存档的兼容性约束是一份隐性 schema，world size
  就是它的字段；「演练发现」比「事故发现」便宜一个数量级，把
  恢复路径的演练频率写进 SOP 是这次最大的沉淀。
- **面试讲法**：适合回答「讲一次你在 deadline 前挽回阻断性故障」，
  也适合反打「你们怎么做变更管理」——演练机制本身就是答案。

### 案 3：RL 权重同步的精度口径不一致，训推输出慢慢漂移

- **背景**：GRPO 后训练，训练侧 PyTorch、采样侧独立推理引擎，每
  20 步从训练侧向推理引擎做卡粒度权重广播。我负责训推一体这条
  链路。
- **遇到的问题**：训练 reward 上升约 8 个百分点后停滞；同时推理侧
  用固定 prompt 集出的结果肉眼变差——重复片段、格式坏——但训练
  侧 eval 一切正常。两种信号互相矛盾，典型「两边都觉得自己没问题」。
- **如何发现的**：固定 prompt 对拍发现的。拿 100 条固定 prompt，
  同一存档分别在训练侧前向和推理引擎各跑一遍，比逐 token
  logprobs：差值远超舍入误差，部分 token 上差出一个数量级。对拍
  是训推一致性问题唯一的法官。
- **如何复现的**：固定存档、固定 prompt、贪心解码，双引擎各跑一遍
  稳定复现；二分权重广播的转换路径，定位到精度口径不一致——训练
  侧行为概率用 fp32 master 权重算，广播给推理引擎时被 cast 成
  bf16，且 cast 路径的舍入方式与训练侧记录概率时用的不一致，单
  token 差三位小数，长链上累积成可见漂移。
- **如何解决的**：止血是回退权重同步到上一个对拍通过的版本、污染
  窗口内的样本作废重采；根治是统一两侧精度口径，权重同步后加对
  拍门禁——固定 prompt 集的 logprobs 最大偏差超阈值就拒绝放行，
  并把该偏差做成常态监控曲线。
- **教训与预防**：RL 链路上「训推一致」不是默认成立，是一道需要
  主动守的防线；后来把对拍门禁写成发版和每次同步的必经步骤，
  从「出了事再对拍」改成「每次同步必对拍」。
- **面试讲法**：适合回答「RL 训推一致性怎么保证」「做过什么跨
  组件的对齐工作」，对拍这个方法论可作金句收束。

### 案 4：5% 的长尾轨迹把整个 rollout 拖成两倍时长

- **背景**：长思维链模型的 RL 后训练，单条输出长到万级 token，我
  负责 rollout 与权重同步链路的吞吐。
- **遇到的问题**：随着训练推进输出变长，单步 wall time 从 45 分钟
  爬到 110 分钟，GPU 利用率只剩三成出头——大部分时间机器在等最
  长的那一小撮轨迹收摊。
- **如何发现的**：周报巡检发现的：分阶段打点显示 update 阶段稳定、
  慢全在 rollout；把输出 token 分布拉出 p50 与 p99，p50 约八千、
  p99 三万上下，且 p99 随训练单调抬升。同步 batch 的耗时由最长一
  条主导，尾部 5% 的轨迹贡献了超一半的空等时间。
- **如何复现的**：固定存档回放四种组合——有无长度截断、有无跨步
  续生，四格里「截断到一万六」那一格单步立刻回到 55 分钟且中途
  reward 无明显下降，机制实锤。
- **如何解决的**：止血是给 rollout 设长度上限，超限轨迹截断并
  按失败样本计入，不让它无限占着引擎；根治是改成 partial
  rollout——超长轨迹跨步续生、不占当前步的同步屏障，同时设
  staleness 上限控制 off-policy 程度；输出长度画像与 p99 进
  rollout 常态监控。
- **教训与预防**：长尾是结构性问题，加卡只是把算力摊给屏障空等；
  同步批的耗时永远由最长一条定价，治长尾要按机制下药（截断、
  跨步续生），不能按算力下药。
- **面试讲法**：适合回答「优化过一次系统性性能瓶颈，怎么定位、
  收益多大」，周期性地给 p50 与 p99 分开看是定位这类病的通用
  动作。

### 案 5：两个 big gang 任务互相等待，排队死锁 18 小时

- **背景**：约 500 卡的混部训练集群，我做调度平台侧。队列头部
  并排两个各要 300 卡的大预训练任务。
- **遇到的问题**：两个任务互相等对方释放资源，各自 pending 了 18
  个小时；期间塞进不去任何 gang，集群利用率从 85% 掉到 40%——
  大任务永远凑不齐 all-or-nothing 的那一刀，小任务又被配额政策
  挡在头部队列后面。
- **如何发现的**：监控没有报警——利用率曲线虽然难看，但没越任何
  红线。是周例行的配额报表巡检看出来的：排队时延报表里两个大
  gang 已经互相压了快一天；随后翻调度决策日志确认是互相 hold
  的策略性死锁，不是资源真不够。
- **如何复现的**：把两天的资源供给与调度决策序列灌进离线的调度
  仿真器重放，同样陷入互斥；再把「大 gang 弹性降配」开关打开
  重放，死锁消失。仿真重放把「策略问题」与「偶发资源紧张」干净
  地分开了。
- **如何解决的**：止血是人工裁决——其中一个任务降配到两个多节点
  的小 gang 弹性起步先跑，另一个保留全量排队；根治是调度器对
  大 gang 强制弹性准入（可以先以小 gang 入场、资源到位后扩），
  队列加「头部超时自动降配」策略，排队时延与利用率纳入周会
  常规指标。
- **教训与预防**：all-or-nothing 的 gang 语义在队列策略面前会
  自己制造死锁，准入策略要内置「小的先跑、以后扩」的退路；
  利用率与排队时延这类慢指标，靠红线告警永远发现不了，得靠
  例行报表巡检。
- **面试讲法**：适合回答「推动过一次机制或流程改进」「讲一个
  不是代码 bug 的系统性问题」，发现路径用「报表巡检」这张牌。

### 案 6：数据 schema 静默漂移，null 污染 loss 三天才发现

- **背景**：SFT 数据管线按周灌批次，上游 ETL 有一次 schema 变更
  没有同步到训练侧。我是训练侧的接口人，管线不是我写的但指标
  是我在看。
- **遇到的问题**：连续三天 SFT loss 缓慢偏高约 0.02，无报错、无
  告警；第三天的离线评测掉了一个多点才惊动所有人。事后核账：
  约 12% 的新批次样本 label 列读出来是 null，这些样本相当于
  空目标在参与训练。
- **如何发现的**：发现路径值得单说——是数据质量监控的血缘告警先
  响的，不是训练指标。样本级 null 率检查器在这个数据集上报警：
  `label` 列 null 占比从万分之一涨到 12%。回查上游，他们把整型
  label 改成了字符串，老 schema 的 reader 静默读成 null。训练
  指标要三天后才浮上来，质量监控当天就响了。
- **如何复现的**：抽新旧两批各一千条 diff schema 必现类型差异；
  再把 null 样本单独喂小模型，loss 偏高确实全部由这批样本贡
  献，因果链闭合。
- **如何解决的**：止血是冻结污染窗口内的 ckpt 不导出、回退数
  据源到旧批次、用干净数据补训三天；根治是数据入库前加 schema
  契约校验——字段类型、null 率、核心列分布漂移，任何一项不过
  就拒收并告警；loss 监控按数据源分桶，让慢病不再被整体均值
  稀释。
- **教训与预防**：数据侧最贵的病是静默漂移——不出错、只慢慢变
  差；「能跑」不等于「喂对了」。契约校验挡在入库前，比任何
  下游排查都便宜。
- **面试讲法**：适合回答「讲一次质量监控体系帮你抓出的问题」，
  以及「数据和训练两个团队之间怎么防止甩锅」——契约就是答案。

### 案 7：dataloader 在每个 epoch 边界周期性饿死 GPU

- **背景**：预训练数据切成两千多个分片，一个 epoch 约六天，跑在
  几百卡上。我负责训练性能这条线。
- **遇到的问题**：吞吐在每个 epoch 边界处下跌约 25%、持续四五个
  小时，然后自己恢复；GPU util 周期性锯齿，loss 无异常——纯
  性能病。
- **如何发现的**：周期的性能周报巡检看出来的：MFU 面板上的锯齿
  与 epoch 边界严格对齐——在做训练排障的人眼里，「周期对齐」
  就已是半份诊断书。随后打点确认：epoch 末尾的最后一个 shard
  分片不均，只覆盖约三成 rank，这些 rank 读长尾分片时其余
  rank 干等且 worker 在边界处整体重建，雪上加霜。
- **如何复现的**：canary job 把 epoch 人为缩短到两小时，锯齿
  按同一节奏复现；shard 级的覆盖计数器印证最后一块分片的
  样本分布严重偏斜。缩短周期做复现是这类慢病的通用加速法。
- **如何解决的**：止血是把 worker 保活跨过 epoch 边界、边界处
  不等齐重分发；根治是 shard 切分从「按文件数均衡」改为「按
  样本数均衡」，last-batch 丢弃策略改为跨 epoch 连续采样，
  rank 级的供数速率进监控。
- **教训与预防**：性能病里的「周期性」是最值钱的线索——先看
  锯齿跟什么对齐（ckpt 周期、epoch 边界、日志回填整点），
  对齐的那个机制八九不离十；监控粒度要到 rank 级，集群均值
  会把这类遮掉。
- **面试讲法**：适合回答「讲一次靠 profiling 解决的非直觉性能
  退化」，「周期对齐即半份诊断书」是可以当金句用的收尾。

## 推理引擎案例（4 例）

### 案 8：CUDA graph 静默未命中，升级引擎后 prefill 慢了三成

- **背景**：70B、TP8 的在线推理集群，引擎从旧版本升级到新版，
  新版顺带改了 CUDA graph 的捕获尺寸策略。我是这次升级的
  引擎侧验收人。
- **遇到的问题**：升级后功能全部正常、无报错、无告警，但 prefill
  的 p50 延迟涨了三成，TTFT 跟着恶化。肉眼功能验收完全无感，
  纯靠测试用例一条都不会挂。
- **如何发现的**：发现机制本身是本案的核心——不是告警也不是用户
  投诉，是版本升级前的性能基线对比门禁拦下的：每次引擎升级都
  用固定请求集回放，TTFT、TPOT、goodput 三项与上一版本对齐，
  任一劣化超阈值就卡住放量。新版在 5% 灰度之前就被门禁拦停。
- **如何复现的**：把门禁的固定请求集在新旧两版各回放一遍，退化
  稳定复现；再按输入长度分桶，发现只有特定几档变慢——这几档
  恰好落在新版 capture 尺寸列表之外，每次都退回 eager 路径，
  CUDA graph 静默未命中且不产生任何错误日志。
- **如何解决的**：止血是把缺失的长度档补进捕获尺寸列表、灰度
  实锤后全量；根治是把 capture 命中率做成一等公民指标进引擎
  看板，升级门禁加一条「capture 未命中率不得超过基线」，长度
  档覆盖矩阵写进发布 checklist。
- **教训与预防**：CUDA graph 未命中是典型的静默性能病——不报错、
  只变慢，功能测试永远抓不到，只有性能基线门禁能抓住；三成的
  退化若裸奔到全量，得花一周从客户投诉倒查回来。
- **面试讲法**：适合回答「讲一次你靠质量门禁（而不是告警）拦下
  的回归」，亮点在发现机制本身——门禁比告警值钱，难在建。

### 案 9：多模态请求不分桶，长短互拖，GPU 打满吞吐反降

- **背景**：同一引擎集群同时承接纯文本对话与图片理解请求，图片
  请求一次 prefill 要吃掉视觉编码加投影后的上万 token。我负责
  推理调度侧。
- **遇到的问题**：图片流量占比不到一成，可一旦进来，实例的 GPU
  util 打到九成以上，总吞吐反而下降近四成——卡很忙、产出变少，
  文本用户的 TTFT 一起恶化。
- **如何发现的**：goodput 与 util 两条曲线背离触发的排查：卡
  打满但产出跳水是「忙错方向」的经典指纹。给请求按类型打标后，
  发现吞吐塌陷与图片请求到达严格同频，嫌疑直接锁定调度构成。
- **如何复现的**：离线回放对拍：纯文本流量重放一切正常，把线上
  日志里的图片请求按同样比例混入重放，吞吐立刻塌陷；再把图片
  请求单独路由到独立实例，文本吞吐当场恢复——「分桶即解」的
  假设被证实。
- **如何解决的**：止血是调度侧把图片请求单独分桶，限制其在单
  实例内的并发占比，不让长 prefill 和短 decode 抢同一个 batch
  槽位；根治是调度器感知 prefill 重量，按预估 prefill token
  数做负载均衡与准入，图文分池、配比上限化。
- **教训与预防**：一个 batch 的产出由最重的那条请求定价，不分
  桶的混调会让少数流量拖垮多数流量；看到「util 高但吞吐降」
  别先怀疑硬件，先看 batch 构成画像是不是变了。
- **面试讲法**：适合回答「解释一次 GPU 打满但吞吐反降的悖论」，
  答案在调度构成而不在算力不足。

### 案 10：投机解码上线收益为负，draft 与 target 采样温度不一致

- **背景**：在线服务论证投机解码降本方案：小 draft 模型起草、
  大 target 模型验算，预期整体吞吐提升约三成。我负责这条特性
  的评估与上线。
- **遇到的问题**：影子流量实测全链路延迟不降反升约 8%——draft
  前向的开销吃掉了全部理论收益，等于每步白跑一个小模型。
- **如何发现的**：金丝雀实验先看的核心指标：上线前在影子流量
  上量 draft 接受率，经验值七成以上才值得开，实测只有四成；
  按收益公式这一代数据就该拦截，放量决策当场被推翻，负收益
  没有流到任何真实用户。
- **如何复现的**：固定一批 prompt 让 draft 自回归起草、target
  逐 token 打分，接受率稳定四成；先查 tokenizer 对齐（无误），
  再核采样参数，发现 draft 侧温度配成了 1.0、target 侧是
  0.6——draft 按高温度采出的草稿天然难被低温度的 target
  接受。参数对齐后接受率立刻回到七成二。
- **如何解决的**：draft 与 target 的采样参数（温度、top-p）
  统一口径，收益转正后才灰度放量；同时把接受率从「事后看板」
  改成「上线门禁」——接受率不达标，特性不许走出影子流量。
- **教训与预防**：投机解码收益公式里接受率是最大的一阶项，
  tokenizer 对齐只是及格线，采样口径一致才是收益线；任何
  加速特性先算理论收益再上影子流量，别先上线再找收益。
- **面试讲法**：适合回答「讲一个你评估过但没有放量的特性」，
  反向证明性能工程的克制——把负收益拦在金丝雀里本身就是成绩。

### 案 11：上游整点刷新 system prompt，前缀命中率周期性归零

- **背景**：多租户对话服务共用同一引擎集群，前缀缓存是吞吐的
  主要来源之一，正常命中率稳定在六成上下。我负责引擎侧的运营。
- **遇到的问题**：每小时命中率先贴零再缓慢爬回，TTFT 曲线跟着
  整点打拍子，全天其余时间一切正常。周期性本身就是最好的线索。
- **如何发现的**：周期对齐锁定方向：锯齿与整点严格对齐，就先找
  整点发生的机制。上游有个定时任务每小时整点批量重发各租户的
  system prompt，模板里嵌了「今天是某月某日」，每次刷新后前缀
  头部内容变化，全部旧 KV 前缀失效，整点后全站冷启动。
- **如何复现的**：离线对同一租户在刷新前后各构造一次请求，前缀
  哈希 diff 必现差异；把日期字段从头部挪到 prompt 尾部再重放，
  刷新不再击穿缓存，机制闭合。
- **如何解决的**：止血是把日期这类动态信息从 system prompt 头
  部移到尾部动态区，静态前缀稳定化；根治是上游刷新改为「无变化
  不重发」（按前缀哈希去重），前缀指纹进监控，命中率掉幅与上游
  任务时间轴自动关联告警。
- **教训与预防**：前缀缓存的全部价值建立在「前缀稳定」上，任何
  进前缀头部的动态字段都是定时炸弹；周期性现象先查周期机制——
  定时任务、整点回填、日切批处理，对齐的那个机制八九不离十。
- **面试讲法**：适合回答「讲一次靠周期性线索定位的隐蔽退化」，
  也是「你怎么看待缓存命中率」这道题的实战弹药。

## Agent 案例（4 例）

### 案 12：工具回包内嵌巨型数组，五轮后上下文溢出截掉系统指令

- **背景**：日志排障 Agent，工具链里有日志检索、指标查询、告警
  查询几个内部工具。我负责这个 Agent 的线上运营与观测。
- **遇到的问题**：用户反馈 Agent 越跑越不听话——跑到第五六步后
  开始无视开头定好的输出格式，还反复冒出「根据系统设定」这种
  套话。单看每一步的模型与工具调用都正常，轨迹整体却跑偏了。
- **如何发现的**：按 step 画 `prompt_tokens` 曲线出现台阶：第三
  步一次跳涨约两万 token——那一步检索工具的回包里内嵌了完整
  的原始日志数组（带 trace 上下文的明细），上下游都没做截断。
  台阶那一格塞进来的东西就是病灶。
- **如何复现的**：拿原轨迹第三步的工具入参重放，回包原样两万
  token；接着跑五步，上下文溢出截断准时把系统指令与格式约束
  截掉，模型失去格式锚点只剩惯性。最小复现只需一条三步轨迹。
- **如何解决的**：止血是工具回包统一加字节与条数上限，超限走
  「摘要加外置文件引用」路径，大工件不内联；根治是把回包契约
  规范化成「上下文内视图」与「全文引用」两层，系统约束 pin 住
  不参与截断，上下文水位进告警。
- **教训与预防**：步级 token 曲线的台阶是上下文失控的最敏感
  指标；工具回包上线的默认假设必须是「它会完整进上下文」，没有
  预算约束的回包就是埋雷。
- **面试讲法**：适合回答「讲一次 Agent 越跑越不听话的排查」，
  台阶图一画病灶自现，发现路径比根因更出彩。

### 案 13：切换新模型后 system prompt 习惯性失效，行为漂移两周

- **背景**：客服 Copilot Agent，system prompt 里沉淀了一整页
  合规与话术约束。业务要整体切到新一代模型，我负责切换评估。
- **遇到的问题**：切换上线后两周客诉缓慢抬升，但没有任何一条
  监控曲线标红；抽样会话发现 Agent 频繁忽视 system prompt 里
  的合规约束（敏感话题口径、承诺式话术）。新模型总体能力更强，
  但对超长 system 的服从性弱于旧模型，行为是悄悄变的。
- **如何发现的**：每日回归集 job 先报的信：一组「约束遵循」
  回归用例每天跑，切换后第三天违规率从 2% 爬到 11%，比客诉
  整整早了一周多。看板没响是因为没有曲线越红线，只有回归集
  在漏血。
- **如何复现的**：回归集在新旧模型下各跑一遍，11% 对 2% 稳定
  对照；把 system 压成核心约束、关键条款挪到每轮 user 端末尾
  重述，违规率当场回落到 3% 以下，机制实锤。
- **如何解决的**：止血是回滚旧模型，新模型配合 prompt 结构重组
  （核心约束前置、压缩、重复锚定）后再灰度；根治是约束遵循用例
  列为模型切换的一票否决指标，灰度观察期拉长到覆盖一个完整
  业务周期。
- **教训与预防**：模型切换最贵的回归是软行为回归——不报错、不
  跌分，只是慢慢不听指令；总体更强的模型不等于在你的 prompt
  上更强，切换评估必须用自己的回归集而不是公开榜单。
- **面试讲法**：适合回答「讲一次模型升级或切换的踩坑」，每日
  回归 job 这个发现机制是全场加分点。

### 案 14：审批拒绝后 Agent 状态分叉，基于「已执行」假象继续

- **背景**：工单 Agent，所有写操作需要人工审批，通过才真正
  下发执行。我负责流程编排与人机交互这一层。
- **遇到的问题**：操作员对一笔审批点了拒绝，Agent 的后续对话
  却基于「该事已执行」继续规划——它接着安排「执行后通知对方」
  的步骤，还告诉用户事情已办妥。两边都觉得自己没错。
- **如何发现的**：例行工单复核抽检发现的（用户投诉「我明明拒了，
  它为什么说办了」）。拉 trace 定位：审批工具在拒绝路径上抛了
  异常，宿主代码把异常包装成一条成功格式的工具结果塞回上下文，
  措辞含混、没有明说「已拒绝」，模型只能猜，并往「已执行」
  方向猜了。
- **如何复现的**：构造拒绝路径重放：同一条轨迹跑到审批步注入
  reject，包装态结果一出现，模型后续判断稳定漂移。复现集做成
  「通过、拒绝、超时」三种审批结局的重放矩阵。
- **如何解决的**：止血是审批结果强制结构化字段（approved 取
  通过、拒绝、待处理三态），禁止模型凭措辞猜；根治是状态与话语
  分离——reject 后向上下文显式写入一条「该操作已被拒绝，禁止
  继续其后续动作」的状态事实，依赖该动作的下游步骤做运行期
  前置校验。
- **教训与预防**：人与 Agent 的交接点是状态一致性最脆弱的地方，
  审批拒绝不是一次调用失败，而是一次状态分叉；工具异常绝不能
  用「假装成功」的格式吞掉——模型的全部后续规划都以工具结果
  文本为地面实况。
- **面试讲法**：适合回答「讲一次流程正确性或状态一致性事故」，
  三结局重放矩阵是复现段的亮点。

### 案 15：两个子 Agent 并发改订单，竞态写出非法状态迁移

- **背景**：订单中心上岗了两类子 Agent：客服 Agent 会改订单
  备注与状态，履约 Agent 会推进同一订单的状态机，两者并发共享
  同一份数据库。我负责订单侧的工程实现。
- **遇到的问题**：偶现订单状态机出现非法迁移——从「已取消」
  跳回「配送中」、状态回退，累计几十笔。诡异的是没有任何一条
  写入报错：两边的写入各自都是合法的。
- **如何发现的**：对账 job 发现的：状态机审计每天比对每笔订单
  的状态流转序列是否合法，非法迁移列表一出即报警；回查写入者
  trace，所有非法迁移都发生在两个 Agent 对同一订单的写入间隔
  小于数秒的窗口里。
- **如何复现的**：构造竞态重放：同一订单并发注入两个子 Agent
  的状态变更请求。两边都是「读当前状态、决策、写回」三步，中间
  没有版本校验，后写覆盖先写、基于过期状态做迁移，非法序列
  稳定必现。最小复现就是一份双写对拍脚本。
- **如何解决的**：止血是所有状态写操作收口到带乐观锁的状态
  服务（版本号条件更新，读到的版本不匹配就拒绝、重读、重决策）；
  根治是把「Agent 不直接持有数据库句柄」写成架构红线，并发写
  一律走 CAS，状态机审计从日切对账升级为实时告警。
- **教训与预防**：单 Agent 系统里隐藏的并发假设，在多 Agent
  共享状态时会全部暴露：读-改-写三步中间只要没有版本号，竞态
  就不是概率问题而是时间问题；「各自合法、合起来非法」是这类
  bug 的统一指纹。
- **面试讲法**：适合回答「讲一个你定位过的并发或竞态 bug」，
  发现路径用「对账审计」这张牌，复现用双写对拍收束。
