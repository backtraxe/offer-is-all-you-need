## 三、torch_npu 与 HCCL：CUDA 思维到昇腾思维的翻译表

### 3.1 torch_npu：PrivateUse1 机制下的一等公民

torch_npu（Ascend/pytorch，**gh 实测 585★**（2026-10-12），GitCode 为大本营、GitHub
做镜像）基于 PyTorch **PrivateUse1** 机制注册 NPU 后端：2.5.1 起 import 后自动
注册（不再强制显式 import，但官方仍建议显式 import torch_npu 保证设备初始化）。
最新版本线 26.0.0（2026-04-30，适配 PyTorch 2.10.0、Python 3.13）；二进制包名
与 torch 版本一一对应（torch-npu==2.12.0 配 torch==2.12.0 级）。

面试能打出下面这张表 = 做过：

| 维度 | CUDA 侧 | 昇腾侧 |
|---|---|---|
| 设备 | tensor.cuda() / .to('cuda:0') | tensor.npu() / .to('npu:0') |
| 设备查询 | torch.cuda.current_device() | torch.npu.current_device() |
| 加速模块 | torch.cuda.*（Stream/Event/memory_stats/empty_cache） | torch.npu.* 同名镜像 |
| 图捕获 | CUDA Graphs | torch.npu.NPUGraph（v2.6.0+） |
| 编译 | torch.compile 默认走 Inductor | Inductor 在 NPU 不可用（use_inductor=False），走 torchair / Npugraph_ex |
| 显存分配 | PYTORCH_CUDA_ALLOC_CONF | PYTORCH_NPU_ALLOC_CONF，上线几乎必设 expandable_segments:True |
| 自定义算子 | 自写 CUDA kernel + torch.ops | torch.ops.npu.* / torch_npu.npu_xxx()（npu_fusion_attention、npu_add_rms_norm 等 fused 算子） |
| 通信后端 | init_process_group(backend='nccl') | backend='hccl' |
| 分布式 | FSDP2/DTensor/collectives | torch_npu 同桩支持（README 实抓） |

表里有三处是**本质差异**，不是改名：

1. **torch.compile 路径断了**：Inductor 在 NPU 上不可用，昇腾走自己的编译后端
   （torchair / Npugraph_ex）。这是与 AMD ROCm（主仓 Inductor 可用）的本质差别，
   也是「CUDA 代码 direct 平移」叙事里最常翻车的一环。
2. **自定义算子是定罪清单**：vLLM 主仓里所有自定义 CUDA op 都需要 aclnn 或
   自定义 kernel 的 NPU 对应实现，**缺一个就是一个 issue**——算子覆盖率才是
   适配工作的真实进度条。
3. **训练与推理一栈**：torch_npu 一个仓同时覆盖训练（FSDP2）和推理（NPUGraph
   是 vllm-ascend 里 ACLGraph 的捕获/回放底座）。

### 3.2 HCCL vs NCCL：语义一致，工程层全换

HCCL（Huawei Collective Communication Library）对位 NCCL，集合通信语义基本一致
（allreduce/allgather/broadcast/alltoall/send-recv 全套），差异全在工程层：

- **环境变量全家桶**（昇腾部署文档/教程实抓，线上必调）：HCCL_IF_IP（绑口）、
  HCCL_SOCKET_IFNAME、HCCL_BUFFSIZE（通信 buffer，官方 PD 分离教程里 P 侧
  配 256、D 侧配 600 的非对称调法）、HCCL_OP_EXPANSION_MODE="AIV"（通信算子
  展开到 AI Vector 核执行）、TASK_QUEUE_ENABLE=1。NCCL 侧熟悉的
  NCCL_PROTO/NCCL_ALGO/NCCL_IB_* 全部没有对应项，**要重调一遍**。
- **传输层三级对位**：HCCS（机内，对位 NVLink）→ RoCE/RDMA（机间，对位 IB）→
  UB 总线（Atlas 850/950 SuperPod、CloudMatrix 的 scale-up 域，协议层独立于
  RoCE，配置走 ASCEND_LOCAL_COMM_RES / ASCEND_GLOBAL_RESOURCE_CONFIG）。
- **工具链**：nccl-tests 没了，健康检查链是 hccn_tool（-lldp/-link/-net_health/
  -netdetect/-ping/-tls 逐项查）+ npu-smi。vllm-ascend 多机教程开头就是一段
  「逐卡跑通 ping/tls 一致性检查」的 checklist。
- **高频踩坑点**：Docker 里 --net=host + --privileged 是 RDMA 必需；PD 分离的
  kv_port 必须与 AscendDirectTransport 随机端口段 [20000, 20000+npu_per_node
  ×1000) 错开（8 卡推荐 >=28000，16 卡 >=36000），否则间歇性
  ZMQError: Address already in use——这类「偶发但必现」的问题，是面试讲坑的
  好素材。

### 3.3 图模式三层栈：ACLGraph + Npugraph_ex + XliteGraph

vllm-ascend 官方图模式文档（2026-10 实抓）的机制拆解，是昇腾适配里最容易被
问倒的一块：

- **ACLGraph** = 运行时捕获/回放层（torch.npu.NPUGraph 底座），对位 CUDA
  Graphs；graph mode 非 NONE 时自动启用。
- **Npugraph_ex** = 编译期 FX 图优化层（v0.15.0rc1 起，torchair 系），
  FULL/FULL_DECODE_ONLY 模式下默认开启；典型动作是融合 add+rms_norm →
  npu_add_rms_norm 减 kernel launch 开销。Atlas 300I DUO 等老卡不支持，必须
  显式关。
- **XliteGraph** = 可选第三路径（pip install xlite，v0.11.0 起），按 batch
  token 预算路由：预算内走 xlite runtime、超出回落 ACLGraph；限定 Llama/Qwen
  dense、Qwen MoE、Qwen3-VL、DSV3/V3.2 类 MoE（含 GLM-4/5、MiniMax-M2）；
  v0.28.0 起按 token 数路由。

cudagraph_mode 矩阵：FULL_AND_PIECEWISE（默认，对应上游策略）/ FULL /
FULL_DECODE_ONLY / PIECEWISE / NONE（=eager）。**关键约束**：MLA backend
（mla_v1）声明的是 UNIFORM_BATCH 级支持——混合 P/D batch 下 MLA 进不了
FULL 图，会自动收窄到 piecewise 或全部回落 eager。**这就是官方教程里 D 侧用
FULL_DECODE_ONLY、P 侧 enforce_eager 的根因**（第五节配方会用到）。

进阶层是 static kernel 编译（预编译定 shape 算子二进制，冷启动要多等几分钟到
几十分钟）→ Super Kernel（对已编译 kernel 二进制再融合，依赖链 Super Kernel
→ static kernel → Npugraph_ex）。

排障口径必须背官方序列。ACLGraph 捕获失败时报 **207008 错误码与 Stream
resources insufficient**（官方口径），排障四步——升 HDK/CANN → 减
cudagraph_capture_sizes → 偏好 FULL 或 FULL_DECODE_ONLY → 用
enforce_eager 验证问题确实出在图捕获。基线姿势一句话：**把
enforce_eager 当作昇腾上的第一求助反应**（相当于 NPU 版
CUDA_LAUNCH_BLOCKING）。

▶ **追问**：「图模式为什么分三层，不是一层 CUDA Graphs 就完了？」——运行时
捕获（ACLGraph）只管重放省 launch；编译期优化（Npugraph_ex）做融合改图才有
算子级收益；Xlite 是特定模型族的专用加速路径。三层互补，且 MLA 的
uniform batch 约束决定 P/D 两侧图模式选型天然不对称。

## 四、算子移植实战：CUDA kernel → NPU 的三条路径

### 4.1 成本阶梯：先查库、再重写、最后手写

按成本从低到高，移植一个 CUDA kernel 到昇腾的顺序永远是这三档：

1. **查 aclnn 直接调**：CANN 的算子库 aclnn 对位 cuDNN/cuBLAS 的角色，主流
   算子基本覆盖。vllm-ascend 里大部分算子替换就是这么接的——**能买不买**。
   前置动作是先查 torch_npu 侧 torch.ops.npu.* 有没有现成封装。
2. **Triton 源码重写**：triton-ascend 把 Triton Python DSL 编译到 NPU，对改动
   小的自定义 kernel（RMSNorm / Rotary / fused MoE indexing）成本最低、可移植
   性最好。口径记好：**Triton 是国产卡算子移植的统一缓冲区**——不只昇腾，
   ROCm 主线、摩尔线程 MUSA 都能吃 Triton 这层。
3. **Ascend C 手写 AICore kernel**：对 cuBLASLt/FlashAttention 这类性能敏感
   大件，必须贴硬件写 Ascend C（TIK/CCE 的继承者）+ 用 msopgen 脚手架出工程。
   成本与写 CUDA kernel 同数量级，但调试工具链与文档密度还差一截。

### 4.2 Ascend C 编程模型对位翻译（手撕题口径）

- **执行模型**：SPMD，kernel 按 block（AICore 核）分片，一核一 block——对位
  CUDA block，但**没有 warp/block 两级层次**；核内再分 Cube unit（对位 Tensor
  Core）和 Vector unit（对位 CUDA core ALU）。
- **存储层次**：GM（HBM，对位 global memory）→ UB/L0A/L0B（片上 buffer，对位
  shared memory + register file），搬运输用 TPipe/TQue 接口显式入队出队（对位
  cp.async + syncthreads），Tile 概念贯穿始终。
- **数据类型**：half/bf16/fp16/int8/int4 全有；MXFP8/MXFP4 是 950 代补缺
  （支持矩阵里「Native mixed MXFP8/MXFP4 weights」落在新卡列）。
- **思维转换关键点**：CUDA 思维是「每线程算一个元素」，Ascend C 思维是
  「每核搬一个 Tile、Cube/Vector 打流水」。写惯 elementwise CUDA 的人转
  Ascend C 第一周不适应的正是 pipeline 式编程。

### 4.3 Triton-on-NPU 生态实抓

triton-lang/triton-ascend（**185★**，2026-10-12 gh 实测）的时间线：

- 2025-05-20 开源（GitCode 首发 + GitHub 镜像）；
- 2025-06-30 官宣支持 **85% Triton Python API**（连续访存场景）；
- 2025-08 补齐 Atomic 类 API + FlagGems 关键算子；
- 2025-09 补齐 Scan/Sort（非连续访存），官宣「vLLM 和 SGLang 开源仓关键
  Triton 算子适配完成」；
- 2025-11 FP8 转换接口 + scatter_ub_to_out（UB→GM 高效 scatter）；
- 2026 版本线：3.2.0（01-20）→ 3.2.1（04-30）→ 3.2.2（07-31，SGLang 文档
  里已上正式 whl）。硬件支持 Atlas A2/A3 + 950PR/950DT，CANN 9.1.0 +
  torch_npu 版本锚定。

姊妹项目 FlagTree（flagos-ai/FlagTree，**gh 实测 359★**）：fork 自 triton 3.1 的
统一编译器，多 AI 芯片后端（昇腾/沐曦/天数等）一套 DSL——「Triton 联邦路线」。
对 CUDA 生态之外的算子碎片化问题，这是目前最系统的解法，面试格局题可一嘴带过。

### 4.4 移植 SOP：先对齐后调优

被追问「具体怎么迁」就按这个四步走：

1. **语义对齐**：先跑通 eager（enforce_eager），逐算子对比 CPU/GPU 参考答案
   （精度比对 dump + torch.npu 侧 golden 对拍）。先把「能不能」做成 checklist
   再谈快不快。
2. **profile 找大头**：torch_npu.profiler（官方输出 op_statistic.csv /
   kernel_details.csv）按算子耗时排序，融合解耦逐步验证。
3. **分路径攻坚**：小算子 Triton 重写、大算子 Ascend C 攻坚；大模型场景优先
   fused 算子直连（npu_fusion_attention、npu_add_rms_norm）。
4. **开图模式收口**：ACLGraph → Npugraph_ex → （静态 shape 场景）static
   kernel / Super kernel 逐级打开，每级单独验证精度与性能。

口诀：**eager 跑通 → 精度对齐 → 融合降开销 → 图模式收口**。

## 五、DeepSeek 在昇腾：论文锚与可复现配方

### 5.1 系统级锚：CloudMatrix-Infer（背论文原文，别背自媒体版）

arXiv 2506.12708《Serving Large Language Models on Huawei CloudMatrix384》
（v3 2025-06-19，59 页），华为官方口径：

- **硬件**：384×910C + 192× Kunpeng CPU，全 UB 互联 all-to-all，资源池化；
- **软件创新三件**：P2P 服务架构（prefill / decode / caching 三侧独立扩缩容）、
  大 EP 支持到 **EP320**（UB 承载 dispatch 通信）、硬件感知优化（专用算子 +
  microbatch 流水 + INT8 量化）;
- **DeepSeek-R1 实测**：prefill **6688 tok/s/NPU**，decode **1943 tok/s/NPU**
  （TPOT<50ms），15ms 严格 SLO 下 **538 tok/s/NPU**；INT8 精度跨基准保值。

口径纪律：这是**384 卡满配系统**的单位卡数字，不能外推到 8 卡单机。配套参照
是 SemiAnalysis 的系统级口径：CloudMatrix 384 整机 dense BF16 300 PFLOPS ≈
2× GB200 NVL72，但功耗 4.1×、每 FLOP 功耗 2.5×。面试答性能题的标准结构：
**单卡级算力密度落后（910C 约 1/3 量级），系统级靠 UB 超节点把大 EP 通信
成本打平甚至反超——性能论证永远分单卡/系统/每瓦三档**。

### 5.2 教程级配方：vllm-ascend 官方 PD 分离多机部署（2026-10 实抓）

官方教程（pd_disaggregation_mooncake_multi_node）给出的最小可复现部署：
**DeepSeek-R1-W8A8 + MTP，4 台 Atlas 800T A3（每台 8 卡 16 芯），2P1D 架构**。
这是全网最可信的公开「DeepSeek 昇腾部署配方」，逐条记账：

| 侧 | 并行 | 图模式 | 批配置 | 显存 | HCCL_BUFFSIZE |
|---|---|---|---|---|---|
| P 侧（2 机 16 卡） | DP2×TP8 | **enforce_eager**（MLA backend 只支持 uniform batch，混合 batch 进不了 FULL） | max-num-batched-tokens 16384 / max-num-seqs 8 | 0.9 | 256 |
| D 侧（2 机 32 实例） | DP32×TP1（每实例单卡） | **FULL_DECODE_ONLY** | max-num-seqs 40 / max-batched-tokens 256 | 0.94 | 600 |

- 精度与解码：--quantization ascend（W8A8，ModelSlim 产线校准的权重）+
  speculative-config deepseek_mtp，num_speculative_tokens=1。
- D 侧专属 NPU 优化四件套（additional-config 实抓）：
  ① recompute_scheduler_enable（重算调度，embedding 复用）；
  ② multistream_overlap_shared_expert（共享专家多流 overlap）；
  ③ finegrained TP 把 lmhead 单独 TP16——lmhead 词表头是 MLA+大词表场景的
  显存+计算热点，单独细切是从底层算力分布反推出来的；
  ④ enable_shared_expert_dp（P 侧）。
- **KV 传输连接器二选一**：MooncakeLayerwiseConnector（逐层传，D 先收请求再
  拉 P，D-pull）vs MooncakeConnectorV1（整 model 传，P 先发请求再推 D，
  P-push）——数据流方向不同，proxy 实现也不同。
- Mooncake 编译：cmake -DUSE_ASCEND_DIRECT=ON 打开 AscendDirectTransport
  （RDMA 直传），版本锚 v0.3.9。Mooncake 项目本身 **6771★**（2026-10-12
  实测）——PD 分离传输层已经是一匹独立开源快马，昇腾 SGLang 侧的
  MemFabric-Hybrid 也是它的 drop-in 兼容替代。
- 950 SuperPod 传输升级：UB 协议默认路径自动生成通信配置
  （ASCEND_LOCAL_COMM_RES），UBG/UBoE/RoCE 三协议可选，RoCE 需配 /etc/hixlep
  端点文件 per-NPU。
- benchmark 工具链：AISBench（昇腾产线压测件）；官方 FAQ 强调**NPU 算子需要
  多轮 warmup 才到最优曲线**——冷启动数字直接报就是被坑。

### 5.3 矩阵级补充与数学口径

- DeepSeek-V4.1-Flash W8A8：2-node A3 或 4-node A2 colocated（P/D 混部不分离）
  = 存量卡部署 1M 上下文的折中方案，代价是 LoRA/投机解码特性列打叉。
- DeepSeek V4 系 950DT 梯队：**MLP 权重预取（MLP Weight Prefetch）**是独占
  特性列——显存压力下的权重流水线优化，是昇腾 MoE 部署的特色线。
- 点破一句：教程 2P1D 放满对应 128 NPU 规模，与 R1 论文满配数字不在一个
  量级——**公开最小配方 ≠ 生产满配**，讲规模时主动点破反而加可信度。

▶ **追问**：「DeepSeek 在你们 910B 上怎么部署的？」——照 5.2 配方一条一条
报（并行切法、两侧图模式不对称、连接器方向、端口段错开、warmup），报完再补
5.1 的满配锚。能同时讲清「教程配方」与「论文口径」的边界，就是高分答案。

## 六、SGLang-NPU 与 MindIE：另两条分支

### 6.1 SGLang-NPU：主仓内置制（官方文档 2026-10 实抓）

SGLang 与 vLLM 路线不同：NPU 支持走**主仓内置制**——
python/sglang/srt/hardware_backend/npu 目录与 cpu/mlx/mps/musa/xpu 并列，
不建独立插件仓。官方 Installation 页（docs.sglang.ai）给出整套组件栈：

- **版本矩阵同样锁死**，每个 CANN 版本一整套组件，禁止跨 set 混装：
  - CANN 9.0.0 套：HDK 25.5.2 + TorchNPU 26.0.0 + Triton 3.2.1.dev(nightly) +
    SGLang NPU Kernel 2026.9.0 + MemFabric 1.1.4，要求 python==3.11；
  - CANN 9.1.0 套：TorchNPU 26.1.0 + triton-ascend 3.2.2 正式 whl + SGLang
    NPU Kernel 20260821，python==3.12。
- **昇腾生态专属四件套**（CUDA 侧没有对应）：
  ① sgl-kernel-npu（sgl-project/sgl-kernel-npu，**gh 实测 192★**）——对位 sgl-kernel
  的 NPU 版融合算子仓；
  ② triton-ascend——官方自述「our own implementation of Triton for Ascend」；
  ③ **MemFabric-Hybrid**——「Mooncake Transfer Engine 的 drop-in 替代」，
  管 PD 分离的 KV cache 传输；
  ④ DeepEP 兼容库——DeepSeek DeepEP 的兼容替代（dispatch/combine 通信算子）。
- PD 分离服务化标配：P/D 分别起 server + router 统一入口；--privileged +
  --network=host 是 RDMA 必需；**CPU 调频 ondemand→performance、关 NUMA
  balancing、关 swap** 的「System Settings」三件套是固定开场白。
- aarch64（鲲鹏）集群需额外装 MemFabric-zbal（Zero Buffer 加速库）。

对比口径：**vLLM = 插件仓制（entry_points 注册、社区同权），SGLang = 主仓
内置制（hardware_backend 目录）**。昇腾侧两条线都在投喂；SGLang 的差异化是把
Mooncake TE / DeepEP 这类 DeepSeek 系开源件干成了 drop-in 兼容层——对接昇腾
时改的不是引擎，而是配套通信件。

### 6.2 MindIE：华为官方商业栈（hiascend 官网 2026-10 实抓）

- 版本线：MindIE 3.1.0 发布，架构升级 + 模块更名（官网新闻稿口径）；文档目录
  已出现 26.0.0/26.1.0，与 TorchNPU 同款「年份.序号」命名切换。
- 模块版图：**MindIE-LLM**（文本生成推理）、**MindIE Motor**（服务化组件，
  官方口径「可对接 vLLM 等开源引擎，增强服务化调度能力」——开源与商业栈
  从竞争变互补的新信号）、**MindIE SD**（多模态生成套件，已开源，含 Diffuser /
  vLLM-Omni 即插即用推理加速 Layer）。
- 生态位（「vLLM-Ascend vs MindIE 怎么选」的答法）：**追新模型/改引擎/二次
  开发选社区栈；交付政企、要官方支持 SLA、全套服务化选 MindIE；两者共用
  CANN/torch_npu 底座**。官网案例是政务 DeepSeek 本地化、校园 800 并发问答、
  航空公司场景等政企交付向。

## 八、面试口径

### 8.1 「你做过昇腾/寒武纪适配吗」三档诚实答法

- **L1 没做过但有方法论**：「没上过生产，但适配链路我拆过——语义对齐、算子
  替换、图模式收口四步；CANN/torch_npu/vllm 版本锁死四元组是第一个坑，基线
  就是用社区镜像把 vllm-ascend v0.23.0 对齐成 set。」
- **L2 调优/排障过**：报环境（CANN 9.1 + torch 2.10 + torch_npu 2.10.0.post4
  + vllm-ascend v0.23.0）+ 坑清单（8.3）+ 一个调优案例（ACLGraph 207008 捕获
  失败 → 降 capture sizes / 换 FULL_DECODE_ONLY → 开 warmup）。
- **L3 移植过模型/算子**：报翻译表（8.2）+ 工作量账（8.4）+ Triton vs
  Ascend C 的选型判断（按算子复杂度与复用范围分）。

加分口语：「昇腾适配本质是跑集合——CANN/torch_npu/vllm 三者每个版本都锁死，
**工程时间大头不在写 kernel，在跟着厂商版本表跳**。」

### 8.2 必备翻译表（一屏背全）

| 维度 | CUDA 侧 | 昇腾侧 |
|---|---|---|
| 设备命名 | cuda:0 | npu:0 |
| 加速库 | cuDNN / cuBLAS | aclnn（CANN） |
| PyTorch 插件 | 原生 / ROCm HIP | torch.npu（PrivateUse1） |
| 图捕获 | CUDA Graphs | ACLGraph（NPUGraph）+ Npugraph_ex + Xlite |
| 通信库 | NCCL | HCCL（HCCS/RoCE/UB 三级传输） |
| 通信健康检查 | nccl-tests | hccn_tool + npu-smi |
| 算子语言 | CUDA | Ascend C / Triton-Ascend |
| MoE dispatch | DeepEP | DeepEP 兼容库 / MoeDispatch-Combine |
| KV 传输 | Mooncake TE / NIXL | Mooncake Ascend Direct / MemFabric-Hybrid |
| 量化工具 | AWQ / GPTQ / Marlin | ModelSlim / ascend quantization（W8A8/W4A8） |
| Profiler | nsys/ncu + torch.profiler | torch.npu.profiler（op_statistic/kernel_details） |

### 8.3 坑排行 top 8（接地气版）

1. **版本矩阵锁死**：CANN/torch/torch_npu/vllm(-ascend) 四元组外加 HDK 与
   驱动；跨 set 混装报抽象错误，排错最先查版本表。
2. **图模式捕获失败**：207008 stream resources insufficient；固定四步排障
   （升栈/降 capture/换 FULL_DECODE_ONLY/回 eager 验证）。
3. **MLA 只支持 uniform batch**：混合 P/D batch 自动降级，**静默变 eager
   比预期慢一截**——要看日志、精准读支持矩阵当前列。
4. **动态 shape 与小 batch 翻车**：图依赖固定 shape，prefix cache、chunked
   prefill 混合形态里踩边界。
5. **量化口径断链**：W8A8 权重必须走 ModelSlim 校准产线（--quantization
   ascend），AWQ/GPTQ 兼容缺位；Kimi K 系的 W4A8 路径只在 A3 实验档。
6. **HCCL 环境全家桶漏配**：IF_IP/SOCKET_IFNAME/BUFFSIZE/AIV/TASK_QUEUE
   缺一个就偶发超时；PD 分离 kv_port 撞 AscendDirectTransport 随机段
   （8 卡 >=28000）。
7. **系统调优漏半步**：CPU ondemand 没切 performance、NUMA balancing 没关、
   swap 没禁、--privileged --net=host 漏了——**吞吐差 10-30% 的「隐形坑」**。
8. **冷启动没 warmup**：benchmark 第一报必废，NPU 算子需多轮预热——官方
   FAQ 原话级口径。

### 8.4 跨卡迁移工程量估算（H 卡 → 昇腾，按人周口算）

- **矩阵内存量模型**（Qwen3 系 / DeepSeek / GLM 主流，支持矩阵已绿）：
  环境 + 一次性 benchmark 对齐 ≈ **1-2 人周**；高级特性（PD 分离 + MTP +
  大 EP）照官方教程配方集成另加 **2-4 人周**。
- **新架构未进矩阵**（如 Qwen3-Next 类 GatedDeltaNet 混合模型初版）：
  **1-2 人月**起跳，预估大头在 attention backend 与 MoE dispatch；
  模板 = 对照上游 vLLM 主仓支持 PR 逐项 grep NPU 兼容项。
- **自研 kernel 密集**（MLA 索引、DSA、flash-mask 类多模态/稀疏注意力）：
  **3-6 人月**，Triton 能兜的长尾兜、不能兜的 Ascend C；精调周期（tiling /
  stream 压榨）另留 **1-2 人月**。

口径备份：「昇腾侧最大的公约数是时间花在**版本适配 + 对齐 + 开图**，不是写
算子——存量模型 50% 的时间在跑通已存在链路。」（工程估算，非官方口径。）

### 8.5 六条高频追问速答

1. **vllm-ascend 和 vLLM 什么关系？** vllm-project 名下社区仓、entry_points
   插件注册、主仓版本一对一绑定、官方博客背书插件制最佳实践——等于社区同权
   的「非 CUDA 一等公民」。
2. **day-0 是哪天？** 950DT 新卡上 DSV4/GLM-5.1/Qwen3.5/MiniMax-M3 发布日
   全特性；A2/A3 存量卡只有实验档——「day-0 红利 = 新卡×新模型」。
3. **图模式为什么分三层？** 运行时捕获（ACLGraph）+ 编译期 FX 优化
   （Npugraph_ex）+ 可选专用路径（XliteGraph）；MLA 只能 uniform batch 是
   设计约束，D 侧 FULL_DECODE_ONLY + P 侧 eager 是落地的非对称选型。
4. **torch_npu 能不能 import 完直接用？** 2.5.1 起自动注册，官方建议显式
   import 保设备初始化；加速 API 全在 torch.npu.* 命名空间。
5. **性能为什么比不过 H 卡？** 单卡 dense BF16 约 1/3（910C vs Blackwell，
   SemiAnalysis 反推口径）；系统级靠 CloudMatrix 384 / 950 超节点 + UB 全互联
   把 MoE/大 EP 通信打平，prefill 6688 / decode 1943 tok/s/NPU 是 384 卡满配的
   单位卡数字——**要报系统口径才能算赢**。
6. **寒武纪怎么还不行？** 公开 vllm-mlu 半年无更新、走大客户私有交付——
   「推理百家饭里，昇腾是目前唯一跑出社区飞轮的国产栈」。
