## 一、主线直觉：成熟度 = 上游插件机制 × 厂商 kernel 库厚度

一句话直觉：**推理适配是「语义对齐」问题，不是「性能调优」问题**——模型代码
一行不改，改的是 attention backend、融合算子替换、图执行模式三件事；能不能
改得动，取决于上游有没有稳定的插件接口、厂商有没有自己的 kernel 库和
通信库。

2026 年的答案分四层：

1. **CUDA 主线仍是参照系**：vLLM 主仓 **93564★**、SGLang **36991★**
   （2026-10-12 实测），attention kernel 层的标杆 FlashInfer **6589★**
   支持矩阵 SM7.5~SM12.1 全 NVIDIA——这个生态位国产侧只能自己填。
2. **ROCm 是开源主仓原生第一方**：不走插件仓，vLLM/SGLang 主仓直接构建，
   配套 AMD 自维护的 AITER（fuse 算子库，star **586★**）与 MORI（RDMA/EP
   通信层，star **186★**）（均 2026-10-12 实测）。
3. **昇腾靠社区插件成为国产事实标准**：vllm-ascend **2949★ / 2421 fork**
   （2026-10-12 实测），vLLM 官方博客背书，支持矩阵扩到 Ascend 950 新
   硬件，是国产侧唯一跑出「day-0 级支持」叙事的仓。
4. **寒武纪/海光走自家渠道，四小龙只有摩尔线程有公开适配仓**：
   vllm-mlu **121★**、vllm-musa **127★**（2026-10-12 实测），与
   vllm-ascend 差 23 倍；海光未找到公开 vLLM-DCU 适配仓（见文末说明）。

## 二、机制拆解：RFC #11162 与三层换位

### 2.1 硬件插件机制：从 fork 魔改到社区同等公民

vLLM RFC **#11162**「Hardware pluggable」（2024-12 立项）把引擎拆成两层：

- **主仓层（跨硬件共享）**：调度器、内存管理、连续批处理、chunked
  prefill、prefix cache、PD 分离调度——V1 引擎语义对所有硬件一致。
- **插件层（per-hardware）**：Worker、Platform 接口、attention backend、
  算子替换、图执行模式——开源硬件走独立插件仓（vllm-ascend、vllm-mlu、
  vllm-xpu 等），通过 entry_points 注册加载。

机制转折点在 **2025-05**：vLLM 官方博客以 vllm-ascend 为案例发布
Introducing vLLM Hardware Plugin, Best Practice from Ascend NPU——国产
硬件适配从「fork 一份私改」变成「上游社区同等公民」，这是所有国产推理
适配仓得以建仓、迭代、被官方版本火车带动的制度前提。记忆钩子：
**插件机制解决的是「改哪里、谁来改」的分工问题**——主仓发版节奏不受任何
单一硬件拖累，插件仓也不被主仓 API 冻结绑死。

### 2.2 昇腾栈数据流：vllm-ascend 内部长什么样

一次推理请求在昇腾栈里的完整路径（文字版，按 vllm-ascend 支持矩阵与
README 2026-10 口径）：

1. 模型层：HF 格式的 Qwen / DeepSeek / GLM 直接加载，**模型代码零修改**；
2. vLLM 主仓 V1 引擎：调度、chunked prefill、prefix cache、PD 分离逻辑
   原样生效；
3. vllm-ascend 插件接管：Worker 换成 torch_npu 设备上下文；
4. attention 走 NPU 原生 backend（AscendAttentionBackend 系），
   attn metadata 按 NPU 上图语义重排；
5. GEMM / MoE 落到 CANN aclnn 与 MindSpeed 系融合算子
   （swiglu / rms_norm / MoE GMM）；
6. 执行模式可选 Ascend 版 CUDA Graph「AclGraph」，分 **piecewise /
   fullgraph 两档**——piecewise 只把无缺口子图包进图，fullgraph 全图
   捕获，性能上限更高但对算子完备度要求更高；
7. 多卡集合通信走 **HCCL**（对位 GPU 的 NCCL，管 TP/EP）；PD 分离的
   KV 传输走 mooncake 等 connector 组件（issue 区证明生产里就是这么
   用的，见第五节）。

对应版本矩阵（vllm-ascend v0.26.0rc1，README 2026-10 实测）：
**CANN 9.1.0 + PyTorch 2.10.0 + torch_npu 2.10.0.post4 + 同版本 vLLM**。
维护节奏是 main 跟 vLLM 主干，每 vLLM 版本开 releases/vX.Y.Z 分支；
稳定版 **v0.23.0**（2026-08-16），候选 v0.26.0rc1（2026-09-03）、
v0.27.1rc1（2026-09-29）。硬件分三档：

- **950PR / 950DT**：2026 年新硬件，支持矩阵 day-0 级收录——DeepSeek
  V4-Flash/Pro（native MXFP8/MXFP4，1M 上下文）、Qwen3 系、GLM-4.x ～
  5.3、Kimi-K2.x/K3、MiniMax-M2.5/M3，含 W8A8 / EP / DP / PD 分离 /
  AclGraph 全特性列；
- **Atlas 800I A2 / A3**：主力推理档位；
- **Atlas 300I Duo**：实验性档位。

### 2.3 ROCm 的等价换位：不是插件，是主仓一等后端

ROCm 与昇腾最大的机制差异：**它不需要插件仓**。vLLM 主仓源码与官方
docker 直接构建，源码构建时锁 `PYTORCH_ROCM_ARCH=gfx942`（MI300）；
Triton、flash-attention（v2.8.0 有 gfx942 分支）、flashinfer 全部有
ROCm 移植版。ROCm 官方文档首页把 vLLM、SGLang 列为 AI Ecosystem 一级
入口（页面标题级 ROCm 10.1.0，2026-10 实测），vLLM 按 ROCm 版本发
预编译 wheel 变体（实例 rocm721）——**AMD 推理支持 = 上游官方渠道，
不是下游 fork**。

ROCm 侧两库补位 FlashInfer 生态位：

- **AITER**（AI Tensor Engine for ROCm；star **586★**，2026-10-12 实测）：
  fuse 算子库，对位 FlashInfer / cuBLASLt 的角色；SGLang 上用
  `SGLANG_USE_AITER=1` 开关启用加速路径。
- **MORI**（Modular RDMA Interface；star **186★**，2026-10-12 实测）：
  EP 通信与 PD 分离的 RDMA 层，对位「NCCL + 推理侧 RDMA 传输」的组合。

注意一条常被问住的口径差异（v1/v2 口径漂移）：ROCm 官方文档首页标题
口径是 ROCm 10.1.0（2026-10 实读），而 vLLM 安装文档同一时期仍在引用
rocm700 / rocm721 wheel 变体与 rocm/pytorch:rocm7.x 镜像。两组口径并存、
交叉映射未核实——面试和写文档时**两组口径分别标注来源页面，不要合并成
单一版本号**（细节见文末说明 3）。

### 2.4 量化与通信的三层错位

**量化矩阵错位**（SGLang AMD 文档 2026-10 实测口径）：

- ROCm 可用面很宽：FP8 / AWQ / MXFP4 / W8A8 / GPTQ / Quark 全列；
- 但**依赖 NVIDIA 专有 kernel 的路径全部缺席**：awq_marlin、
  gptq_marlin、modelopt_fp8、modelopt_fp4 不可用——Marlin kernel 是
  NVIDIA-only 的 dequant 实现，搬不过去；
- AWQ 在 ROCm 上退化为 Triton 反量化 kernel，慢于 Marlin 路径；
- MXFP4 需要 CDNA3 / CDNA4 + AITER；AMD 独有 quark_int4fp8_moe 在线
  量化路径。

**昇腾侧量化**（支持矩阵 2026-10 口径）：W8A8 列对 DeepSeek V3 /
GLM 系全勾；W4A8 配合 DSpark 落在 Kimi-K3；native MXFP8 / MXFP4 落在
DeepSeek V4 —— 量化完备度取决于厂商把 dequant / GMM 融合算子写进了
CANN / MindSpeed 多少，而不是引擎侧开关。

**通信层对位**也分三家：HCCL（昇腾）对位 NCCL 管 TP/EP 内通信，EP 大
规模部署的 MC2 通信融合在 MindSpeed 侧仍属「未发布」边界（边界文档口径，
见 [国产卡后补篇](./国产卡后补篇.md)）；PD 分离的 KV cache 池化走
Mooncake 类 connector + RDMA/NFS 或 AscendStoreConnector；摩尔线程
MCCL 只在 S4000 平台提供（边界文档口径），是四小龙推理多卡扩展的硬
约束。

三个读数结论：

1. **热度分层比想象中陡**：vllm-ascend = vllm-musa 的 23 倍、vllm-mlu
   的 24 倍；所有适配仓加起来仍只是主仓的零头——「适配仓 star 数」
   直接反映厂商愿意投入多少社区人力。
2. **寒武纪 vllm-mlu 是「渠道制」而非社区制**：README（2026-10 实读）
   宣称 day0 支持 DeepSeek-V4、支持 Chunk Prefill / Prefix Caching /
   Spec Decode / Graph Mode / Sleep Mode，但仅支持 MLU370 以上，安装
   需要寒武纪 SDK、镜像要联系 ecosystem@cambricon.com 获取；push 停于
   2026-05-11。宣称口径无第三方复测，见文末说明。
3. **SGLang 走另一条路线——主仓内置后端**：SGLang 主仓
   `hardware_backend/` 目录实测含 npu、musa（以及 xpu / mlx / mps /
   gpu / cpu），不是 vLLM 的插件注册路线。被问「两家引擎对国产硬件的
   支持方式差异」时这是一句加分答案：**两家路线不同——vLLM 用
   entry_points 插件制，SGLang 用主仓目录内置制**。

## 四、昇腾跑 vLLM 的六类典型坑（issue 区实抓）

以下六类坑全部来自 vllm-ascend issue 区 2026-10 实抓，按「现象 → 模式
→ 对策」整理。面试答「昇腾上最常出什么问题」就按这六类走。

### 4.1 AclGraph 捕获期间的算子缺口

- issue 实例：#18304「missing causal_conv1d_update_npu →
  CausalConv1dBwd ACL-graph crash kills decode EngineCores」
  （DeepSeek-V4.1，A3）；#18012「batch_matmul_transpose ignores
  failed synchronous tiling copy during GLOBAL graph capture」。
- 模式：**图捕获期任何一个未适配或同步失败的算子，都会以整引擎崩溃
  收场**——不是慢，是直接死。图模式把算子缺陷从「单点错误」放大成
  「进程级故障」。
- 对策：先 `--enforce-eager` 跑通确认语义，再开 piecewise 图；定位到
  reverse 出问题的算子名再查 issue。

### 4.2 图模式与精度（输出乱码而非报错）

- issue 实例：#15831「Qwen3.5-35B + graph mode accuracy issue on A5」。
- 模式：图模式精度问题的普遍形态是**输出乱码而不是报错**——比 OOM
  难排查一个量级，因为服务看起来「活着」。
- 对策：二分法——eager 正确、piecewise 乱码，把捕获范围逐段收窄。

### 4.3 EP 开启后的精度异常

- issue 实例：#8223「MoE 模型开 --enable-expert-parallel 后吐字乱码，
  不开正常」。
- 模式：印证一贯结论——**MoE AlltoAll / EP 通信是新硬件栈的短板**，
  功能能跑通，但数值语义边界还没打磨平。
- 对策：EP 相关异常先回到 TP-only 验证模型本身路径，再单独压 EP。

### 4.4 量化 OOM 与混部容量账

- issue 实例：#8817「GLM5.1 运行 w8a8 出现 OOM」、#11295
  「Qwen3-235B OOM on A3」、#4379「Qwen3-Next-80B 在 8×910B 64G 上
  OOM」。
- 模式：910B 64G 显存档位跑大 MoE，**量化后的容量账必须现场算**——
  权重压缩了，但 KV cache、激活、通信 buffer 不按同比例缩。
- 对策：先按 [显存计算专题](./显存计算专题.md) 的公式把权重 / KV /
  buffer 三笔账算清，再谈量化档位。

### 4.5 PD 分离 + KV 池化的工程坑

- issue 实例：#9168「A3 单节点 PD 混部下 AscendStoreConnector +
  mooncake KV Cache Pool 大量报错 Failed to get key」、#17756
  「双机 1P1D，超长请求代理端未透传处理」。
- 模式：PD 分离本身在 vLLM 主仓是语义稳定的，**坑都长在 connector
  与 KV pool 的接缝上**——键空间、代理透传、超时重试。
- 对策：对账先对 connector 层日志（Failed to get key 类），再回到
  调度层。

### 4.6 新特性两两组合的互斥

- issue 实例：#17706「Kimi-K3 开 DCP + mrv2 + gmmsituquant 推理
  失败，关 DCP 正常」；#16997「A5 上 DeepSeek V4 Flash 开 DSpark 后
  TTFT 劣化十倍」；#2771「vLLM Ascend 不支持 MTP mix quantization」；
  #8585「软切分 NPU + Piecewise 图模式不支持」。
- 模式：坑不在「跑不起来」，在**五条新特性任意两两组合后的语义
  边界**——每个特性单独测过，组合没有。注意 #16997 的「TTFT 劣化
  十倍」是该特性组合下的退化 case，不是整体水位口径（见文末说明 6）。
- 对策：新特性一次只开一个，出问题先回退组合。

**共性结论（面试收尾金句）**：昇腾的坑不是「跑不起来」，是「组合边界」；
排障第一动作永远是 **--enforce-eager 二分定位**，第二步看图捕获日志。

## 五、ROCm / AMD 侧工程细节

1. **系统级调优是 ROCm 特有的前置工序**：SGLang 文档级建议——MI300X
   需要系统级 GRUB / NUMA 调优，AMD 官方有 MI300X System
   Optimization 指南；CUDA 侧没有等价步骤，这是 AMD 集群交付成本里
   容易被漏估的一块。
2. **量化可用面宽但有明确缺口**：见 2.4 节——Marlin / modelopt 系
   NVIDIA-only kernel 全缺席，AWQ 退化为 Triton 反量化。
3. **AITER 不是万能开关**：gfx1151（Strix Halo iGPU）必须
   `SGLANG_USE_AITER=0`，因为 AITER 是 CDNA / wave64 取向；边缘 /
   桌面 APU 形态别开。
4. **公开基准渠道**：SemiAnalysis 的 InferenceMAX（2025-10 起）是
   MI300 系 vs NVIDIA 的唯一公开持续跑分平台——覆盖 MI355X /
   GB300 / GB200 / B200 / H200 / H100，每周 **1000+ 数据点**，
   GitHub Actions 全公开可复现（inferencemax.ai 2026-10 实测）。但
   MI300X / MI325X 具体吞吐数字本次未能实读（JS 渲染），正文不引用，
   见文末说明 1。

## 六、深档追问：V1 引擎语义 × NPU 图语义的对齐冲突

浅档答案（背下来够用）：插件机制 + AclGraph 两档 + 三类高频坑
（图捕获缺口 / EP 精度 / 量化 OOM）。

深档答案要能讲清一对结构性冲突：vLLM 的 **V1 引擎语义是动态形状的**
（async scheduling、调度和执行解耦、cuGraph 只包 decode 热点），
而**昇腾图语义偏静态**——static shape、stream budget 固定。两者的
对齐压力全部落在 AclGraph 的 piecewise 档上：哪些子图能包进图、
哪些必须留在 eager，由算子缺口和 stream budget 决定。

issue 实例把这个冲突说得最直白：#8585「软切分 NPU + Piecewise 图
模式不支持」——软切分（把一张物理 NPU 切成多个推理实例）下 stream
budget 被固定划死，piecewise 捕获需要的动态 stream 分配无法满足，
于是该组合直接不被支持。面试里能把「为什么 piecewise 在某些部署
形态下不可用」讲回 stream budget 与静态图语义，就是深档与浅档的
分水岭。

同理，「推理适配为什么比训练适配快」也能讲回机制：**推理的 kernel
复用面窄**（attention + GEMM + 少量融合算子），且不需要长稳训练
（7×24 周级别不失速）的数值稳定性背书——这解释为什么 vllm-ascend
能跑出 day-0 叙事，而训练侧证据链要慢一拍（训练侧见
[国产卡生态专题](./国产卡生态专题.md)）。

## 六·增、NZ 权重布局：Cube 分形排布与量化分工

拼多多 AI infra 一面那句「**NZ 权重布局是什么、它和量化有什么区别**」
（见[小红书面经合集二十四节](../interview-experiences/小红书社招面经合集-2026h2.md)）
问的正是昇腾栈最容易混的一对概念。口径说明：以下为昇腾社区 CANN
数据排布文档与 Ascend C 文档的多源转述（CANN 商用版 8.0RC1 帧口径，
本仓未逐字对原文），数字以官方文档为准：

```text
ND (linear):  行主序线性排布,统计算图里的"逻辑格式"
NZ (Fractal_NZ): 芯片内部"物理格式"——为达芬奇 Cube 定制
  基本块: FP16/BF16 → 16×16 | FP32 → 16×8 | INT8 → 16×32
  (N0=16 固定, K0 随 dtype 变)          ┌── 分形之内按块排
  整矩阵 = (H1×W1) 个分形, 分形之间按   │
  列主序逐列排布(先存满一列分形再下一列) └── 分形之间按列组织
```

三层面试答法：其一，**为什么存在 NZ**——Cube 单元每拍吞吐天然按
16×16 微核计算，把矩阵预摆成 Cube 视角的分形序，A/B/C 矩阵流
进计算单元时访存连续、免搬运重组；ND 进芯片要么转换要么走慢速
通路，这就是 transdata 算子与「离线预转 NZ」存在的理由。其二，
**布局与量化是两个正交轴**——布局回答「块在内存里怎么摆」，
量化回答「每个数用几 bit」；但落地时它们**打包出现**：低精度权重
在线上的形态是「NZ 分形容器 × 逐块量化 scale」，所以工作里
看到的「NZ 权重」血缘上是容器、不是精度格式。其三，**为什么
A5 的 MXFP4 不能照搬到 H20**——MX 系列的 scale 按 32 元素块组织（OCP MX 规格，
块=32），A5 侧沿用的是「分形数据 + 块 scale」的打包哲学（面经口径：
A5 有对应硬件支持），H20 的访存与指令体系按 linear 布局组织，
照搬的不是数字精度而是「块 scale + 分形」的整条数据通路。
这也回扣本篇 §六的图语义主题：**格式与布局是 NPU 图语义的一
部分**——换硬件时它跟算子一起换，不是跟着权重文件走。


## ▶ 高频面试题

1. **vLLM 怎么支持非 CUDA 硬件？**（极高频，仙班题）
   答法：RFC #11162（2024-12）硬件插件机制——主仓管调度/内存/连续
   批处理，插件层换位 Worker / Platform / attention backend / 算子
   替换，entry_points 注册；2025-05 官方博客以 vllm-ascend 为案例
   背书。深档加分：对比 SGLang 主仓 `hardware_backend/` 内置路线。
2. **vllm-ascend 怎么做到 Qwen / DeepSeek / GLM 全兼容的？**
   （高频）答法：模型代码零修改，改的是 attention backend、融合算子
   替换（aclnn + MindSpeed）、AclGraph 执行模式三处；依赖矩阵 CANN
   9.1.0 + PT 2.10.0；硬件三档 950PR/DT、A2/A3、300I Duo。
3. **昇腾上跑 vLLM 最常出什么问题？**（高频）
   答法：按第四节六类走——图捕获算子缺口（#18304/#18012）/ 图模式
   精度乱码（#15831）/ EP 精度（#8223）/ 量化 OOM（#8817 等）/
   PD+KV 池化（#9168/#17756）/ 特性互斥（#17706 等）；尾句收
   「先 --enforce-eager 二分，再看图捕获日志」。
4. **AMD 上跑 vLLM / SGLang 是什么体验？**（中高频）
   答法：主仓一等支持 + 官方 docker（锁 gfx942）→ AITER 586★ 补
   FlashInfer 生态位、MORI 186★ 管 RDMA/EP → 量化宽但 Marlin 系
   缺口 → MI300X 需 GRUB/NUMA 系统调优。深档加分：gfx1151 要关
   AITER（CDNA/wave64 取向）。
5. **FlashInfer 为什么国产卡用不了？替代品是什么？**（中频）
   答法：README 支持矩阵 **SM7.5~SM12.1 全 NVIDIA**（2026-10 实测），
   无 ROCm / NPU 后端；昇腾替代 = 自研 Ascend attention backend +
   CANN aclnn，AMD 替代 = AITER + Triton 移植链。这题本质是考
   「attention kernel 库是最深的上游依赖」。
6. **寒武纪 / 海光的 vLLM 有了吗？**（中频）
   答法：寒武纪 Cambricon/vllm-mlu 存在（**121★**，2026-10 实测），
   README 宣称 day0 DeepSeek-V4 且功能面齐全，但渠道制分发、push 停
   于 2026-05；海光未找到公开 vLLM-DCU 适配仓——DTK 与 ROCm 有血缘
   理论上可蹭上游，但没官宣证据就如实说「未核实」，这是诚信分。
7. **W8A8 / FP8 在国产卡上什么状态？**（中频）
   答法：昇腾支持矩阵 W8A8 对 DeepSeek V3 / GLM 系全勾，W4A8 落在
   Kimi-K3（配合 DSpark），native MXFP8/MXFP4 落在 DeepSeek V4；
   AMD 侧量化宽但 NVIDIA-only dequant kernel（Marlin/modelopt）是
   移植瓶颈——**量化的短板不在引擎开关，在 dequant/GMM 融合算子的
   移植深度**。
8. **PD 分离在国产卡上谁负责 KV 传输？**（中高频）
   答法：昇腾 = Mooncake connector + AscendStoreConnector；AMD =
   MORI RDMA 层；集合通信本身 = HCCL（昇腾）/ RCCL（AMD）；
   摩尔线程 MCCL 只在 S4000。深档加分：把「KV 传输」与「集合通信」
   分开讲——前者是跨节点池化语义，后者是 TP/EP 内 allreduce/alltoall。
