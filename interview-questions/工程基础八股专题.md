## 一、为什么 AI 岗还在考传统后端八股

三条不容辩驳的理由：

1. **业务系统同化**：Agent 平台 = 网关 + 模型服务 + 状态存储 +
   消息队列 + 监控，一个在产 Agent 系统的 90% 是传统后端；
2. **面试成本锚定**：模型侧你有经历（又深又偏），面试官找到
   共同语言最快的方式就是**后端公共八股**——不会这波八股，
   其它的你说了别人也不信；
3. **工程判断力代理**：Redis 大 key 这题本质上问的是「你对自己的
   服务的容量和危险面了解多少」，这在 Agent 岗位直接映射到
   「你对请求成本/延迟/失败的容量有没有概念」。

为什么 → 接生产案例**。离开这个模板怎么答都像背词。

## 二、Redis：四切面 + Agent 联动

### 2.1 缓存三座大山（穿透/击穿/雪崩）

| 名称 | 病征 | 经典三句 | 生产案例 |
|---|---|---|---|
| 穿透 | 查询不存在的 key，全到 DB | 布隆过滤器先行拦截 + 缓存空值短过期 + 入口参数校验 | Agent 检索缓存：无结果也缓存 60s，防止攻击者刷不存在的知识库文档 |
| 击穿 | 单一热点 key 过期瞬间被打 | 互斥重建（第一个请求 setnx 重建，其余等）或逻辑过期（不过期 + 后台异步刷新） | 热门系统 prompt/知识库索引结果缓存，早高峰百万请求下必须互斥重建 |
| 雪崩 | 大量 key 同时过期 | 过期时间加随机抖动 + 多级缓存（本地 L1 + Redis L2） | 模型版本切换发布时提前分批预热 |

### 2.2 大 key 治理

危害：阻塞单线程（Redis 是单线程事件循环）、占带宽、数据倾斜、
删除瞬阻。处理四板斧：**拆分（按业务/哈希拆）、改结构（Hash 代替
散 key、bitmap/HLL 代替大集合计数）、渐进删除（UNLINK 异步 /
SCAN 分批）、预防（上线前评估 + 监控巡检）**。
Agent 联动：长会话历史/大工具结果别直接塞 Redis，放对象存储留
引用；共享预算「三账」用 Hash 一次原子多字段更新而不是三次写。

### 2.3 分布式锁

经典三句：`SET NX PX`（同时设置互斥与过期）+ 唯一 value + Lua
脚本原子释放；Redisson 看门狗续期；fencing token 防旧持有者
延迟交付。争议点：Redlock 实战中多数团队认为单实例 + 业务幂等
更稳，**单靠锁保护不了的场景在上游加幂等键**（同 harness 帖
「三账并发记账」的对照组）。

### 2.4 热 key

本地缓存（进程内 LRU）+ 读写分离 key + 随机后缀拆扇区——在
推送热门知识库索引结果/嵌入向量时与击穿题的互斥重建联用。

## 三、MySQL：索引、事务、慢查询

### 3.1 索引（B+ 树）

经典三句：B+ 树 = 多路平衡查找树，内部节点只存键、叶子节点存
行数据/主键并用双向链表串连；聚簇索引（主键）叶子是整行，二级
索引叶子是主键、查到后要**回表**；**最左前缀匹配**决定联合索
引生效与否，覆盖索引避免回表。

- 频考题：为什么用 B+ 树不用 B 树/哈希——B+ 树叶子链表利于
  范围扫描、内部节点页密度高减少 IO 层数；哈希等值 O(1) 但
  不支持范围。
- explain 要看哪几个字段：`type`（const/ref/range/index/ALL
  满扫）、`key`（实际用了哪条索引）、`rows`、`Extra`（Using
  index/Using filesort/Using temporary）。

**AI 场景联动**：向量库的 HNSW vs IVF 选择题可以反手回「像
MySQL 索引选型：ANNI 索引是精度的 trade-off」——IVF 聚类先全
后扫 = B+ 树；HNSW 多层图 = LSM 结构跳表。面试官很吃这个联系
对照（比背两种算法好在多了一个联系点）。

### 3.2 事务与 MVCC

ACID + 四级隔离（读未提交/读提交/可重复读（MySQL 默认）/串行）
+ InnoDB 用 **MVCC（多版本：read view + undo log 链）** 在
RC/RR 下放行读写不阻塞；间隙锁防幻读。生产中写多场景用 RC
更多（binlog 恢复/主从延迟小），为什么：RR 间隙锁影响并发。

### 3.3 慢查询排查套路

慢查询日志 → explain → 看是否全扫 → 决策：加索引/改 SQL（拆
分页/子查询）/拆表/读写分离/加缓存。**先建统计，别上来就优化**。

## 四、Kafka/消息队列：可靠性、顺序、幂等

- **可靠性**：ack=-1 + ISR 半数副本落盘 + 本地不重试不重发；生产
  端幂等（PID + Sequence number）+ 事务消息（两阶段）防重复；
- **顺序**：单分区内有序；要全局序用单分区或分区键路由+消费侧
  重排；扩分区后顺序会乱——业务上预设好；
- **积压**：看是生产太快还是消费太慢；临时扩消费者组到分区数
  上限 + 拉取阻尼；批量消费并开事务批量提交；
- **重复消费**：消费侧幂等（业务 ID + 去重表/Redis setnx）答
  案是这句，不是「broker 不重复」。

**Agent 联动**：工具调用异步队列、HITL 人工接管事件、训练侧
在线/离线数据互传、评测回流通道——所有面经里出现的「异步
解耦」「削峰」「事件溯源」都用这一桶答。

## 五、网络：TCP 三问 + HTTP 演进 + SSE

- **三次握手为什么不是两次**：防止旧的重复 SYN 占用服务资源
  （半开状态被伪造），并同步双方初始序列号 seq；
- **四次挥手为什么不是三次**：被动方收到 FIN 后可能还有数据
  未发完，ACK 与 FIN 分两步；
- **TIME_WAIT 为什么存在**：保证最后一个 ACK 能到达，防旧包
  干扰新连接；
- **HTTP/2 改进**：多路复用（单连接多流）、头部压缩 HPACK、
  二进制分帧；HTTP/3 QUIC：0-RTT、无队头阻塞（UDP + 流内
  独立 ub）、连接迁移；
- **SSE vs WebSocket vs 轮询**：SSE（`text/event-stream`、单向、
  断线重连、HTTP/1 也能跑）——Agent 流式输出默认选 SSE 的
  两个理由（HTTP 生态兼容、只需服务端到客户端单向）；WebSocket
  是双向通道，实时交互强；轮询是 fallback。阿里国际 Agent 面
  真题：SSE 的 `data: [DONE]` 约定、客户端断开要及时中止生成
  省 token、Nginx 要关响应缓冲。

## 六、Docker 与 K8s：三句掌握 + GPU 场景

- **Docker 本质三句**：namespace 做隔离（pid/net/mnt/uts/...）、
  cgroups 做限额（CPU/内存/IO）、联合文件系统（overlay2）做
  镜像分层复用；「容器是受限的进程，不是虚拟机」；
- **K8s 核心对象**：Pod（最小调度单位）、Deployment（副本 +
  滚动更新）、Service（服务发现与负载）、Ingress（入口）、
  HPA（水平伸缩，按 CPU/自定义指标如 QPS/token 吞吐）、
  Operator（领域化生命周期管理）、nodeSelector/Taint 调度约束；
- **GPU 场景**：NVIDIA device plugin 上报 `nvidia.com/gpu` 资源、
  GPU Operator 管理驱动与 DCGM 监控、MIG/时间片做 GPU 共享、
  推理服务通常配 PodDisruptionBudget + 优雅下线（先摘掉流量再
  停 batch）。推理 infra 岗对这几句必须顺口。

## 七、限流、熔断、降级

| 护栏 | 机制 | AI 场景的落点 |
|---|---|---|
| 限流 | 令牌桶（平滑 + 突发）/漏桶（恒速）/滑动窗口 | 多租户 AI 网关按 token/user 双维度限流 |
| 熔断 | 滑动窗口失败率超阈值开闸，半开试探恢复 | 模型 adapter 独立熔断、单 Provider 故障不拖死全站 |
| 降级 | 预设落地方案优先级 | 主模型 → 备用模型 → 固定 RAG 模板 → 转人工队列；工作流退化为线性 Chain 而非 Agent |

## 八、场景题两则（端到端）

**Q1：设计一个问单机器人的全链路（API 入口 → 回答）。**
入口：API 网关限流（令牌桶按用户）+ SSE 流式；解耦：模型请求
与控制逻辑分（队列缓冲削峰、失败重试幂等）；存储：会话状态在
Redis（Hash，YAML 序列化状态 + TTL）、RAG 索引结果多级缓存
（本地 + Redis）+ 温存预热；工程：K8s HPA 按 TTFT/QPS 扩缩 +
PodDisruptionBudget 保证滚动更新不断流。

**Q2：上线后 P95 延迟从 800ms 涨到 3s，怎么排查？**
层级倒查：① 流量端——是否涌入旧 cohort（与其 cache hit 比例；
场距数据）；② 引擎端——batch size/KV 缓存打满率/并发与 GPU
利用率是否撞线；③ 引擎外——Redis 慢日志、锁竞争、GC 长停、
K8s 是否被驱逐或调度到了非亲和节点；④ 依赖侧——上游 embed
服务/向量库延迟是否异常变高；工具用 langfuse/nsys/pprof 各层
对照。**先归因后优化**——每次改一个变量、打四张曲线图验证。

## 九、面试问答（汇总八股答法）

**Q：Redis 缓存穿透怎么解决？**
经典三句（布隆 + 空值短过期 + 参数校验）→ 为什么（把不存在的
查询拦在 Redis 之前，防止缓存被绕过打 DB）→ 生产案例（Agent
检索缓存防刷不存在的知识库 ID）。

**Q：索引为啥用 B+ 树？**
三句（叶子存数据双向链表、内部只存键、矮胖减少 IO 层数）→
与随机访问的哈希索引对比（哈希等值快但不支持范围）→ 工程联动
（向量库 IVF/HNSW 的精度-delay trade-off 同构）。

**Q：SSE 为什么不直接用 WebSocket？**
HTTP 生态兼容（代理/网关/CDN 不用改）+ Agent 场景是单向流式
（发起只需客户端 → 服务端一条）+ 断线自动重连用 Last-Event-ID；
客户端断开要及时中止省 token；Nginx 关响应缓冲是关键配置。

**Q：限流选令牌桶还是漏桶？**
令牌桶：允许有限突发、平均速率可控（更适合 LLM 网关——tokens
脉冲天然突发）；漏桶：恒速平滑（适合下游冷脆服务）；滑动窗口
介于两者（精度/开销 trade-off）。
