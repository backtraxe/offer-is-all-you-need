## 方法论：排障题的四段论

面试官描述一个线上现象，他要的不是答案，是**你的排查秩序感**。固定
招式四段，按顺序报：

1. **定位（先指标后假设）**：第一句话永远是「我先看 X 指标的 Y 字段」，
   不是「我觉得可能是……」。把现象翻译成观测量：延迟问题看
   p50/p99 分位而别看均值；挂死问题看 watchdog/timeout 日志；质量
   问题先固定输入重放。
2. **复现（最小复现集）**：定位出嫌疑后，先回答「怎么稳定复现」——
   单请求重放、canary job、灰度对照。不能复现的根因只是猜想，
   这句话说出来就赢了半程。
3. **方案（先止血后根治）**：先说 5 分钟内能做的（限流/降级/回滚/
   摘节点），再说根治（容量/配置/流程/监控）。顺序反了会显得没
   上过生产。
4. **验证（灰度+对照）**：方案上线怎么确认有效——灰度组对照
   指标、回归集、告警压测。没有第四步的方案是祈祷。

两个致命扣分点：**上来就猜根因不报依据**（显得没体系）；**方案不提
验证**（显得没闭环）。四段说完，再补一句与 STAR 的关系：现象即
Situation，指标确认即 Task 量化，四段本身就是 Action 的证据链。

## 一、推理服务排障（10 题）

### 推 1：高峰期 TTFT 的 p99 从 2s 涨成阶梯式 8s

- **现象**：晚高峰 TTFT p99 阶梯上升，p50 基本不动，持续约 40 分钟。
  60-90 秒节奏报：
- **第一三板斧**：① 看 `vllm:num_requests_waiting` 曲线确认是不是
  排队堆积；② 看 `vllm:gpu_cache_usage_perc` 是否顶到水位线；
  ③ 看 `vllm:num_preemptions_total` 是否在持续上涨（抢占风暴前兆）。
- **分诊深挖**：waiting 涨而 running 不涨 → 容量到 knee point，
  对照历史同时段判断是突量还是画像漂移；running 涨但 TTFT 也涨 →
  前缀命中率掉（跳推 3）；单实例TTFT 高 → 慢节点（跳推 6）。
- **复现**：压测环境按同比例重放高峰 QPS 与长度分布，确认 knee
  point 位置。
- **方案**：止血=网关 429 限流+高优队列；根治=水位 ρ 控制在 60%
  并提前扩容，长度画像周报进容量评审。
- **追问压迫**：「怎么证明是容量问题不是代码回归？」——对比昨天同
  时段同指标的基准线，并查近 24h 发布记录；发布记录干净且负载
  超线即容量问题。
- **评分点**：先指标后假设、能区分「突量」与「退化」两种表象相似
  的病。

### 推 2：KV 打满，请求大面积超时

- **现象**：`gpu_cache_usage_perc` 顶到 100%，waiting 暴涨，超时
  率飙升。
- **第一三板斧**：① `vllm:num_preemptions_total` 增速确认是否
  抢占风暴；② 拉长度分布画像看是否有异常长请求滞留；③ 查
  `max_num_seqs` 与 `max_model_len` 相对画像是否合理。
- **分诊深挖**：抢占增长+吞吐反而降 → 抢占重算死循环；长请求滞留 →
  大请求占着 KV 不放；画像没变 → 纯流量超配。
- **复现**：用画像里抽样的混合长度压测，复现抢占风暴拐点。
- **方案**：止血=限流+截断一个条目队列+降 `max_num_seqs` 提水位；
  根治=按画像重设 `max_model_len` 上限、长请求分桶独立池、
  KV 水位 80% 告警。
- **追问压迫**：「max_num_seqs 调大不就完了？」——恰恰相反，并发
  越高 KV 越紧张，抢占越凶，吞吐不升反降；KV 是硬约束时提并发
  是火上浇油。
- **评分点**：知道 KV 是硬资源、抢占的代价是重算，会算这只账。

### 推 3：前缀缓存命中率从 80% 掉到 20%

- **现象**：命中率先导下跌，随后 TTFT 全面上浮，QPS 没变。
- **第一三板斧**：① 看命中率指标的时间拐点对事件（发布/配置变更/
  上游改 prompt）；② 抽 20 条真实请求的 system prompt 做 diff；
  ③ 查路由层负载均衡策略是否带 session 亲和。
- **分诊深挖**：system prompt 里混入时间戳/request id → 前缀永远
  不同（最常见）；路由换成 round-robin → 同会话打不到同实例；
  截断策略变化 → 前缀被从中间切断。
- **复现**：灰度实例上重放线上 prompt 样本，两次发送同一 prompt
  直接看命中计数。
- **方案**：止血=路由开一致性 hash 亲和；根治=system prompt 模版
  治理（动态字段放 user 轮），命中率进 SLO 看板。
- **追问压迫**：「prefix cache 对 TTFT 到底影响多大？」——按
  prefill tokens × 命中率估算省下的预填充 FLOPs，能给出一个量级
  口径（命中一次长前缀≈省掉整段 prefill 计算）。
- **评分点**：知道命中率是「前缀内容稳定性 × 路由稳定性」的乘积。

### 推 4：W4A16 量化版本上线后用户投诉「变笨了」

- **现象**：切量化版后主观投诉增多，离线评测掉两个点。
- **第一三板斧**：① 固定 seed+greedy，同 prompt 对 bf16 基线与
  量化版单请求重放，对比输出；② 对比逐 token logprobs 找最早
  分叉位置；③ 查量化配置（group size、calibration 集、跳过层
  清单）与基线权重 sha256。
- **分诊深挖**：整体漂移 → 量化本身损失；特定任务掉 → 校准数据
 八股偏离线上分布；随机性大 → 可能不是量化，是并发/采样参数
  被一起改了。
- **复现**：抽 50 条投诉类 prompt 建回归集，双跑对拍。
- **方案**：止血=回滚 bf16 灰度；根治=回归集进发布门禁、敏感层
  （down_proj/embedding）保留高精度、校准集换成线上分布采样。
- **追问压迫**：「怎么区分量化损失和模型本来就烂？」——同输入
  对拍是唯一法官，greedy 下 logprob 曲线逐 token diff。
- **评分点**：质量事故的对照实验素养：控制变量、固定 seed、
  单请求重放。

### 推 5：GPU util 95% 以上,吞吐却掉了三成

- **现象**：util 打满但 output tokens/s 降 30%。
- **第一三板斧**：① 看 batch 内平均输出长度构成（长输出占比上升
  会让 token 吞吐降但 util 高——decode 是 memory-bound）；② 看
  抢占重算计数（util 在做无用功）；③ 投机解码命中率（接受率掉
  会让 draft 计算变纯浪费）。
- **分诊深挖**：画像变了 vs 引擎内部退化——拿昨天的画像重放即知。
- **复现**：按新旧两版长度画像分别压测对比。
- **方案**：止血=按画像调 `max_num_seqs`；根治=按工作负载分池，
  投机解码接受率进监控。
- **追问压迫**：「util 高为什么不代表性能好？」——decode 阶段
  瓶颈是显存带宽不是算力，util 只看 SM 活跃度；利用率冒烟而
  token 产出降，多半在搬数据或重复计算。
- **评分点**：破除 util 迷信，懂 memory-bound 阶段的收益指标
  是 tokens/s 不是 util。

### 推 6：某实例 TPOT 是同组三倍，拖高全局 p99

- **现象**：单台 TPOT 异常，摘流量后全局 p99 立刻恢复。
- **第一三板斧**：① `nvidia-smi -q -d PERFORMANCE,ECC` 看降频与
  ECC 计数；② dmesg/DCGM 查 XID（13 非法指令、31 MMU fault、
  48 双比特 ECC、79 fallen off the bus、94 contained ECC）；
  ③ 看同机邻居/混部任务是否抢占（CPU、PCIe、显存带宽）。
- **分诊深挖**：XID 有记录 → 硬件；干净但慢 → 邻居抢占或散热降频
  （看 clocks_throttle_reasons）；换 slot 实验判断「跟人还是跟
  位置」。
- **复现**：canary job 独占该节点跑标准负载对比基线。
- **方案**：止血=摘流 drain；根治=DCGM 健康分接入调度，坏节点
  自动隔离维修队列。
- **追问压迫**：「重启能不能好？」——XID 79/48 类的硬件病重启
  只会复发；先读 XID 再决定重启还是送修。
- **评分点**：慢节点三板斧「XID→降频→邻居」，不重启先取证。

### 推 7：推理服务跑一周后缓慢 OOM

- **现象**：显存逐日爬升，第七天 OOM；重启归零。
- **第一三板斧**：① 定时 dump `torch.cuda.memory_summary` 看
  allocated 与 reserved 谁涨；② reserved 涨 allocated 平 →
  碎片，查分配器配置（`PYTORCH_CUDA_ALLOC_CONF`）；③ 查 CUDA
  graph 捕获后是否有句柄/缓冲累积。
- **分诊深挖**：allocated 涨 = 真泄漏（KV 释放路径 bug/LRU 失效）；
  reserved 涨 = 碎片（尝试 expandable_segments 口径）。
- **复现**：压测环境小显存重复负载加速爬升曲线。
- **方案**：止血=滚动重启+水位告警；根治=升级引擎修泄漏点或开
  expandable_segments，显存曲线进日检。
- **追问压迫**：「碎片和泄漏怎么区分？」——allocated 跟着请求
  走、reserved 只涨不跌是碎片；allocated 在请求走后不回落才
  是泄漏。
- **评分点**：会读 `memory_summary` 三区块，知道两类病的不同
  处方。

### 推 8：引擎偶发 CUDA illegal memory access，难复现

- **现象**：高负载下偶发崩溃，日志只有 IMA。
- **第一三板斧**：① 线上采样 core dump + 崩溃时请求的
  （长度/batch 构成）画像；② 压测上用 `CUDA_LAUNCH_BLOCKING=1`
  跑同画像负载把异步报错变同步定位；③ 二分 custom kernel /
  采样参数边界（超长、空 prompt、极端 temperature）。
- **分诊深挖**：同步后可定位到具体 kernel → 该 kernel 的边界
  条件；只在高并发出现 → 显存越界对手是 race，降并发复现。
- **复现**：构造最简请求集在压测环境必现（没有必现就不叫复现）。
- **方案**：止血=崩溃自动拉起+重放保护（崩溃前请求不落盘丢）；
  根治=修 kernel 或绕开触发路径，最小复现集进回归。
- **追问压迫**：「为什么要开 LAUNCH_BLOCKING」——CUDA 异步执行
  让报错点远离真实出错 kernel，同步执行把报错钉在元凶上，
  代价是性能，所以只在复现环境开。
- **评分点**：懂 CUDA 异步与复现方法论，先钉现场再谈修复。

### 推 9：某天起输出突发大量重复片段

- **现象**：响应出现重复循环，特定场景高发。
- **第一三板斧**：① 查当日变更：采样参数（重复惩罚/repetition_penalty
  被关）、投机解码配置（draft/target 不匹配）、系统 prompt 改动；
  ② 灰度实例单请求重放复现；③ 回滚最近一个变更验证。
- **分诊深挖**：全场景重复 → 全局配置（采样参数/引擎）；特定 prompt
  → 数据诱发的退化（前缀里有重复文本被放大）；伴随延迟下降 →
  投机解码 draft 版本错配。
- **复现**：挑 3 个必现 prompt，固定 seed 对拍新旧配置。
- **方案**：止血=回滚配置；根治=采样参数进版本管理、重复率进
  线上质量指标。
- **评分点**：「某天起」三个字是钥匙——先查变更再查模型。

### 推 10：升级 vLLM 版本后延迟全面上浮两成

- **现象**：版本升级后 TTFT/TBT 全线 +20%，无报错。
- **第一三板斧**：① 双版本灰度对拍（同流量镜像）锁定是版本本身；
  ② 对比两版的调度器/ chunked prefill / CUDA graph 默认配置
  diff；③ 看 kernel trace（nsys）哪个阶段时间变长。
- **分诊深挖**：默认值变更（最常见：某优化默认关闭/开启）/ kernel
  回归 / 权重格式转换引入额外拷贝。
- **复现**：压测环境两版本同负载 A/B，指标差稳定复现。
- **方案**：止血=回滚旧版；根治=对上配置差异后逐项恢复新版特
  性，升级前必跑性能基线对比门禁。
- **追问压迫**：「为什么不用最新版就行了吗？」——引擎升级 = 换
  了一组默认行为，性能基线对比是发布必修，不是选修。
- **评分点**：双版本对拍的工程惯性与「默认值敬畏」。

## 二、训练系统排障（10 题）

### 训 1：loss 曲线突然一根尖刺，要不要回滚

- **现象**：稳定运行的预训练 job 某一步 loss 跳高一个量级后又回落，
  grad norm 先行抬头，其余指标正常。
- **第一三板斧**：① 回看 grad norm 是否先于 loss 抬头，先行即走
  spike 流程；② dump 可疑 batch 查数据特征（乱码/极端长度/标签错位）；
  ③ 逐 rank 对比该步 loss 与梯度范数，单卡离群是 SDC 坏卡信号。
- **分诊深挖**：grad norm 先抬、全员齐炸 → 数值 spike 移交算法侧；
  只此一步且自愈 → 脏 batch，查该步样本画像；固定 rank 持续离群 →
  SDC 坏卡；全员齐爆且画像干净 → 查 lr 调度与配置最近变更点。
- **复现**：回退尖刺前 ckpt，固定该 batch 重放单步前向加反向，看
  grad norm 是否稳定复现；换正常数据对照。
- **方案**：止血=跳过坏 batch / 回退好 ckpt 重启验证；根治=grad
  norm 先行告警进监控，坏卡下线，脏数据进清洗黑名单。
- **追问压迫**：「怎么证明是脏数据不是坏卡？」——逐 rank 对齐定罪：
  坏卡是固定 rank 持续离群，脏数据是全员同一步同炸，处置方向相反。
- **评分点**：五分钟分诊先决定送算法侧还是系统侧，不越界乱修。

### 训 2：千卡 job 全员日志停住，十分钟后 watchdog 超时

- **现象**：所有 rank 日志同时停住，600 秒后抛 `Watchdog caught
  collective operation timeout`，此前无任何报错。
- **第一三板斧**：① flight recorder（`TORCH_NCCL_TRACE_BUFFER_SIZE`，
  2.4 起超时自动 dump）按 `seq_id` 对齐所有 rank，找「有的 rank 进了、
  有的没进」的最后一次集合通信；② `NCCL_DEBUG=INFO` 拉每 rank 日志
  确认缺谁；③ `py-spy dump --pid` 看缺人 rank 主线程卡在哪行。
- **分诊深挖**（四分支）：缺人固定在几台机 → 慢节点拖尾（转训 6）；
  无规律缺人、`perfquery` 的 `XmitWait`/重传尖刺与时刻重合 → 同 ToR
  拥塞加 PFC 扩散；某 rank 先退出（OOM/段错误）→ 非对称崩溃，最早
  异常才是真凶；缺条件触发的 op → `if` 分支藏 `all_reduce` 的 bug。
- **复现**：canary job 同配置小规模重跑；分支 bug 用必命中/必不命中
  两组数据对比通信调用序列。
- **方案**：止血=`timeout` 600s 提到 1800s、拥塞租户限流错峰；根治=
  通信走统一 wrapper 禁裸调用进条件分支、canary `all_reduce` 探活、
  flight recorder 自动 dump 接告警。
- **追问压迫**：「timeout 提到 1800s 不就解决了？」——那是止血，
  把慢节点拖尾从「挂死」掩盖成「慢」；集合通信真实耗时超 600s 说明
  通信已严重退化，根因还在。
- **评分点**：挂死先问「谁在等谁」，按 `seq_id` 对齐是破案现场。

### 训 3：MFU 从 45% 掉到 38%，loss 完全正常

- **现象**：tokens/s/GPU 下滑，MFU 从 45 掉到 38，`nvidia-smi dmon`
  里 SM 利用率呈锯齿，loss 曲线干净——纯性能病。
- **第一三板斧**：① `nsys profile -t cuda,nvtx,nccl` 抓 50~100 个
  step，NVTX 标 step 边界；② 时间线分三段：kernel 在跑、kernel 间隙、
  被 `ncclDevKernel` 占满，占比定桶；③ `torch.profiler` 补框架侧
  调用栈找慢算子。
- **分诊深挖**（四桶）：间隙被 NCCL 填满 → 通信桶（TP 跨节点、PP
  bubble、`overlap_grad_reduce` 没生效）；util 锯齿、step 双峰 →
  饿卡桶（转训 9）；某 kernel 变慢 → 算子桶（FA 回退 math、`tf32`/
  `bf16` 没开）；launch 开销爆炸 → 配置桶（micro batch 太小、full
  recompute 白烧）。
- **复现**：canary job 同数据同配置重跑并 re-profile 确认分桶结论。
- **方案**：止血=只砍占比最大的那桶；根治=基线 profile 入库，升级
  先过 canary 对比再放量，MFU 面板按周巡。
- **追问压迫**：「为什么不四桶一起优化？」——砍第二桶前先确认第一
  桶不占大头；遍地开花搅乱时间线，无法归因哪一招有效。
- **评分点**：`nsys` 时间线是 MFU 分桶唯一权威视图，按占比归因不
  按直觉猜。

### 训 4：稳定三周的训练突然 OOM

- **现象**：三周没动配置的 job 某 step 抛 `torch.cuda.OutOfMemoryError`，
  此前显存水位一直健康。
- **第一三板斧**：① `torch.cuda.memory_summary()` 打 allocated /
  reserved / 碎片三块账；② 对 step 索引查数据长度画像是否漂移；③
  确认 OOM 时刻是否恰在 ckpt/eval（gather 全量权重、eval batch 超配）。
- **分诊深挖**（四分支）：allocated 偏高 → activation 账超（seqlen/
  重计算/micro batch 超配）；reserved 高 allocated 低 → 碎片
  （`expandable_segments:True` 对照）；optimizer 状态爆 → ZeRO 档位
  开错；某 step 起炸 → 突发型（画像漂移、ckpt/eval 时刻）。
- **复现**：最长合法样本单步跑显存压测，叠加 ckpt 动作复现时刻峰值；
  快照级排查用 memory history 加 `_dump_snapshot()` 回放分配火焰图。
- **方案**：止血=降 micro batch 或开 selective recompute；根治=上线
  前最长样本显存压测、reserved/allocated 比值漂移进监控、数据按长度
  分桶。
- **追问压迫**：「为什么三周后才炸？」——三周没遇到极端样本不等于
  不存在，画像漂移把它送进来的那天就是炸的那天；预算按最长合法样本
  算。「调大上限有用吗？」——allocated 真超限调上限是拖延，碎片病
  才轮得到分配器策略。
- **评分点**：会读 `memory_summary` 三区块，区分「账面 OOM」与「时刻
  OOM」两类处方。

### 训 5：断点续训后 loss 曲线无缝但数值对不上

- **现象**：kill 恢复后续训能跑，loss 大致延续但接缝处出现台阶，与
  首训曲线逐位对不上。
- **第一三板斧**：① 核 dataloader state 是否存全（样本顺序、shuffle
  偏移）；② 核 RNG state 是否全量恢复（python/numpy/torch、各 rank）；
  ③ 核 optimizer state 精度与版本（fp32 master 是否落盘、框架版本）。
- **分诊深挖**：接缝台阶但后段形状一致 → 样本顺序变了；统计特征
  相似但逐点对不齐 → RNG 没恢复（dropout/数据增强噪声序列变了）；
  缓慢漂移 → optimizer state 精度差（fp16 存的 master）或版本差；还要
  查 resume 路径是否与首训一致（warmup 重跑、调度器重置）。
- **复现**：存档—kill—恢复验收：前一百步 loss 逐位对齐，对不上即失败。
- **方案**：止血=回退验收过的好 ckpt 与恢复流程；根治=state dict
  完整性清单进存储 schema，恢复正确性纳入发版回归。
- **追问压迫**：「差一点有影响吗？」——预训练长训的接缝台阶会污染
  后续 scaling 结论；「能跑」不等于「恢复的是同一条优化轨迹」。
- **评分点**：背得出 resume 三件套，有逐位对齐验收意识而非「看着
  差不多」。

### 训 6：iteration p99 是 p50 两倍，整 job 被一台机器拖慢

- **现象**：step time p99 明显大于 p50，集合通信等待集中在同一来源
  rank，整 job MFU 被单边拖低。
- **第一三板斧**：① 各 rank 上报 iteration time 聚合 p50/p95/p99，
  看离群是否固定同一 rank；② `nvidia-smi -q -d PERFORMANCE,ECC` 查
  降频与 ECC、`ibstat` 查端口 `Rate` 掉档；③ dcgm 面板看温度与 PCIe
  重传，必要时 `dcgmi diag -r 3` 体检。
- **分诊深挖**（四分支）：SM clock 低于基频、throttle reason 实锤 →
  热/供电降频；ECC 重试或 row remap → 纠错降速型慢卡（不报错只变慢）；
  `Rate` 400G 掉 100G 不告警 → 网卡半伤；同 ToR 邻居抢带宽 → 跟位置
  有关的慢。
- **复现**：换位实验——疑似节点与健康节点互换 slot 重启：慢跟人走
  是节点坏，下线送修；慢跟位置走是网络/拓扑问题。
- **方案**：止血=隔离换机重跑；根治=准入前 `dcgmi diag -r 3`、per-rank
  step time 常态监控、p99/p50 超阈自动标记慢节点。
- **追问压迫**：「直接重启节点不行吗？」——纠错降速型慢卡重启无用
  还丢证据；先取证再隔离，重启是最后一步。
- **评分点**：换位实验「跟人还是跟位置」是标准判据。

### 训 7：每到 ckpt 步 MFU 就周期性骤降

- **现象**：MFU 每隔固定步数骤降一次，与 ckpt 周期严格对齐，写 ckpt
  的 step 时间尖刺数倍于正常。
- **第一三板斧**：① 对时间轴确认尖刺与 ckpt 周期逐一重合（周期对齐
  就是半份诊断书）；② `iostat -x 1` 看本地盘 util 是否打满；③ 对象
  存储网关日志看限流（429/503、SlowDown），并行文件系统看 MDS 负载。
- **分诊深挖**（四分支）：主线程等落盘 → 同步写挡训练（该上异步
  ckpt：先拷 pinned memory 再后台落盘）；几千路分片并发写触发限流 →
  小文件风暴（合分片、前缀打散、退避重试）；create/stat 打爆 → MDS
  元数据热点（合并分片、目录分桶）；尖刺后跟着 loss 接缝 → 写出
  完整性问题（转训 5）。
- **复现**：canary job 缩短 ckpt 间隔压测，量出写带宽与尖刺的函数
  关系再选异步方案。
- **方案**：止血=调大 ckpt 间隔、多 job 错峰写；根治=async save
  （DCP / Megatron async）、分片聚合、写带宽与耗时入监控。
- **追问压迫**：「async save 有什么坑？」——后台落盘未完成时挂掉
  会留半个 ckpt：要写完成标记、保留上一份好 ckpt、恢复时校验各 rank
  分片同一轮写出。
- **评分点**：从「周期对齐」一步锁定 ckpt；存储三类瓶颈（带宽/限流/
  元数据）处方不同。

### 训 8：升级训练镜像后 MFU 掉 15 个百分点

- **现象**：例行升级镜像后同配置 job 的 MFU 从 47 掉到 40，loss 曲线
  正常——纯性能病，归入「慢」类。
- **第一三板斧**：① `nsys` 对比升级前后时间线：通信等待一成二涨到
  二成七、kernel 没变 → 锁通信桶；② `NCCL_DEBUG=INFO` 双版本对比
  `AllReduce` 算法与 channel 数；③ 查机内段 NVLS 是否启用。
- **分诊深挖**：新版 NCCL 拓扑识别结论变化 → 算法切换、机内段不走
  NVLS——慢在算法选择不慢在硬件；kernel 段耗时也变 → 升级动了算子
  （`FlashAttention` 回退），另一条线别混着查。
- **复现**：双版本 A/B 同数据同配置 canary 各跑一份，显式 `NCCL_ALGO`
  锁回旧算法，MFU 恢复即实锤。
- **方案**：止血=`NCCL_ALGO` pin 回旧算法；根治=版本与拓扑参数双
  pin、升级先过 canary kernel 级时间线门禁、附 `INFO` 日志提 issue。
- **追问压迫**：「新版有新特性为什么 pin 旧算法？」——正确性用新、
  性能回归用 pin；性能基线对比是升级必修门禁，回归在灰度里抓。
- **评分点**：双版本对拍加环境变量锁回是可背诵的标准动作。

### 训 9：GPU util 规则锯齿、step 时间双峰，通信桶干净

- **现象**：GPU util 规则锯齿，step time 双峰；`nsys` 显示 kernel
  间隙无 NCCL 占用，纯空转等数据。
- **第一三板斧**：① 时间线确认间隙无通信占用，归饿卡桶；② 查
  dataloader 四件套：`num_workers`、`pin_memory`、prefetch 深度、解码
  耗时；③ 打点数据侧各段（解码/tokenizer/远端读）找供数瓶颈。
- **分诊深挖**：worker 不足或解码太重 → CPU 供不上；`pin_memory`
  没开、prefetch 太浅 → H2D 与计算串行化；随机小 IO 读远端对象存储
  → shard 没顺序化；step 双峰对应「读到快/慢 shard」——双峰是数据
  布局的签名。
- **复现**：canary job 数据预热到本地 NVMe 重跑，锯齿消失即瓶颈在
  数据通路。
- **方案**：止血=调大 `num_workers` 与 prefetch、开 `pin_memory`；
  根治=重解码样本离线预处理成顺序化 shard、数据本地化/分层缓存、
  供数速率入监控。
- **追问压迫**：「num_workers 越大越好？」——受 CPU 核数与内存带宽
  约束，过大会互相抢核拖垮主进程；按实测供数速率标定。
- **评分点**：锯齿与双峰是可读的表象签名；能在时间线上区分饿卡桶
  与通信桶。

### 训 10：RL 训练的 rollout 阶段越来越慢

- **现象**：GRPO/RLHF job 前期 rollout 耗时稳定，数百步后持续上涨，
  update 阶段正常，GPU 空转等采样。
- **第一三板斧**：① 分阶段打点：rollout 与 update 各占多少时间，
  确认慢在采样侧；② 看输出长度画像——长思维链场景输出 token 数随
  训练上涨，生成本身变长；③ 看引擎侧指标（`vllm:gpu_cache_usage_perc`、
  tokens/s）是否退化。
- **分诊深挖**：输出变长 → 同步批 generation 时间由最长一条主导，
  长尾 straggler 被同步屏障放大；引擎 tokens/s 退化 → KV 池被长输出
  堆积占满、并发被压、抢占重算抬头；reward 噪声同步变大 → 警惕训推
  不一致（两引擎精度/kernel/路由差异让 verifier 评错模型）；weight
  sync 全量且频繁 → 同步开销被算进 rollout。
- **复现**：固定 ckpt 四格回放：旧引擎/新引擎 × 同步批/partial
  rollout，哪一格慢得复现就锁哪一格。
- **方案**：止血=截断长尾上限、调 group size；根治=异步化加 partial
  rollout（长轨迹跨步续生）、训推对齐校验进门禁、KV 水位入监控。
- **追问压迫**：「为什么不直接加卡？」——长尾是结构性问题，加卡只
  把算力摊给屏障空等；batch 最长一条决定整批耗时，partial rollout
  才按机制下药。
- **评分点**：把「越来越慢」拆成长度上涨、长尾放大、引擎退化三机制；
  知道 RL 算力大头在采样。

## 三、Agent 线上排障（10 题）

Agent 排障与普通 LLM 服务排障的本质差别是**排查单位是轨迹不是请求**：
单请求故障会被轨迹结构放大成几十步、几十倍 token 的跑偏。本章十题
素材与 [agent线上排障手册](./agent/agent线上排障手册.md) 同源，特征词
记住四个：轨迹、步级 trace 下钻、失败模式聚类、最小复现轨迹。

### A 1：客服 Agent 单轨迹步数暴涨、成本长尾

- **现象**：平时 8 步内完成的客服任务开始跑出 40 步的轨迹，
  `max_steps` 熔断触发率抬升，轨迹级成本出现长尾尖刺，请求量没变。
- **第一三板斧**：① 抽最贵几条轨迹按 `trace_id` 步级下钻，逐步看
  模型输入输出与工具调用；② 给每条轨迹算「同工具同参数连续调用计数」，大于等于 3 基本就是打转，这是最便宜的死循环指纹；③ 同时间段问题轨迹按「出错步骤类型加错误签名」聚类，先打最大那一簇。
- **分诊深挖**：工具持续返回相同错误、模型原样重试 → 看工具 span
  的 `status_code` 与回包文案是否给了可行动信息；上下文被截断、模型忘了已试过 → 对比截断点前后模型可见的工具历史；目标不可达但没写退出条件 → 看终态步是否仍朝同一方向硬磨。
- **复现**：剥掉无关步骤，构造三到五步的最小复现轨迹（例如让工具
  稳定返回同一错误），观察模型是否原样重试。
- **方案**：止血=同工具同参数连续 N 次强制打断并注入系统提示让
  换路径，不收敛则降级重规划或失败退出；根治=`max_steps` 与单轨迹 token 预算硬上限、去重式记忆、回包文案改写成可行动的。
- **追问压迫**：「直接把 `max_steps` 调小不就行了？」——步数上限
  是挡烧钱不是治病，打断后没把「已重复 N 次、换参数」喂回模型，只是把 40 步的失败变成 N 步的失败，任务完成率不会回来。
- **评分点**：知道排查单位是轨迹不是请求，会同工具同参数检测
  这个最便宜的打转指纹。

### A 2：第三方工具超时致任务失败率飙升

- **现象**：某第三方接口抖动，工具 span 超时比例抬升、该工具 P99
  恶化，大量轨迹卡在同一步，任务成功率腰斩。
- **第一三板斧**：① 工具 span 按工具名 × 错误类型做分布，确认
  失败集中在单个工具还是全面开花；② 看超时、限流、解析失败、参数非法各占多少；③ 查该工具近期上游变更与配额用量。
- **分诊深挖**：单工具超时加限流 → 对方服务问题（看 `status_code`
  的 429 与超时签名）；解析失败集中在同一字段 → 上游 schema 漂移（改了字段没通知）；失败与模型灰度版本相关 → 模型侧参数生成错误；401/403 签名 → 认证过期或配额耗尽。
- **复现**：隔离环境用同一入参直接调该工具重放，绕过 Agent 层
  确认是对方坏还是自己坏。
- **方案**：止血=超时预算加指数退避重试（只对幂等调用开放）、
  写操作带幂等键且重试前先查状态；根治=工具降级链（主切备、备无就明确告知「这一步做不到」绝不假造）、工具健康度看板与上游契约测试进 CI。
- **追问压迫**：「超时重试三次不就完了？」——非幂等写重试会有
  重复副作用，必须带幂等键；且重试回包进上下文会推高后续步成本，死循环病往往就是这么起的。
- **评分点**：处置三件套（超时预算/幂等键/降级链）背得全，且
  知道降级终点是诚实告知而不是编造结果。

### A 3：Agent 成本一夜翻倍

- **现象**：token 账单环比翻倍但请求量只涨一成；轨迹级
  `prompt_tokens` 的 P99 涨约两倍、均值没怎么动——涨价集中在少数长尾轨迹，是价涨不是量涨。
- **第一三板斧**：① 抽最贵轨迹按 step 画 `prompt_tokens` 曲线：
  健康轨迹是缓坡、问题轨迹是台阶，跳涨那一格塞进来的东西就是病灶；② 量一下跳涨格的工具回包体积；③ 看前缀缓存命中率是否同步暴跌。
- **分诊深挖**：回包台阶 → 上游给回包加了整页 HTML 或带完整
  日志的调试字段且没截断；缓存掉 → 有人把时间戳插进 system prompt 中间，前缀每轮都在变；检索一次塞太多 chunk → 召回精度没换来预算先爆；步数膨胀 → 与 A 1 的死循环互为因果。
- **复现**：灰度环境重放同一条轨迹，先把嫌疑回包截断再跑一遍，
  对比 step token 曲线形状是否变回缓坡。
- **方案**：止血=工具回包统一截断、调试字段进黑名单不进上下文、
  动态字段移出前缀；根治=回包字节上限进发布 checklist、前缀稳定化写进 prompt 模板规范、缓存命中率与步均 token 进监控告警。
- **追问压迫**：「缓存命中率掉一个点有多大影响？」——按系统
  前缀 token 数乘以调用量折算全价重算的额外成本量级；前缀缓存失效是沉默病，账单不涨报警不响，成本只是慢慢胖起来。
- **评分点**：会把成本病分成量涨与价涨，会用 step token 曲线
  的「台阶」一格锁定病灶。

### A 4：升级模型后 JSON 输出错乱

- **现象**：灰度新模型后工具调用解析失败率抬升、
  `finish_reason=length` 样本增多、自愈重试轮数变长。
- **第一三板斧**：① 拉解析失败样本原文做指纹两问：是不是升级
  后才出现、是不是集中在某一类输入上——两个答案直接把根因树砍半；② 看失败形态是参数塞进字符串、多余散文前后缀，还是长输入截断出的不完整 JSON；③ 核对宿主侧工具描述拼接是否同期改动，排除发了模型没见过的工具描述。
- **分诊深挖**：数字进引号加解释性散文 → 新模型输出习惯微漂移；
  `finish_reason=length` 集中在长输入 → 截断病；嵌套结构被拍平 → 参数类型病；未灰度流量也有 → 宿主拼接 bug，别赖模型。
- **复现**：失败样本输入固定，喂给新旧两版模型对拍，比较解析
  失败率差是否稳定复现。
- **方案**：止血=带错误信息重试一轮（多数能自愈）、正则提取与
  常见错误修复兜底、schema 硬校验不过不执行并把错误原文喂回；根治=大面积漂移上约束解码（`xgrammar`/GBNF 类）让非法 JSON 在生成端不可能出现，格式回归集进模型升级门禁。
- **追问压迫**：「约束解码会不会伤模型能力？」——它缩的是输出
  空间不是推理过程，对窄 schema 的工具调用利大于弊；但它只保证格式不保证语义，参数语义错误仍要靠校验喂回那一层兜。
- **评分点**：指纹两问先砍根因树，三件套与约束解码的分工边界
  讲得清楚。

### A 5：长会话「第二十轮丢信息」

- **现象**：长会话后半段答非所问，用户投诉「明明是你之前说
  过的约束，它又违反了」，前半段完全正常。
- **第一三板斧**：① trace 里找到最近一次压缩或截断发生的
  步骤；② 对比压缩点前后模型可见内容，点名早期系统指令与用户硬性约束还在不在；③ 把「丢的那条信息」和「它在压缩前的位置」对起来，对上就定位完了。
- **分诊深挖**：压缩点在、约束丢了 → 摘要模型没把它当重点；
  约束在压缩点之外 → 被整体截掉；约束还在但被淹没 → 关键工件常年内联上下文，挤占了指令的注意力生存空间。
- **复现**：构造最小用例——前段给一条硬约束、触发一轮压缩
  后提问约束相关问题，压缩开关两版对照输出。
- **方案**：止血=关键约束 pin 住不参与压缩并每轮复述、大工件
  外置成文件引用按需重读；根治=压缩策略上线前跑「压缩后关键信息保留率」评测，上下文水位告警主动触发整理而非等溢出。
- **追问压迫**：「把所有约束都 pin 住不压行不行？」——pin 位
  本身吃预算，pin 太多等于没压缩；该 pin 的是少量硬性约束（合规红线、输出格式、否定项），业务上下文走外置重读路线。
- **评分点**：定位动作固定为「压缩点前后对比」，能区分摘要
  丢、截断丢与注意力稀释三种病。

### A 6：模型升级后工具调用成功率 97% → 88%

- **现象**：新模型灰度 5% 流量两小时后，工具调用成功率从九成
  七掉到八成八，解析失败告警触发，未灰度流量一切正常。
- **第一三板斧**：① 对照组确认纯版本问题——未灰度流量无异常，
  排除第三方与宿主改动；② 失败样本做指纹分析：是否集中在长输入任务，形态是否「数字参数包进字符串、调用前后多解释性散文」的典型新模型微漂移；③ 成功率按任务类型拆分，分全面掉还是结构性地掉在某些工具上。
- **分诊深挖**：集中在长输入 → 输入变长触发格式退化或截断；
  格式微漂移 → 新模型输出习惯变了（与 A 4 同族病灶）；特定工具掉得凶 → 这些工具的 schema 对新模型敏感度不同，描述写法是放大器。
- **复现**：灰度双跑对拍——同任务旧模型与新模型各跑一遍比较
  成功率差，失败样本当场沉淀成格式回归集。
- **方案**：止血=解析层类型纠错（字符串数字自动还原）、schema
  校验不过不执行加错误喂回自愈、重试上限两轮，救不回的长尾上约束解码拉回九成七；根治=回归集作为后续所有模型升级门禁，灰度观察期拉长到覆盖一个完整业务高峰。
- **追问压迫**：「为什么不直接回滚了事？」——先看新模型能力
  收益值不值得加兼容层：兜底能把成功率拉回基线就共存，拉不回才回滚；回滚是保底手段，不是第一反应。
- **评分点**：灰度双跑对拍的工程惯性，加「把事故样本转成
  门禁资产」的闭环意识。

### A 7：多租户记忆串话

- **现象**：某租户 Agent 说出了别的租户才有的偏好信息；另有
  用户反馈 Agent 坚持一条已被本人推翻的旧结论。
- **第一三板斧**：① trace 里看该步检索召回的记忆条目原文与
  来源命名空间——出现不属于当前租户的内容就是串话实锤；② 查隔离过滤条件在召回、重排、拼上下文各层是否全程生效；③ 查写入端有无校验，幻觉是否被当事实写进了记忆库。
- **分诊深挖**：命名空间隔离有洞 → 召回跨了租户边界；同租户
  内旧记忆压过新指令 → 冲突记忆按相似度排前面、缺少时效权重；写入端失控 → 模型自述的偏好未经用户确认直接入库，越滚越脏。
- **复现**：测试租户写入标记记忆，从另一租户构造高相似度
  查询，看是否被召回穿透。
- **方案**：止血=涉事命名空间的记忆整体失效或回滚（宁可重
  不可慢），再修检索过滤条件；根治=写入校验（事实性与用户确认过才入库）、记忆加过期遗忘策略、来源标记支持召回追溯、命名空间隔离进发布 checklist。
- **追问压迫**：「串话为什么比普通质量 bug 严重？」——它
  同时是质量事故与安全事件，跨租户泄露一次信任就归零，所以止血可以重到整域失效，不能等根因查清再动手。
- **评分点**：指纹明确（召回条目不属于当前租户），处置知道
  先大范围止血再修边界这类安全优先的次序感。

### A 8：RAG 召回质量突然变差

- **现象**：知识库问答命中率突然下滑，用户抱怨「以前能查到
  的答案现在查不到」，模型与 prompt 同期都没动。
- **第一三板斧**：① trace 里看问题请求召回条目的原文与打分，
  先分清是召回环节丢还是生成环节答非所问；② 对齐时间拐点查近期事件：索引重建或批量灌库、嵌入模型版本切换、权限过滤规则改动；③ 用已知答案的历史问题做探针重放，看目标条目还在不在召回集合里。
- **分诊深挖**：条目在库但召不出 → 嵌入模型版本切换让新旧
  向量不可比；条目被稀释 → 新灌库文档切分变了、噪声 chunk 污染召回；条目召回到了但答案说没有 → 权限过滤或重排把正确条目掐死在半路。
- **复现**：固定一批「问题-答案文档」探针对，在索引重建前后
  各跑一次召回，对比召回集合差集。
- **方案**：止血=回滚拐点那次变更（索引版本或过滤规则）；
  根治=嵌入模型版本与索引版本绑定管理、切版本必须全量重建并跑召回回归、灌库 pipeline 加切分质量抽检、探针集每日监控报警。
- **追问压迫**：「嵌入模型换个版本为什么就得全量重建？」
  ——不同版本向量空间不可比，混在同一索引等于拿两把不同的尺量距离；稳的做法是双索引并行，新库探针达标再切流。
- **评分点**：把「质量差」拆到召回、重排、过滤、生成四个
  环节逐一定罪，探针重放是标准动作。

### A 9：MCP 接入 50+ 工具后上下文爆炸、选错工具变多

- **现象**：通过 MCP 接入 50 多个工具后，每步上下文里工具
  schema 吃掉可观 token，步均成本抬升；模型选错工具、同名参数张冠李戴的比例同步上升。
- **第一三板斧**：① trace 按 step 拆 `prompt_tokens` 构成，
  先算出工具 schema 占了多少这笔账；② 拉工具选择错误样本，看错误集中在名字相似的还是参数结构相似的工具之间；③ 查是否所有请求都挂了全量 50+ 工具清单。
- **分诊深挖**：schema 全量常驻 → 上下文账面上的纯浪费；
  工具名或描述语义重叠 → 清单越长越像，模型区分度自然下降；同域工具参数相似 → 描述里没写清边界与反例，正确工具的辨识度不足。
- **复现**：同批任务在「全量清单」与「按任务预筛 10 个」
  两种配置下对拍，比选择正确率与步均 token。
- **方案**：止血=请求级工具预筛，按任务路由只挂相关子集；
  根治=工具分层（常用常驻、长尾检索式按需加载）、工具描述治理（边界、反例、互斥关系写清）、schema token 配额进成本看板。
- **追问压迫**：「检索式选工具引入了新的召回问题怎么办？」
  ——本质是把 RAG 搬到了工具选择层：建工具召回探针集，监控「该出现的工具没进清单」这一失败类型，召回不达标就退回分层常驻加白名单。
- **评分点**：会把工具 schema 计入上下文账，且能看出工具
  选择本质是检索问题、可复用 RAG 方法论治理。

### A 10：长任务跑 3 小时后目标漂移跑偏

- **现象**：几十步、跑了 3 小时的长任务，交付物与原始需求
  对不上；逐步看每步都像「合理推进」，终点却偏了。
- **第一三板斧**：① trace 做步骤与目标的一致性抽检——隔
  几步抽一条问「这一步在服务原始目标吗」；② 找漂移起点：哪个中间反馈第一次带偏了方向；③ 看全程有没有任何一步被要求对照目标。
- **分诊深挖**：原始目标被中间结果挤出注意力 → 长上下文
  稀释病（与 A 5 同族）；中间反馈悄悄改写隐式目标 → 模型迁就工具能做的事，把「能做的」当「该做的」；全程无 checkpoint → 微小偏差复利滚大，没有任何纠偏机会。
- **复现**：把轨迹在疑似拐点截断，从该点以原始目标重放，
  回到正轨即拐点定位成功。
- **方案**：止血=目标卡机制嵌入任务模板，每 N 步 echo 一次
  当前目标与已完成进度，偏了当场可见；根治=长任务拆成有验收标准的阶段、关键 checkpoint 需人或高层策略审批后继续、阶段验收协议写进任务模板。
- **追问压迫**：「每 N 步 echo 目标浪费 token 怎么办？」
  ——复述成本相对一条 3 小时跑偏轨迹的总成本是噪声级；且 echo 记录可当审计日志与断点续跑的上下文锚点复用。
- **评分点**：知道目标漂移是复利病不是突变病，对策是阶段
  性对照目标而非跑完再验收。
