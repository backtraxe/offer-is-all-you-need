# 消费级硬件推理实战专题：FastH3 上 RTX 的全案拆解

> 面向已经读过 [量化与压缩](./inference/量化与压缩.md)（FP8/NVFP4/INT8
> 口径）与 [蒸馏与剪枝专题](./蒸馏与剪枝专题.md)（KD 谱系、剪枝三代）
> 的读者。本篇是一篇**生产级案例课**：把 137.7 GiB 的视频生成模型
> （FastH3，八步蒸馏、视频+音频同出）塞进单张 RTX 5090/4090/Mac 的
> 完整工程过程，拆成「砍层、量化、蒸馏、校准、剪枝、显存工程」六把刀，
> 每把刀都标注对应的面试高频问法。
>
> **口径声明**：全部数字来自 Hao AI Lab 官方博客（2026-10，FastVideo
> 组织）及其中文转述，未独立复测；实验性内容（Trim、模拟显存档位）
> 原文已声明，引用时同标。

## 一、案例全景：一张表看懂「为什么这事难」

目标负载：八步生成 5 秒视频+同步音频。模型由三张网组成，BF16 权重共
**137.7 GiB**——单张 32 GB 的 RTX 5090 连 DiT 一张网都装不下。

| 组件 | 作用 | BF16 | 瘦身手段 | 瘦身后 |
|---|---|---|---|---|
| Qwen3-VL 文本编码器（64 层） | 读 prompt | 62.1 GiB | 砍最后 14 层 + LM head，其余 NVFP4 | 15.3 GiB |
| 扩散 Transformer（50 block） | 同时给视频/音频 latent 去噪 | 65.3 GiB | attention/MLP/稀疏 gate 全层 NVFP4（无 FP4 的卡用 FP8） | 11.1 GiB（Trim，NVFP4） |
| 双 VAE（视频+音频各一） | latent 解码成帧与声音 | 10.3 GiB | 换蒸馏版 26 block 轻量视频 VAE，INT8 | 6.5 GiB（INT8 部分 2.3 GiB） |

成绩单（5 秒 480p 片段，热机端到端、prompt 到 MP4 落盘，官方口径）：

- RTX 5090：**13.4 秒**（DiT 11.1 GiB 常驻显存，请求间只流式搬文本编码器）；
- RTX 4090：**43.9 秒**（无 FP4 Tensor Core，走 FP8 + 部分流式搬运）；
- DGX Spark（128 GB 统一内存）：**42.6 秒**，全常驻零搬运，两台可用
  序列并行分一个请求；
- Apple Silicon：MLX INT6 权重 + NVFP4 文本编码器 + 轻量 VAE，能跑
  但去噪占 91%（attention 还在 reference 路径，非调优 Metal kernel）；
- Trim 剪枝版：**最低 8 GB 显存可跑**，比 base H3 小 4.2 倍。

## 二、第一把刀：砍层——「模型只读到第 N 层」就吃定后半

文本编码器 62.1 GiB 里，最大的浪费是：**H3 只读 Qwen3-VL 第 50 层的
hidden state，而且从不生成文本**。于是最后 14 层和语言模型头全部删掉，
H3 实际用到的特征一位不变；剩余线性层存 NVFP4。

**面试映射**：「怎么压一个大模型？」的第一答不是剪枝也不是量化，而是
**先搞清楚消费方到底读了哪几层**——只读中间层表征的编码器，后半直接是
死重。同理可迁移：只拿 CLS/平均池化做检索的 encoder，也可以砍 LM head。

## 三、第二把刀：NVFP4 全层化——只量化 MLP 是失败的中间态

第一版 NVFP4 只量化了 MLP（数据中心 GPU 的惯用设置），结果在 5090 上
DiT 还有 20 GB：单是 BF16 attention 投影就占 9.7 GB，文本编码器挤不下，
**每次请求把 DiT 从主机内存搬进搬出 → 480p 要 26.4 秒，768p 直接跑不了**。
把 attention 和稀疏 gate 也压进 NVFP4 后，DiT 稳态 11.1 GiB 常驻 GPU，
文本编码器逐层流式进卡——同一片段 13.4 秒，768p 解锁。

**面试映射**：「量化覆盖率」是显存公式里的隐藏变量——只量化 MLP 意味着
attention 的 KV/QKV 投影仍是 16 bit 大头。回答显存估算题时先报「我量化
了哪些张量」，再报 bit 数。

## 四、第三把刀：NVFP4 校准——单位 scale 在真实模型上是会溢出的

NVFP4 每 16 个值一组存 4 bit 浮点，组内共享一个 FP8(E4M3) scale，再加
每层一个 per-tensor scale 定整体范围。权重 scale 从权重本身算没问题，
**activation 的 scale 必须在数据到来前固定**——最省事的单位 scale（=1）
覆盖上限约 2688。

FastH3 的实测把这件事钉成了教科书案例：校准集（1000 条 prompt × 全部
8 步采样）跑下来，**42 个 block 里 40 个的 MLP 输出投影输入超过 2688，
block 37 的峰值是 368640——上限的 137 倍**。单位 scale 下这些激活每次
前向都被裁剪。解法是逐层静态校准：每个量化线性层记录最大输入，存一份
静态 activation scale 进 checkpoint；Trim 一共标了 **294 个校准层**
（attention 投影 + MLP + 稀疏 attention gate），并把上一版「只标 MLP」
的配方扩展到全部量化层。

**面试映射**：「FP8/NVFP4 怎么做 scale？」标准三段——per-tensor 静态
校准给 activation、per-channel/per-group 给权重、校准集要覆盖真实采样
路径（本例连 8 个扩散步都跑全）。追问「校准集多大」就用这个数：**1000
条 prompt，覆盖完整采样步数序列**。

## 五、第四把刀：FP8 的单位 scale 技巧（4090 实战）

RTX 4090 没有 FP4 Tensor Core，只能 FP8：8 bit 权重（每输出通道一个
scale）+ 8 bit activation（每 token 一个 scale）。尴尬在于：PyTorch 这种
双 scale 的 FP8 矩阵乘在 4090 上只有 **约 70 TFLOPS，比 BF16 的约 160
还慢**；而 per-tensor scale 的 FP8 kernel 能到 **220–305 TFLOPS**。

工程解法：**用单位 scale 调用快 kernel，再把两个 scale 向量 fuse 到输出
上一次性应用**——数值结果与 per-token/per-channel 严格一致，代价只比
per-tensor 贵 5%–10%。另外两处：稀疏 attention 把 Q/K 量化到 INT8、V 留
BF16，fine attention kernel 快 1.6 倍、相对误差约 0.6%；VAE 的 Q/K/V
投影共享一个量化输入，解码结果与未优化路径逐 bit 一致。

**面试映射**：「给定硬件 kernel 支持矩阵，怎么设计量化调用路径？」——
先查 kernel 的 scale 粒度支持，再谈精度。这道题在字节 infra 题单里是
连问题型，和 [量化与压缩](./inference/量化与压缩.md) 的 INT8 scale 手算
互为表里。

## 六、第五把刀：剪枝（Trim）——每个 block 的重要性是「测」出来的

Trim 走的是结构化剪枝路线，但选块方法值得单独背：

- **直接跳过测**：从 base H3 出发，一次跳过一个 block，记录视频/音频
  预测变化量；4 个例子（运动、说话、音乐、声音事件）× 3 个噪声水平，
  共 **600 次测量**；每个 block 按「任一条件下造成的最大变化」排名，
  视频或音频任一重要的都保留。
- **结果**：首尾的 block 变化最大（最不能删），被删的 8 个全落在网络
  前半——50 block 删 8 个，比按等间隔删明显靠谱。
- **失败对照实验（同样值钱）**：按 activation 选块 + teacher 恢复 + DMD
  压缩采样步数的路径，运动连贯性、细节、prompt 服从都偏弱；**量化感知
  蒸馏（QAD）在并排对比里没赢过训练后量化（PTQ）**——先 PTQ 后蒸馏
  的默认顺序又多一个工业佐证。

配套的第二个压缩点是 **timestep conditioning 低秩化**：H3 用 AdaLN 把
2688 维时间 embedding 投到每个 block 的 6 个调制向量，50 个 block 的
投影权重 BF16 占 24 GiB；但输入只是单个标量 timestep 的光滑函数，用不
满 2688 维。Trim 换成「共享的 2688→16 基 + 每 block 一个小投影」
（rank-16 分解），权重改存 FP16，重建误差只放大 1.7 倍——**24 GiB 的
投影层基本被抹掉了**。

**面试映射**：「剪枝怎么选删谁？」——等间隔 < 启发式（activation 幅度）
< **直接任务影响测量（skip-one 重放）**；「QAT/QAD 什么时候上？」——
先 PTQ，蒸馏只在 PTQ 精度不达标时才值得追加，本例 QAD 没赢。

## 七、显存工程的两个「刁钻坑」

1. **pinned 内存按 2 的幂取整**：PyTorch 的 pinned 分配器把每块向上
   取整，2.87 GiB 的 FP4 权重实际占 5.06 GiB 主机内存——在 60 GB 的
   云容器里直接被 OOM kill。解法：每个模块用 `cudaHostRegister` 手动
   注册精确尺寸的 buffer，只占 2.90 GiB。**追问链**：为什么主机内存
   也会在 32 GB 卡上成为瓶颈——因为分层搬运时代，主机侧才是 staging
   仓库。
2. **常驻 vs 流式的分水岭**：5090 的 26.4 秒到 13.4 秒，全部差别只在
   「DiT 能不能请求间常驻显存」。判断式一句话：**单请求显存峰值 =
   常驻权重 + 流式层 × 单层峰值 × 2（双缓冲）**——能常驻就常驻，显存
   带宽比 PCIe 高一个数量级。

## 八、蒸馏训练侧：八步模型怎么训出来的

Trim 的 42 block 新模型**直接按八步 DMD2 训练**（目标函数沿用 V2），
不是先剪再恢复：base H3 同时初始化 frozen teacher 与可训练 critic，
attention 保持 80% 稀疏；8 个采样 timestep 固定为
999/874/749/624/500/375/250/125。

时间账（5 秒 480p Trim，官方口径）：RTX PRO 6000 全常驻，12.0 秒里
**去噪占掉 78% 的时间**；5090 去噪同为 9.1 秒、总 13.4 秒（多出来的是
文本编码器与解码器搬运）；4090 去噪占 43.9 秒里的 33.1 秒；DGX Spark 上
**VAE 解码吃掉三分之一**（42.6 秒）——不同硬件上瓶颈阶段完全不同，
优化顺序必须按自己的时间拆账排。这正是
[推理 Profile 实战专题](./inference/推理profile实战专题.md) 的区域思维
在生成式模型上的复用。

## 九、▶ 面试题与追问

**Q1【高】把一个 140 GB 的模型塞进 32 GB 消费卡，你的总思路？**
先砍死重（未消费层、LM head）→ 再全层量化到硬件原生低 bit（NVFP4/
FP8）→ 解码器换蒸馏轻量版 → 校准保精度（静态 activation scale）→
最后考虑剪枝（任务影响测量选块）。每一步都报显存账：137.7 → DiT
11.1 + 文本 15.3 + VAE 6.5。

**Q2【高】NVFP4 的量化的 scale 怎么设计？什么时候单位 scale 会崩？**
16 值一组共享 FP8 scale + 每层 one-tensor scale；上手先用校准集跑完整
推理路径取每层最大 activation。单位 scale 在真实生成模型上崩给你看：
40/42 block 超上限，峰值 137 倍——**校准不是可选优化，是 NVFP4 的
必选项**。

**Q3【中高】4090 上没有 FP4 kernel，怎么权衡量化方案？**
查 kernel 支持矩阵：双 scale FP8 matmul 比 BF16 慢（70 vs 160
TFLOPS），per-tensor FP8 快（220–305）；于是单位 scale 调快 kernel +
fuse scale 到输出，精度等价、成本 +5~10%。结论一句话：**量化方案是
「kernel 菜单 × 精度预算」的匹配问题，不是 bit 数问题**。

**Q4【中高】剪枝的三种选块粒度，你选哪个？**
等间隔删除（没用模型行为信息）< activation 幅度启发式（间接信号）
< skip-one 直接任务影响测量（600 次重放、按最大变化排名）。本例的
反直觉发现：首尾 block 最重要，删掉的 8 个全在前半——**「中间层
冗余」不是普遍成立，按任务实测**。

**Q5【中】QAT/QAD 和 PTQ 怎么选？**
先 PTQ（便宜、无训练管道依赖）；PTQ 精度不达标再上蒸馏/QAT。FastH3
的并排实验里 QAD 没赢 PTQ——增加训练成本的方案必须自带证据。
低秩/秩分解类「结构压缩」（timestep 投影 rank-16）与量化正交，可叠加。

**Q6【中】为什么 pinned 内存也会让 32 GB 卡的服务崩掉？**
分层搬运架构里主机内存是 staging 仓库；PyTorch pinned 分配器按 2 的
幂取整，碎片和虚高利用率在小容器里直接 OOM（2.87 → 5.06 GiB 案例）。
生产解法：精确尺寸注册 pinned buffer + 复用，别让分配器替你取整。

**Q7【中】DGX Spark / 统一内存架构下还有搬运问题吗？**
128 GB 统一内存全常驻、零搬运，但瓶颈转移：VAE 解码占三分之一时长。
**瓶颈从不消失，只会搬家**——每换一种硬件就重新拆一次时间账。
