# 负载均衡专题：从网关到专家的六层战场

> 负载均衡（Load Balancing, LB）在 LLM 系统里不是一道题，而是**同一个
> 问题在六个层次的六次变形**：网关选实例、引擎排批次、模型分专家、
> 并行切算力、会话找宿主、插件分流量。每一层的答案各不相同，但底层
> 是同一组权衡：**吞吐量 vs 局部性（cache 亲和）vs 公平性 vs 抖动**。
> 本篇把六层串成一张地图，每层给出「均衡对象、主流策略、面试追问点」，
> 最后给一条贯穿全部层次的主线话术。
> 阅读顺序：先看总表建立地图，再按面试方向深入对应层。

## 〇、总表：六层一览

| 层 | 均衡的对象 | 核心矛盾 | 主流策略 | 深挖文档 |
|---|---|---|---|---|
| L1 大模型网关 | 请求 → 上游 provider/实例 | 成本 vs 延迟 vs 可用率 | 权重切流 / 健康路由 / 熔断降级 | [设计大模型统一接入网关](../system-design/设计大模型统一接入网关.md) |
| L2 推理引擎调度 | 请求 → batch 槽位 | prefill 与 decode 抢资源 | continuous batching / chunked prefill / PD 分离 | [vllm与推理加速核心](./inference/vllm与推理加速核心.md) |
| L3 路由亲和 | 请求 → 哪个引擎副本 | cache 命中率 vs 负载均衡 | prefix-aware / session-aware routing | [vllm与sglang深度对比](./inference/vllm与sglang深度对比.md) |
| L4 MoE 专家 | token → 专家 | 专家利用率 vs 专家容量 | aux loss / aux-loss-free bias / EPLB 冗余 | [moe架构](./llm基础/moe架构.md) |
| L5 并行维度 | 层/参数 → 卡 | 通信量 vs 利用率 vs 显存 | TP 切计算 / PP 切层 / EP 切专家 / DP 切数据 | [三维并行](./distributed-training/三维并行.md) |
| L6 Agent 运行时 | 会话/任务 → 实例 | 会话粘性 vs 弹性调度 | 会话亲和 / restore 接管 / 任务队列 | [harness工程实战](./agent/harness工程实战.md) |

**一条主线记全局**：越靠近用户（L1/L6），均衡以「会话/租户」为粒度，
关心可用率与成本；越靠近硬件（L2/L4/L5），均衡以「token/FLOP/字节」
为粒度，关心吞吐与通信。**中间 L3 是桥梁**——它决定了「上层看到的
负载」有多少能转化成「下层 cache 的命中」。

## 一、L1 大模型网关：请求选上游

> ▶ 面试题：LLM 网关的路由策略？和传统 API 网关有什么不同？——**中高**

路由表本质是 **(请求特征) → (候选模型+权重) → (策略)** 的映射，
策略三条线（[网关设计文](../system-design/设计大模型统一接入网关.md)）：

- **能力路由**：显式 model 指定 > 自动路由（按任务类型/内容分类选模型）；
- **成本路由**：按 input/output token 单价排序，满足质量阈值选最便宜的；
- **延迟/负载路由**：看实时 TTFT/TPOT 与排队长度，把流量倾向当前健康的
  实例；叠加熔断器（错误率超阈值摘除、半开探测恢复）。

与传统 API 网关的三点不同：

1. **上游异构不标准**：不同 provider 的限流口径（QPM vs TPM）、错误码、
   流式行为都不同，健康检查必须基于**真实探针流量**而非 ping；
2. **失败代价不对称**：一个请求卡住 30 秒的代价远高于传统 API
   （用户盯着流式输出），超时要按 TTFT/TPOT 分段而非整体；
3. **有状态优化空间大**：传统服务无状态随便轮询，LLM 的 prefix cache
   让「去哪台」影响成本——这就引出 L3。

**工程诚实点**：生产 80% 流量是「业务显式指定模型 + 权重切流」，
主路做稳再谈智能路由。权重切流（灰度 5%→50%→100%）是发布新模型/
新配置的标配动作，比任何动态策略都高频。

## 二、L2 推理引擎调度：batch 槽位的分配

> ▶ 面试题：continuous batching 怎么实现？PD 分离解决什么？——**高**

引擎内的 LB 是「token 预算在多请求间的分配」，三次演进：

1. **ORCA/continuous batching**：每个 iteration 重排 batch，
   完成的走、新来的填——GPU 不再为单个请求的空转子买单
   （细节在 [vllm与推理加速核心](./inference/vllm与推理加速核心.md)）；
2. **chunked prefill**：长 prefill 切片与 decode 混入同一 batch，
   防止一个 8K 长 prompt 的 prefill 独占一步、几百个 decode 被卡出
   TPOT 毛刺——**调的不是请求数而是 token 配比**；
3. **PD 分离**：prefill（compute-bound）与 decode（memory-bound）
   放不同节点池，各自扩缩容、各自被调度——把「两种互相干扰的负载
   剖面」拆成「两个各自干净的容量池」，KV 经 NIXL/mooncake 传输。

配套的「防不均衡」机制：

- **抢占/回退**：vLLM preempt（KV 重算或换出）、SGLang retract
  （踢回队首 + HRRN aging 防饿死 + PD 端 retraction 先备份 KV）；
- **优先级**：多租户混部时高优先级请求可打断低优先级
  （SGLang `enable_priority_preemption`）。

## 三、L3 路由亲和：cache 命中与均衡的权衡

> ▶ 面试题：prefix cache 面前怎么路由？会话亲和 vs 负载均衡怎么选？——**中高，2026 升温**

关键事实：**路由到哪台，决定前缀 cache 命中不命中，进而决定
TTFT 和成本**。三种策略谱系：

| 策略 | 原理 | 均衡性 | cache 命中 |
|---|---|---|---|
| 轮询/随机 | 无视内容 | 最好 | 最差（命中率 ≈ 1/N，N 副本数） |
| 会话亲和（sticky） | 会话 ID 哈希到固定副本 | 差（热门会话压垮单点） | 好（同会话前缀全命中） |
| **prefix-aware 路由**（SGLang Router） | 按请求前缀的 Radix 匹配度路由到「最可能已缓存」的副本，负载超阈值时退回均衡 | 较好 | 最好 |

prefix-aware 的核心工程点：

- **近似而非精确**：路由层不真查各副本 cache，用轻量近似（前缀树的
  各副本计数）估计命中概率——查准的成本可能高于省下的 prefill；
- **水位退让**：目标副本负载高过阈值就放弃亲和退回均衡——
  **命中是优化，均衡是底线**，顺序不能反；
- **会话亲和的简单版**：对多轮对话场景，会话 ID 一致性哈希是
  80%/20% 答案（lru-session 路由），prefix-aware 是进阶版。

## 四、L4 MoE 专家：训练/推理两套均衡

> ▶ 面试题：MoE 负载均衡怎么解决？aux loss 有什么问题？——**高频深挖**

MoE 的 LB 是「token → top-k 专家的路由决策」，目标是专家利用率均匀
且无 token 被丢弃（capacity 溢出）。三条技术线（
[moe架构 第三节](./llm基础/moe架构.md)）：

1. **辅助 loss 派**（Switch/GShard）：均衡 loss = f(mean router prob,
   mean 实际分配)，惩罚分配集中；**问题：与主 loss 目标冲突**，
   均衡做得好主任务可能受损，权重难调，且 signalling 粒度粗；
2. **aux-loss-free bias 派**（DeepSeek-V3）：给每个专家一个不进梯度的
   偏置 b_i，定期按「超收降、欠收升」规则直接调——路由仍看打分，
   但打分线被偏置平移；**优点：不动 loss 结构、粒度细到 step**；
3. **推理侧 EPLB**（DeepSeek 开源）：训练均匀的模型在线仍会因流量
   分布产生热点专家，EPLB 做**专家冗余布置**——预估各专家负载，
   热点专家复制到多卡，再按层级/节点做放置优化，均衡 EP 组间
   all-to-all 通信。

追问准备金句：「aux loss 是**用优化器求均衡**（梯度派），
bias 是**用控制回路求均衡**（负反馈派），EPLB 是**用冗余资源
换均衡**（运筹派）——同一问题三种世界观。」

## 五、L5 并行维度：切哪一刀通信最少

> ▶ 面试题：TP/PP/DP/EP 怎么选？各自解决什么均衡？——**高**

四种切法 = 四种 LB 方案，各自均衡的对象不同（
[三维并行](./distributed-training/三维并行.md)）：

| 切法 | 均衡什么 | 不均衡的代价 | 通信特征 |
|---|---|---|---|
| DP（数据并行） | 卡间样本数 | 慢卡拖慢 step（梯度同步等最慢） | 每步 allreduce 梯度 |
| TP（张量并行） | 单层计算切片 | 切片不均 → 卡间空转 | 每层前/反向都通信，**量最大** |
| PP（流水并行） | 层数/stage | stage 不均 → 气泡放大 | 仅 stage 边界点对点 |
| EP（专家并行） | 专家分布 | 热点专家所在卡 bottleneck | all-to-all，突发性最强 |

选择口诀：**机内有 NVLink 才敢放大 TP（通信密集）；跨机只放
DP/PP/EP（通信稀疏）；MoE 模型 EP 与 DP 常二选一或用 EDP 混合**。
气泡治理（interleaved 1F1B、虚拟 stage）本质也是 LB——
把「时间轴上的利用率」摊匀。

## 六、L6 Agent 运行时：会话与任务的派发

> ▶ 面试题：Agent 服务怎么做负载均衡？会话粘性怎么办？——**中，2026 升温**

Agent harness 的 LB 与无状态 API 不同在**会话有状态**（
[harness工程实战 第二节](./agent/harness工程实战.md)）：

- **会话内串行**是硬约束（上下文 append-only），LB 的粒度只能是
  「会话」而非「请求」；
- **亲和路由**：同会话请求路由到持有其 Activation 的实例
  （pi/dsh/codex 默认模式）；代价是热门会话压垮单点 + 实例宕机
  影响面大；
- **状态外置 → 任意实例接管**（dsh 路线）：会话全量事件溯源到
  日志，实例只是临时工，调度器可把会话「搬」到健康实例——
  **把 LB 的「粘性问题」转化为「恢复问题」**，这是更现代的答案；
- **任务级 LB**：goal/后台 job/cron 长任务走队列而非交互会话，
  worker 池按队列深度扩缩容——与在线流量隔离，互不抢资源；
- **子 agent 派发**：`maxDepth` / `maxParallelSubCalls` 是 LB 的
  并发闸门，防一个会话的 fan-out 把全系统配额打爆。

## 七、贯穿六层的主线（面试收尾段）

被问「负载均衡」时，先反问**我们在均衡什么**——这一个问题就把
答案钉到地图上了：

```text
均衡"请求"     → L1 网关 / L6 会话（关心可用率、成本、粘性）
均衡"token"    → L2 引擎调度（关心吞吐与 TPOT 平滑）
均衡"前缀缘分" → L3 路由亲和（关心 cache 命中率）
均衡"专家热度" → L4 MoE（关心分配熵与丢弃率）
均衡"FLOP/字节" → L5 并行切分（关心通信与气泡）
```

然后给出权衡三件套：**局部性（cache/亲和）与均衡性的顺序
（均衡是底线、亲和是优化）、观测先行（先量出热点在哪个层再治理）、
反馈循环优于一次性分配（aux-loss-free bias、EPLB、动态路由全是
负反馈回路，不是开环规划）**。

## 八、▶ 面试挂钩（快问快答版）

**Q：LLM 网关路由和传统 LB 的区别？**
「上游异构（限流口径/错误码不统一，健康检查要真实探针）；失败
成本不对称（TTFT 卡 30 秒用户就跑，超时按段）；前缀 cache 让
路由成本敏感——多一层 L3 亲和的权衡。」

**Q：为什么 prefix-aware routing 还要保留负载退让？**
「命中是优化、均衡是底线：最热的 system prompt 对应的副本会被
所有人的前缀选中，没有退让机制就是新单点。水位超限退回均衡，
保证了 LB 的下界不被亲和破坏。」

**Q：训练好的 MoE 上线为什么还要 EPLB？**
「训练时的均衡是按训练分布调的，线上流量分布不同（比如某领域
请求扎堆），热点专家单卡成为 all-to-all 瓶颈。EPLB 用专家冗余
+ 放置优化做推理侧的二次均衡——训练解决期望，推理解决实现值。」

**Q：TP 和 EP 的负载问题有什么共性？**
「都是『切片不均 = 同步等待放大』：TP 切片不均卡每层两次通信，
EP 专家不均卡每层一次 all-to-all。治理思路也同构：让切片均匀 +
让通信 overlap 计算（TP 的 sequence parallel、EP 的 DeepEP 分层）。
并行计算里的 LB 本质是**消同步点**。」

**Q：Agent 集群为什么不能像 Web 服务那样轮询调度？**
「会话上下文是有状态的：随便换实例意味着每轮都要重建/重传整个
历史，成本无法接受。答案两条：亲和路由（承认粘性），或事件溯源
+ restore（消化粘性）——后者的代价是每个实例都要能读全局日志，
写入端变成瓶颈，所以成熟做法是两类混合：短会话亲和、长会话外置。」
