## 〇、直觉一句话：K8s 原生调度的三个结构性不匹配

kube-scheduler 的世界观是「一个 Pod 一次决策、资源即 request」。这套世界观
碰上 GPU 分布式训练，有三个结构性不匹配：

1. **训练是集合体，调度是逐个的**。一个 32 节点的训练作业是 32×8=256 个
   rank 的整体，逐个调度会产生「部分启动」——先到的 rank 占着卡等后面的，
   等不到就死锁。K8s 原生没有 all-or-nothing 语义。
2. **它不知道通信贵**。机内 NVLink 与跨机网卡有 18 倍带宽差（900GB/s vs
   50GB/s），把 TP=8 的 8 个 rank 撒到 8 台机器上，等于亲手把训练打死。
   kube-scheduler 的资源模型里没有「带宽拓扑」这一维。
3. **它没有租户概念**。request/limit 是单机词表；谁该先用、配额怎么借还、
   低优任务怎么让路，原生一概不管。

于是社区演化出**两层栈**：上面一层管配额与准入（Kueue / Volcano / YuniKorn，
决定「这个作业现在能不能上、用哪片资源」），下面一层管单机和节点内放置
（kube-scheduler + scheduler-plugins，决定「这些 Pod 具体落在哪台哪个卡上」），
再往下是节点与容错层（gpu-operator / DCGM / NPD，管装机、监控、自愈）。
本篇的机制主线就按这三层讲。

## 一、GPU 怎么被 K8s 看见：device plugin 与 gpu-operator

### 1.1 机制链：从驱动到 allocatable

一张 GPU 要变成 Pod 能申请的资源，链条是这样的：

1. 节点装好 NVIDIA driver + container toolkit（容器里能看到卡）；
2. `k8s-device-plugin` 以 DaemonSet 形式跑起来，向 kubelet 注册
   **device plugin API**（v1beta1）；
3. 节点的 `allocatable` 字段里出现 `nvidia.com/gpu`，GFD（GPU Feature
   Discovery）给节点打上 `gpu.product` 之类的 label；
4. Pod 在 `limits` 里写 `nvidia.com/gpu: 2`，调度器据此放置。

生产上不裸装，统一用 **gpu-operator**（⭐2924，v26.7.1，2026-09-23，
注意是日历版本号）：一个 `ClusterPolicy` CR 把 driver（本体也容器化成
DaemonSet）、toolkit、device-plugin、DCGM-exporter、MIG-manager、NFD
一套全装好，升级和回滚走 operator 语义，不用再登裸机。

### 1.2 两个易考点

- **为什么 `nvidia.com/gpu` 只能按整数申请？** 这是 device plugin API 的
  语义决定的——插件上报和分配的都是「整数设备」，没有 0.5 张卡的概念。
  想要半卡，必须另开资源名（MIG 的 `nvidia.com/mig-3g.40gb`、HAMi 的
  `gpumem` 等），走切分方案，而不是在原资源名上做小数。
- **device plugin 只管「发现 + 分配」，health check 能力很弱**——官方
  README 自己承认。节点上卡坏了，allocatable 不会自己掉，要靠
  DCGM-exporter + Node Problem Detector 这条健康线补上（见第五节）。

## 二、Gang scheduling：all-or-nothing 的第一性约束

### 2.1 为什么 gang 不是优化项而是约束

AllReduce 是同步集合通信：一个 step 结束于**最慢的那个 rank**，任何一个
rank 缺席，整个作业不可用（轻则全员空转，重则 NCCL 超时死锁）。这就是
**gang scheduling 的第一性**：要么整组同时上，要么一个都别上。它不是
调度优化，是正确性前提。

### 2.2 失败模式与空转账

逐个调度的经典事故：32 节点的作业起了 31 个，第 32 个 pending——
等于 **31 台 8 卡机（248 卡）全额空转**，烧着电等一台不知道什么时候来的
机器；如果配额本身就不够，则 31 个 Pod 互相抱住资源不放，永久死锁。
这笔账面试官爱算：31/32 的资源拿着，产出是零，浪费率按「占用」算接近
百分之百。

### 2.3 三条实现路线与一个新变量

| 路线 | 形态 | 一句话定位 |
|---|---|---|
| scheduler-plugins **Coscheduling** | kube-scheduler 插件，`PodGroup.minMember` | 最轻量的 all-or-nothing，只管放置 |
| **Volcano** PodGroup/Job | 调度器+控制器一体（CNCF incubating，⭐6006，v1.15.3，2026-09-30） | 自带队列/抢占/binpack，国内大厂存量大 |
| **Kueue**（kubernetes-sigs，⭐3051，v0.20.1，2026-10-08） | 准入层组件，不做单机放置 | 只在 admission 层保证整组同时放行，2026 主流增量 |

2026 年的新变量是 **NVIDIA Grove**（ai-dynamo/grove，⭐274，v0.1.0-alpha.14，
2026-10-06，alpha）：把「层级化 gang + 拓扑」做成一组 CR（PodClique /
PodCliqueScalingGroup），主打多节点 PD 分离推理里「若干个 prefill +
若干个 decode 跨角色同时就位」这种需求。**训练调度 2026 的默认答案是 Kueue**——它是 kubernetes-sigs 官方项目，与 kube-scheduler 互补（管配额
和 admission，不管单机放置），Volcano 存量大但社区重心明显在向 Kueue 迁移。
另有 YuniKorn（⭐1033，v1.10.0，2026-10-06）走资源调度器替换路线，热度
明显低于前两条。

## 三、拓扑感知：通信域 = 调度域

### 3.1 拓扑的三个层级

- **机内**：GPU—NVLink—PCIe—NUMA。Koordinator 的 Device CR 会上报 GPU
  partition 与 NVLink 组，v1.6 起支持 Pod 申请「同一 PCIe/NUMA 下分配」。
- **rail（leaf）**：8 卡机每卡各接一张 400G NIC，同 rail 的卡跨机直连。
  rail-optimized 组网下，DP/EP 并行组要沿 rail 摆。
- **Block/spine**：云厂商把故障域暴露成 label，GKE 给的是
  gce-topology-block / subblock / host 三层。

核心数字锚再背一遍：**机内 NVLink4 900GB/s（H100）对单张 400G 网卡 50GB/s，差 18 倍**。所以「通信域 = 调度域」——TP/PP 的切分按卡数对齐
NVLink 域，调度就必须整域分配。

### 3.2 Kueue TAS（Topology-Aware Scheduling）

Kueue 从 v0.14 起把 TAS 做成 beta（当前 v0.20.1）。用法：Topology CR 定义
label 层级，ResourceFlavor 引用它，作业用 `podset-required-topology` /
`preferred-topology` annotation 表达「必须在同 rack / 同 Block」或「最好
在同 rack」。后续版本一路加码：v0.19 起 multi-layer slice（比如 64 个
Pod：32 一组约束在 Block 内、16 一组约束在 rack 内，分层并行各自摆），
v0.20 加 topology spreading（推理副本跨故障域打散，alpha）和
**hot swap**（坏节点原地替换，不改其余 topology assignment）——这是把
「容错-调度闭环」做进调度器本体的信号。

### 3.3 为什么 8 卡机要整机分配，以及碎片治理

8 卡 NVLink 整机分配的原因上面说了：机内碎片（A 作业拿 3 卡、B 作业拿
5 卡，剩 3+5 分在两机）对 TP=8 的通信模式是灾难。反过来，「永远整机」
会制造无法装入的碎片空位，治理手段是打分插件：binpack /
GPU MostAllocated 打分（Koordinator 的 NodeResourceFitPlus：GPU 尽量堆叠
到大卡数池，CPU 打散）。**保守排布保通信，激进出空位保单机装箱率**，
这组张力是拓扑调度的日常。

### 3.4 实证：字节 Arnold

拓扑感知不是玄学，有生产数字：字节 Arnold（NeurIPS 2025，arXiv
2509.15940）在**超过 9600 卡的生产预训练**上，把通信组的拓扑 spread 最多
降 1.67 倍，端到端性能**提升 10.6 个百分点**（论文口径，作者生产自报）。面试官问
「TAS 值多少」，这就是现在最好的答案。可追问：Allgather 类流量为什么
从 balanced placement 受益更大——容量 (10,10) 的两组，摆成 (6,6) 优于
(10,2)，因为后者把两组流量挤进同一条上联。

## 四、切分与共享：四选一而不是组合解

一张卡给多个任务用，有四条路线，**彼此互斥、各管一段**，选型是工程题：

| 方案 | 隔离级别 | 动态性 | 故障域 | 适用 |
|---|---|---|---|---|
| **MIG** | 硬件级（SM/L2/DRAM 端口） | 静态几何，改分区要杀 GPU client | 独立 | 多租户硬隔离、确定性 SLO |
| **MPS** | 软限额（等分算力+显存，control daemon） | 动态 | 共享 | 同一信任域内推理共享 |
| **time-slicing** | 零隔离（共享显存与故障域） | 动态（调度标签游戏） | 共享 | 开发/CI/压密度不在乎干扰 |
| **vGPU（HAMi）** | 驱动钩 cudart，显存+核限额 | 动态 | 共享但可限额 | 推理堆密度、国产卡混布 |

几个必背细节：

- **MIG 几何**：H100-80GB = 7×1g.10gb（1g 含 16 个 SM）；A100-80GB 有
  1g.10gb / 2g.20gb / 3g.40gb / 7g.80gb；A100-40GB 是 1g.5gb～7g.40gb。
  MIG mixed 策略下，节点上会出现 `nvidia.com/mig-3g.40gb` 这类独立资源名。
- **MPS 在 MIG 上不支持**，且 MPS 官方支持从 device plugin v0.15+ 起仍标
  experimental；time-slicing 与 MPS 互斥；device plugin 的共享策略全节点
  统一、不能逐 GPU 配置。
- **time-slicing 的演示值**：8 卡机 replicas=10，节点上报 80 个
  `nvidia.com/gpu`——看板很漂亮，实际是时间片轮转。
- **HAMi**（CNCF incubating，⭐4678，v2.10.0，2026-08-21）是推理多模型
  共享卡的主流走法：宿主级注入而非 MIG，且支持昇腾/寒武纪/海光/摩尔线程。

## 五、混部、弹性与容错闭环

### 5.1 混部的三层：瓶颈不在调度器而在干扰治理

在线推理 + 离线训练混一台机器，分三层看：

1. **身份层**：在线 Prod / 离线 BE，PriorityClass + Kueue 的 ClusterQueue
   borrowing/preemption 决定「谁活」。注意 K8s 原生 PriorityClass 抢占只管
   谁活，**不管干扰**。
2. **数量层**：超卖多少。Koordinator（⭐1762，v1.8.0，2026-04-16）的
   Mid 资源从 Prod 峰值冗余算可回收量，v1.6 起未分配资源也能静态超卖，
   防高峰期冷启动无位。
3. **干扰层**：真正的硬骨头。CPU 侧有成熟答案——group identity +
   Intel RDT / resctrl 做 LLC 与内存带宽的 Pod 级隔离（Koordinator v1.6
   起 Pod 级 resctrl）；GPU 侧则是短板——**至今没有硬件级配额**，时间片和 MPS 都不
   隔离 L2 cache 与带宽，只能靠 HAMi-core 限算力显存 + SLO 守护 + 驱逐
   兜底。

### 5.2 容错闭环五拍

万卡集群一台节点 XID 报错到训练恢复，全链路五拍：

1. **DCGM exporter** 出指标：XID 错误码、温度、ECC；
2. **Node Problem Detector** 把 XID 翻译成 node condition；
3. 自动化做 **cordon + drain**（触发条件与误杀风险是追问点）；
4. **Kueue evict workload**，TAS hot swap 在原 topology assignment 下换掉
   坏节点（v0.14 beta 起）；
5. **训练框架从 checkpoint 重启**（torchelastic 等接接口点）。

关键分工一句话：**重调度决策在集群层，恢复语义在框架层**——Kueue 只保证
「给你换新节点」，「从哪个 step 接着跑」是训练框架自己的事。

## 七、工程议题：七个反直觉点

1. **MIG 的「静态税」**。切一次几何要停掉节点上所有 GPU client
   （stop pods → reconfigure → restart），不是热操作。推理上 MIG 的真实
   收益是「小模型拿确定性 SLO 卡位」，代价是 7×1g 算力总和小于整卡
   （每个 instance 只有 1/7 的 SM 且不共享），分区组合还受硬件合法几何
   约束。**面试别拍「7 倍利用率」**。
2. **time-slicing 的欺骗性指标**。节点上报 80 卡、看板利用率拉满，实际
   时间片轮转，P99 延迟直接翻倍。在线推理开 time-slicing 是事故温床。
3. **gang + 配额的二阶死锁**。minMember 满足了但配额抢不到全部 flavor，
   或者 minAvailable 与中任务相互挤兑，作业在 admitted→evicted 之间反复
   震荡。用 waitForPodsReady.recoveryTimeout 和 FailFast hot swap 收敛。
4. **拓扑约束 × 碎片的公地悲剧**。全员 `required-topology: rack` 会把
   集群切成一堆无法装入的空位。解法：preferred 为主、required 留给硬
   约束作业，小作业 unconstrained 回填，binpack 打分压制碎片。
5. **hot swap 只救单机**。作业吃满一个 rack 时，同域里找不到替换节点，
   只能整作业 evict 重排。这又是为什么 checkpoint 频率和热备卡预算要
   反复强调。
6. **混部 GPU 干扰没有银弹**。resctrl 管得住 CPU 侧 LLC/内存带宽；GPU
   侧多进程共享 L2/DRAM 带宽无硬件配额，生产上的答案是纪律而不是技术：
   **在线卡不共享、离线 HAMi 限额、压测定超卖水位**。
7. **虚拟化与直通的调度盲区**。vGPU / 国产卡虚拟化实例的资源名各家
   自定义（HAMi 的 gpumem、koordinator 的 gpu-core），YAML 跨调度器
   不可移植，平台层必须做资源模型抽象，否则每接一个调度栈重写一遍。

## 八、面试题（含频率标注与追问拆解）

> ▶＝必考级（几乎每家 AI Infra 都问）；▷＝高频；○＝进阶加分题。

**Q1（▶）Kueue 和 Volcano 的本质区别是什么？**

答在分层：Kueue 只做 **admission 与配额**（Workload/ClusterQueue、
borrowLendingLimit），Pod 的单机放置仍然交给 kube-scheduler；Volcano 是
调度器 + 控制器一体，自带队列、抢占、binpack，自己下场放 Pod。所以
Kueue 是「kube-scheduler 的互补件」，Volcano 是「kube-scheduler 的替代件」，
Kueue 因为侵入小、能叠加在任何调度器上，成为 2026 的默认增量。追问：
为什么不自己调度 Pod（分层解耦、社区分工、生态兼容）；可反问
ProportionalQueue / DRF 公平性语义。

**Q2（▶）gang scheduling 的死锁怎么产生，怎么解？**

答语义：AllReduce 同步集合通信，缺一个 rank 全员不可用；逐个调度会
部分启动——32 节点起 31 个，248 卡空转，配额不足时永久死锁。解法三件套：
minMember 的 all-or-nothing 语义（Coscheduling / PodGroup）、Kueue 准入层
整组放行、超时回滚（等不到全组就释放已占资源）。追问：空转算力账
（31/32 占用 = 97% 浪费）；为什么需要超时而不是干等（活锁）。

**Q3（▶）为什么 8 卡机要整机分配？**

18 倍带宽差：机内 NVLink4 900GB/s vs 单 400G 网卡 50GB/s。TP=8 的通信域
就是 NVLink 域，拆到两机等于把最热的通信量推上最慢的链路。追问：
rail-optimized 组网下，DP/EP 跨机并行组怎么摆（沿 rail）；机内碎片怎么
治理（binpack / MostAllocated 打分、整机池划分）。

**Q4（▷）MIG / MPS / time-slicing 怎么选？**

三张维度答：**故障域**（MIG 独立，其余共享）、**显存隔离**（MIG 硬隔离，
MPS 等分软限额，time-slicing 无）、**动态性**（MIG 静态要停机改，其余
动态）。细节加分：MPS 在 MIG 上不支持；time-slicing 与 MPS 互斥；共享
策略全节点统一。场景题「灰度一个 7B 小模型怎么落」：要确定性 SLO 用
MIG 切一个 1g，不在乎干扰压密度用 HAMi/MPS，绝不 time-slicing。

**Q5（▷）在线推理 + 离线训练混部，在线延迟抖了，怎么排查？**

分层下钻：一看是否**同 GPU 共享**——MPS/time-slicing 无 L2/带宽隔离，
离线把 SM 和带宽吃满；二看是否**同节点 LLC/内存带宽争抢**——resctrl
有没有做 Pod 级隔离；三看是否 **PCIe/NVLink 争抢**（离线大流量拷贝挤占
总线）。治理对应：koordinator QoS class / group identity、压制与驱逐链。
面试官要的答案是「分层定位」，不是背组件名。

**Q6（▷）万卡集群一台节点 XID 报错，到训练恢复，全链路怎么走？**

五拍照背：DCGM exporter 出 XID → NPD 翻成 node condition → 自动
cordon + drain → Kueue evict + hot swap 换节点 → 框架 checkpoint 重启。
追问点：cordon 自动化的触发条件与误杀风险（抖动卡别误杀好节点）；
hot swap 的边界（满 rack 无同域替换）；torchelastic 接口在哪接；
**集群层管重调度、框架层管恢复语义**的分工。

**Q7（○）TAS 到底能值多少？**

Arnold：>9600 卡生产预训练，通信组拓扑 spread 最多降 1.67 倍，端到端
**提升 10.6 个百分点**（论文口径）。追问：为什么 Allgather 类流量从 balanced
placement 受益更大——(10,10) 容量下 (6,6) 优于 (10,2)，均匀铺开避开
上联热点；再追一层就是本仓通信与网络专题的两级 fat-tree 口径。

## 九、口径与未核实说明

- 「集群 GPU 平均利用率普遍 30–50%」：行业常引说法，本轮未找到可引用的
  2025–2026 一手调查源，按社区口径对待，面试里别说死出处。
- 混部利用率提升「20%→60% 典型值」：Koordinator 早年案例是 CPU 混部
  口径且年份偏旧；本轮只拿到论文定性结论，未取到可写死的企业生产数字。
  建议表述为「量级是两位数百分点」。
- K8s 上游原生 gang / Workload API 在 v1.34+ 的 GA 状态：本轮未实测确认，
  **不要当成已 GA** 去讲。
- Grove 在训练场景的适用性：官方定位是推理编排（多节点 PD 分离），
  训练侧大规模采用的证据暂无，别拔高。
- Arnold +10.6% 为作者在生产系统上的自报数字；GKE TAS 文档的
  「significantly improve」是厂商定性宣称，引用时带口径。
