# 分方向简历范文：推理 infra / Agent 开发 / RL·算法

> 本篇给三份可直接改写的简历正文样块。使用前必读两条：
> ① 所有 [bracket] 替换为你的真实测量值（不可复现的数字会被连环追问反噬）；
> ② 句子模板抄用，但可以追述的**特有难点与对比方案**必须是你自己跑过的，
> 防造假三问见 [简历结构与量化写法](./简历结构与量化写法.md) 第四节。

> 住五层的地方。

## A. 推理 infra 岗范文

CUDA/Triton、vLLM/SGLang/TRT-LLM、PagedAttention/Prefix Cache、
PD 分离与调度、性能分析（Perf/eBPF/Nsight）、SLO 吞吐/延迟权衡、量化。

**个人优势（4 条模板）**

- 推理引擎工程：在 [vLLM/nano-vllm/SGLang 自定义 fork] 上落地
  [Continuous Batching 调度循环 / Radix Prefix Caching / chunked prefill]，
  单卡吞吐 [x] tok/s → [y] tok/s（压测口径见项目 repo）
- 性能分析与优化：习惯先用 [Nsight Systems / bench] 再动代码，
  定位过 [KV block 分配峰 / CUDA Graph capture 失败 / NCCL 阻塞
  反向传播] 类线上事故 [n] 起并给出量化修复报告
- Kernel 与硬件理解：用 Triton 复现过 [FlashAttention / RMSNorm /
  GEMM blocking]，报告 occupancy 与访存带宽占用 [x%]→[y%]
- 模型结构与量化：MLA/GQA 显存数学建模实测一致；INT8 weight-only
  量化 decode 提速 [x%]，精度损失控制在 [x 分] 以内

**技能分层（示例四行）**

- 引擎框架：vLLM（读源码 + 自定义调度策略）/ SGLang（RadixCache）/ TRT-LLM（会用）
- Kernel：CUDA（key kernels 复现）、Triton（GEMM/attention）、Nsight Compute
- 模型结构：GQA/MLA/MoE、RoPE、量化（PTQ weight-only / W4A16）
- 工程：Python / C++ / 压测脚本、langfuse+nvtx、K8s 部署基础

**主项目 4 段式（示例）**

> **背景**：生产侧 LLM serving 在低并发下 GPU 利用率不足 30%，每
> token 成本超限 40%。
> **难点**：prefill/decode 混编时显存碎片与调度抢占导致的长尾——
> 不是「GPU 不够」，解决不了就不能满足 SLO。
> **工作**：
> - 基于 [nano-vllm] 复刻 vLLM 离线核心：实现 BlockManager
>   （free list + 引用计数回收）、Continuous Batching 调度循环与
>   chunked prefill，跑通 Qwen3；
> - 增量落地 [Radix Prefix Caching]：系统 prompt 场景前缀命中率
>   从 [x%] 到 [y%]；
> - 接入 [Liger-Kernel] 并实测：显存峰值降 [x%]，
>   吞吐提升 [y%]；
> - 排障：定位 CUDA Graph 在变 batch padding 下 capture 失败的根因
>   并修复（issue #x）。
> **成果**：输入分布 [1024±256 / 输出 256±128] 下，并发 [1→64]
> 吞吐提升 [x.x]×、P99 TTFT 降 [x%]；数据与 benchmark 脚本见
> GitHub（README 附四张曲线图）。

**追问预警**（面试官会深挖的点）

- BlockManager 的空闲块怎么组织？free 复杂度多少？
- RadixCache 的驱逐策略、节点结构；
- chunked prefill 的 token budget 分配、为什么 2048/4096/8192；
- 为什么不用 TP？NCCL 阻塞 vs CUDA Graph 的顺序怎么处理的；
- 你的压测输入分布是什么、怎么保证可复现。

## B. Agent 开发岗范文

**JD 关键词锚**（来自 [jd分析-agent开发岗](../resources/jd分析-agent开发岗.md)：
RAG / function calling / 多 agent 编排 / LangGraph / MCP / 工具权限 /
prompt 工程 / 评测（RAGAS/LLM-as-judge）/ 可观测性 / 成本与延迟优化 /
SSE 流式 / 后端基本功（Redis/K8s）。

**个人优势（4 条模板）**

- Agent 工程化：基于 [OpenManus/LangGraph] 搭建生产可用 Agent：
  工具错误分类重试、step 记账与成本护栏、超时幂等核对链；
  故障注入回归后自愈率 [x%]
- RAG 检索：全链路（解析→切块→混合检索→rerank→citation 校验→
  评测回归），引入自适应检索策略后固定评测集 top-5 召回
  [65%] → [82%]
- 工具与协议：自研 MCP server 对接 [内部系统]，工具描述工程 +
  结果分页 + 只读围栏；熟悉 MCP/JSON-RPC 权限模型
- 可观测性：langfuse 全链路 trace + 成本看板，token 成本 A→B；
  badcase 按周回流成回归 eval 集

**技能分层（示例四行）**

- Agent 栈：ReAct/CodeAct/Plan-Execute、LangGraph、OpenManus、MCP
- RAG 栈：chunking/HNSW/BM25+向量混合检索/Cohere-rerank/RAGAS
- 工程：Python/FastAPI、SSE 流式、Redis（大 key/穿透治理）、
  Docker/K8s、CI/CD
- 模型与提示：prompt 设计/结构化输出保证/Few-shot 消融/LLM-as-judge

**主项目 4 段式（示例）**

> **背景**：客服团队 80% 工单是重复查询；早期 Demo 型 RAG Bot
> 在真实流量下幻觉率高，无法过安全审。
> **难点**：高并发多租户场景下的工具失败与上下文漂移——
> 不是「模型不够聪明」，而是编排、权限和成本不能同时保证。
> **工作**：
> - 拆意图识别/检索/生成三个子 Agent，LangGraph 状态图编排 +
>   checkpointer 断点续跑；分支失败降级为模板回复 ≠ 系统挂掉；
> - 工具层三件套：错误分类指数退避、超时幂等键远端核对（不盲目
>   重建）、共享预算「已消费/已预留/待确认」三账并发记账；
> - 长期记忆：对话摘要 + 用户画像双轨，重复提问率降 [40%]；
> - 引入自适应检索层：LLM 先判断要不要检索/检哪个库，
>   无效检索请求降 [x%]；
> - 评估：自建 [x] 条 bad-case 集 + RAGAS 四指标回归 CI，prompt
>   版本灰度与回滚机制。
> **成果**：回答召回准确率 [x%] → [y%]、P95 端到端延迟
> [A]s → [B]s、单次请求成本降 [x%]、人工接管率 [x%]。

**追问预警**

- 工具返回超时 / schema 不符，代码层怎么兜?（指数退避 + 降级 + 人工
  兜底三层答）
- 同一工具同参数重复死循环怎么发现？（指纹连打检测 + 预算中止）
- 你的 RAG 评测集怎么建的？有没有标注一致性校验？
- 为什么选 LangGraph 不是原生 Chain？分支失败怎么回滚？
- SSE 流式怎么做的？NGINX 关没关响应缓冲？

## C. RL/算法岗范文

**JD 关键词锚**：SFT/DPO/PPO/GRPO/RLVR、reward model、数据工程
（配比/合成/去污染）、采样吞吐、训推一致性、前沿 paper（DAPO/GSPO）、
最大规模卡时训练/微调。

**个人优势（4 条模板）**

- RL 后训练：GRPO 全链路八次迭代（冷启动 SFT→RL→拒绝采样 SFT→
  对齐 RL），高难评测准确率 [58%] → [73%]
- Reward 工程：结果/过程奖励解耦、verifier 四维固定巡检
  （答案/过程/judge/训推一致性），reward 真实评测偏离度从
  [30%] 降至个位数
- 数据工程：通过率 [20-80%] 窗口筛选 + 过程奖励剔「答案对过程凑」
  + 课程式调度（简单:中:难 ≈ 3:5:2）
- 热点跟进：复现过 [minimind RL 段 / nanoGPT speedrun Muon]，
  按周读并复现前沿 paper（DAPO 的 clip-higher 熵崩塌对策等）

**技能分层（示例四行）**

- 训练框架：PyTorch、FSDP/DeepSpeed、TRL/verl、Megatron（会用）
- 算法：SFT/DPO/PPO/GRPO/GSPO、reward model、课程学习、agentic
  SFT 数据合成
- 推理协同：vLLM 采样接入、训推一致性验证、rollout 吞吐优化
- 基础：Transformer 手撕、算量估算、5ND/显存公式

**主项目 4 段式（示例）**

> **背景**：数学 Agent（推理模型）在某内部 benchmark 准确率与
> reward 曲线背离——真实能力没涨。
> **难点**：verifier 被糊弄（reward hacking）+ 长思维链训练不稳，
> 不是「调 KL 就行」的系统问题。
> **工作**：
> - 定位三类漏刷样本：字符串特判（三成高 reward 样本人工复核
>   确认）、过程奖励加权污染、judge 审美讨好；
> - 改造 verifier：符号判等替代字符串比对、结果/过程奖励解耦
>   多输出头 RM、judge 打分可复现约束；
> - 监控体系：response 级 entropy 曲线 + 跨输入互信息 + 按题型拆
>   audit，训推双引擎一致性校验（>5k token 差 3-5 倍告警）；
> - 动态采样滤全对全错组，课程调度 3:5:2；长思维链分段软惩罚 +
>   token 级 KL。
> **成果**：高难评测 [x%] → [y%]、相同算力预算有效训练步数
> 提升 [x]×、推理长度缩短 [20%]。

**追问预警**

- 你的 reward 偏离度 30% 怎么测出来的？
- 动态采样滤组后 effective batch 是多少，为什么没变噪？
- group size 怎么定的、有没有扫参？
- 训推一致性校验的原理，为什么 thinking 越长差越大？
- 下一步还想解决的 RL 问题是什么？（考你前沿阅读）

## 通用结尾：三份范文的公共红线

- 每个 [bracket] 都必须替换为真实数据并且**今天被问都能答口径**；
- 「难点」一节是该项目的**特有难点**，不是「资源不够」这类共性词；
- 副项目贝一行即可，与主项目互不重叠（infra 范文加一行 kernel/
  llm.c 副件，Agent 范文加一行 RAG 副件，算法范文加一行 speedrun
  副件）;
- 写完用 [防造假三问](./简历结构与量化写法.md#四防造假三问写完简历必自查)
  自查三题，全过才发出去。
