# 系统设计：个人助理 Agent（OpenClaw 类常驻个人 AI 助理）

> ▶ 题目形态：2026 新形态题——"设计一个个人助理 Agent（类 OpenClaw / Claude Code 的
> 常驻个人形态）"。
> 答题模板不变：**澄清问题 → 架构图 → 关键设计取舍 → 评测 → 追问预案**。
> 八股支撑：[Agent 基础与规划 §七 L1–L7 分层](../interview-questions/agent/agent基础与规划.md)
> （那篇是**通用分层模型**，本篇是"个人助理"这一具体形态的系统设计落地——架构
> 里每一层都能映射回 L1–L7，讲的时候直接点名对应关系，但不重复那边的内容）、
> [记忆与上下文工程](../interview-questions/agent/记忆与上下文工程.md)、
> [工具调用与 MCP](../interview-questions/agent/工具调用与mcp.md)、
> [多 Agent 与评测](../interview-questions/agent/多agent与评测.md)。

个人助理题不是[企业客服题](./设计ai客服agent.md)的缩小版，开场第一件事就是把这个
差异说透——它决定了后面每一个设计决策的方向：

| 维度 | 企业客服 Agent | 个人助理 Agent（本题） |
|---|---|---|
| 用户模型 | 海量匿名用户，会话彼此独立 | **单用户、长期驻留**，越用越懂你 |
| 上下文范围 | 单次会话内闭环 | 跨会话、跨周月年的深度个人上下文 |
| 通道 | 单一客服窗口/app | IM / CLI / Web **多端并发**，随时切换入口 |
| 触发方式 | 用户发话才动（纯被动） | **自驱**：cron 定时 + heartbeat 巡检主动干活 |
| 信任边界 | 企业数据、企业服务 | **本地优先**，私人数据全量托管给它 |
| 失败成本 | 幻觉 → 资损/客诉 | 幻觉 → **打扰你、替你发错消息、泄露隐私** |

总原则一句话：**个人助理 = 一个常驻的、有记忆的、多通道的、会自己醒过来的 Agent
运行时**——前两台题（知识库、客服）你设计的是"一次请求的服务"，这题你设计的是
"一个住在用户设备上的数字雇员"。

## 一、场景定义与澄清问题

主动报出假设，表明你设计的是具体形态（OpenClaw 类开源个人助理是标准参照）：

| 澄清维度 | 本题假设 | 为什么这么问 |
|---|---|---|
| **用户规模与设备形态** | 单用户、本地常驻（笔记本 + 家庭服务器/Node），非多租户 SaaS | 决定架构中心是"个人设备"而非"服务集群"，扩容题直接不考 |
| **通道** | IM（微信/Telegram 类）、CLI、Web 三类入口并存 | 决定要不要 Gateway 统一协议——不要 Gateway 的方案基本挂在这 |
| **动作范围** | 读：文件/邮件/日历/浏览器；写：代办、日程、消息草稿；高危：代发消息、删文件、支付 | 决定工具权限分级与确认闸的位置 |
| **自驱边界** | 允许做什么：定时提醒、收件箱巡检、监控项报警；**主动对外联系一律要确认** | 个人助理和被动 Agent 的本质差异点，也是失控风险源 |
| **隐私红线** | 本地优先：文件、记忆、人格文件全部落本地磁盘；云端只出 token（模型调用），敏感内容可配置本地小模型兜底 | 这是用户敢不敢全量托管数据的根本 |

补一句面试话术：澄清完补一句"**所以这个系统的第一约束不是 QPS，是信任——
单用户产品没有'万分之一的资损摊到大盘'这回事，一次误发消息就是 100% 的事故
率**"。这句话能和企业题的容量估算思维拉开差距。

六层一句话：**通道层收口多端入口，Gateway 管"谁在跟我说话、发到哪个会话"，
Runtime 管"怎么想和怎么做"，记忆层管"记得什么"，Node 管"真的去动设备"，
自驱层管"没人说话时它自己醒着"。** 逐层说：

### 2.1 通道层：IM / CLI / Web → 统一会话协议

三个入口各自适配（IM 的 webhook/长连接、CLI 的 stdio、Web 的 SSE），由 Gateway
适配成**同一份内部会话协议**：`{channel, identity, thread, message}`。通道只负责
收发，不碰任何 Agent 逻辑——新增一个通道 = 新增一个适配器，Runtime 完全无感。
这对应 L1–L7 的 **L6 通道层**。

### 2.2 Gateway（控制面）：会话路由 + 身份与配对 + 长连接

- **身份与配对**：IM 账号 ↔ 唯一用户身份的配对表（首次发消息做配对确认），IM 侧
  无法证明身份的消息一律不入 Agent。
- **会话路由**：同一用户跨 IM/CLI 的消息收敛进**一条主线会话**（详细取舍见 3.2），
  长任务、独立专题可以开旁线，但主线只有一条。
- **长连接管理**：IM/Node 的心跳、断线重连、消息队列缓冲全在 Gateway。

**Gateway 与 Node 分离是被问烂的追问**（预案见第五节）：Gateway 是控制面，可以
放在一台 24h 在线的小主机/家庭服务器上；Node 是执行面，贴在有真实能力的设备
（笔记本）上。**笔记本合盖、换机、断电，都不丢会话主线**——Gateway 那侧连 IM、
存队列，等 Node 上线再投递。如果合在一台笔记本上，合盖 = 助理下线，消息流
断掉，这是个人形态不可接受的。

### 2.3 Agent Runtime：人格 / 循环 / 工具 / Skills

- **人格层**：系统提示之外单独维护一份 **SOUL.md 式长期身份文件**（名字、口吻、
  用户偏好、禁区），版本化管理、可随用户反馈演进。它回答"像谁、守什么规矩"，
  对应 **L5 人格层**——和企业客服把话术写死在 workflow 里不同，个人助理的
  人格是资产，越沉淀越值钱。
- **Agentic loop**：标准 ReAct/TAO 循环 + steering（用户随时插话纠偏、可打断）
  + 循环控制（max_iterations / 重复指纹 / 任务预算，见
  [Agent 基础与规划 §五](../interview-questions/agent/agent基础与规划.md)）。
- **工具系统：读写分级**，只读零确认、可逆写低确认、高危（代发消息/删文件/支付）
  强制确认闸——详细分级在 3.3。
- **Skills 机制**：知识/SOP 按需注入（"怎么报销""怎么订机票"做成 skill 文件，
  命中才进上下文），不靠一份巨型系统提示装下所有领域知识。

### 2.4 记忆层：会话级压缩 + 长期透明记忆

- **会话级**：token 水位触发 compaction——上下文逼近阈值（比如窗口 80%）就把
  历史滚动压缩成事件摘要，避免长任务中途爆窗；详见
  [记忆与上下文工程](../interview-questions/agent/记忆与上下文工程.md) 的压缩节。
- **长期**：**Markdown 文件记忆 + 向量召回**。刻意做成用户可读可改的透明文件
  （`memory/2026-10.md` 这种），而不是黑盒向量库——单用户场景下"它记了我什么"
  必须可审计可删除，这是个人信任边界的产品表达，和企业知识库的通用向量库方案
  相反。

### 2.5 Node（执行面）：受控暴露的本地能力

shell、文件、浏览器、相机类能力挂在 Node 上，**按最小权限暴露**（目录白名单、
命令黑白名单、危险命令二次确认）。Node 崩了只影响执行，不影响 Gateway 侧会话
主线和消息接收——这也是分离的第二个理由。

### 2.6 自驱层：cron + heartbeat，个人助理的灵魂

- **cron 定时任务**：用户显式排程（"每天早上 8 点给我今天的日程摘要"），
  确定性触发，行为完全可预期。
- **heartbeat 心跳巡检**：周期性唤醒，带着一小段"巡检 prompt"去检查收件箱、
  监控项、待办到期——发现没事就静默，发现有事才说话。**配可配置的静默时段**
  （夜间/会议中不打扰）和主动行为预算（3.6）。

这层是个人助理与被动 Agent 的**本质差异点**，面试里必被追问，预案在第五节。

## 三、关键设计取舍

每一条按"问题 → 选项 → 推荐"组织。

### 3.1 本地优先 vs 全云

- **问题**：助理要看全部私人数据，放本地跑全套（含本地模型）体验受限，
  放云端隐私红线又守不住。
- **选项**：全云端 SaaS；全本地（本地小模型）；**混合**：数据、记忆、人格全部
  本地落盘，模型调用走云端 API，敏感类目可切换本地小模型兜底。
- **推荐**：混合。本地拿到**数据主权和离线可用**（断网时本地模型降级可用），
  云端拿到**能力上限**；敏感内容（日记、财务）路由到本地模型，宁可慢不可泄。
  成本上单用户月 token 量有限，不是主要矛盾。

### 3.2 单会话语义 vs 多通道并行

- **问题**：用户在微信说"帮我查下机票"，十分钟后在 CLI 跑别的命令，晚上回到
  微信问"机票查得怎么样了"——跨通道消息如何收敛？
- **选项**：每通道一条独立会话；**一条主线 + 融合视图 + 旁线**。
- **推荐**：主线只有一条（个人助理的核心价值是"它知道我最近的一切"），
  Gateway 负责把各通道消息按身份融合进主线时间序；同时开**旁线**承载长任务
  （"帮我盯这个航班降价"）和独立专题（工作/生活分组），旁线在主线里只留下
  摘要位，不污染主线上下文。纯"每通道独立"会让晚上的问题答不出，体验断层。

### 3.3 写操作分级：从只读到高危

直接沿用 [工具调用与 MCP §三](../interview-questions/agent/工具调用与mcp.md)
的权限声明，落成本题的三档：

| 档位 | 例子 | 确认策略 |
|---|---|---|
| **只读** | 查文件/邮件/日历、搜网页 | 零确认，直接执行 |
| **可逆写** | 建档代办、加日程、写记忆文件 | 低确认（默认放通 + 记事本可撤回），幂等键防重 |
| **高危** | **代发消息、删文件、支付、对外 API 写** | 强制确认闸：HITL 状态机（paused → 用户在任一通道点确认 → 恢复），超时不确认自动作废 |

个人助理的高危线比企业客服画得**更靠左**——因为它的权限是"代表我本人"，一次
误发消息没有客服工单兜着。详细状态机见
[多 Agent 与评测 §四](../interview-questions/agent/多agent与评测.md)。

### 3.4 Context 压缩策略：阈值触发 compact vs 每轮全量注入

- **问题**：会话长了怎么办？长期记忆每轮都塞吗？
- **选项**：每轮全量注入长期记忆；阈值触发 compaction + 按需召回。
- **推荐**：后者。每轮全量注入长期记忆，token 成本随记忆量线性膨胀，且无关
  记忆会稀释当轮注意力（一致性差）。**水位触发 compaction 管会话内部，向量
  召回按需取长期记忆**，两者各管一段——成本 O(当前任务) 而非 O(全部记忆)，
  一致性靠"scratchpad 常驻当轮事实 + 摘要可回溯"保。

### 3.5 Subagent 隔离：长任务派生独立上下文

- **问题**：海航班监控、跑一份调研报告都要几十轮工具调用，全堆在主上下文吗？
- **选项**：主线单循环硬扛；派生 subagent。
- **推荐**：长任务/专业任务派生独立上下文的 subagent（自己的循环、自己的工具
  预算、自己的 compaction），**主上下文只回传摘要**——主线的每一轮都不为
  subagent 的几十步中间态付 token。这同时是自驱任务的执行模型：heartbeat 发现
  "有事" → 派生 subagent 去办 → 只在主线留一条"已办 + 要点"。

### 3.6 自驱失控防护：预算、黑白名单与审计

- **问题**：会自己醒着干活的助理，怎么防止它半夜发 50 条消息打扰你，
  或者替你做了不该做的事？
- **防线（层层递进）**：
  1. **主动行为预算**：heartbeat 触发的消息有频率上限（每小时 ≤N 条主动消息，
     超限进队列等下个周期），配的静默时段绝对不说话；
  2. **动作黑白名单**：自驱模式下允许的动作列表比被动模式**更窄**（主动模式
     下代发消息这类高危动作直接禁用，只提示不执行）；
  3. **动作审计日志**：每一次自驱唤醒、每一个工具调用落账本（谁触发、触发了
     什么、花了多少 token、结果如何），出事可归因，也是用户手动校准边界的依据。

## 四、可观测与评测

个人助理是大不了量级的系统，观测指标和客服题不是一个口径：

- **会话回放**：全量落 trace，可整段回放（自驱任务尤其要支持"它刚才在干嘛"）。
- **动作账本**：工具调用台账——按"触发源（用户/自驱）× 动作档位"切，自驱
  高危动作命中率 = 红线指标。
- **满意度信号**：个人助理的满意度信号**以负反馈为主**——对主动行为的
  吐槽/撤回/关静默是头等大事，比"答得好不好"高一个权重。主动消息被正面
  互动（回复/转任务）才算有效自驱，否则是打扰。
- **成本**：单用户月 token + 自驱循环 token 占比单独核算——自驱的钱是
  "闲置时烧的"，要压，通常自驱用小模型/本地模型跑巡检，只有发现事才升级
  大模型。

## 五、追问预案

**Q：Gateway 和 Node 为什么要分？**
四个理由：① 笔记本合盖/换机/断电不丢会话主线（Gateway 24h 在线，Node 随设备
上下线）；② Node 崩了不丢消息（Gateway 侧缓冲）；③ 安全边界——执行面贴设备、
控制面谈连网收消息，中间协议化，Node 上出问题不波及身份与会话；④ 多端设备
（台式 + 笔记 + 家庭服务器）可以共享一个 Gateway 和一套记忆。

**Q：心跳巡检怎么避免打扰？**
三件事：**静默时段硬约束**（时间窗内主动消息全部进队列）；**主动消息预算**
（频率上限）；"**没事就静默"原则**——巡检发现无事 → 零出声，有事也先进性
重判（值得马上说 vs 队列攒着周报），用户要的是一个懂分寸的助手，不是闹铃。
评测上负反馈信号（吐槽/撤回/被迫开静默）直接进回路。

**Q：人格层放系统提示还是放记忆？**
分层放，职责不同：系统提示放**不可变的硬约束**（安全红线、工具使用纪律）；
SOUL.md 放**可演进的人格与用户偏好**，本质是结构化记忆，版本化可回滚；
长期记忆文件放**事实性沉淀**（项目上下文、人际关系）。全塞系统提示会让一份
文档同时承担"规矩"和"资产"，改偏好要么污染红线、要么不敢演进。

**Q：这和 ReAct 单循环有什么本质不同？**
ReAct 是解决"一个开放式问题"的**框架层循环**；个人助理是一个**系统**——多了
通道收敛（多对一输入）、身份配对、长期记忆的版本化生命周期、自驱触发源
（cron/heartbeat 开启的一轮同样走 ReAct 循环），以及贯穿始终的权限分级与
审计。一句话：ReAct 是引擎，本题是把这台引擎装进一辆带变速箱、仪表盘和
安全带的整车。映射回 [L1–L7](../interview-questions/agent/agent基础与规划.md)：
ReAct 只是 L2。

**Q：安全模型怎么设计？**
纵深防护：① 身份与配对（IM 侧不可信消息不入 Agent，防账户名冒用）；
② 工具最小权限（目录/命令白名单）；③ 写分级 + 高危强制确认闸（最重的一刀，
见 3.3）；④ Prompt Injection 四件套（指令分层、工具最小权限、人工闸、注入
检测扫工具返回——邮件和网页内容对个人助理是天然的注入面，见
[工具调用与 MCP §七](../interview-questions/agent/工具调用与mcp.md)）；
⑤ 审计账本兜底归因。和企业题的区别：企业防的是"业务资损"，这里防的是
"代表我本人做错事"，所以高危线画得更靠左。

**Q：自驱巡检发现"有事"，怎么决定说不说？**
先判断巡检结果（有事/没事/拿不准）→ 拿不准按没事处理（宁亏一次巡检，不换
一次打扰）→ 有事再过打扰必要性二分（立即值得说 vs 队列攒着）→ 高危动作
一律不说也不做，只在你下次主动开口时提示。
