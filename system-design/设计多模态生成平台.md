# 设计多模态生成平台

▶ **真题来源：多模态 / 推理 Infra 岗的高频延伸题**——"如果让你搭一个文生图 + 文生视频的统一
serving 平台，架构怎么分？"。它是 [设计分布式推理服务](设计分布式推理服务.md) 的姊妹题：
LLM 推理那面考的是 token 级调度，这面考的是 **任务级调度**，两题答题骨架相似、取舍完全相反。

> **面向谁**：面 AI Infra / 推理平台方向，被开到"生成式模型怎么部署成服务"类系统设计题的同学。
> **读完获得什么**：一套"API 网关 → 队列 → 多档 worker 池 → 并行执行层"的答题主线，
> 加上画质 / 延迟 / 并发三权衡、分池铁律、防滥用、质量回归四组追问预案，以及一张可复述的
> 数字锚表（全部带来源口径）。
> **时效口径**：2026-10；扩散模型 kernel / solver 细节不在本文，全部推给
> [多模态生成与 diffusion 专题](../interview-questions/多模态生成与diffusion专题.md)，
> 本文只讲平台层的编排与调度形态。

## 一、先澄清问题（面试前 3 分钟清单）

面试官只丢一句"设计一个多模态生成平台"，先把范围钉死，展示的是工程直觉：

1. **模态与模型范围**：文生图 + 文生视频都要吗？模型是自部署开源模型（Flux / HunyuanVideo
   类），还是也要代理外部 API？——默认答案：自部署开源模型为主，图与视频都接，但**必须分池**
   （后述铁律）。
2. **规模与 SLA**：峰值并发是几十还是几千任务/分钟？秒级响应是谁的要求——文生图通常要秒级
   首图，文生视频分钟级可以接受吗？——决定异步任务模型和池子比例。
3. **质量档位**：是"一个模型一种输出"，还是要向产品暴露 fast / balanced / quality 三档？
   ——三档几乎必答，它把"步数 / 蒸馏变体 / 并行策略"的取舍收进了产品接口。
4. **计费和配额**：按请求数、按张数、还是按资源消耗（卡·时）？——正确答案是按资源消耗，
   因为不同分辨率 × 时长的成本差在 10 倍以上（后述）。
5. **边界**：只做推理 serving，还是也管训练 / fine-tune？——经典答案：先做在线生成闭环，
   fine-tune 后置；两者不要用同一套在线资源池。

一句话立题："**把'一次生成 = 一次巨型 GPU compute job'的资源申请、排队、并行执行、
交付与审计收口到一个平台**——类似传统任务调度系统之于离线计算，只不过每个任务的
资源单位从 CPU 分钟换成了 GPU 卡·时，且延迟近似不可拆分。"

## 二、直觉一句话：调度单位从 token 变成了整个请求

先把最根本的差异说死，后面所有设计都从它推出来：

| 维度 | LLM serving | Diffusion 生成 |
|---|---|---|
| 调度粒度 | token（每步解码一个） | **整个请求**（所有扩散步全都算） |
| 核心复用 | KV cache / prefix cache | 几乎没有（跨请求无精确复用） |
| 请求时长 | 秒级，可随时抢占换入换出 | 数十秒到数十分钟，独占一组 GPU |
| continuous batching | 是主菜 | **基本不适用**（没有增量 token 进出的概念） |
| 批处理形态 | 动态拼批、按 token 算 budget | 只能整请求级的 data parallel |
| 延迟与吞吐 | 被 decode 过程天然绑定 | **被强行解耦**：延迟靠并行堆卡，吞吐靠 DP 和排队 |

▶ 面试官最想听的那句："LLM 的调度器在 token 级做决策，Diffusion 的调度器在
**作业级**做决策——一个请求进来就是要几十秒到几分钟独占 1～8 张卡，这是排队论形态
完全不同的另一个系统。」这句话之后，continuous batching 为什么无效、长尾为什么
没有 meaning、"升级档位收费"为什么是产品自然形态，都能顺出来。

讲这张图时的标准动线（三个泳道自上而下）：

1. **接入与审核层**：请求过 API 网关做鉴权与计量，提交即返回 task_id；prompt 机审
   **前置到入队之前**（先拒被拒的请求，绝不让它先占住 GPU 再被打回来）；出口侧做后置
   审核、打水印、直写对象存储走 CDN 分发。
2. **队列与多档调度层**：优先级队列按付费额度 / SLA 等级 / 成本封顶排队；三档质量路由
   把 fast / balanced / quality 映射到不同的模型变体 × 并行策略；弹性 gang 池管理器
   负责低峰合并、高峰拆散（后述）。
3. **GPU 并行执行层**：三档 worker 池——轻量图池（蒸馏模型，单卡 / 4 卡）、标准图 gang
   （USP + compile，4 卡）、视频档专属 gang（必须预开 4/8 卡）。worker 无状态，
   权重挂共享并行文件系统，工件直写对象存储。

一个细节值得时刻挂在嘴边：**机审为什么要前置**。回答："GPU 是不会错的稀缺资源，
审核可以错杀一千次也不痛——把审核放在排队之前，被拒请求的成本就是一次 CPU 推理；
放在后面就是白白烧掉几十秒卡时。"

## 四、关键子设计

### 4.1 任务模型：默认异步，同步只是甜点

- 提交即返回 task_id，轮询 / WebSocket 推送是**默认形态**。秒级文生图（蒸馏档）可以
  提供同步接口做体验加分项，但这是甜点不是主链路。
- 分钟级视频必须异步——HTTP 长连接保活、客户端重试幂等、超时策略都按"任务系统"
  而不是"请求-响应"来设计。
- 幂等性是送分点也是高分点：task_id 需兼具幂等语义，客户端重复提交同一任务键
  直接复用旧任务，避免"用户刷新一下烧两遍卡时"。

### 4.2 分池铁律：文生图和文生视频绝不能共池

▶ 面试高频："文生视频和文生图为什么必须分池？能共用吗？"

- **量纲差异**：文生图秒级、文生视频分钟级，时延差 2～3 个数量级（蒸馏 1024px 图
  **0.82 秒（8×A100，Flux-schnell，xDiT 官方 benchmark）**、720p 视频很慢——数字见下
  锚表）。放同一个队列，总有一方饿死：全让给图就视频永远排队，优先视频就图的
  P99 爆炸。
- **并行 gang 的形成代价不同**：视频必须预开 4/8 卡 gang 才能跑（并行是主解法，
  见 4.3），图片可以单卡弹性伸缩。共用一个池，等于每次调度都要在"gang 组装成本"
  和"单卡碎片"之间纠结。
- 配额按 **卡·时** 而不是请求数计：不同分辨率 / 时长的请求成本差 10 倍以上，
  按请求计费等于鼓励用户都点 4K 长视频。

### 4.3 并行执行层：调度器感知拓扑

并行是视频 Diffusion serving 的**主解法**，收益是确证的，但效率会塌缩：

- **USP（Ulysses + Ring 序列并行）**、PipeFusion（流水并行，吃扩散步之间的时间冗余）、
  VAE 并行（2048px 以上必开，单卡解码激活直接 OOM）、CFG 并行、torch.compile 是
  执行层的常规武器库。kernel 层的细节请移步
  [多模态生成与 diffusion 专题](../interview-questions/多模态生成与diffusion专题.md)，
  面试里平台题讲到"知道有哪些并行手段 + 什么时候选哪个"这一层即可。
- **平台的核心职责是按请求大小自动选并行度**：1024px 图 4 卡足够，别上 8 卡——
  xDiT 实测在 8×L40 的 PCIe 拓扑上 **4 卡反而比 8 卡快（1.41 秒 vs 更慢，xDiT 官方
  benchmark）**，跨机通信吃掉并行的收益。这叫"调度器感知拓扑"：调度器的资源画像
  必须知道 NVLink / 机内 / 跨机的带宽分层。
- **铁律：并行降延迟、不省算力；吞吐靠 DP 和排队，延迟靠 USP**。HunyuanVideo
  720p 从 4 卡加到 8 卡只有 **约 1.53 倍加速（514 秒 → 337.6 秒，xDiT 官方
  benchmark）**，扩展效率随卡数明显塌缩——花两倍卡省三分之一时间，是产品级取舍
  而不是工程免费午餐。

### 4.4 画质 - 延迟 - 并发三权衡 × 三档质量路由

平台的能力最终收敛成三个旋钮，产品接口暴露 fast / balanced / quality 三档，
每档各自映射"模型变体 + 步数 + 并行策略"：

| 权衡轴 | 往哪边拧 | 代价 |
|---|---|---|
| 步数 / 蒸馏档位 | 蒸馏 2～8 步模型（schnell / Turbo 类）快一个数量级 | 画质上限降低 |
| 并行度 | 加卡降单请求延迟 | 摊薄吞吐，且 4→8 卡效率塌缩（上表 1.53 倍） |
| step 缓存（TeaCache / FBCache） | 免费省一半步数 | 画质有损，必须灰度 |

把这三轴映射进产品档位：

- **fast 档**：蒸馏变体 + 少步数 + 最多 4 卡 gang，目标是秒级出图 / 最短队列。
- **balanced 档**：标准 20～50 步模型 + step 缓存 + 4 卡，调"够用画质 × 可接受
  延迟"。
- **quality 档**：全步数 + 关缓存 + 可达 8 卡的 gang + 2048px 以上开 VAE 并行，
  按卡·时顶格计费。

为什么必须把**档位**收进路由而不是让用户自由组合参数？两个原因：① 防止
"1024px 蒸馏模型上 8 卡"这种浪费资源的组合；② 成本封顶——路由器直接拒绝
"超大分辨率 × 超长视频"的超预算组合，这是防成本失控最简单的一刀。

### 4.5 无状态 worker 与工件存储

- **worker 不存状态**：生成结果直写对象存储，走 CDN 分发；worker 挂了任务重投，
  中间产物（latent）不值得跨节点保存——重算 vs 迁移是离线计算里算过的账。
- **模型权重挂共享并行文件系统**：多个 worker 池共用一份权重副本，避免每张卡
  独占一套几十 GB 的本地拷贝；启动时按池按需加载，配合 gang 预热的策略把
  "加载时间"藏进池子的轮换里。
- **弹性伸缩的粒度是"一组卡"（4/8 卡 gang）而不是单卡**——这决定了 autoscaler
  的接口设计：申请/归还的都是 gang 单元。

### 4.6 弹性 gang：生成平台的"假并发"问题（Muxer 问题）

▶ 面试加分题，一句话讲透："把 8 卡绑成一个 gang 能降视频延迟，但峰值期队列会崩；
拆成 8 个单卡 worker 能扛并发，但 4K 图 / 视频根本吃不下。"

- 答案是**弹性 gang**：低峰期把卡合并成大 gang 接大请求，高峰期拆散成小池保
  并发。但热切换并行度在编译图场景下很贵（torch.compile 的图重建要分钟级），
  现实做法是**预开多档 worker 池按比例调配**——固定有 4 卡池和 8 卡池，调度器
  只改两个池子的流量配比，不改存量 worker 的并行形态。
- 这个答案的升级版是"潮汐调度"：白天图高峰拆散，夜间视频批量任务合并——平台
  调度系统里的经典盘面，说出来能立住 infra 的实战感。

### 4.7 防滥用与合规

▶ 面试高频："生成平台怎么防滥用和保证安全？"

- **前置机审**：prompt 在入队之前先过审核模型，被拒请求一颗 GPU 都不碰（见
  三、图动线第 1 条）。
- **后置审核**：出图 / 出片后过 NSFW classifier 再交付；这两层一个都不能省。
- **审核本身也要 GPU**：审核模型是有负载的——独立的**审核池**，或者风险分级
  （risk-based）：低风险请求旁路异步审核 + 先展示后召回，高风险请求同步审核
  再交付。面试官让你选，答"按风险分级，高危同步、低危旁路"。
- **限流按卡·时**：幂等 task_id + 按资源消耗限流，配合 4.4 的成本封顶构成完整
  防线。
- **水印与合规**：SynthID 类不可见水印默认开，注意 2026 年各主要市场的生成内容
  合规要求已经普遍落地；这一条说出来是"平台懂产品法规"的信号。
- （审核与护栏的完整方法论在 [guardrail 系统专题](../interview-questions/agent/guardrail系统专题.md)，
  本文只讲平台侧怎么接。）

### 4.8 质量回归：没有人知道画质变差了

▶ 面试高分点："Diffusion 输出画质无法像 LLM 那样用 loss 盯，质量回归怎么发现？"

- 盯不了 loss，只能**二级模型抽检**：CLIP-score / aesthetic scorer 打分流 + 抽样
  人审；叠加用户侧信号——**点踩 / 重新生成回流**是宽表里的核心指标。
- **灰度画质门禁**：任何变更（新模型变体、新并行策略、新缓存配置）上线前必须
  过画质抽检阈值才允许全量——并行策略本身会轻微改变输出分布（截断/切分引入
  的数值差异），不要指望"数学上等价"。
- 降本动作必须带观测链路：你省钱省在哪、画质掉了多少、点踩率动了没有，三张图
  要一起摆——这是"成本-质量"这对平台核心指标的日常链路。

## 六、容量的一页纸账（选讲，但被追问要能算）

给一个能当场心算的规模感：

- 假设平台单日 100 万张文生图，其中蒸馏档占 80%、每张约 0.8 秒卡时，标准档
  20%、每张约 1.6 秒卡时 → 每天图卡·时约 **128 万秒 ≈ 356 卡·时**。按 0.6 利用率
  与峰谷比 3 估算，峰值并行需求约 **60～90 卡等效**。
- 视频侧单日 5000 条、每条 720p 8 卡 gang 跑 5.6 分钟 → 每天视频卡·时约
  **224 卡·时**，但因为 gang 不可分割，需要照峰值 gang 数预开，利用率天然低于
  图池——这就是为什么视频必须专属池 + 专属弹性策略。
- 讲完账补一句"所以计费按卡·时、配额按卡·时、gang 预开按峰值"，整题就有尾了。

## ▶ 面试追问

1. **文生视频和文生图为什么必须分池？能共用吗？**
   答要点：时延量纲差 2～3 个数量级 → 同队列互相饿死；gang 形成代价不同 → 视频
   必须预开 4/8 卡 gang，图片可单卡弹性。深追"弹性 gang 怎么搞"——预开多档
   worker 池按比例调配，而不是运行时热切换并行组（编译图重建成本太高）。
2. **成本怎么降？**
   三层答法：**模型层**（蒸馏变体 50 → 4 步、FP8 attention）；**系统层**（step
   缓存 FBCache 约 2.1 倍、torch.compile 约 2.6 倍，均 xDiT 官方自测口径）；
   **产品层**（三档路由 + 成本封顶拒绝超大组合）。高分点：画质损失没有 loss 可
   盯，只能靠二级 scorer 抽检 + 灰度门禁，任何降本必须带观测链路。
3. **8 张卡先做什么？**
   拆 2 个 4 卡 gang 覆盖中档，先上蒸馏模型 + step 缓存把单机延迟打下来；视频档
   暂不接——考的是取舍排序：先吃"免费的蒸馏和缓存"，再谈"烧卡的并行"。
4. **生成平台怎么防滥用？**
   prompt 审核前置到入队前、出图后后置审核、限流按卡·时、幂等 task_id、水印
   合规；深追"审核负载怎么隔离"——单独审核池，或按风险分级：高危同步审核、
   低危旁路异步 + 先展示后召回。
5. **质量回归与评估怎么做？**
   CLIP-score / aesthetic scorer 抽检 pipeline + 用户点踩回流 + 灰度画质门禁
   （并行 / 缓存策略变更要过阈值才能全量）；讲清楚"并行会轻微改变输出分布，
   不要迷信数学等价"。
6. **和 vLLM 那套能不能直接搬？**
   队列 / 调度 / LoRA 基础设施能搬；continuous batching、prefix cache、PD 分离
   这套以 token 为中心的机制搬不了——Diffusion 的解法是序列并行 × 蒸馏 × 步间
   缓存 × 稀疏/量化 attention 这一条新栈（详见
   [多模态生成与 diffusion 专题](../interview-questions/多模态生成与diffusion专题.md)）。
