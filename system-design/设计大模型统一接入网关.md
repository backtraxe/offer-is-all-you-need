# 设计大模型统一接入网关

▶ **真题来源：京东科技 / 腾讯（中高频）**——"大模型统一接入网关解决什么问题、怎么选型"
（收入 [高频面试真题汇总 - 系统设计题](../interview-questions/高频面试真题汇总.md#八系统设计题)）。

> 平台/Infra 岗的高频设计题，也是 [JD 分析-AI Infra 岗](../resources/jd分析-ai-infra岗.md)
> 里"MaaS / 平台方向"JD 的对应题："后端转 AI Infra 的最佳入口"。这篇按统一答题框架
> 组织：**澄清问题 → 架构图 → 容量/数据估算 → 关键设计取舍 → 评测与 SLO → 追问预案**。
> 推理引擎层面的原理（vLLM/Continuous Batching/PD 分离）都在
> [inference 模块](../interview-questions/inference/vllm与推理加速核心.md)，本文只讲
> "引擎之外、请求进来之后到引擎之前"的那一层。

## 一、先澄清问题（开口必说的 4 件事）

面试官只丢一句"设计一个统一接入网关"，先把范围钉死，展示的是工程直觉：

1. **规模**：多少租户/业务线接入？峰值 QPS 是 10 还是 1w？（决定要不要谈分片和异地）
2. **模型范围**：只接内部自部署模型，还是也要代理 OpenAI/Claude/文心等外部 API？
   （决定适配层的复杂度）
3. **核心诉求排序**：成本优先（多模型比价调度）还是稳定性优先（不挂、可审计）？
   企业级场景 90% 是后者。
4. **边界**：只做推理接入，还是也管 fine-tune / embedding / rerank？（经典答案是：
   先做推理 Chat/Embedding 两个 API 面，其他后置。）

一句话立题："**把分散在各业务线里的 Direct-to-API 调用收口到一个控制平面，统一做
鉴权、路由、限流、计量、缓存、降级**——类似传统微服务网关之于后端服务，只不过
'服务'换成了模型。"

## 二、为什么需要网关（vs 各业务线直接调各家 API）

▶ 被追问："直接调 OpenAI SDK 不就完了？"——**高频追问题**

| 痛点（各业务自己接） | 网关统一做 |
|---|---|
| 每家厂商一套 SDK / 协议 / 鉴权方式，接 N 家 = N 套代码 | **OpenAI API 兼容层**：内部全部按一套协议调，适配层消化各家差异 |
| API Key 散落各个仓库和服务配置里，泄露即全量失控 | Key 收口到网关管理，业务侧用网关签发的影子 Key，可随时吊销轮换 |
| 某模型挂了/涨价了，要改 N 个业务代码 | 路由表改一行：切模型、降级到备用模型，业务无感 |
| 谁用了多少 token 算不清账，成本失控 | 统一 **token 计费与配额**：按部门/项目/Key 拆账，quota 超过即拒 |
| Prompt 里有 PII / 涉密内容直接打给外部厂商，合规风险 | 入口统一脱敏/审查，敏感流量强制走私有化模型 |
| 公司里的 system prompt、vLLM 里的 prefix cache 没人管 | 网关层缓存高频前缀/高频请求结果（后述） |

**答题要点**：网关把所有"和模型对话无关、和让模型可靠被使用有关"的能力收进
一个平面——这个分层说法直接套用到架构图的引出。

## 四、核心功能设计（逐一展开）

### 4.1 路由策略：发给谁

▶ 面试高频："路由按什么维度？"

路由表本质是 **(请求特征) → (候选模型列表 + 权重) → (策略)** 的映射，策略三条线：

- **能力路由**：明确模型指定（用户 request 里带 model 名）＞ 自动路由（按任务类型/内容
  判断——比如代码类 → 代码模型，长 context → 窗口大的模型；一句话：模型注册表里存
  每个模型的"能力标签"，路由规则匹配标签）。
- **成本路由**：按模型单价（input/output token 分开计价）排序，满足质量阈值的前提下选
  最便宜的；配合 AB / 灰度把一定比例的流量打到便宜模型上验证效果。
- **延迟/负载路由**：看到实时 TTFT/TPOT 与排队长度，把流量倾向当前健康的实例；
  对自部署集群可直接读引擎的 waiting queue 长度（[推理引擎全景图
  ](../interview-questions/inference/推理引擎选型与源码路线.md#二技术栈全景从用户请求到-cuda-kernel)
  里调度层那一格）。

**工程诚实点**：自动路由是锦上添花，生产上 80% 流量是"业务显式指定模型 + 权重切流"
，把这条主路做稳，再谈智能路由。

### 4.2 Fallback 与熔断：挂了怎么办

- **重试**：同实例重试（只对超时/网络抖动）→ 换实例重试 → **换模型重试**（fallback
  链：`主模型 → 同档备用模型 → 更便宜但可用的兜底模型`）。重试要限制【次数 + 总
  预算时间】，且只对**幂等的请求**（非流式已部分返回后不能再无脑重发；流式响应里已
  吐出 token 的不能静默重发，只能终止或向客户端显式续传）。
- **熔断**：按 (模型 × 厂商 × 地域) 统计错误率/超时率，连续超阈值就打开熔断器
  （半开探测恢复），把流量让给其他路由目标——这就是微服务里 Sentinel/Hystrix 的
  同款语义，放到 LLM 网关上多了"模型级"这个维度。
- **降级**：服务整体过载时，按租户优先级丢流量（免费/低优先级租户先限）、切换为
  排队 + 预估等待时间返回，或降级到小模型/短 max_tokens。

### 4.3 缓存：能不复算就不复算

▶ 面试："网关层也有缓存？引擎里不是有 prefix cache 吗？"——区分层级的经典追问

| 缓存类型 | 位置 | 命中逻辑 | 例子 |
|---|---|---|---|
| **精确缓存** | 网关 | (租户，模型，prompt, 采样参数) 哈希完全一致 | FAQ 客服里千人问同一句话 |
| **语义缓存** | 网关 | 把 prompt 做 embedding，相似度 > 阈值就复用旧答案 | 同义不同字的提问 |
| **prefix / KV cache** | 引擎内部 | token 级前缀复用 | 同 system prompt、多轮对话 |

前两者在网关水到渠成（一次哈希/向量查询省一次全量调用），第三者是
[vLLM 与推理加速核心](../interview-questions/inference/vllm与推理加速核心.md#五prefix-cache--radixattention多轮对话与同前缀请求的缓存复用)
的事，别混在一起说。语义缓存的坑也要主动提：**相似不等于等价**，缓存命中可能给出
过时/错的答案——必须按业务允许打开，给低温度、高风险业务宁可不缓存。

### 4.4 Token 计费与配额

- **计量单位统一**：各厂商 tokenization 不同 → 适配层统一换算成"厂商原始 token 数
  + 内部归一估算数"两套账。成本 = input_tokens × 单价 in + output_tokens × 单价 out，
  费率表放配置中心，热更新。
- **配额维度**：租户 → 部门 → 项目 → API Key 多级；配额支持"日配额 + 速率（QPS/
  TPM）"两种，TPM 决定限流，日配额决定账单。
- **出账**：旁路写计量流（Kafka → OLAP），按小时聚合出用量大表；这一步别放在
  主链路事务里，宁可丢一条埋点也不能拖慢请求。
- **自部署模型也要计费**：按 GPU 时摊到 token 上做"内部转移定价"——这是 MaaS JD
  里"成本归集"能力的体现，说出来很加分。

### 4.5 可观测性：Trace / 日志 / 用量大盘

▶ "线上 Agent 不返回结果怎么 debug？"（也在
[高频真题汇总](../interview-questions/高频面试真题汇总.md#三agent-方向)）——网关是第一站

- **Trace**：每个请求发 trace_id，贯穿网关 → 适配层 → 引擎（OpenAI 协议无 trace 字段，
  放进 header 或 metadata 字段透传）。关键 span：排队时间、TTFT、TPOT、上游耗时、
  命中缓存、重试次数。
- **结构化日志**：请求侧脱敏后落盘（prompt 全文按需开关，别默认开），至少保留
  （租户、模型、tokens、延迟分布、错误码）。
- **大盘三视图**：租户视角（我花了多少）、运维视角（哪个模型/实例在拖后腿）、
  商业视角（成本与毛利）。TTFT/TPOT 的 P99 必须上大板——指标定义在
  [推理加速核心 - 第八节](../interview-questions/inference/vllm与推理加速核心.md#八吞吐-vs-延迟ttft--tpot--itl-指标必须脱口而出)。

## 五、流式输出的网关处理（SSE 透传）

▶ 面试："网关会不会破坏流式？"——**高频**

LLM 绝大多数流式是 SSE（为什么是 SSE 而不是 WebSocket，见
[vllm 与推理加速核心 - 第九节](../interview-questions/inference/vllm与推理加速核心.md#九sse--websocket流式输出怎么到用户)）。
网关的正确姿势是**透传式转发**，而不是攒批缓冲：

1. **不改写事件流语义**：上游来一个 `data:` chunk，立刻 flush 给下游；Nginx/
   Envoy 要关掉响应缓冲（`X-Accel-Buffering: no` / `proxy_buffering off`），
   否则 TTFT 被网关自己拉高——线上最常见的坑。
2. **边透传边统计**：token 数、TPOT 在透传过程中流式累加，响应结束后再出一次完整
   计量记录；这样用量统计不依赖上游是否返回 usage 字段。
3. **断连与取消**：客户端断开要能级联取消上游（反向传播 close），否则后端还在烧
   GPU；流式请求的重试边界是"还没吐过 token"，吐过之后只能终止。
4. **协议不改写**：对外仍按 OpenAI SSE 格式吐，适配层把厂商私有增量格式（比如某些
   家一段 JSON 包里塞多个 delta）归一成标准 chunk——差异消化在进入网关主干之前。

## 六、容量估算模板（可复用）

▶ "网关要承载多大流量？"——给 HTTPS 层面的粗估即可，别陷进去

**假设**（公开量级，注明假设）：

- 企业内 50 个业务线接入，合计 DAU 折算 **100 万次调用/天**，平均输入 1.5K +
  输出 0.5K tokens。
- 峰值系数取 3：峰值 QPS ≈ 100w × 3 / 86400 ≈ **35 QPS**；中型企业真实量级在
  几十到几百 QPS——**网关本身是无状态 HTTP 转发，横向扩容零压力**，瓶颈从不在
  网关而在后面的 GPU。
- 真正有意义的容量账在 GPU 侧：100w 次/天 × 500 out-tokens ≈ 5×10⁸ tokens/天 ≈
  平均 **5800 out-tokens/s**，峰值 ×3 ≈ 1.7w tokens/s——这个数字拿去
  [设计分布式推理服务](./设计分布式推理服务.md) 接着算卡数。
- 缓存命中假设 20%：直接砍掉 20% 的下游调用成本——这是网关最直观可量化的收益，
  汇报里就放这个数。

**答法要点**：网关联测 QPS、连接数（SSE 是长连接，单机连接数过万要调整内核
和 LB 配置）；压测时以三段链速分别打点：接入层延迟、排队延迟、上游延迟。

## 七、SLO 与压测

| 指标 | 建议 SLO | 怎么压 |
|---|---|---|
| 网关自身附加延迟 | P99 < 50 ms（透传流量；不含上游） | 打桩上游，压纯转发 |
| 端到端 TTFT | P99 < 2~5 s（看模型/prompt） | 用真实业务 prompt 分布回放到网关 |
| 错误率 | 5xx/超时 < 0.1%；重试成功率 > 99% | 故障注入（kill 上游实例 / 打满排队） |
| 计量准确性 | 计量 token 数与厂商账单误差 < 1% | 对一周账单做对账回归 |

压测三场景：常规峰值、双峰值（重试风暴）、上游降级下的熔断切换——第二、第三个
是拉开"想过"和"做过"的差距。

## 八、参考开源实现（一句话，不吹细节）

社区生态里 **LiteLLM**（Python 侧多模型统一代理 + 计费）和 **One-API** 系
（Go 侧分发与额度管理）是这个设计最常见的参考实现——面试时点到"思路和它们类似，

## 九、追问预案

| 追问 | 答题要点 |
|---|---|
| 网关和推理引擎里的调度重复了？ | 分层不同：网关管"租户/模型级"路由与计费，引擎调度管"请求级" batch/KV[推理引擎全景图](../interview-questions/inference/推理引擎选型与源码路线.md#二技术栈全景从用户请求到-cuda-kernel) |
| 语义缓存命中错了怎么办？ | 默认只对幂等低风险场景开；命中先记录（影子模式），再灰度放开 |
| 多租户配额打满时的反压怎么传导？ | 排队 + 限流码（OpenAI 风格的 429 / Retry-After），不许内部队列无限膨胀 |
| 怎么防止 Key 落到业务代码里被 GitHub 扫出来 | 影子 Key + 网关侧 IP/身份双因子；Key 轮换不依赖业务发版 |
| 合规要求数据不出域？ | 路由规则加"数据分级"标签：标敏感的业务强制路由到自部署集群 |
| 能不能把 fine-tune 也走网关？ | 训练作业走平台走（见 [设计 ai 开发平台](./设计ai开发平台.md)），网关只做推理 |
